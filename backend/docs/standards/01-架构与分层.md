# 01 架构与分层

请求链路：

```
router → middleware → handler → service → repository / cache → PostgreSQL / Redis
                                    ↘ provider（外部平台）/ storage（对象存储）/ pkg/ws（推送）
```

---

## A1 分层依赖只能单向（必须）

每一层只能依赖下表“可以依赖”一栏里的包。

| 层 | 可以依赖 | 禁止依赖 |
|----|----------|----------|
| `model` | 标准库、`gorm.io/gorm`、`gorm.io/datatypes`（表定义需要） | 任何 `video-canvas/internal/...` |
| `repository` | `model`、gorm | `gin`、`service`、`handler` |
| `cache` | `model`、go-redis | `service`、`handler` |
| `service` | `model`、`repository`（只用接口和哨兵错误）、`provider`（只用契约）、`storage`/`cache`/`pkg/ws` 的接口、`internal/pkg/*`、`config`、`gorm.io/datatypes` | `gin`、`gorm.io/gorm`、`handler`、`middleware`、`provider/engine`、`provider/worker` |
| `handler` | `service`、`model`、`internal/pkg/response`、`internal/pkg/errcode` | `repository`、`cache`、gorm、go-redis |
| `middleware` | `service`（通过接口）、`model`、`internal/pkg/*` | `repository`、gorm |
| `pkg/`（仓库根下） | 标准库、三方库 | 任何 `video-canvas/internal/...` |
| `initialize` | 全部 | — |

- **原因**：依赖方向一旦出现环，或者下层开始认识上层，分层就只剩目录名了。最常见的腐化方式是 service 直接用 gorm、handler 直接查库，都是“先这样，以后再改”，结果再也没人改。
- **正例**：[service/generation_task.go](../../internal/service/generation_task.go) 只认 `repository.ErrNotFound`，不认 `gorm.ErrRecordNotFound`；翻译由 [repository/repository.go](../../internal/repository/repository.go) 的 `translate()` 完成。
- **登记的例外**：[handler/health.go](../../internal/handler/health.go) 直接持有 `*gorm.DB` 和 `*redis.Client` 做探活（存量问题清单 X1）。
- **检查**：`depguard`。

## A2 依赖接口声明在使用方（必须）

service 依赖的 repository、外部客户端，都以接口的形式声明在 **service 包内**，只列出本服务用到的方法。

- **原因**：
  - 单元测试可以直接换成 fake；
  - 接口只包含使用方真正需要的方法，改 repository 的其他方法不会波及它。
- **正例**：`UserRepo`、`CanvasProjectRepo`、[GenerationTaskRepo](../../internal/service/generation_task.go)。
- **例外**：被多个包共同消费的契约，放在提供方的 `types.go` 里，例如 [provider/types.go](../../internal/provider/types.go)、[storage/types.go](../../internal/storage/types.go)、[pkg/ws/types.go](../../internal/pkg/ws/types.go)。
- **检查**：review。

## A3 service 只依赖 provider 的契约，不依赖实现（必须）

service 只能 import `internal/provider`，也就是 `types.go` 里的 `Registry`、`Executor` 等接口。不能 import `provider/engine` 或 `provider/worker`。

- **原因**：上游协议正在从 DSL 改为 JS 插件运行时（见 [协议插件设计](../../../docs/design/协议插件设计.md)）。service 对实现包的依赖越少，这次替换和以后的替换，改动面就越小。
- **存量**：目前有 6 个 service 文件依赖 `provider/dsl`，而且 `provider/types.go` 本身也 import 了 `dsl`，也就是契约依赖了实现（X2）。插件化重构时一并消除。**新代码不要再增加对 `provider/dsl` 的依赖。**
- **检查**：`depguard` 负责 engine 和 worker；dsl 的部分靠 review，等存量清掉后加进 depguard。

## A4 依赖只在 initialize 组装（必须）

- 所有 `repo → service → handler` 的组装都写在 [initialize/app.go](../../internal/initialize/app.go)，不引入 DI 框架。
- 构造函数统一命名 `NewXxx`，依赖通过参数传入。
- 依赖超过 4 个时，改用 `XxxDeps` 结构体传参，正例是 [GenerationTaskDeps](../../internal/service/generation_task.go)。
- 可选依赖在构造函数里降级成空实现，调用方就不用到处判空。正例：`Broadcaster` 为 nil 时换成 `ws.NopBroadcaster{}`，`cache` 在 `rdb == nil` 时所有方法都是空操作。
- `init()` 只能做本包内、无外部副作用的初始化，例如 [handler/bind.go](../../internal/handler/bind.go) 给校验器注册中文翻译。不能在里面建立连接、读取配置，也不能向其他包注册组件。
- 禁止包级可变单例（`logger.L()` 是唯一例外）。包级变量只能放只读的 regexp、map、常量表。
- **原因**：依赖关系集中在一个文件里，一眼就能看全，测试时也能随时替换。
- **检查**：review。

## A5 事务只通过 repository 的 WithTx 开启（必须）

```go
err = s.repo.WithTx(ctx, func(tx repository.GenerationTaskTx) error { ... })
```

- 事务的边界和组合逻辑（锁账户 → 查余额 → 插入 → 冻结积分）属于业务规则，写在 service 里；事务原语（`LockCredit`、`InsertTask` 这类）写在 repository 里。
- `fn` 里只用参数 `tx`，不要用外层的 `s.repo`，否则那条语句不在这个事务里。
- 事务里不做网络 I/O：调外部平台、WebSocket 推送、写对象存储都放到事务提交之后。
  - **原因**：事务持有行锁期间等外部响应，会把同一个用户的所有请求都串住。
- 需要回滚、但又不算业务错误时，用包内哨兵，比如 `errIdempotentConflict`。
- **正例**：[GenerationTaskService.Create 的第 7 步](../../internal/service/generation_task.go)。
- **检查**：review。

## A6 HTTP 边界的统一出口（必须）

- 响应只能通过 `response.OK / OKPage / Accepted / Fail` 写出，这样才能保证带上 `request_id`，格式也统一。
- handler 只做四件事：取参（`bindJSON / bindQuery / bindURI / pathID`）、取当前用户（`currentUserID(c)`）、调用 service、返回响应。
- **检查**：`forbidigo` 禁止在 `response` 包以外调用 `c.JSON`、`c.AbortWithStatusJSON`、`c.String` 等；handler 里有没有写业务判断靠 review。

## A7 数据归属（必须）

- 涉及用户数据的查询、更新、删除，SQL 条件里必须带 `user_id`。
- 资源不存在和不属于当前用户，统一返回“不存在”。
- **原因**：返回 403 会告诉攻击者“这个 id 的资源确实存在”，统一返回不存在就不会暴露这一点。
- **正例**：[GenerationTaskRepository.GetByID](../../internal/repository/generation_task.go) 的条件是 `id = ? AND user_id = ?`。
- **检查**：review；repository 测试要覆盖“别人的资源查不到”。

## A8 context 与 goroutine（必须）

- 会做 I/O 的函数，第一个参数都是 `ctx context.Context`。
- handler 传给 service 的是 `c.Request.Context()`，不要把 `*gin.Context` 往下传。
- `context.Background()` 只允许出现在两个地方：`initialize` 包，以及后台 goroutine 的根上（worker、ws hub）。请求链路里一律向下传 ctx。
- 发出去的 HTTP 请求必须带 ctx（`http.NewRequestWithContext`），否则取消和超时不会生效。
- 每个 goroutine 都要有明确的退出路径（ctx 取消或 channel 关闭），并由它的拥有者在 `Shutdown` 时等待它退出。正例：[worker.go](../../internal/provider/worker/worker.go) 用 `wg.Wait()` 等待。
- **检查**：`revive: context-as-argument`、`noctx`；goroutine 的退出路径靠 review。

## A9 错误码按模块分号段（必须）

- 错误码定义在 [errcode.go](../../internal/pkg/errcode/errcode.go)。号段划分：通用 `1xxxx`、用户 `2xxxx`、画布 `3xxxx`。
- **新模块从 `5xxxx` 开始，一个模块占一个号段。**
- 已发布的错误码数值永远不改，因为前端依赖它做判断。
- 历史情况：`4xxxx` 同时容纳了任务、积分、素材、AI 配置、WS 五个模块（X3）。已发布的不迁移，但这几个模块再新增错误码时，仍然追加在 `4xxxx`。
- **检查**：review。

## A10 配置（必须）

- 新增配置项的步骤：
  1. 在 [config.go](../../internal/config/config.go) 的结构体里加字段；
  2. 在 `configs/config.yaml` 里写默认值并加注释；
  3. 配置缺省时，代码里要有合理的兜底值，常量写在使用方，例如 `defaultMaxActiveTasks`。
- service 通过构造函数拿到自己需要的那一段配置（例如 `config.AI`），不要读全局配置。
- 密钥只走环境变量（`APP_` 前缀），不要写进 `config.yaml`；本地的私有配置放在 `configs/*.local.yaml`，这类文件已被 gitignore。
- **检查**：review。
