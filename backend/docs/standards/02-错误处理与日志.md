# 02 错误处理与日志

## E1 错误分三类，各有归属（必须）

| 类别     | 在哪产生                         | 形态                                          | 谁消费                                                                  |
| -------- | -------------------------------- | --------------------------------------------- | ----------------------------------------------------------------------- |
| 业务错误 | **只在 service**                 | `errcode.*` 预定义变量，或它的 `WithMsg` 副本 | `response.Fail` 转成 `code` + HTTP 状态码，返回给前端                   |
| 哨兵错误 | repository、storage 等基础设施包 | `var ErrNotFound = errors.New(...)`           | service 用 `errors.Is` 判断后，翻译成业务错误                           |
| 内部错误 | 任何层                           | `fmt.Errorf("...: %w", err)`                  | 一路往上返回，最终由 `response.Fail` 记录日志，并统一返回“服务内部错误” |

- **原因**：前端只能看到业务错误，内部细节不会泄露；service 以下的层不需要知道 HTTP 的存在。
- **检查**：review。

## E2 业务错误只用预定义的 errcode（必须）

- 新的业务错误先在 `errcode.go` 对应模块的号段里定义，然后在 service 里返回。
- 需要把字段级的细节带给前端时，用 `ErrXxx.WithMsg("...")`。`WithMsg` 返回一个副本，不会修改预定义的变量。
- 不要在 service 以外构造 `errcode.New(...)`。
- **检查**：review。

## E3 往上返回下层错误时加上下文，并用 %w 包装（必须）

```go
// 正例：internal/provider/worker/worker.go
return nil, fmt.Errorf("转存第 %d 个产物失败：%w", i+1, err)
```

- 文案描述“正在做什么”，建议写成 `<动作>失败：%w`，与现有的大多数写法保持一致。
- 如果本函数已经是同一个动作，没有新的上下文可加，直接 `return err` 就行，不要为了包装而包装。
- 禁止用 `%v` 格式化 error，因为这样会切断错误链，上层的 `errors.Is` 就失效了。
- **检查**：`errorlint`。

## E4 用 errors.Is / errors.As 判断错误（必须）

- 不要用 `==` 比较错误，也不要对 error 做类型断言，因为被包装过的错误会匹配失败。
- 判断业务错误时比较 `Code`，不要比较指针：

```go
var e *errcode.Error
if errors.As(err, &e) && e.Code == errcode.ErrTaskNotFound.Code { ... }
```

- **检查**：`errorlint`。

## E5 新建错误的写法（必须）

- 没有格式化参数时，用 `errors.New`，不要写成 `fmt.Errorf("固定文案")`。
- 错误文案末尾不加标点、不加换行（staticcheck ST1005 会检查）。
- 包级哨兵命名为 `ErrXxx`（导出）或 `errXxx`（包内），并且写一行注释说明它表示什么。
- **检查**：`staticcheck`、`revive: error-naming`。

## E6 panic 只用于启动期不可恢复的情况（必须）

允许的场景：

- 包初始化时编译常量正则、解析常量 CIDR，比如 `regexp.MustCompile`、`mustCIDRs`；
- 系统级资源不可用、继续运行会不安全，比如 [asset.go](../../internal/service/asset.go) 里 `crypto/rand` 失败。

其余情况一律返回 error。需要 panic 的地方要在同一行或上一行写明原因。

- **检查**：review（`grep -rn "panic(" internal`）。

## E7 日志只在边界记一次（必须）

- 返回错误的函数**不记日志**，由最终处理这个错误的地方来记。边界有两个：
  - HTTP 请求：由 `response.Fail` 统一记录内部错误；
  - 后台任务：由 worker 的顶层循环记录；队列任务另有运行日志中间件兜底（重试、重试用完、panic），见 E10。
- **原因**：每一层都 log 一次再 return，同一个错误会在日志里出现 N 次，排查时反而更难找。
- service 可以记日志的情况有两种：
  - **审计事件**，用 `Info`，必须带操作人。正例：[ai_config.go](../../internal/service/ai_config.go) 里“发布 AI 配置”带了 `admin_id`；
  - **吞掉或降级的错误**，用 `Warn` 或 `Error`，同时要写明降级之后的行为。正例：`重新加载 Registry 失败，继续使用旧状态`。
  - **运行的过程事件**（E10）：后台运行或同步运行可以对关键过程节点打 `run.step`，记录「这一步做了什么」，不是「这个错误发生了」。失败原因仍只在运行终态（`run.finish`）记一次。
- 只用 `logger` 包，不要用 `fmt.Print*`、`log.Print*`。
- 日志用结构化字段。不要用 `Sprintf` 把变量拼进 message，否则无法按字段检索。
- 运行相关的日志用 `logger.Ctx(ctx)` 打，它自动带上关联字段（E10），不要手写 `task_id`、`run_id` 等编号字段。
- **检查**：`forbidigo` 检查打印语句；“只记一次”靠 review。

## E8 日志级别语义（建议）

| 级别    | 什么时候用                                         |
| ------- | -------------------------------------------------- |
| `Info`  | 状态变化和审计事件：发布、回滚、上下架、任务终态   |
| `Warn`  | 已经降级或能自愈的问题：缓存失败、重试、使用旧状态 |
| `Error` | 需要人来处理：内部错误、数据不一致、配置无法解析   |

日志的 message 用中文短句，字段名用英文 snake_case。和请求、运行相关的日志一律用 `logger.Ctx(ctx)`，自动带 `request_id`、`user_id`、`run_kind`、`run_id`（值和界面上展示的编号相同，生成任务、短剧、营销是十六进制，不是数据库里的十进制主键）；另用 `event` 字段标事件类型（E10）。

## E9 敏感信息与故意忽略的错误（必须）

- 以下内容**不能**出现在返回前端的响应里：凭证、token、密码、宿主内部错误（网络、存储、插件异常、SQL 错误）。
- 以下内容**不能**出现在日志里：凭证、token、密码。需要展示时先脱敏，dry-run 结果对凭证的脱敏就是正例。
- **后台排查例外**：后台「使用记录」接口（`GET /admin/usage/:ref`，仅 admin / super_admin）可以返回失败任务的**上游错误原文**（记在 `generation_task_events` 的 `failed` 事件里，上限 16KB）。渠道 Key 仍然不得出现在任何落库内容和响应里（宿主在构造上游错误文本时已遮掉）。设计见 [日志管理](../../../docs/design/日志管理/日志管理.md)。
- **上游错误原文给用户看**：生成失败（画布、短剧工作室、营销工作室的文字、图片、视频、音频）时，用户侧看到的失败原因是**上游返回的错误原文**，让用户知道真实原因。原文里上游自己的请求 / 追踪编号（`request id`、`trace_id` 等）由 `provider.StripTraceIDs` 去掉，排查用平台自己的任务编号（界面上和失败原因一起展示）：
  - 异步任务：插件执行器把上游非 2xx 响应里的原文（遮掉渠道 Key、截到 500 字）放进 `provider.Error.Upstream`，插件 `parseQueryResponse` 返回的失败原因同样算上游原文；worker 的 `failureFor` 有原文就用原文，见 [policy.go](../../internal/provider/worker/policy.go)。
  - 文本模型：`llmgateway.UpstreamError.Message` 是上游 `error.message`（遮掉 Key、截到 300 字），service 用 `upstreamText` 取出写进失败原因。
  - 没有上游原文的失败仍用固定文案，不透出宿主内部信息：超时、转存失败、提交结果未知、插件级失败（异常 / 返回值不合规 / runner 崩溃）、SSRF 拦截、网络断开。
- 故意忽略的错误必须写明原因：

```go
// 正例：internal/service/user.go
// 3. 回写缓存（30 分钟过期），写失败只影响下次命中率，所以忽略错误
_ = s.cache.Set(ctx, u)
```

- **检查**：`errcheck` 负责找出没处理的错误；原因注释和脱敏靠 review。

## E10 统一服务器日志：两个文件、关联字段、事件（必须）

设计见 [统一服务器日志](../../../docs/design/统一服务器日志/统一服务器日志.md)。

**两个文件**

- `app.log`：过程事件、运行汇总、访问日志、错误原因；同时写标准输出。文件固定 JSON 行。
- `payload.log`：每次上游调用（文本模型、供应商插件、其他外部 HTTP）的请求和响应全文，成功的也记；只写文件。用 `logger.Payload` 写，和 `app.log` 的调用行用 `call_id` 对应。

**关联字段**（`logger.Ctx(ctx)` 自动带，不要手写）

| 字段 | 谁挂上 |
| --- | --- |
| `request_id` | `RequestID` 中间件；由请求入队的后台任务经任务 metadata 还原 |
| `user_id` | `JWTAuth` / 分析令牌中间件；后台任务由 `RunArgs.RunRef()` 或 `Run.SetUser` 提供 |
| `run_kind` / `run_id` | 队列中间件（`RunArgs.RunRef()`）或同步运行的 `logger.BeginRun` |
| `parent_kind` / `parent_id` | 派生运行（如 Agent 生成的任务） |
| `attempt`、`job_kind` | 队列中间件 |
| `instance` | 启动时，每行都有 |

`run_kind` 取值：`gen`（生成任务）、`drama`（短剧任务）、`mkt_round` / `mkt`（营销轮次 / 环节运行）、`agent`、`adapt`（片段转写）、`preflight`（预检）、`step_trial`（环节试跑）、`system`（不属于用户的后台任务）。新增取值先加到这里。

**事件**（`event` 字段，`logger.Event*` 常量）：`http.request`（访问汇总，中间件打）、`run.create`、`run.start`、`run.step`、`llm.call`（网关打）、`provider.call`（插件宿主打）、`ext.call`（统一出站客户端打）、`run.retry`（队列中间件打）、`run.finish`（运行汇总）。

**新功能接入清单**（评审检查项）

1. 新的后台任务：参数实现 `queue.RunArgs`，用 `queue.AddWorker` 注册（不要直接调 `river.AddWorker`）；`run_id` 和界面上显示的编号相同。
2. 新的同步运行（不走队列、但会调模型或外部服务）：`ctx, run := logger.BeginRun(...)`，开始干活时 `run.Start(...)`，终态 `run.End(...)`。
3. 外部调用：文本模型走 `llmgateway`；供应商走插件；其他走 `outbound.Client` / `outbound.Transport`（`internal/pkg/outbound`），不要自己构造 `http.Client`。确实不属于用户运行的（内部进程、运维、后台检测）加进 `internal/tests/arch` 的白名单并写原因。调用前可以用 `logger.WithCall(ctx, 用途, 业务位置字段...)` 声明用途，拿到的 call_id 能在 `run.step` 里指向这次调用。
4. 终态调用 `run.End(status, ...)`，补积分、`error_code`、`error_message`、`error_type`、`error`。没调时队列中间件会兜底打 `finish_fallback=true` 的收尾行，看到它就要补上。
5. 关键过程节点打 `run.step`；失败原因不要吞，通过 error 带到终态。

- **检查**：编译期（`queue.AddWorker` 的类型约束）+ 架构测试 + review。
