## 规则级别

- **必须**：违反即视为未完成。大部分由 `make lint` 自动检查；工具查不了的在 review 时拦。
- **建议**：默认照做；有更好的理由可以不做，但要在代码注释或 PR 描述里写出理由。

## 每条规则的写法

新增或修改规则时，照这个格式写：

> **A1 规则标题**（必须 / 建议）
> 一句话说清要求。
>
> - **原因**：为什么要这样。
> - **正例 / 反例**：链接到仓库里的真实代码，不要凭空编示例。
> - **检查**：哪个 linter，或者“review”。

写不出“检查”一栏的规则，要么降为“建议”，要么删掉。

## 自动检查与规范的对应关系

规则的自动检查全部配置在 [.golangci.yml](../../.golangci.yml)，每个 linter 的注释里写了对应的规则编号。

- **`make lint`**：只检查相对 `master` 的增量（包含未提交的改动）。**提交前必须通过**。
- **`make lint-all`**：全量检查，用来跟踪存量问题的消化进度。

规范生效时（2026-09-30）的基线是：全量 192 个问题，增量 0 个。存量问题不要求一次性清完，改到哪个函数就顺手修掉哪个函数，见 [存量问题清单](存量问题清单.md)。

## 怎么改规范

1. 规范和 `.golangci.yml` 在同一个提交里改，两边的规则编号保持一致。
2. 放宽一条“必须”规则时，在提交信息里写明原因。
3. review 中发现规范没覆盖、但反复出现的问题，就补成一条新规则。规范是这样长出来的，不是一次写完的。
