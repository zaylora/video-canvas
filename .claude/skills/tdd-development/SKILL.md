# 测试驱动开发

把测试当成需求的可执行描述。除文档、纯格式和没有运行时行为的配置改动外，代码行为改动都按 RED → GREEN → REFACTOR 完成。

## 开始前

1. 读取仓库根目录 `AGENTS.md`，再读取目标目录的规则文件。
2. 查看 `git status`，保留用户已有的未提交改动，不覆盖或回退它们。
3. 找到真实入口、调用链、数据契约、错误码、状态机和现有测试。优先复用现有 fake、fixture、测试辅助函数和公共设施。
4. 写下本次行为的验收条件：正常路径、输入边界、业务错误、并发或异步恢复场景，以及不应改变的旧行为。

## RED：先写测试

- 先添加最小测试，再修改生产代码。测试必须先运行并因目标行为缺失而失败；如果测试在没有实现时就通过，检查它是否真的锁定了需求。
- 测试用户可观察的结果、状态转移、HTTP 响应、持久化调用或消息，而不是私有函数调用顺序或局部实现细节。
- 至少覆盖成功路径和本次改动会影响的边界、错误或回归路径。接口改动要覆盖参数校验和一个业务错误；服务层要覆盖每个业务错误分支。
- 每个用例独立创建可变 fake 和输入。异步结果使用条件轮询和超时；不要用固定 `sleep` 等待“应该已经完成”。

### 后端测试位置与约束

- 测试放在 `backend/internal/tests/<被测包路径>/`，使用外部测试包。
- service 使用手写 fake repo 做表驱动测试；handler 使用 `gin.SetMode(gin.TestMode)`、`httptest` 和 fake 依赖。
- 只使用标准库 `testing`、`httptest` 等已有依赖，不擅自添加 testify、gomock 等断言或 mock 库。
- 业务错误按错误码断言，不比较错误指针。需要未导出符号时，在被测包添加仅供测试使用的 `export_testing.go`。
- 涉及 goroutine、worker、WebSocket 或缓存的改动，补充可重复的并发/生命周期测试，并计划运行 race 检查。

### 前端测试位置与约束

- 测试放在 `web/src/tests/`，按 `constants`、`utils` 等被测目录组织。
- 使用项目已有的 Bun 测试运行方式（`bun test`）和现有测试辅助函数，不为了单个功能引入新测试框架。
- 纯函数优先用表驱动测试；组件或请求流程只断言用户可见行为、请求契约和状态结果。
- API 映射、任务合并、画布保存/历史、WebSocket 退避和错误提示等跨层边界要优先补回归测试。

## GREEN：最小实现

只实现让新增测试和已有测试通过所需的行为。保持现有架构方向：后端遵循 `router → middleware → handler → service → repository/cache`，前端请求集中在 API 层，业务纯函数保持可测试。不要为了让测试通过而放宽断言、跳过用例、吞掉错误或修改无关的测试数据。

## REFACTOR：在测试保护下整理

测试全绿后再合并重复逻辑、改善命名、提取公共函数或调整结构。重构前后保持验收条件不变；每次小步重构都重新运行受影响测试。发现存量测试失败时，先确认是否由本次行为变化导致，再修实现、更新契约测试或记录真实的基线问题，不能把失败测试删掉来制造绿色结果。

## 验证顺序

1. 运行新增/修改测试。
2. 运行受影响包或模块的测试。
3. 运行静态检查和格式化：后端 `make fmt`、`make lint`；前端 `bun run format:check`、`bun run typecheck`、`bun run lint`。
4. 运行完整测试：后端 `make test`，前端 `bun run test`；需要时运行 `make test-race` 和 `bun run build`。
5. 交付时报告 RED 测试锁定了什么、实现改了什么、执行过哪些命令及结果。

若环境无法运行某项检查，仍先提交测试文件和实现所需的验证命令，不伪造通过结果，并说明阻塞原因。
