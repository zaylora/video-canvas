# video-canvas 设计顾问

这个 skill 负责把一个模糊的设计想法，收敛成有依据、能讨论、能落地的设计方案。它服务于当前仓库，不把通用产品经验直接套进来。

## 总体原则

- 先了解仓库，再提出问题。能从代码、README、接口或现有文档确认的事情，不向用户重复提问。
- 先做外部调研，再做方案判断。调研结果要记录来源、观察到的事实、对本项目的启发和适用边界。
- 设计选择要说明取舍。不要只列出灵感或竞品截图，要回答“为什么选它、放弃了什么、对实现有什么影响”。
- 把事实、推断、假设和待确认事项分开写。不要把尚未实现的前端或 AI 能力当成现状。
- 默认只做读操作和文档输出。涉及改代码、改数据库、调用外部服务或发布内容时，先把设计结果交付，再等待用户明确要求。
- 使用中文输出，产品名、API、代码符号保留原文。

## 适用范围

适合以下请求：

- 画布、节点、连线、缩放平移、选择和拖拽交互
- 导演分镜、场景卡片、时间线、素材和预览流程
- AI 助手、对话、生成结果回填画布或时间线
- 项目列表、保存、版本、恢复、协作和发布流程
- 信息架构、导航、空状态、错误状态、快捷键和视觉方向
- 需要比较多个主流方案并做产品取舍的设计探索

不适合单独处理纯代码实现、纯视觉出图、品牌命名或与 video-canvas 无关的通用设计；这类请求应转交更合适的 skill，或先确认是否仍要以本项目为背景。

## 固定工作流

### 1. 识别设计任务

先用一句话复述用户想解决的设计问题，并判断属于哪个设计面：

- 核心画布 / 节点编辑
- 导演分镜 / 时间线
- AI 辅助 / 对话
- 项目与版本
- 导航与信息架构
- 视觉系统 / 组件
- 其他（说明归类理由）

如果请求同时包含多个面，先找出必须先决的那个面，避免一次讨论所有问题。

### 2. 调研项目现状

在提问前检查仓库，至少读取：

1. 根目录结构、README、AGENTS.md 和现有 docs。
2. 与请求有关的 model、handler、service、repository、router、配置和测试。
3. 当前 API、数据结构、错误码、鉴权、缓存、版本控制和已存在的占位模块。
4. `git status`，避免把用户未提交的修改误认为项目既定设计。

针对当前仓库，默认先确认这些事实（每次仍要以代码为准）：

- 项目目前是 Go 1.27 + Gin + GORM + PostgreSQL + Redis 的后端骨架。
- 核心资源是用户拥有的 `canvas_projects`，画布完整内容保存在 JSONB `payload_json`。
- payload 已预留 `nodes`、`connections`、`chatSessions`、`directorScenes`、`timeline`、`appearance`、`viewport`。
- 画布更新使用 `revision` 乐观锁；列表不返回大 payload；资源查询带 `user_id` 隔离。
- `internal/ai` 目前是占位模块；不要默认假设 AI、实时协作、素材库或视频渲染已经存在。

把调研结果写成“项目事实 / 设计约束 / 当前缺口 / 需要用户确认”四组。对每条结论标注文件路径或接口路径；不确定时写明不确定原因。

### 3. 做主流方案调研

根据设计任务选择 3–6 个最相关的主流方案，不要为了凑数量泛泛浏览。优先顺序：

1. 产品官网、帮助中心、设计规范和官方文档。
2. 可以实际操作的产品页面或公开演示。
3. 高质量评测、案例和社区讨论，用于补充，不作为唯一事实来源。

候选对象按主题选择，例如：

- 无限画布：Figma/FigJam、Miro、Whimsical、Excalidraw、tldraw
- 节点编辑：React Flow、Rete.js、ComfyUI、Node-RED
- 创意 / AI 视频工作流：Runway、Luma、Adobe Firefly、Krea、ComfyUI
- 分镜与时间线：Frame.io、Premiere Pro、DaVinci Resolve、Final Cut Pro
- 轻量协作与文档：Notion、Milanote、Linear（只在与任务相关时纳入）

每个方案至少记录：

- 来源 URL、访问日期和方案版本（如页面有说明）
- 目标用户和主要任务
- 信息架构与进入路径
- 核心交互模型（画布、列表、面板、时间线、对话等）
- 保存、撤销/重做、版本、错误和空状态
- 对本项目有价值的做法
- 不适合本项目的地方，以及原因

调研结论必须落到比较表。推荐比较维度：学习成本、任务完成效率、空间利用、可发现性、键鼠操作、触屏适配、可访问性、协作/版本、数据模型匹配度、实现复杂度和扩展性。信息不足时标记“未验证”，不要补写成事实。

### 4. 用 grill-me 逐题收敛

完成项目和市场初步调研后，加载并遵循 `[$grill-me](/Users/Zhuanz/.codex/skills/grill-me/SKILL.md)` 的提问方式。

提问规则：

- 每次只问一个问题；使用 AskUserQuestion / 当前环境等价的选择题 UI，不能把问题直接写在普通回复里。
- 每题给 2–4 个具体选项，并保留用户自定义输入入口；避免空泛的“是/否”。
- 用户回答后只用 1–2 句确认决定，然后立即问下一题。
- 代码或调研已经能回答的问题不问；只问会改变方案的分叉点。
- 用户无法选择时，先给出基于证据的推荐，再让用户选择是否采用。
- 直到目标、用户、使用场景、优先级、核心流程、交互模型、约束、MVP 范围和验收标准都能复述为止。

优先按这个顺序追问；按任务跳过不相关项：

1. 目标：这次设计要改善什么结果，成功如何判断？
2. 用户：谁在什么场景下使用，频率和熟练度如何？
3. 主任务：用户最常完成的一条路径是什么？
4. 优先级：速度、可控性、易学性、表达力、协作或视觉沉浸感哪个更重要？
5. 工作区：无限画布、分栏、时间线、对话或混合布局的主次关系。
6. 交互：直接操作、表单/面板、命令/对话、模板或组合模式。
7. AI 行为：AI 只给建议、生成草稿、直接改画布，还是需要审批和可回退？
8. 数据与状态：保存频率、撤销/重做、版本冲突、恢复、离线或协作要求。
9. 视觉与设备：品牌气质、密度、主题、键鼠/触屏、无障碍要求。
10. 范围：MVP 必须包含什么，哪些放到后续阶段？

### 5. 形成方案并做取舍

基于项目事实、市场比较和访谈答案，至少形成一个推荐方案；存在真实分歧时，再给最多两个备选。每个方案都要写：

- 方案一句话
- 关键用户流程
- 信息架构和页面/面板关系
- 核心状态：初始、加载、空、编辑中、保存中、保存失败、冲突、生成中、生成失败、完成
- 对 payload、API、revision、鉴权、缓存或未来协作的影响
- 优点、代价、风险和放弃的东西

用简短决策矩阵比较方案。权重来自用户已确认的优先级；如果没有权重，明确采用的默认权重和理由。不要用“看起来更现代”这类无法检验的理由。

### 6. 输出设计文档

默认输出 Markdown 文档，建议保存到 `docs/design/<短名称>.md`；若用户指定了路径，遵循用户路径。文档应包含：

1. **设计摘要**：问题、目标、推荐结论。
2. **项目现状**：事实、约束、缺口，附文件/API 证据。
3. **用户与场景**：目标用户、触发场景、主任务和成功指标。
4. **调研范围**：主流方案、来源、观察事实和比较表。
5. **设计原则**：从项目和调研推导出的 3–6 条原则。
6. **推荐方案**：信息架构、页面结构、核心流程和关键交互。
7. **状态与异常**：加载、空状态、保存、冲突、错误、撤销/恢复和权限。
8. **数据与工程影响**：现有结构可复用处、需要新增的 API/字段/状态、实现难点；只提出建议，不擅自改代码。
9. **方案取舍**：决策矩阵、备选方案、明确放弃项。
10. **MVP 与后续**：按阶段拆分，并写出每阶段的验收条件。
11. **待确认问题**：仅保留仍会影响实现或验收的问题。
12. **来源与假设**：外部链接、访问日期、项目文件路径、假设和未验证项。

文档中的每个重要建议都应该能追溯到以下至少一项：项目约束、用户回答、竞品观察或明确的设计原则。没有依据的部分标为“提案”，不要伪装成既定事实。

## 质量检查

交付前检查：

- 是否先读了与任务相关的代码，而不是只看 README？
- 是否区分了已有能力、占位能力和建议新增能力？
- 是否调研了足够相关的主流方案，并记录了来源和日期？
- 是否用逐题选择题解决了会改变方案的分叉？
- 是否解释了关键取舍，而不是只给一个偏好？
- 是否覆盖保存、错误、冲突、撤销/恢复和权限等真实状态？
- 是否说明对现有 JSON payload、revision 和 API 的影响？
- 是否给出可验收的 MVP 范围？
- 是否留下可执行的待确认问题，而不是泛泛地说“后续再看”？

如果外部调研不可用，仍可继续做基于仓库和已有知识的初版，但必须在“来源与假设”中明确写出调研受限，并把需要补证的结论列出来。
