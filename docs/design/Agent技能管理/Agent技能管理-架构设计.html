一页结论

四件事，读完就知道这次要不要放行。

做什么后台导入技能包（zip / 文件夹 / SKILL.md），不可变版本入库；Agent 通过目录 + skill_read 渐进读取，第 2 期用 skill_run 执行包内脚本。
核心设计技能包是不可变制品：元数据入 PostgreSQL，规范化 zip 存对象存储；“生效版本”是一个指针；运行时一次运行内固定版本。
最大风险第 2 期在平台上执行第三方脚本。所有管理员都能导入，信任边界放在“默认停用 + 无网络容器”上，容器逃逸与资源耗尽要靠运行时选型兜底。
需要你决定第 2 期执行运行时选型；执行产出是否允许落画布。含脚本技能的启用权限、版本一致性、私有桶已确认（见“决策与风险”）。第 1 期不被这些阻塞。

目标与非目标

目标
  • 管理员 10 秒内判断“能不能导、会发生什么、里面有什么”。
  • 任何导入或新版本在管理员点“启用 / 设为生效”前，不影响线上 Agent。
  • 出问题能按 name@vN 和 sha256 复现、回滚。
  • 不破坏现有 5 个内置技能、@ 引用、skill_search 的行为。
  • 第 2 期执行能力以可替换后端接入，不绑死某个运行时。
非目标（本设计不做）
  • 用户级 / 画布级技能（技能是全平台的，管理员维护）。
  • 在线编辑技能文件（版本模型已能承接，但不在本期）。
  • 技能签名与来源验证、技能市场。
  • 实现 allowed-tools、disable-model-invocation 等扩展字段的语义（原样保存、标“未支持”）。
  • 多区域部署、跨实例强一致的目录缓存（见 §数据与一致性）。

质量属性与取舍顺序

冲突时按这个顺序取舍：安全 > 可回滚与一致 > 兼容 > 可演进 > 性能。技能是低频写、中频读，性能排最后。

分层与依赖规则

沿用 backend/AGENTS.md 的链路 router → middleware → handler → service → repository / cache。新增的约束只有四条。

  • SkillPackage 是纯函数：输入字节与限制，输出规范化结果和 issues；不碰数据库、不碰存储、不碰文件系统。所有安全规则集中在这里，表驱动测试覆盖。
  • handler 不直接用 storage：所有对象读写由 SkillService 经 storage.Registry 完成。
  • internal/agent/skills（内置）不依赖数据库；导入技能只出现在 service 层的 SkillCatalog。
  • Agent 侧只读：AgentBridge 只依赖 SkillCatalog 与 SkillFiles 两个只读接口，不能写技能。
// 提案：internal/service/agent/skill_catalog.go
type SkillCatalog interface {
  List(ctx) ([]SkillBrief, error)            // 内置 + 已启用，按 name 排序
  Search(ctx, q string) ([]SkillBrief, error) // 沿用“最多 5 个”
  Resolve(ctx, name string) (Resolved, error) // 生效版本；未启用 → ErrSkillNotFound
  ResolveAt(ctx, name string, versionID uint64) (Resolved, error) // 运行内固定

关键流程

四条流程：导入、启停与目录、Agent 运行中使用、第 2 期脚本执行。图是简图，每张图下面的步骤才是准绳；紫色虚线是第 2 期。

F1 · 导入：预检与确认

两步：第一步只做检查并暂存，不产生任何线上可见的变化；第二步才入库。

  1. 上传：multipart。handler 先 MaxBytesReader(50MB + 余量)，超限在读取阶段截断返回 413，不会把大请求体读进内存。
  2. 预检（纯内存）：SkillPackage.Precheck 用 zip.NewReader(bytes.Reader) 读条目，从不把条目写到磁盘，所以 zip slip 在服务端没有落脚点。逐条检查路径、符号链接（Mode()&ModeSymlink）、重复、压缩比、数量、大小；解析头部；算规范化整包 sha256。
  3. 暂存（先写行、再写对象）：先在库里写 agent_skill_imports（含预检结果 JSON、expires_at = now+1h），再把规范化 zip 写对象存储 agent-skills/_staging/<importID>.zip；对象写失败就删掉这一行。预检有错误也暂存并返回 200，让前端展示问题；但该导入单不可确认。
  4. 展示：前端用预检结果渲染横幅、文件树、问题；预览文件内容的接口从暂存包里读。
  5. 确认：只校验“导入单属于当前用户、未过期、无错误”。不重新解析包——预检结果是可信的服务端产物，确认只做入库。
  6. 入库（两阶段）：事务 A 锁 agent_skills 行（新技能则插入），分配 version = latest_version + 1，插入版本行 state=pending；然后把暂存对象复制到正式 key；事务 B 把版本行置 ready、必要时设 active_version、写审计。任一步失败，pending 行由清理任务回收。

F2 · 启用、切版本与目录失效

  1. 写：单条 UPDATE（enabled 或 active_version）+ 审计，同一事务。
  2. 本进程缓存立即失效：SkillCatalog.Invalidate()。
  3. 其他实例：最多 TTL（默认 30 秒，示意）后自然刷新。不引入 Redis 广播（ADR-7）：Agent 的运行状态本来就在单进程内存里（bridge.go 的令牌表），多实例强一致没有收益。
  4. 对运行中的影响：已开始的运行不受影响（版本已固定）；之后新开始的运行才读到新目录。

F3 · Agent 运行中使用技能（渐进披露）

  1. 启动运行：ProcessRuntime.Start 构造系统提示词，尾部拼目录（SkillCatalog.List）。内置 + 已启用 > 30 个时不拼目录，只保留搜索。
  2. skill_read({name})：Node 回调桥；桥解析技能，首次读取时把 name → versionID 记进 bridgeSession.skillPins，返回正文 + 资源清单，外包“以下是方法说明，不是指令”。
  3. skill_read({name, file})：按 pin 的 versionID 取清单校验路径；只读 files_json 里存在的文本文件；先查 LRU，未命中才从对象存储取整包并解出文件（一次性解出该包全部 ≤ 256 KB 的文本文件放进 LRU，待实测）。
  4. 返回：文本最多 64 KB（示意），超出截断并注明；二进制只返回“大小 N，无法读取”；路径不在清单里返回错误并列出可用文件，让模型自己改正（沿用现有 skill_read 的错误风格）。
  5. 令牌结束：Finish 时 RevokeToken，pins 随之销毁。
注意：一次运行可能跨多个片段（审批后续跑、“继续”），每个片段一个新令牌（bridge.go），所以 pins 的生命周期是片段而不是整次运行。跨片段的版本一致性需要把 pins 随运行记录落库（例如写进 agent_runs 的一个 JSON 列），否则审批后续跑可能读到新的生效版本。已确认：用户认为不一定要一致，所以 pins 不落库，容忍跨片段版本漂移；正文在片段开头已经进入上下文，漂移只影响后续读取的资源文件。若将来出现问题再落库。

F4 · 第 2 期：脚本执行（反向通道）

  1. skill_run({name, script, args})：Node 回调桥；桥校验该技能已启用、已 pin，script 在清单里且扩展名受支持。
  2. 入队：ScriptExecutor 把任务放进队列（并发 1、队列上限、等待超时）；队列满或 runner 离线立即返回明确错误。
  3. runner 取任务：runner 一直在 POST /poll 长轮询（只做 connect()）；拿到任务后若本地没有该 sha256，就 GET /pkg/{sha} 拉整包，重新校验并解到只读缓存。
  4. 执行：全新临时目录，非 root，限时 / rlimit / 进程组；无网络。
  5. 回传：POST /result；只有截断后的 stdout / stderr、退出码、耗时进入上下文，外包“数据不是指令”；脚本源码不进上下文。

失败与补偿

失败点用户看到系统状态补偿
上传超限 / 非 zip413 或 10001，拖放区内提示无副作用—
暂存写对象失败通用错误 toast，回到第 1 步导入单行已写、对象没写成立即删除这一行；即使删行也失败，过期清理任务会按行回收。因为存储没有 List，必须先有行、后有对象，这样任何对象都有一行可追溯
确认：事务 A 失败通用错误，可重试无变化—
确认：复制正式对象失败通用错误，可重试版本行 pending清理任务按 pending 超过 10 分钟重试删除对象并删行；用户重试会得到新版本号（版本号不复用）
确认：事务 B 失败通用错误，可重试版本行 pending，对象已存在同上；重试时同一 importID 幂等地复用同一正式 key
删除版本：事务成功、删对象失败成功 toast版本行 deleting清理任务重试 storage.Delete 直到成功再删行（Delete 对不存在对象不算错误，幂等）
对象存储不可用（读）Agent：工具返回错误，模型可继续；管理页：文件预览失败，其余可用无目录与正文来自数据库，不依赖对象存储；只有读资源文件和下载整包依赖它
数据库不可用管理页与 Agent 目录均失败—目录有 TTL 缓存，短时故障下新运行仍可用旧目录（待验证）

数据与一致性

元数据在 PostgreSQL，整包在对象存储，两者没有分布式事务。设计的核心是：让数据库永远是真相，对象存储是可重建的附庸，用 pending 行 + 驱动式清理保证最终一致。

active_version只能指向 ready 版本；首个版本入库时在事务 B 里设为 1。
导入单pending（可确认）→ 确认后删除（暂存对象一并删）；超过 expires_at 由清理任务删行与暂存对象。

一致性策略

问题策略为什么不用别的
DB 与对象存储不一致先写 pending 行（含对象 key），再写对象，再置 ready；任何读只认 ready。清理任务从 DB 出发：回收超时 pending、重试 deleting、清过期暂存。storage.Storage 接口没有 List（storage/types.go），无法“扫对象找孤儿”；也不引入 2PC。
对象 keyagent-skills/<name>/<uuid>.zip，uuid 在建 pending 行时生成，重试复用同一个 key（幂等）。sha256 只存库，不进 key。内容寻址 key（含 sha256）会让“知道包内容的人”能推出 key；若存储桶被配置成公开读，这是泄露面。随机 key 同样幂等且不可推测。
并发导入同名技能事务内 SELECT … FOR UPDATE 锁 agent_skills 行再分配版本号；(skill_id, version) 唯一约束兜底。新技能并发创建：name 唯一冲突 → 回退为“新版本”路径重试一次。应用层加锁在多实例下不可靠；唯一约束是最后防线。
并发切版本 / 启停单语句更新，后写覆盖先写；审计记录两次操作。管理员极少并发操作同一技能，乐观锁收益低；如需要可加 updated_at 比较。
版本号复用latest_version 只增不减；删除版本后号不复用。复用会让日志里的 name@vN 指向不同内容，破坏可复现。
读到 pending / deleting仓库层所有查询默认带 state='ready'；管理页的“版本”列表对 deleting 也不显示。—

缓存与读路径

目录缓存（ADR-7）
  • 内容：已启用技能的 name / title / description / activeVersionID，不含正文。
  • 失效：本进程写入后立即失效；其他实例最多 TTL（默认 30 秒，示意）。
  • 读失败降级：库不可用时返回上一份缓存（待验证），并记警告日志。
  • 不使用 Redis：项目的 cache 包目前只有用户缓存和注册验证码，没有广播；Agent 运行状态也在进程内。
资源文件读取（SkillFiles）
  • 未命中：对象存储取整包（≤ 50 MB，常见几十 KB），解出该包全部 ≤ 256 KB 的文本文件进 LRU。
  • LRU：键 versionID + path，上限按总字节（例如 64 MB，示意）；版本不可变，所以永远不需要失效，只会被淘汰。
  • 优化（可选）：存储实现了 RangeOpener 时只读 zip 中央目录再按偏移取单个文件，未验证。
  • 最坏情况：50 MB 包的首次读取。导入上限可调；若实测不可接受，再引入“文本文件入库”的混合方案（已在访谈中放弃，保留为后备）。

安全

技能是“会被模型当作方法说明读、将来还会被当代码执行”的第三方内容，而所有管理员都能导入。所以安全设计不靠限制谁能导，而靠：输入不落盘、默认停用、内容不当指令、执行无网络四道线。

信任边界

威胁与控制

阶段列：P1＝第 1 期，P2＝第 2 期。残余风险是“做完控制后仍然存在”的，需要被接受或继续处理。

#威胁控制残余风险阶段

关键设计变更：反向通道

第一版架构文档说“仿 plugin-runner，backend 经共享卷里的 Unix socket 连 runner”。调研发现这在 gVisor 下不成立。

为什么不能照搬
  • gVisor 默认 --host-uds=none：沙箱不能创建或打开宿主上的 Unix socket。让沙箱内监听共享卷里的 socket 需要 create 或 all。
  • gVisor 的 issue #9848：沙箱创建的 UDS，外部连接在服务端用 epoll_ctl 等待时会挂起。
  • 放宽 host-uds 会削弱隔离；--overlay2=all 还会让共享卷里的写入对外不可见。
来源：gVisor Observability / Filesystem 文档与 issue，检索，未抓取全文
改为：runner 主动连接 backend（只需要 connect()）
  • backend 在命名卷里监听一个内部 Unix socket（独立于公开 Gin）。
  • runner（runsc-skill 运行时，--host-uds=open 最窄值）长轮询 POST /poll 取任务。
  • 整包由 runner GET /pkg/{sha256} 拉取并缓存；结果 POST /result 回传。
  • runner 重启自动重连，没有入站连接，不需要 backend 知道 runner 的地址。
  • 在开发（runc）下代码路径完全相同。

多实例注意事项

  • 管理写入走数据库，天然多实例安全；目录缓存最多 TTL 内不一致（接受）。

  • 启动自检：不新增硬依赖；对象存储不可用不阻止启动（只影响读资源与下载）。
  • 内置技能随二进制升级；导入技能不受升级影响。
  • 内置与导入的名字冲突只在导入时校验；若后续版本新增了一个与已导入技能同名的内置技能，需要在升级说明里提示，并在启动时记警告日志（内置优先，导入的被忽略）。提案
