画布拖动卡顿 P1：别让被拖的节点每帧整棵重渲染

拖动录制里，每个 React 渲染任务平均 26.6 ms，超出 60fps 的 16.7 ms 预算。其中一半时间是 React 自己在遍历组件，另一块是被拖节点的整棵子树：xyflow 每帧给它传新的坐标，节点的 memo 就失效了，而节点本身根本不读坐标。P1 的核心是给节点加一个只比较 id、data、selected 的 memo 比较器。

根因

被拖节点每帧都整棵重渲染，而它并不需要

拖动时 xyflow 每帧给被拖节点传新的 positionAbsoluteX、positionAbsoluteY 和 dragging。

CanvasNodeView 用的是默认 memo，浅比较全部 props，所以每帧都重渲染。

web/src/pages/canvas/canvas-node.tsx:13

可它只读了 id、data、selected 三个 props。在 pages/canvas、components/canvas、hooks 里搜索 dragging 和 positionAbsolute，节点相关代码没有任何读取（节点位置由 xyflow 的外层容器用 transform 更新，不经过我们的组件）。

于是每帧白白重渲染一遍整棵子树：useTaskNode（几十个 hook 和 memo）、NodeCard 外壳、4 个 useSpring、连接点，被拖节点处于选中态时还有 NodeOverlays 里的提示词面板。

子树越大，React 自身遍历和提交的开销越大，这也解释了 React 自身占 51%

松手那一下更明显：dragging 从 true 变 false，又触发一次整棵重渲染，叠加 select 变化，5 次 mouseup 各 68 ms。

方案

P1 做两件事，第三件先量再定

P1-1　节点 memo 比较器（主要收益）

把比较逻辑抽成纯函数，只比较视图实际用到的三项。新增 props 如果将来要用，必须同时改这个函数，测试里把比较的键列出来，防止悄悄漏掉。

P1-2　onNodeClick 稳定引用（小收益，几乎无风险）

flow.tsx:692 把内联函数传给 ReactFlow，它会一路传到 200 个 NodeWrapper。换成 useCallback，依赖是 overlayGate.onNodeClick 和 setMenuId，前提是这两个本身引用稳定，实现时先确认。预计省 0.9 ms/帧以内。

P1-3　onlyRenderVisibleElements：先量，再决定

它不会减少拖动时的 JS，因为每帧只有 1 到 2 个节点在渲染。它能减少的是 DOM 规模，也就是浏览器侧的 Layerize、Paint、HitTest。P1-1 和 P1-2 做完后重新录制，如果浏览器侧仍然占大头，再单独评估。

  • 风险 滚出视口的节点会卸载：视频节点的播放进度、输入框里没提交的内容都会丢。
  • 风险 画布加载时会先按视口裁剪，要确认任务回填（useTaskBackfill）只依赖 Flow 层的节点数据，不依赖节点组件是否挂载。目前看是这样。

功能回归

  • 拖动、框选、多选拖动后，节点位置正确，松手能触发保存。
  • 选中节点后提示词面板正常浮出；取消选中后收起。
  • 节点改名、改模型、任务完成回填内容后，节点能立即更新（这几项都经过 data 变化）。
  • 拖进组、拖出组的高亮与归属正常（useGroupDrag 直接改 DOM，不受影响）。

风险

  • 漏更新 以后如果节点组件开始读位置或尺寸类 props，比较器不会放行，界面会不更新。注释和测试里列出了比较的键，改动时能看到。
  • GroupNodeView 组节点是否也套同样的比较器，要先确认它不读位置类 props。组的数量远少于素材节点，不在 P1 范围。

不在 P1 范围

  • xyflow 受控模式的往返开销（约 8%）：要改成非受控或自管 store，改动很大，留给后续。
  • 浏览器侧 Layerize、Paint、HitTest（约占忙碌时间的 36%）：先看 P1 之后的占比，再用 Layers 面板定位具体原因。
