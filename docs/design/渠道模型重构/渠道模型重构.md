# 渠道与模型重构：渠道只管连接，协议在模型里选

> **范围**：把“协议插件绑在渠道上”改成“协议插件绑在模型上”。渠道只保留连接信息（地址、Key、请求头、限流）；模型从渠道拉取，再逐个选能力和协议。同时把后台的渠道页与模型页合并成“左渠道、右模型”的主从页。
> **日期 / 状态**：2026-10-15，后端与前端均已实现并通过自动化检查，**前端界面尚未在浏览器里看过**（见 §13）。
> **证据约定**：**事实**附文件路径或来源链接；**推断**是基于事实的判断；**提案**是尚未实现的设计。
> **方案演进**：本次访谈方案没有中途转向。有两处用户**没有采纳推荐项**，已按用户的决定写入，见 §11“已确认”：① 取消 `allow_credentials` 开关，所有插件都可读 Key；② 升级时不迁移，渠道和模型（含 Key）一起清空。
> **关联文档**：[协议插件设计](../协议插件设计/协议插件设计.md)（插件三层结构，本文改写其中“渠道固定插件版本”一层）、[渠道与插件表格化](../后台管理设计/渠道与插件表格化.md)（本文取代其中渠道页与模型页的布局）、[插件简化](../插件简化/插件简化.md)（`allowedHosts` 与 `trusted_internal` 已删，本文沿用）。
> **配套演示**：[渠道模型重构-演示.html](渠道模型重构-演示.html)

## 1. 设计摘要

- **问题**：今天要先选协议才能建渠道，渠道一旦建好协议就换不了（最近一次提交还专门加了“已有渠道不能更换协议”的校验）。但真实的上游是“一个地址 + 一个 Key，下面挂很多模型，不同模型走不同协议”（同一个网关里，文本走 `/chat/completions`，视频走 `/v1/video/generations`）。绑在渠道上的协议无法表达这件事，只能为同一个上游建多个渠道、重复填 Key。
- **目标**：运营按“建渠道 → 拉取模型 → 给每个模型选协议 → 测试 → 启用”的顺序一屏完成；同一个渠道下的模型可以走不同的协议；渠道表单里没有任何协议概念。
- **推荐结论**（均已确认，见 §11）：
  1. 渠道只有：名称、Base URL、API Key、Secret Key（可选）、自定义请求头、限流、启停、排序。
  2. “拉取模型”由宿主内置的通用请求完成（`GET {base_url}/models` + Bearer），不再经过插件；拉不到可手动新增；拉到的模型是“待配置”。
  3. 协议插件、版本、协议设置项都放到模型的配置里；模型固定插件版本，插件页一键批量升级。
  4. 取消 `allow_credentials`，不区分插件来源。
  5. 渠道不再要求“检查通过才能保存”，连通验证挪到模型的“测试模型”。
  6. 渠道页与模型页合并成主从页；用户看到的模型顺序 = 渠道顺序 + 渠道内顺序。
  7. 升级时不迁移：渠道、模型、渠道 Key 一起清空，插件保留。
  8. 第一期做完以上全部，只有“渠道内批量调价与批量上下线”放第二期。

### 2.2 设计约束

- 插件版本不可变，任务快照记 sha256；**快照结构尽量不变**，worker 与执行器不应因此重写（F12）。
- 插件契约只增不改：已上传的插件代码不用重新上传就能跑。
- 渠道 Key 只写不读、永远不下发（F1、`AISecret`）。
- 单模型的启用检查仍然是“半成品可保存、启用要过检查”（F10）。
- 出站请求的 SSRF 防护与“只有发往 `base_url` 同源的请求才注入 Key”不能被削弱（[插件简化](../插件简化/插件简化.md) §6.1）。

### 2.3 当前缺口

- 渠道和协议强绑：同一个上游里不同协议的模型要建多个渠道，Key 重复填（F1、F3）。
- 拉取模型依赖插件钩子，只有 3 个内置插件能用（F5）。
- 协议列表没有厂商和请求路径，运营选协议时看不出它请求哪个路径（F4）。
- 模型顺序是全局一个数，没有“渠道”这一层的分组（F17）。

## 3. 用户与场景

- **用户**：后台运营（`admin`）和站长（`super_admin`）。`super_admin` 上传协议、建渠道、填 Key；`admin` 拉取模型、给模型选协议、定价、测试、启用（F18）。
- **触发场景**：① 接入一个新的上游，里面有几十个模型；② 上游新增了几个模型；③ 某个模型换一种协议；④ 协议插件出了新版本。
- **主任务**：建渠道 → 拉取模型 → 逐个选能力和协议 → 测试 → 启用。
- **成功指标**（提案，实现后统计）：
  - 接入一个已有 20 个模型的上游，从建渠道到第一个模型可用的操作步数；
  - “渠道配置错了到发现”的时间（现在要等保存时的检查，之后要等到测试模型）；
  - 因“协议选错”导致的试跑失败占比。

## 5. 设计原则

1. **渠道只管“连到哪里、用什么凭证、一次最多发多少”**；协议、版本、协议参数一律是模型的事。（F1、F7；用户回答）
2. **半成品可以存在，启用才检查**：拉到的模型是“待配置”，不需要新状态，沿用 F10。
3. **模型兜底手动加**：拉取只是便利，不是唯一来源。（Cherry Studio、New API 的失败案例）
4. **契约只增不改**：已上传的插件不改一行就能运行；`ctx.channel.settings` 的名字保留，值改由模型提供。（§2.2）
5. **快照形状不变**：worker 与执行器的改动压到最小，只改“快照由谁拼出来”。（F12）
6. **一个概念一处拖拽**：渠道顺序在左，模型顺序在右，用户看到的顺序就是两者叠加。（用户回答）

## 6. 推荐方案

### 6.1 信息架构

```
后台 / AI
├─ 总览
├─ 渠道与模型（主从页，取代原“渠道”“模型”两页）
│    ├─ 左：渠道列表（搜索、状态筛选、新增渠道、设置排序）
│    └─ 右：选中渠道的 详情 + 模型管理
├─ 插件（上传、启停、版本、升级模型）
└─ （原“模型”页删除）
```

路由：`/admin/ai/channels`（主从页）；`/admin/ai/models` 保留为重定向到主从页（带 `?model=<key>` 时打开该模型弹窗，兼容旧链接）。

### 6.2 主流程

1. **（super_admin）上传协议插件**：同现状。
2. **（super_admin）新增渠道**：名称、渠道 key、Base URL、API Key、Secret Key（可选）、自定义请求头、限流。保存时只做字段校验，不发请求。
3. **（admin / super_admin）拉取模型**：右侧点“拉取模型”→ 宿主请求 `GET {base_url}/models` → 弹窗列出上游返回的模型，默认全选，已存在的标“已存在”且不重复导入 → “确认导入”创建“待配置”模型。
4. **给模型选能力和协议**：编辑模型 → “基本信息 / 能力与参数 / 积分定价”三个页签。“基本信息”里“能力与协议”：先选能力，再从协议列表里选；选完后在右侧填协议设置项、选版本。
5. **测试模型**：模型弹窗底部“测试模型”用该模型的协议真实跑一遍（沿用现有 `test-run`）。
6. **启用**：启用前检查链见 §7.3。

### 6.3 渠道表单（提案）

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 渠道名称 | 是 | 显示名，≤128 |
| 渠道 key | 是 | 小写字母、数字、连字符，≤64，创建后不可改；表单从名称自动生成建议值（名称里没有可用字符时用 `channel-xxxx`），可手改 |
| Base URL | 是 | 沿用现有校验（http/https、无用户名密码、不指向内网） |
| API Key | 创建时可空 | 只写不读；已设置时显示“已设置” |
| Secret Key | 否 | 只写不读；供 AK/SK 签名类协议使用（见 §8.3） |
| 自定义请求头 | 否 | 最多 32 条；名称/值校验见 §8.3；默认有一条宿主默认 UA，用户加 `User-Agent` 后覆盖 |
| 限流 | 否 | `rps`、`max_concurrency`、`max_running`，同现状 |
| 启用 | 是 | 同现状 |

**没有**：协议、插件版本、协议设置项、“允许插件读取 Key”开关。

### 6.4 拉取模型弹窗

- 标题“选择要导入的模型”；说明“上游共返回 N 个模型。默认已选，可批量全选或取消全选；已存在的模型不会重复导入。”
- 顶部搜索框（按模型标识过滤）；“已选择 x / N 个模型”、“全选”、“取消全选”。
- 每个模型是一个可勾选的标签；“已存在”的模型（同渠道、同 `upstream_model`）显示“已存在”小字，**默认勾选但不会重复导入**（与截图一致，保证“全选”的语义稳定）。
- 底部提示“将导入 X 个新模型，另有 Y 个已存在模型已勾选”。
- 失败（请求不通、401/403、返回不是 OpenAI 形状、列表为空）：弹窗内给出原因和下一步（“检查 Key 和 Base URL”“该上游可能不提供 `/models`，请手动新增模型”），并保留“手动新增模型”入口。
- 只新增、不删除：上游少了模型，本地模型不动。

### 6.5 模型编辑弹窗

三个页签沿用现有的“基本信息 / 能力与参数 / 积分定价”（`model-dialog.tsx:48-49`）。“基本信息”页新增“**能力与协议**”区块：

1. **模型能力**（必选）：文本 / 图片 / 视频 / 音频（分段控件）。`agent` 模型的处理见 §6.8。
2. **调用协议**：下方一个可搜索的列表。
   - 列表内容：所有最新版本声明了所选能力的 endpoint 的插件。**已停用的插件也显示，但置灰、不可选，并写明“插件已停用，不可选”**（不可选的选项不隐藏）。每行显示：协议名称、请求路径（`POST /v1/messages`，来自新增的 endpoint 展示字段）、厂商、同步/异步、最新版本。
   - 搜索：协议名称、厂商、请求路径。
   - 单选；右侧“当前选择”区域显示：插件描述、鉴权方式（Bearer / Header / Query / 自定义签名）、版本下拉（默认最新，可选更早的版本）、**协议设置项表单**（按所选版本的 `channelSettings` 渲染）。
3. 切换能力：如果已选协议不支持新能力，清空协议并提示“已选协议不支持图片，请重新选择”；已填的协议设置项丢弃。
4. 切换协议 / 版本：设置项按新版本重新校验，取值不再被声明的丢弃，确认框里列出。
5. 底部“测试模型”（`model-test-dialog.tsx`）、“取消”、“保存”；“模型停用”开关在左下（沿用现有启用检查）。

## 7. 状态与异常

### 7.1 模型状态

| 状态 | 条件 | 画布可见 | 能否启用 |
| --- | --- | --- | --- |
| 待配置 | 拉取或手动新增，`kind` 为空或没选协议 | 否 | 否，提示缺什么 |
| 已配置未启用 | 通过校验，开关关 | 否 | 是 |
| 已启用 | 开关开且渠道、协议、Key 都可用 | 是 | — |
| 已启用但暂不可用 | 渠道停用 / 插件停用 / 版本被删 | 否（Registry 里 `rt = nil`） | 保存会被拒绝 |

### 7.2 页面状态

| 场景 | 行为 |
| --- | --- |
| 渠道列表为空 | 左栏空状态“还没有渠道”+“新增渠道”；右栏提示“先新增渠道，再拉取模型” |
| 渠道下没有模型 | 右栏空状态：“拉取模型”（主按钮）和“新增模型” |
| 拉取中 | 弹窗内骨架 + “正在向上游请求模型列表…”，可取消；超时 30s |
| 拉取失败 | 弹窗内错误卡片 + 原因 + “重试”“手动新增模型”；Key 明文已脱敏 |
| 拉取成功但没有新模型 | “上游返回 N 个模型，都已存在”，“确认导入”禁用 |
| 保存冲突 | 沿用现有模型保存规则：已启用模型保存前必须过启用检查，不通过拒绝保存并给原因 |
| 渠道被停用 | 该渠道所有模型在画布里不可见；右栏顶部显示“渠道已停用”提示条；进行中的任务按快照继续 |
| 角色 | `admin` 的“新增渠道 / 编辑渠道 / 设置 Key / 启停与删除渠道 / 设置排序”、插件页的启停与“升级模型”**置灰，悬停提示“仅 super_admin 可用”**（不隐藏）；“拉取模型”和模型的全部操作可用。`super_admin` 全部可用 |

### 7.3 启用检查链（提案，替换 F11）

对模型 `channels[0]`：

1. 正文校验通过（含 `kind` 在允许集合内、`label` 非空、定价完整）。
2. 渠道存在且启用（`ErrChannelNotFound` / `ErrChannelDisabled`）。
3. `kind = agent`：渠道 API Key 已设置，结束。
4. 其他 kind：`protocol` 已选（缺失返回“该模型还没有选择调用协议”，`ErrConfigInvalid`）。
5. 插件存在且启用（`ErrPluginDisabled`）。
6. 固定的版本存在、属于该插件、`meta` 可解析（`ErrConfigInvalid`，文案“模型固定的插件版本不存在”）。
7. 版本的 `endpoints[kind]` 存在（`ErrConfigInvalid`）。
8. 协议设置项按版本的 `channelSettings` 校验并补全默认值。
9. 版本的鉴权不是 `none` 时，渠道 API Key 已设置（`ErrChannelSecretUnset`）。

### 7.4 撤销、恢复与权限

- 模型没有版本管理（沿用现状：保存即覆盖）；误拉的“待配置”模型可直接删除（`delete-check` 沿用）。
- 渠道删除：仍然要求渠道下**没有模型**且没有进行中的任务（`ErrChannelInUse`），错误里列出模型。批量清理用“批量删除”（一期）。
- 权限见 §7.2；拉取模型对 `admin` 开放（与现有 `POST /channels/:key/import` 一致，F18）。

## 8. 数据与工程影响

### 8.1 数据表（提案）

**`ai_channels`**

| 变更 | 字段 | 说明 |
| --- | --- | --- |
| 删除 | `plugin_key`、`plugin_version_id`、`allow_credentials`、`settings_json` | 升级时随清空一起删列 |
| 新增 | `sort int not null default 100` | 渠道顺序，越小越靠前 |
| 新增 | `headers_json json not null default '{}'` | 自定义请求头 `{ "名称": "值" }`，**明文存储，不要放密钥** |
| 保留 | `key / name / base_url / rate_limit_json / enabled / updated_by / created_at / updated_at` | 不变 |

**`ai_secrets`**：每个渠道最多两行：`channel:<key>`（API Key，同现状）和 `channel:<key>:secret`（Secret Key，新增）。渠道 key 的正则不含 `:`，所以两个名字不会冲突。

**`ai_models`（指针表）**：`kind` 允许为空串（“待配置”）；`sort` 的语义改为“渠道内顺序”。不新增列：渠道归属仍从正文取，渠道页按 `channel=<key>` 查询（F16 已有）。

**模型正文 `channels[0]`**（`ai_config_revisions.body_json`，JSON）：

```jsonc
{
  "channel": "yingce",
  "upstream_model": "gpt-image-2",
  "protocol": {                       // agent 模型没有这一项
    "plugin": "openai-image",         // 插件 key
    "version": "1.0.0",               // 固定的 semver，保存时服务端补成所选版本
    "settings": { "api": "responses" } // 插件 channelSettings 的取值，保存时按声明校验并补默认值
  }
}
```

Go 侧：`modelcfg.ChannelRef` 增加 `Protocol *Protocol`；`modelcfg.JSONSchema()` 同步（Monaco 补全）。

### 8.2 运行时装配（尽量不动执行器与 worker）

- `provider.ChannelRuntime` 与 `Snapshot` 的**形状不变**。`ChannelSnapshot.PluginKey / PluginVersionID / Settings` 仍在，只是来源变了：由“渠道行”改成“渠道行 + 模型的 `protocol`”拼出。
- `AIConfigService.reload()`（Registry 加载）：对每个模型，取其 `channels[0].channel` 的渠道行、`protocol` 指向的版本行，组装 `rt`；缺任何一项 `rt = nil`（不可用）。
- `provider.RuntimeOf(ch, ver)` 增加参数 `settings map[string]any`。
- `ctx.channel.settings` 的名字保留；`ctx.credentials`：当版本的 `auth.type = custom` 时宿主直接提供（`allow_credentials` 判断改为 `auth.type == custom`），新增 `ctx.credentials.secretKey`（Secret Key 已设置时）。
- 请求头优先级（低 → 高）：宿主默认 UA < 渠道自定义头 < 插件请求描述里的头 < 宿主注入的鉴权头。**渠道自定义头只加到发往 `base_url` 同源的请求上**（与 Key 注入同一条规则），产物下载等发往其他主机的请求不加。
- Agent：LLM 网关从渠道直接取 Base URL、API Key 与自定义头（`service/agent/bridge.go`、`llmgateway.Target.Headers`），不再经过渠道的插件；渠道头先于网关自己的 Content-Type / Accept / Authorization 写入，所以覆盖不了它们。Agent 模型的快照只有渠道部分，`Plugin` 为零值（`provider.AgentRuntimeOf`）。

### 8.3 渠道校验细节

- 自定义请求头：名称符合 HTTP token 规则，最多 32 条，值 ≤1024 字符；**禁止**：`Host`、`Content-Length`、`Transfer-Encoding`、`Connection`、`Authorization`、`Proxy-Authorization`、`Cookie`（宿主独占或敏感）。与插件鉴权头同名时按优先级由宿主鉴权覆盖，不报错。
- Secret Key：只写；`PUT` 空串视为“清除”；已设置的渠道表单显示“已设置”。
- 即梦、可灵的 `AccessKeyId|SecretAccessKey` 写法**继续有效**（契约只增不改）；新插件可以改读 `secretKey`。

### 8.4 插件契约与元数据的增量（提案）

- `meta.vendor`（可选，小写字母/数字/连字符，同 `ModelConfig.Vendor` 的规则）：协议列表里显示厂商。
- `meta.endpoints[kind].path`（可选，字符串，≤200，**仅展示用，宿主不据此发请求**）：协议列表里显示“POST /v1/messages”。方法写在 `endpoints[kind].method`（可选，默认 `POST`）。
- 缺失时列表显示“—”；内置插件补上这两项，**统一升到 `1.1.0`**（内置插件改代码必须升版本号，见 `plugin-contract.md`）。
- `meta.import`、`buildImportRequest`、`parseImportResponse`、`buildCheckRequest`：**契约暂不删除，宿主不再调用**，文档标“已弃用”；预检继续接受它们，已上传的插件不受影响。后续版本再清理。
- 提示词（`plugin-prompt.ts`）与 `backend/docs/plugin-contract.md` 同步：去掉“必须实现检查与导入”的要求；说明 `ctx.channel.settings` 现在来自模型的协议设置。

| 方法与路径 | 权限 | 说明与业务错误 |
| --- | --- | --- |
| `POST /admin/ai/channels` | super | 创建渠道：`{key, name, base_url, headers?, rate_limit?, enabled?}`；去掉 `plugin_*`、`allow_credentials`、`settings`。`ErrChannelExists` / `ErrChannelInvalid` |

### 8.6 通用拉取请求（提案）

```
pullModels(channel):
  key = secret("channel:"+channel.key)            // 为空 → ErrChannelSecretUnset
  req = GET channel.base_url + "/models"       // 只补 /models，不自动补 /v1
  req.headers = defaultUA + channel.headers
  req.header["Authorization"] = "Bearer " + key
  resp = guardedClient.Do(req)                     // 复用 SSRF 守卫与限流（渠道 rps / max_concurrency）
  if resp.status ≥ 400 → 错误（401/403：Key 无效或无权限）
  list = resp.json.data[].id                       // OpenAI 形状；不是该形状 → "返回格式不符"
  return dedupe(list), mark exists by (channel, upstream_model)
```

- 请求走现有宿主的出站守卫（`netguard`），Key 只发往 `base_url`。
- 导入时的模型 key：取上游 id，把不在 `modelKeyRe` 内的字符替换成 `-`；与已有模型 key 冲突时加渠道前缀 `<channel>-<id>`；仍冲突再追加 `-2`、`-3`…。`label` 默认等于上游 id，`kind` 为空。（**默认值**，§11.3）

### 8.7 清空旧数据（已实现）

仓库在设计之后改成了**版本化 SQL 迁移**（`backend/migrations/`，规则见 `backend/AGENTS.md`“数据库迁移”：已发布的迁移文件不改、只向前、**先加后删**），所以不是 `repository/migrate.go` 的收敛步骤，而是新增 `0002_channel_protocol_on_model.sql`：

1. `DELETE` 模型配置（`ai_config_revisions` 里 target=model）、`ai_models`、`ai_secrets` 中名字以 `channel:` 开头的行、`ai_channels` 全部行；
2. `ai_channels` 新增 `headers_json`、`sort`；
3. **先加后删**：旧的四列（`plugin_key`、`plugin_version_id`、`allow_credentials`、`settings_json`）本版本**不删**，只补默认值，让新建渠道不用写它们，退回上一个版本的镜像仍能用当前的库；Go 里它们叫 `Legacy*`，代码不再读写。**下一个版本再删这四列。**

**保留**：插件及其版本、历史任务（`generation_tasks` 里的快照不改）、审计、用户数据。迁移测试：`internal/tests/migration/channel_protocol_on_model_test.go`（用老库结构验证清空范围与新列默认值）。

> **升级前必须告知**：进行中的任务在清空之后会因找不到渠道 Key 而失败（快照里没有 Key，执行时按渠道名解密）。升级请选在没有进行中任务的时间，或先把渠道停用等任务跑完。

## 9. 方案取舍

### 9.1 决策矩阵

权重来自用户确认的优先级：“渠道里不再有协议”和“拉取→选协议一屏完成”是核心（权重高），迁移成本次之。

| 维度（权重） | A 本方案：模型选协议 + 主从页 | B 渠道仍绑协议，只加拉取 | C 渠道可绑多个协议 |
| --- | --- | --- | --- |
| 同一上游多协议（高） | 一个渠道搞定 | 多个渠道、重复 Key | 渠道里要维护“协议列表”，模型再从里面选，多一层 |
| 渠道表单简洁（高） | 最简 | 不变 | 更复杂 |
| 一屏完成接入（高） | 是 | 拉取后仍要在模型页逐个绑渠道 | 是 |
| 数据与运行时改动（中） | 大 | 小 | 最大 |
| 与参考产品一致（中） | 一致 | 不一致 | 不一致 |

### 9.2 明确放弃的东西

- **渠道级连通性检查与“检查通过才能保存”**：视频类上游没有通用探测接口，渠道级检查给不出可靠结论（用户确认挪到“测试模型”）。
- **插件的 `import` 钩子对渠道的作用**：覆盖面窄（3 个插件），被通用请求取代；契约里保留但不再调用。
- **`allow_credentials` 开关与“可信插件”标记**：用户确认不区分插件来源。风险见 §11.2。
- **自动迁移**：用户确认升级时清空。
- **全局“模型”页与跨渠道的全局排序值**：并入主从页，顺序由“渠道顺序 + 渠道内顺序”决定。
- **多渠道路由**：数据结构仍是数组、预留，本期仍然一个模型一个渠道。

## 11. 待确认问题与已确认事项

### 11.1 已确认（用户的回答）

1. **拉取方式**：宿主内置通用请求（`GET /models` + Bearer），失败可手动新增；拉到的模型是“待配置”。**路径只在 `base_url` 末尾拼 `/models`，不自动补 `/v1`**（用户 2026-10-15 指定；上游要 `/v1` 就写进 Base URL）。
2. **插件版本**：模型固定 `plugin + version`，插件页一键批量升级。
3. **协议设置项**（`channelSettings`）：放在模型的“协议设置”里填。
4. **`allow_credentials`**：取消开关；**不区分插件来源，所有插件都可读 Key**（用户的理由：插件一般都是管理员自己写的）。
5. **渠道表单字段**：新增“自定义请求头”和“独立 Secret Key（可选）”。
6. **连通性检查**：渠道不强制检查，挪到模型的“测试模型”。
7. **页面结构**：渠道与模型合并成主从页（左渠道、右模型）。
8. **模型页**：并入主从页，去掉独立的模型页。
9. **模型顺序**：渠道顺序 + 渠道内顺序。
10. **存量数据**：不迁移；渠道、模型和渠道 Key 一起清空。
11. **范围**：第二期只放“渠道内批量调价与批量上下线”，其余第一期做完。
12. **内置插件的 `vendor` 与 `endpoints[kind].path/method`**：字段按 §8.4 的写法，内置插件一次性升到 `1.1.0`。
13. **导入数量**：一般不存在很多模型，不做分批导入；单次 ≤500，超出时提示分两次导入即可（不再单独设计）。
14. **用户端不显示渠道名**：画布只显示模型的 `label` / `vendor`，渠道对用户不可见。

### 11.2 用户接受的风险

- **插件都可读 Key**：上传的插件不做代码评审。缓解（现状，非新增）：插件钩子跑在独立的 `plugin-runner` 进程（生产容器 `network_mode: none`），Key 只在宿主发往 `base_url` 同源的请求里注入；但 `custom` 鉴权的插件拿到 Key 后，可以把它写进发往其他公网主机的请求里（[插件简化](../插件简化/插件简化.md) §6.1 已放开绝对地址）。**这一点由用户接受**，文档里不再有 `allow_credentials` 的审计事件。
- **升级即清空**：升级到新结构的那一刻，线上模型全部不可用，直到运营重建；进行中的任务会失败（§8.7）。

### 11.3 默认值（不需要用户决定，实现时按此做）

- Agent 模型不选协议，由宿主网关直接用渠道 Bearer 请求（推断自 F9）。
- 拉取只新增不删除；上游少了模型不动本地。
- 导入的模型 key 的生成与冲突规则见 §8.6。
- 渠道自定义请求头只加到发往 `base_url` 同源的请求；`Host`、`Authorization` 等头禁止设置。
- 插件的 `import` / `buildCheckRequest` 钩子保留但不再调用，不强制内置插件升版本。
- 渠道的删除规则不变：渠道下还有模型就不能删，先在表里批量删除模型。
- 渠道限流仍在渠道层面（F13），不挪到模型。
- 排序用“上移 / 下移 + 原生拖拽”，不引入拖拽库（§4.3）。
- 模型可以在“基本信息”里更换所属渠道（协议与渠道无关，换渠道不影响协议）；设置项不变。
- 旧路由 `/admin/ai/models` 重定向到主从页。
