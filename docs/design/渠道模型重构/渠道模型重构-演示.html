渠道模型重构演示

渠道只管连接，协议在模型里选

今天要先选协议才能建渠道，渠道建好协议就换不了，同一个上游里不同协议的模型只能拆成多个渠道、重复填 Key。新方案把它拆开：渠道只有地址、Key、请求头、限流；模型从渠道拉取，再逐个选能力和协议。后台的渠道页和模型页合并成“左渠道、右模型”的主从页。

阅读说明。本页是设计提案，尚未实现。对应 Markdown 设计文档 渠道模型重构.md（§1–§11）。项目现状来自代码核对；外部产品来自检索。原型里的数据、协议路径、耗时、上游返回都是示意，没有真实调用任何服务。

主线流程：从协议插件到画布里能用的模型

运营按这个顺序一屏完成。高亮的两步是和现在不同的地方：渠道里不再选协议，协议挪到了模型里。

1 上传协议插件super_admin；同现状
2 新增渠道名称、地址、Key、请求头、限流。不选协议
3 拉取模型宿主发 GET /v1/models；得到“待配置”模型
4 模型里选协议先选能力，再从协议列表选；填协议设置
5 测试模型用该协议真实跑一遍
6 启用过检查链后画布可见
设计：渠道回答“连到哪里、用什么凭证、一次最多发多少”；模型回答“用哪种协议、什么参数、卖多少积分”。放弃了“渠道级连通性检查”：视频类上游没有通用探测接口，检查挪到第 5 步。
拉不到模型时（回退，永远可用）：上游没有 /v1/models、Key 无效、格式不符，弹窗里给出原因，并可以手动新增模型。没选协议的模型保持“待配置”，不会出现在画布里，也不能启用。

三个对象各管什么

协议、版本、协议设置项从渠道挪到模型；渠道多出请求头和 Secret Key；插件页的“升级渠道”变成“升级模型”。

渠道
super_admin 管

连接信息。名称、Base URL、API Key、Secret Key（可选）、自定义请求头、限流、启停、顺序。没有协议、版本、“允许插件读取 Key”开关。

模型
admin 也能管

能力 + 协议。能力（文本 / 图片 / 视频 / 音频 / Agent）、固定的插件 + 版本、协议设置项、参数、定价、启停。拉取得到的是“待配置”。

协议插件
super_admin 上传

翻译上游协议。版本不可变；声明能力、鉴权、协议设置项；新增可选的厂商和请求路径（只用于展示）。

对比：现状、本方案、只加拉取

本方案改动最大，但它是唯一让“同一个上游多种协议”不用建多个渠道的做法。

现状（渠道绑协议）本方案（模型选协议）只加拉取，仍绑协议
同一上游多协议要建多个渠道，Key 重复填一个渠道，模型各选各的同现状
渠道表单含协议、版本、设置项、Key 开关只有连接信息同现状
拉取模型仅 3 个内置插件有导入钩子内置通用请求；其余手动加仍靠插件钩子
协议升级升级渠道升级模型（批量）升级渠道
实现改动—大：数据、接口、运行时装配、两个页面小

接入一个新上游，会发生什么

以“一个带 8 个模型的 OpenAI 兼容网关”为例；第二张卡是升级到新结构时必须提前说清的边界。

  1. super_admin 新增渠道填名称、地址、API Key；保存只做字段校验，不发请求。
  2. 点“拉取模型”宿主向 {base_url}/v1/models 发请求，弹窗列出 8 个，默认全选。
  3. 确认导入创建 8 个“待配置”模型，已存在的不重复导入。
  4. 逐个或批量选能力和协议文本模型选 OpenAI，图片模型选图片协议；选完填协议设置。
  5. 测试模型 → 启用测试通过、检查链通过后，用户在画布里看到它。
边界：升级到新结构时，渠道、模型和渠道 Key 一起清空。
  • 线上模型全部不可用，直到运营重建；渠道 Key 需要重新填。
  • 进行中的任务会因找不到渠道 Key 而失败。
  • 保留：协议插件与版本、历史任务、审计、用户数据。

交付时提前告知：升级选在没有进行中任务的时间，或先停用渠道等任务跑完。这是用户确认的决定（Markdown §11.1、§11.2）。

接口

权限沿用现有划分：渠道增改与 Key 是 super_admin；拉取、模型增改是 admin 也可以。

方法与路径权限说明与业务错误
POST /admin/ai/channelssuper创建：{key,name,base_url,headers?,rate_limit?,enabled?}；无 plugin_*。ErrChannelExists / ErrChannelInvalid
PUT /admin/ai/channels/:keysuper更新；headers 整体替换
PUT …/:key/secret、…/secret-keysuper设置 API Key / Secret Key；Secret Key 空串 = 清除
PUT /admin/ai/channels/sortsuper{keys:[全集]}，服务端按 10、20、30… 重写；不是全集 → ErrInvalidParams
POST …/:key/pull-modelsadmin拉取，不落库：{models:[{id,exists}],total}。ErrChannelSecretUnset、上游不通 / 401 / 格式不符 / 超时（ErrPluginOpFailed 502，文案区分）。限制：响应 ≤4MB、≤2000 个、30s
POST …/:key/models/importadmin{ids:[…]}，事务内创建未启用的“待配置”模型，已存在的跳过；单次 ≤500；返回 {created,skipped}
PUT …/:key/models/sortadmin该渠道内模型的完整新顺序，只改这些模型的 sort
GET /admin/ai/plugins/optionsadmin协议列表数据：vendor、各 endpoint 的 mode/method/path、channelSettings、鉴权类型
POST/PUT /admin/ai/modelsadmin正文含 channels[0].protocol；version 缺省补最新；settings 校验并补默认值；半成品照存；已启用的模型保存前过检查链
POST /admin/ai/plugins/:key/upgrade-modelssuper新增：批量升级固定在旧版本的模型；逐个处理，返回 {upgraded,failed}，失败不中断
GET …/plugins/:key/delete-checksuper阻断原因 plugin_channels 改为 plugin_models
删除—check-draft、:key/check、旧 :key/import、渠道的 plugin_version 修改

启用检查链、拉取与运行时装配（伪代码，提案）

检查链替换现有 checkEnableable；运行时装配让 Snapshot 的形状保持不变，worker 与执行器基本不用改。

// 启用检查链（提案）——前一步不过就不往下
checkEnableable(model):
  1 校验正文                     → ErrConfigInvalid（kind 为空 / label 为空 / 定价不全）
  2 渠道存在且启用               → ErrChannelNotFound / ErrChannelDisabled
  3 kind == agent → 渠道 API Key 已设置 → 通过（不看协议）
  4 protocol 已选                → ErrConfigInvalid "该模型还没有选择调用协议"
  5 插件存在且启用               → ErrPluginDisabled
  6 固定版本存在，meta 可解析     → ErrConfigInvalid
  7 版本 endpoints[kind] 存在    → ErrConfigInvalid
  8 settings 按 channelSettings 校验并补默认值
  9 版本 auth != none → 渠道 API Key 已设置 → ErrChannelSecretUnset

// 拉取（提案）
pullModels(channel):
  key  = secret("channel:" + channel.key)             // 空 → ErrChannelSecretUnset
  req  = GET channel.base_url + "/v1/models"           // base_url 以 /v1 结尾不重复拼接
  req.headers = defaultUA + channel.headers
  req.Authorization = "Bearer " + key
  resp = guardedClient.Do(req)                         // 复用 SSRF 守卫与渠道限流；Key 只发往 base_url
  list = resp.json.data[].id   // 不是 OpenAI 形状 → "返回格式不符"
  return dedupe(list) + exists 标记（同渠道、同 upstream_model）

// Registry 装配（提案）：快照形状不变，只改拼装来源
for model in models:
  ch  = channels[model.channels[0].channel]
  ver = versions[model.protocol.plugin @ model.protocol.version]
  rt  = ChannelRuntime{ Channel: ch + settings: model.protocol.settings, Plugin: ver }   // 缺任何一项 → rt = nil（不可用）
// 请求头优先级（低 → 高）：宿主默认 UA < 渠道自定义头 < 插件请求描述里的头 < 宿主注入的鉴权头
// 渠道自定义头只加到发往 base_url 同源的请求，与 Key 注入同一条规则

已确认的决定

  1. 拉取走宿主内置的通用请求（GET /v1/models + Bearer），失败可手动新增，拉到的是“待配置”。
  2. 模型固定插件版本，插件页一键批量升级。
  3. 协议设置项跟着模型走，在模型的“协议设置”里填。
  4. 取消 allow_credentials，不区分插件来源，所有插件都可读 Key。用户的理由：插件一般都是管理员自己写的。这一条是用户没有采纳推荐项的决定，风险写在 Markdown §11.2。
  5. 渠道新增“自定义请求头”和“独立 Secret Key（可选）”。
  6. 渠道不强制连通性检查，检查挪到模型的“测试模型”。
  7. 渠道与模型合并成主从页（左渠道、右模型），去掉独立的模型页。
  8. 用户看到的模型顺序 = 渠道顺序 + 渠道内顺序。
  9. 升级时不迁移，渠道、模型和渠道 Key 一起清空；插件与历史任务保留。这一条同样是用户没有采纳推荐项的决定。
  10. 第二期只放“渠道内批量调价与批量上下线”，其余第一期做完。
  11. 已搁置：渠道级连通性检查；插件 import 钩子对渠道的作用；“可信插件”标记；自动迁移；一个模型绑多个渠道。
  12. 主文档已回写：本页新增的细节（禁用的协议行写原因、admin 的渠道按钮置灰而不隐藏）已同步到 Markdown §6.5、§7.2。
