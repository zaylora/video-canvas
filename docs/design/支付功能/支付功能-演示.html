积分充值与支付管理

用户用微信或支付宝买积分，后台管渠道、档位和订单

现在积分只能靠注册赠送和管理员手动调整获得。这次加两样东西：一个积分商城，用户选固定档位，用微信或支付宝付款；后台一个支付管理，下面是支付渠道、充值商品、支付订单三页。底线只有一条：付了钱一定到账，不会多到账。本期不做退款、会员、礼品卡和对账页，也不做手机端。

阅读说明。本页是设计提案，尚未实现。依据有三份：飞书需求文档、两个开源项目的源码（sub2api、影策 open-ai-canvas，2026-10-16 读过），以及仓库现有的积分代码。完整证据和来源见同目录的 支付功能.md。原型里的二维码、商户号、耗时都是示意，没有调用任何真实服务。

从用户点「立即支付」，到右上角积分数字变化。

扫码或跳转付款微信显示二维码；支付宝新开标签页
回调验签 + 核对金额签名、商户号、实付金额都对上才算数

推送到账WebSocket 推送，弹框显示「已到账」，同时每 3 秒轮询兜底
设计：渠道适配器只做四件事：签名、拼请求、解析响应、验签。「是否已付、付了多少、给谁加多少积分」全部由 Go 宿主判断。积分记账直接复用现有的 user_credits 和 credit_ledger，只新增一种流水类型 recharge。
回调没到时（兜底）：还有三条路能发现「其实已经付了」：用户点「我已完成支付」时主动查单；后台任务每 30 秒补查一次；管理员在订单页点「查单」。订单超时前也一定先查单再关单。首批四个渠道都支持查单。

用户说「付了钱没到账」时，会发生什么

这是支付最常见的投诉。系统先自己找，找不到再由人工处理。全程没有「不经渠道直接加积分」的按钮。

  1. 用户在弹框点「我已完成支付」后端立刻向渠道查单，已付就当场入账。同一笔订单每 5 秒最多查一次。
  2. 后台任务每 30 秒补查创建超过 2 分钟还没结果的订单，每 2 分钟查一次；到期的订单先查单再关单。
  3. 运营在「支付订单」搜订单号，点「查单」和上面走同一个入账入口，已付就入账，写审计。
  4. 还是不行：人工核实运营在商户后台核对流水后，用现有的「调整积分」补发并写备注。
边界：系统不做退款，也不能强制入账
  • 易支付、虎皮椒关单后用户仍可能付款：迟到的回调照样入账，订单会标「迟到入账」。
  • 回调金额与订单不符：订单标为「异常」，不入账，由运营人工处理。
  • 用户要退款：运营在商户后台退钱，再用「调整积分」扣回。

交付时要提前告知运营：第 4 步只在渠道查单也查不到时才会用到，例如用户付错了商户。

选一个渠道，把一笔订单推着走

订单状态迁移

共六个状态。credited、abnormal 是终态；closed 和 create_failed 在收到已付通知后还能转为 credited（abnormal 不会被后续通知自动入账）。

从到条件
creatingpending / create_failed渠道下单成功或失败；进程中途崩溃的订单，2 分钟后由补单任务处理
pendingcredited验签通过的回调，或查单结果为已付，且金额、商户身份、交易号都校验通过
pendingclosed超时、用户取消、管理员关单；都要先查单，已付就转 credited
pendingabnormal实付 ≠ 应付，或渠道交易号已被别的订单占用
closedcredited关单后收到已付通知，同时 late_paid=true
create_failedcredited下单请求超时但渠道其实建了单、用户随后付了款：照常入账，不入账等于吞钱

核心：唯一的入账入口 CreditOrder

回调、主动查单、补单任务、管理员查单，最后都调用它。按项目规范，事务内不做任何网络请求。

// service.CreditOrder（提案）—— 调用前，渠道结果已在事务外拿到：{order_no, trade_no, paid_fen, identity}
WithTx(func(tx) {
  order := tx.LockOrder(order_no)                 // SELECT … FOR UPDATE
  if order.status == credited  { return Duplicate }               // 幂等成功
  if order.status ∉ {pending, closed, creating} { return ErrOrderState }   // 65007
  if identity != channel.identity   { markAbnormal("identity_mismatch"); audit; return }
  if paid_fen != order.amount_fen   { markAbnormal("amount_mismatch");   audit; return }
  EnsureCredit(order.user_id); LockCredit(order.user_id)
  inserted := InsertLedger({type: recharge, payment_order_id: order.id, amount: order.credits})   // ON CONFLICT DO NOTHING
  if !inserted { setCredited(order); return Duplicate }
  AddCredit(order.user_id, +order.credits)
  n := UPDATE payment_orders SET status=credited, trade_no, paid_*, late_paid=(old==closed)
       WHERE id=? AND status<>'credited'            // 交易号唯一冲突 → abnormal("trade_no_conflict")
  assert n == 1; products.sold_count += 1
})
afterCommit: ws.Publish(user:{id}, "payment.updated", {order_no, status, credits})

已确认的决定

  1. 只做积分充值：会员（黑卡）、礼品卡、支付对账页放后续。
  2. 系统不做退款：需要时运营在商户后台退钱，再用「调整积分」扣回。
  3. 固定档位，每档可配赠送积分：不支持自定义金额。
  4. 渠道用 Go 内置适配器：资金链路要稳、好测，新增渠道走发版。复用 JS 插件运行时的方案已搁置，以后可以在同一个接口下补一个插件适配器。
  5. 首批四个渠道全接：支付宝电脑网站、微信 Native、易支付、虎皮椒。支付FM 已去掉（不能查单和关单）。
  6. 引用 smartwalle/alipay/v3 和 wechatpay-go：三个第三方渠道用标准库手写。
  7. 前台只显示「微信 / 支付宝」：后台为每种方式指定一个承接渠道。
  8. 只做桌面端：扫码类在弹框里完成，跳转类新开标签页。
  9. 订单页只提供「查单 + 关单」：不提供强制入账。
  10. 二维码用前端 qrcode.react：只在积分商城弹框里懒加载。
  11. 点积分胶囊直接打开积分商城：余额和冻结信息移到商城顶部；支付未开启时保持现有的小卡片。
  12. 搁置：JS 插件化、渠道配置版本化、多实例负载均衡、通知收件箱加异步重试（主文档 9.2、9.3）。
仍待实测：易支付站点是否支持 act=query；虎皮椒查询不存在的订单时返回什么码。这两项只影响后台「校验」的实现方式，不影响整体结构。
