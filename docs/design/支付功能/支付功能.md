# 支付功能设计（积分充值）

> **范围**：用户在「积分商城」用微信或支付宝购买固定档位积分；后台新增「支付管理」，含支付渠道、充值商品、支付订单三页。只做积分充值，不做会员、礼品卡、退款和账单对账页。
>
> **日期和状态**：2026-10-16，已确认待实现。
>
> **证据约定**：**事实**附仓库文件路径或外部来源链接；**推断**是基于事实的判断；**提案**是尚未实现的设计。本文第 6–8 节的表、接口、错误码全部是提案。
>
> **方案演进**：首批渠道原定五个，2026-10-16 用户决定去掉支付FM（它不能查单和关单，丢了回调只能人工补），剩四个，调研记录保留在 4.1。曾考虑把支付渠道做成 JS 插件，复用现有 `plugin-runner`，这也是影策的思路。用户选了 Go 内置适配器，理由是资金链路要稳、好测，新增渠道走发版。被搁置的插件方案见 9.2。
>
> **配套演示**：[支付功能-演示.html](支付功能-演示.html)，建议先读它。

## 1. 设计摘要

- **问题**：项目已有积分记账，生成任务按积分冻结和结算，但积分只能靠注册赠送和管理员手动调整获得，没有自助充值。
- **目标**：
  - 用户能用微信或支付宝自助购买积分，**付了钱一定到账、不会多到账**。
  - 运营能在后台配渠道、配档位、查订单。
- **推荐结论**：
  1. **渠道**：四个渠道写成 Go 内置适配器，实现统一的 `PaymentProvider` 接口。四个是支付宝电脑网站支付、微信 Native、易支付、虎皮椒。
  2. **用户侧**：前台只出现「微信 / 支付宝」两个支付方式，后台给每种方式指定一个承接渠道。
  3. **订单**：锁定商品快照。支付结果以三条路径为准：渠道回调、主动查单、后台定时补查。
  4. **入账**：在一个事务里完成，以积分流水的唯一索引作为最后一道防重。
  5. **账务边界**：不做退款，不提供强制入账按钮。

### 2.2 约束

- **分层**：链路是 router → middleware → handler → service → repository。依赖接口写在 service 包；事务只走 repo 的 `WithTx`，**事务内不做网络 I/O**；业务错误只在 service 层产生，用 errcode。依据：`backend/AGENTS.md`、`backend/docs/standards/01-架构与分层.md` A1–A9。
- **测试**：每个接口都要有 service 表驱动测试和 handler 测试，DB 测试读 `TEST_DATABASE_DSN`。依据：`backend/docs/standards/05-测试.md`。
- **数据隔离**：用户数据查询必须带 `user_id`；资源不属于当前用户时，统一返回「不存在」（A7）。

### 2.3 缺口

- 没有订单、支付渠道、充值商品，也没有对外回调路由（全仓库没有 webhook 路由）。
- 没有站点公网地址配置。现有的 `server.allowed_origins` 是 CORS 白名单，不能用来拼回调地址。
- `c.ClientIP()` 没有设置 TrustedProxies，nginx 后面拿到的是代理 IP。订单只用 IP 做记录，不做风控，**推断**影响有限。
- 前端没有二维码库。

## 3. 用户与场景

- **普通用户**：
  - 触发场景：生成前发现积分不足，遇到 402；或者主动想囤积分。
  - 使用设备：桌面浏览器。
  - 支付习惯：大多数人用手机扫码，或者跳转到支付宝付款。
- **运营（admin）**：维护档位和角标、查订单、处理「付了没到账」的投诉。
- **运维（super_admin）**：录入商户号和密钥、开关渠道、指定支付方式由哪个渠道承接。
- **主任务**：打开商城 → 选档位 → 选微信或支付宝 → 扫码或跳转付款 → 弹框里看到「已到账」，余额立刻变化。
- **成功指标**（提案）：
  - 已支付订单 100% 入账，以每日人工抽查或日后的对账为准。
  - 重复入账为 0。
  - 从付款成功到前端显示到账的 P95 ≤ 5 秒（有回调的渠道）。

## 5. 设计原则

1. **钱的真相只来自渠道**。订单变成「已入账」只有三条路：验签通过的回调、主动查单返回已付、后台补查返回已付。没有任何按钮能绕过渠道直接入账。依据：用户回答「查单 + 关单」、影策。
2. **入账幂等，靠数据库约束兜底**。业务层先判断订单状态，流水表的 `(payment_order_id, type)` 唯一索引是最后一道防线。依据：现有流水幂等模式 `uk_ledger_task_type`。
3. **先查单，后关单**。超时、用户取消、管理员关单，一律先查单；已付就入账而不是关单。关单后如果收到已付回调，照样入账。依据：影策、sub2api，加上「不做退款」带来的公平性要求（推断）。
4. **用户只面对「微信 / 支付宝」**。渠道是运维的概念，换渠道用户无感。依据：用户回答、sub2api。
5. **密钥只写不读，改身份要锁**。复用 `ai_secrets` 加密；渠道有未完成订单时，禁止修改商户身份字段和密钥。依据：`ai_config_secret.go`、sub2api、影策。
6. **渠道能力差异不藏起来**。每个渠道声明自己能不能查单、能不能在上游关单，后台把这些写在渠道卡片上。依据：影策调研中易支付、虎皮椒的能力缺口。

## 6. 推荐方案

### 6.1 信息架构

**用户侧**

- 积分胶囊（首页顶栏、画布右上角）：
  - **支付已开启**：点击直接打开「积分商城」弹框。
  - **支付未开启**：保留现有的余额 Popover。
- 积分商城弹框（Dialog，桌面宽约 1080px）：
  - **顶部条**：标题「积分商城」，右侧显示可用积分、总余额、生成中冻结（从原 Popover 移过来）。
  - **左侧**：商品网格，一行四个。每张卡显示积分数、售价、「到账 X 积分」，有赠送时写「含赠送 Y」，有角标时显示角标。
  - **右侧**：「当前选择」面板，分两态：
    1. 确认态：显示基础积分、赠送积分、到账合计、实付金额；下面是支付方式单选（微信 / 支付宝，不可用的置灰并写原因）；底部是「立即支付」按钮。
    2. 收银态：显示二维码（或「前往支付宝付款」按钮）、倒计时、订单号、「我已完成支付」「取消订单」。
  - 支付成功后右侧切换为「已到账 +N 积分」，余额数字滚动更新。
- 其他入口：生成时积分不足（402）的提示、个人中心积分页，都加一个「充值」按钮打开同一个弹框。
- 个人中心 → 积分 → 流水：新增类型「充值」，筛选项增加「充值」。

**后台**

- 「用户」分组下新增「支付管理」（`/admin/payment`），三个页签：
  1. **支付渠道**：
     - 顶部「全局设置」卡：支付总开关、站点公网地址、微信由哪个渠道承接、支付宝由哪个渠道承接、每个用户最多几笔未支付订单。
     - 下方是四个内置渠道的列表：渠道名、支持的支付方式、收银方式（扫码 / 跳转）、能力（查单 / 上游关单）、状态、未支付订单自动关闭的时间、未完成订单数、「配置」按钮。
     - 配置在抽屉里完成，步骤是：填写 → 校验 → 启用。
  2. **充值商品**：表格，列有排序、名称、售价、基础积分、赠送积分、角标、状态、已售笔数。支持新建、编辑、上下架、上移 / 下移排序；有订单的商品不能删除，只能下架。
  3. **支付订单**：
     - 筛选：订单号、用户、状态、支付方式、渠道、时间段。
     - 列表列：订单号、用户、商品、金额、积分、方式 / 渠道、状态、创建时间、入账时间。
     - 详情抽屉：订单快照、状态时间线、收到的回调记录，以及「查单」「关单」两个操作。

### 6.2 核心流程

**A. 下单**

1. 用户点「立即支付」，前端生成 `idempotency_key`（`crypto.randomUUID()`），调 `POST /payment/orders`。
2. 后端依次校验：
   - 支付已开启；
   - 商品存在且已上架；
   - 该支付方式已映射到一个已启用的渠道；
   - 该用户未支付的订单数小于上限（默认 3）；
   - 同一个 `(user_id, idempotency_key)` 已有订单时，直接返回那笔订单。
3. 事务一：插入订单，状态 `creating`，同时写入商品快照和渠道快照（provider、config_version）。
4. 事务外：调用 `provider.CreateOrder`，超时 15 秒。
5. 事务二：
   - 成功：状态转为 `pending`，写入收银信息 `checkout_mode`（`qrcode` 或 `redirect`）、`checkout_value`、`expires_at`。
   - 失败：状态转为 `create_failed`，记录原因，返回 65005。
6. 前端拿到收银信息：
   - `qrcode`：用 qrcode.react 渲染。虎皮椒返回的是图片 URL，`checkout_mode=qrcode_image`，前端直接显示图片。
   - `redirect`：显示「前往支付宝付款」按钮，点击用 `window.open` 新开标签页。不自动打开，避免被浏览器拦截弹窗。

**B. 等待结果**

- **主通道**：WebSocket 在 `user:{id}` 频道推送 `payment.updated {order_no, status, credits}`。
- **兜底轮询**：前端每 3 秒调一次 `GET /payment/orders/:no`。这个接口只读库，不打上游。
- **主动查单**：用户点「我已完成支付」，或从跳转标签页切回本页（`visibilitychange`）时，前端调 `POST /payment/orders/:no/check`。后端向渠道查单，已付就入账。同一笔订单每 5 秒最多查一次，超过返回 65014。
- **恢复**：用户关掉弹框或刷新页面后，订单不受影响。再次打开商城时调 `GET /payment/orders/pending`，有未支付订单就直接进入收银态继续等。

**C. 回调（无鉴权）**

1. 渠道请求 `POST|GET /api/v1/payment/notify/:provider`。请求体上限 64KB。
2. 用当前渠道配置验签：
   - 微信：验签名，再用 APIv3 Key 解密 resource。
   - 支付宝：RSA2 验签。
   - 易支付、虎皮椒：MD5 验签。
3. 验签失败时：只在 warn 级日志里记 order_no 和 IP，不落库，按渠道格式返回失败。
4. 从验签结果里取出订单号、渠道交易号、实付金额、状态、商户身份（appid、mchid、pid 等），再做三项校验：
   - 订单存在，且 `order.provider == :provider`；
   - 商户身份等于渠道配置；
   - 实付金额（分）等于 `order.amount_fen`。
5. **二次确认**：MD5 签名的第三方渠道，如果能查单（易支付、虎皮椒），验签通过后再向上游查一次单，确认已付才入账。
6. 在事务里入账（见 D）。
7. 存一条通知记录 `payment_notifications`（见 8.2），按渠道格式返回成功：微信返回 HTTP 200 加 JSON `{"code":"SUCCESS"}`，其余返回纯文本 `success`。
8. 订单号不存在时也返回成功，避免上游一直重试，同时记录 warn 日志。

**D. 入账事务（唯一入口 `CreditOrder`）**

```
WithTx:
  order := SELECT ... FROM payment_orders WHERE order_no=? FOR UPDATE
  if order.status == credited      → 返回 duplicate（幂等成功）
  if order.status ∉ {pending, closed, creating} → 返回 ErrOrderState
  if paid_amount_fen != order.amount_fen → 订单置 abnormal(reason=amount_mismatch)，写审计，返回
  if trade_no 已被其他订单占用（唯一索引冲突） → 订单置 abnormal(reason=trade_no_conflict)
  EnsureCredit(user_id) ; LockCredit(user_id)
  InsertLedger(type=recharge, payment_order_id=order.id, amount=order.credits) ON CONFLICT DO NOTHING
  if 没插入 → 视为已入账：把订单状态补成 credited 后返回 duplicate
  AddCredit(user_id, +order.credits)
  UPDATE payment_orders SET status=credited, paid_at, credited_at, provider_trade_no, paid_amount_fen,
         late_paid = (旧状态 == closed)
  WHERE id=? AND status <> 'credited'   -- 检查影响行数 == 1
提交后：WS 推送 payment.updated；推送积分变化，复用现有刷新余额的路径
```

**E. 关单（超时、用户取消、管理员关单共用 `CloseOrder`）**

1. 能查单的渠道：先查单。已付就走 D，入账后结束。
2. 能在上游关单的渠道（支付宝、微信）：调用上游关单接口。
   - 支付宝返回 `ACQ.TRADE_NOT_EXIST`（用户还没扫码）时，视为已关。
   - 上游关单失败时再查一次单，防止付款恰好发生在两次请求之间。
3. 不能在上游关单的渠道（易支付、虎皮椒）：只在本地标记 `closed`。如果之后收到已付回调，仍然入账，并标记 `late_paid`。
4. 状态转为 `closed`，写入 `close_reason`（timeout / user / admin），推送 WS。

**F. 后台补单任务（backend 进程内，每 30 秒一次）**

- 多个后端实例同时跑也是安全的：每一步都是行锁或 CAS，最多重复向渠道查几次单，所以**没有**加 advisory lock（`RunMaintenance` 的注释写明了这一点）。
- 每轮做三件事，每批最多 100 笔：
  1. `pending` 且 `expires_at < now()` → 执行 E，`close_reason=timeout`。
  2. `pending` 且创建超过 2 分钟、上次查单超过 2 分钟、渠道能查单 → 查单；已付就执行 D。用来兜住丢失的回调。
  3. `creating` 超过 2 分钟（进程在下单中途崩溃）→ 能查单就查；查不到或不能查 → 转 `create_failed`。

### 6.3 渠道适配器接口（提案）

```go
// service 包内定义；实现放在 internal/payment/<provider>/
type PaymentProvider interface {
    Key() string                       // alipay_page / wechat_native / epay / xunhupay
    Capabilities() ProviderCaps        // Methods []Method; CanQuery; CanCloseUpstream; CheckoutMode

type TradeResult struct {
```

### 6.5 关键交互细节

- **商品卡**：
  - 售价显示到元，分为 0 时不显示小数。
  - 到账积分 = 基础 + 赠送；有赠送时显示一个「+赠送」小标签。
  - 默认选中第一个带角标的商品，没有就选第一个。
- **支付方式不可用时**：按钮禁用，并写明原因，例如「未配置承接渠道」或「渠道已停用」。两种都不可用时，「立即支付」禁用，并提示「暂未开放支付，请联系管理员」。
- **二维码**：显示 220px 的二维码，下方是「请使用微信扫码支付 ¥100.00」和倒计时 mm:ss。倒计时结束后，二维码蒙层显示「已过期」，并给出「重新下单」按钮，点它会先关闭旧单。
- **跳转类**：
  - 显示「前往支付宝付款」主按钮，以及「付款完成后回到这里，系统会自动确认」的说明。
  - 用户切回本页时自动查单。
- **取消**：点「取消订单」后，按钮转圈等待；后端执行 E。如果查到已付，直接显示已到账。
- **关闭弹框**：订单仍在后台等待结果，胶囊上显示一个小圆点提示「有待支付订单」，再次打开商城时进入收银态。

## 7. 状态与异常

### 7.1 订单状态机

| 状态 | 含义 | 可迁移到 |
| --- | --- | --- |
| `creating` | 已落库，正在向渠道下单 | pending、create_failed |
| `pending` | 等待用户付款 | credited、closed、abnormal |
| `credited` | 已付款，积分已入账（终态） | — |
| `closed` | 超时、用户取消或管理员关单 | credited（迟到的已付通知，同时标 `late_paid`） |
| `create_failed` | 渠道下单失败 | credited（下单请求超时但渠道其实建了单、用户随后付了款：收到已付通知照常入账） |
| `abnormal` | 金额不符或交易号冲突，不自动入账（终态，人工处理） | — |

`abnormal` 的订单不会被后续通知自动入账（否则「金额不符」的拦截形同虚设）。

`abnormal` 的处理方式：运营核实后，在商户后台退款，或者用现有的「调整积分」手动补积分并写备注。系统不提供强制入账按钮。

### 7.2 前端状态

| 位置 | 状态 | 表现 |
| --- | --- | --- |
| 商城 | 加载中 | 商品网格显示骨架屏 |
| 商城 | 空（没有上架商品） | 「暂无可购买的积分商品」 |
| 商城 | 支付未开启 | 不进商城，胶囊保持现有 Popover |
| 商城 | 方式不可用 | 见 6.5 |
| 下单 | 提交中 | 「立即支付」按钮转圈；同一个 `idempotency_key` 重复点击只会产生一笔订单 |
| 下单 | 失败 65005 | 右侧红色提示「支付宝下单失败，请稍后重试或换一种支付方式」，保留选择 |
| 下单 | 失败 65004 | 「你有 3 笔未完成的订单」，并提供「查看并继续支付最近一笔」 |
| 收银 | 等待 | 二维码或跳转按钮 + 倒计时 |
| 收银 | WS 断线 | 轮询兜底，用户无感 |

| 收银 | 异常 abnormal | 「支付金额异常，已通知管理员处理」，并显示订单号 |
| 后台渠道 | 未配置 / 已配置未启用 / 已启用 / 校验失败 | 卡片上分别显示状态标签；校验失败时显示渠道返回的错误摘要（已脱敏） |

### 7.3 停用、开关和权限

- **停用渠道**：前台立即不能再选这个渠道承接的支付方式；**已有订单不受影响**，回调照常接收，补单任务照常查单。
- **关闭支付总开关**：前台恢复成余额 Popover，下单接口返回 65001；回调和补单照常运行。
- **权限**：
  - super_admin：全局设置、渠道配置和启用停用。
  - admin：充值商品增删改、订单查看、查单、关单，渠道只能看不能改。
  - user：只能看到自己的订单，别人的订单统一返回 65006「订单不存在」。
- **审计**：以下操作都写管理员审计日志（复用 `admin_audit`）：`payment.settings_update`、`payment.channel_update`、`payment.channel_enable`、`payment.channel_disable`、`payment.product_*`、`payment.order_query`、`payment.order_close`。

### 7.4 已知边界（需要提前告知）

1. **易支付、虎皮椒不能在上游关单**：本地关单后用户仍可能付款成功，系统会照样入账（`late_paid`）。
2. **关单后修改了密钥**：之后迟到的回调会验签失败。由于有未完成订单时禁止修改密钥，这个窗口只出现在「订单已关闭但用户还在付」的少数情况。能查单的渠道会被补查兜住（补查只覆盖 pending）。**接受这个风险**，见 9.3。
4. **不做退款**：用户要退款时，运营在商户后台退钱，再用「调整积分」扣回积分；积分不够扣的情况由运营自行处理。

### 8.5 实现难点

- 回调和补单可能同时对同一笔订单入账：行锁加流水唯一索引，加 UPDATE 时检查影响行数，三层兜住。需要并发测试：同一订单 10 个 goroutine 同时入账，只入一次。
- 「事务内不做网络 I/O」：下单、查单都在事务外完成，事务里只做状态迁移和记账。
- 渠道 SDK 与 netguard：支付网关都是公网地址，出站请求统一走带 netguard 的 HTTP client；SDK 支持注入 client 的就注入（**未验证**：两个 SDK 注入 client 的方式需要实测）。
- 测试向量：微信和支付宝的验签、解密用官方文档里的示例，或者自己生成密钥对做往返测试；三个 MD5 渠道用固定参数和期望签名做测试向量。

## 9. 方案取舍

### 9.1 决策矩阵

采用的权重：资金正确性 40%、实现与测试成本 25%、扩展性 20%、用户体验 15%。资金场景里正确性优先，这是默认权重。

| 方案 | 正确性 | 成本 | 扩展性 | 体验 | 加权 |
| --- | --- | --- | --- | --- | --- |
| **A. Go 内置适配器（采用）** | 5 | 4 | 3 | 4 | 4.15 |
| B. 复用 JS 插件运行时 | 4 | 3 | 5 | 4 | 3.95 |
| C. 混合（官方 Go，第三方 JS） | 4 | 2 | 4 | 4 | 3.50 |

### 9.2 搁置的方案：支付渠道 JS 插件化

- **做法**：新增「支付插件」类型，跑在现有 `plugin-runner` 里（无网络，由宿主发 HTTP）。宿主补 md5、rsaSignSHA256、rsaVerifySHA256、aesGcmDecrypt 这几个 utils，新增 `verifyNotify` 钩子。
- **优点**：新增聚合渠道不用发版。
- **搁置原因**：
  - 插件不做代码评审、拿得到密钥，等于把「判断是否已付」交给了插件；
  - 需要扩展契约和 utils；
  - 用户选择资金链路求稳。
- **重新启用的条件**：第三方聚合渠道的需求频繁出现时，可以在 `PaymentProvider` 接口下增加一个「JS 插件适配器」实现，订单和入账层不用改。

### 9.3 明确放弃 / 简化

- **渠道配置版本化**（影策做法）：简化为「有未完成订单时锁定身份字段和密钥」。代价见 7.4 第 3 条。
- **同一渠道多实例和负载均衡**（sub2api 做法）：每种渠道只有一份配置，每种支付方式由一个渠道承接。
- **通知收件箱加异步重试**（影策做法）：改为同步入账。入账失败（例如数据库错误）时返回失败给渠道，让渠道重试，由补单任务兜底。只存验签通过的通知记录。

### 13.3 实现中发现并修复的问题

- **请求日志泄露商户密钥**：后台「日志」面板会记录 `/admin/` 请求体，而它只脱敏顶层 `secret_key`，支付渠道保存请求里的 `secrets` 对象（商户私钥、APIv3 密钥）会明文留在浏览器内存日志里。已把 `secrets` 加入脱敏字段并加测试。
- **网络错误带出密钥**：易支付查单把商户密钥放在 URL 查询参数里，Go 的网络错误会把整条 URL 写进错误文本，进而进日志和订单失败原因。适配器统一去掉 `*url.Error` 里的 URL，并有测试（变异验证：去掉脱敏测试立刻红）。
- **微信 `REFUND` 状态**：查单返回「已付款又退款」时不当作已付，报错让人工核实，否则会给已退款的订单发积分。
