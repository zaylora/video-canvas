# 视频节点「视频修剪」设计

> **范围**：视频节点功能区的「视频修剪」——在节点下方的修剪面板里拖两端手柄选出要保留的片段，点 ✓ 后在浏览器里编码，产出一个新的「剪辑」视频节点（原节点不动）。
> **日期与状态**：2026-10-14，设计中（已完成访谈，待实现）。
> **证据约定**：**事实**附文件路径或来源链接；**推断**是基于事实的判断；**提案**是尚未实现的设计；**未验证**需要实现时实测。
> **方案演进**：起点是用户给的 5 张参考图（图 1 修剪面板、图 2 功能区入口、图 3 编码进度、图 4 新节点上传中、图 5 剪辑完成）。调研后确认**图 3→图 4 的"先编码、再上传"说明剪辑发生在浏览器里**，后端不参与；访谈中用户依次确认了依赖、面板控件范围和编码期间的行为（见 §11）。
> **配套演示**：[视频修剪-演示.html](视频修剪-演示.html)（含可点击原型，修剪、编码、失败都能走一遍；编码是模拟的）。

## 1. 设计摘要

- **问题**：画布里的视频常常只有一小段有用（AI 生成的视频带多余开头结尾、上传素材太长）。现在功能区的「视频修剪」按钮是占位，点了只提示"敬请期待"。
- **目标**：选中视频节点 → 点「视频修剪」→ 拖两端手柄 → 点 ✓ → 右侧长出一个只含选中片段的新视频节点。全程不扣积分、不依赖后端算力。
- **推荐结论**：
  1. **浏览器内剪辑**，引用 **Mediabunny**（WebCodecs，MPL-2.0）；用户已确认引用。后端不改。
  2. **非破坏**：原节点原样保留，结果是一个新的"上传素材"类视频节点（`uploaded: true`），沿用现成的 `uploadRunner` 上传。
  3. **模式照扩图做**：独立的模式状态 + 节点下方的面板，取代平时的功能区和生成面板。
  4. **编码期间面板锁定**，取消选中和 Esc 不退出，只有 × 能中止（用户确认）。
- **第一版刻意不做**：循环预览、键盘快捷键说明面板、整段拖动、多段拼接、替换原节点、刷新后恢复编码（见 §10）。

### 设计约束（推断）

- 修剪是**纯前端能力**：不新增后端接口、不改 payload 结构的关键字段，保存仍走 `revision` 乐观锁。
- 编码结果要走既有上传通道，所以受 200MB 上限约束；上限在编码**前**就要拦，别让用户等完编码才发现传不了。
- 编码期间主线程不能被占满（WebCodecs 是异步的，推断可行；进度写入要节流，沿用 `uploadRunner` 的"整数百分点才写一次"）。
- 节点的生成面板被取代后，别的节点仍可正常操作（模式只属于一个节点）。

### 当前缺口

- 没有"本地剪辑一段视频"的任何代码。
- **另一条分支 `feature/video-frame-capture`（截取帧）未合并到当前分支**，它的 `frame-capture.ts`（隐藏 video + canvas、`crossOrigin`、`captureUrl` 加 `cap=1`）和"来源线"设计在当前分支上不存在。本设计**不依赖那条分支**，只借用它沉淀下来的经验（见 §8.3 的 CORS 与缓存问题）。

## 3. 用户与场景

- **用户**：在画布上编排 AI 生成素材的创作者，会反复试几版视频再挑片段。
- **触发场景**：① AI 生成的视频开头几秒是定格 / 结尾穿帮，只想要中间；② 上传的长视频只用一小段；③ 想用某段的画面继续做图生视频的参考，先剪出来。
- **主任务**：选中视频节点 → 拖手柄 → ✓ → 得到新节点。一次修剪应在 **10 秒内操作完**（编码耗时另算）。
- **成功指标**（提案）：修剪入口点击后 300ms 内出现面板；1 分钟以内的 1080p 视频，从点 ✓ 到新节点可播放不超过 30 秒（示意，需实测）。

## 5. 设计原则

1. **非破坏**：修剪只产出新节点，原节点、原素材、历史版本都不动。要"替换原节点"留到后续。
2. **一次只编码一段**：模式只属于一个节点，编码中不能再开另一个修剪，避免占满硬件编码器。
3. **失败不丢选区**：编码失败回到可编辑状态，手柄位置保留，用户可直接重试。
4. **提前拦、别等到最后**：浏览器不支持、选区太短、预估结果超 200MB，都在点 ✓ 之前（或点的瞬间）给出原因，不等编码完。
5. **复用而不新造**：模式状态、新节点摆放、上传、占位框全部沿用扩图和上传的现成实现。
6. **能力探测代替版本判断**：不写浏览器白名单。

## 6. 推荐方案

### 6.1 信息架构

```
视频节点（选中，有素材，非生成中）
 └─ 功能区「视频修剪」 ──点击──► 修剪模式（useTrimStore.nodeId = 该节点）
        ├─ 节点正文：修剪预览播放器（取代平时的 VideoFacade）
        └─ 节点下方：修剪面板（取代功能区 + 生成面板）
              ├─ 编辑态：× | 胶片条 | 去音轨 | ✓
              └─ 编码态：胶片条锁定 | 进度条「编码中 x%」 | ×（二次确认中止）
 ──✓ 编码完成──► 右侧新建「剪辑」视频节点（上传中 → 完成）+ 连线，退出修剪模式
```

### 6.2 关键用户流程

1. 选中视频节点，点功能区「视频修剪」。若浏览器不支持 WebCodecs 或素材地址未就绪，toast 说明原因，不进入模式。
2. 进入模式：面板淡入；预览播放器从头开始**暂停**；胶片条先画骨架，缩略图陆续填入；手柄默认在 0 和视频总长（即"全选"）。
3. 拖手柄：拖动时预览跳到被拖的那一端（左手柄显示入点画面，右手柄显示出点画面）；中间的时长胶囊实时显示 `28.87 s`；播放头跟随预览。
4. 点播放：从入点开始播放，播到出点自动暂停；再点从入点重播。条上点空白处 = 在选区内定位。
5. 可选：点「去音轨」图标切换静音导出。
6. 点 ✓：手柄锁定、✓ 变成转圈；面板下方出现进度条「编码中 x%」。
7. 编码完成：在原节点右侧建「剪辑」节点和连线，节点占位显示「上传中 x%」；面板立即退出；上传走现成流程，传完节点可播放。
8. 任何时候点 ×（编码中要二次确认）：退出，不产生任何节点。

### 6.3 修剪面板

布局按参考图 1，**去掉键盘图标和循环图标**（用户确认第一版只保留「去音轨」）：

| 区域 | 内容 | 说明 |
| --- | --- | --- |
| 左 | × 关闭 | 编辑态直接退出；编码态弹确认「中止编码？」 |
| 中 | 胶片条 | 高 48px、圆角；两端蓝色手柄（`--primary` 之外的强调色，沿用图里的蓝，具体 token 实现时对照 `index.css`）；选区外的缩略图压暗；居中时长胶囊；白色播放头 |
| 右 | 去音轨 | 开关图标按钮，按下后图标带斜杠；有音轨才可用，源视频没有音轨时禁用并写"该视频没有声音" |
| 右 | ✓ 确认 | 实心白底圆角按钮；**未修剪（选区=全长）时禁用**，悬浮提示"拖动两端选择要保留的片段" |
| 下 | 进度条 + 文案 | 仅编码态出现：「编码中 12%」，细白条，位置在面板正下方（参考图 3） |

**交互细节（提案）**：

- 手柄是 `role="slider"`，可聚焦；← / → 微调 0.1s，Shift + ← / → 微调 1s；`aria-valuetext` 读出时间。
- 手柄点击热区宽 ≥ 24px（视觉 8px），触屏同样用 Pointer Events + `setPointerCapture`。
- 两手柄最小间隔 **0.5s**（默认值，见 §11）；拖到极限时停住，不反弹。
- 手柄位置取整到 0.01s，时长显示两位小数（与参考图一致）。
- 面板里按钮加 `nodrag nopan`，拖手柄不能触发画布平移或节点拖动（沿用 `node-action-bar.tsx` 的做法）。
- 面板宽度、位置沿用 `usePanelPlacement`，始终在节点下方。

### 6.4 修剪预览播放器

- 进入模式时，节点正文由 `VideoFacade` 换成专用的 `TrimStage`：独立 `<video>`，不占 `videoSlots` 名额（原因：名额池会在别的视频开播时收走本视频，修剪中不能被收走）。**这一点是推断，实现时要核对名额池的回收逻辑。**
- 控件沿用参考图的样子：播放键、`当前/总时长`、进度条（全片范围，选区内高亮）、音量。
- 在 `timeupdate` / `requestVideoFrameCallback` 中检查：`currentTime ≥ end` 就暂停并回到入点。拖手柄时 `currentTime = 被拖的那一端`，节流到每帧一次。
- 退出模式时清掉 `src` 并 `load()` 释放解码器（沿用 `VideoFacade` 里已有的做法）。

### 6.5 编码与产出

**编码**（提案，API 以 Mediabunny 实际版本为准）：

```ts
const input = new Input({ source: new UrlSource(trimUrl(src)), formats: ALL_FORMATS });
const output = new Output({ format: new Mp4OutputFormat(), target: new BufferTarget() });
const conversion = await Conversion.init({
  input,
  output,
  trim: { start, end },
  audio: muted ? { discard: true } : undefined, // 去音轨
});
if (!conversion.isValid) throw new TrimError(reasonOf(conversion.discardedTracks));
conversion.onProgress = (p) => setProgress(Math.floor(p * 100));
await conversion.execute(); // 可被 conversion.cancel() 中止
const file = new File([output.target.buffer!], fileName, { type: "video/mp4" });
```

- 输出容器固定 **MP4**（H.264 视频；音频由 Mediabunny 在 MP4 允许的编码里选浏览器能编的）。理由：所有浏览器和后续上传、下载都通用。
- 画质：保持原分辨率；码率用 Mediabunny 预设的"高"档（实现时对比源码率，**未验证，需实测画质与体积**）。
- 整个结果先放内存（`BufferTarget`）。第一版接受这一点：结果上限 200MB，且选区只是片段。更大的素材留待后续用流式写入。
- 动态 `import("mediabunny")`：只在进入修剪模式时才加载，不拖慢画布首屏。

**拦截（编码前）**：

| 条件 | 行为 |
| --- | --- |
| `typeof VideoEncoder === "undefined"` | 点「视频修剪」时 toast「当前浏览器不支持视频修剪，请使用最新版 Chrome / Edge」，不进入模式 |
| 选区 < 0.5s | ✓ 禁用（手柄本身也拖不到） |
| 选区 = 全长 | ✓ 禁用 |
| 预估大小 = 源文件大小 × 选区占比 > 200MB | 点 ✓ 时拦下，「剪出来的视频预计超过 200MB，缩短选区试试」（预估偏保守，**只是粗估**） |

**产出节点**（提案）：

```ts
// 数据与扩图新节点同族，但这是"上传素材"，不是生成节点
{
  kind: "video",
  label: newNodeLabel("剪辑", existingLabels),   // 参考图叫「剪辑」，重名自动「剪辑 2」
  status: "running", uploadProgress: 0,
  mediaType: "video", uploaded: true,
  fileName: `${源节点标题}-剪辑.mp4`,
}
```

- 位置：沿用 `buildOutpaintNode` 的摆法（原节点右侧 80px、垂直居中、撞到就往下错开）。**建议把这段摆放逻辑抽成公共函数**，扩图和修剪共用，而不是复制一份。
- 占位画幅：沿用源节点的画幅（实现时确认 `resolveNodeAspect` 的入口；上传前新节点还没有 `src` 可测）。
- 连线：源节点 → 新节点，`ANIMATED_EDGE_OPTIONS`（参考图 4 里就是蓝色流动线）。**这条线只表示来源**：新节点是 `uploaded: true`，永远不会作为生成目标去读入边，所以不需要新增"来源线"字段（对比：扩图因为新节点是生成节点，才需要 `outpaintFrom`）。
- **没有提示词框**（用户确认，和扩图出来的节点一样）：选中「剪辑」节点只出上方功能区，下方不出生成面板。现有代码已经满足——`uploaded: true` 的节点不出生成面板（`node-overlays.tsx:185` 的 `!data.uploaded && !data.outpaintFrom`），**不需要为此改代码**，但实现时要核对一次：上传完成、重新打开画布后，节点仍带 `uploaded`（已在 `canvas-persistence.ts` 白名单里，见 §2）。
- 撤销：创建节点 + 连线记一次历史（`history.record()`），和扩图一致；编码过程中不写历史。
- 上传：`uploadRunner.start(id, file, patchNode)`，失败时节点显示「上传失败，请重试」并留着文件供重试（已有能力，不改）。

### 6.6 取舍：编码期间的行为（用户已选）

| | 面板锁定到编码完（**已选**） | 点确认立刻建节点、后台编码 | 可退出面板、结果后台完成 |
| --- | --- | --- | --- |
| 与参考图一致 | 是 | 否 | 否 |
| 新增状态量 | 只在面板里 | 要新增节点级编码状态 + 取消 / 重试 | 要新增"收起态" |
| 编码中能不能干别的 | 不能操作这个节点 | 能 | 能 |
| 刷新后 | 丢（没有节点） | 留下空壳节点 | 丢 |

**已选方案的细则**：

- 编码中 Esc、取消选中、框选多选都**不退出模式**，也不中止编码；只有 × 并确认才中止。
- 实现上，编码任务放在**模块级的 runner**（同 `outpaintRunner` / `uploadRunner` 的写法，按节点 id 存），**不跟面板组件的挂载走**。节点被取消选中时面板卸载，但编码继续；重新选中时面板重新出现并接上进度。
- 为了不让"取消选中后看不到进度"，源节点标题行的状态位显示「编码中 x%」（**提案，小改动**：复用 `NodeStatusLabel` 的位置）。
- 源节点被删除、画布被关闭或切换：中止编码并清理。
- 同一时刻只允许一个修剪会话：编码中点别的节点的「视频修剪」，toast「另一段视频正在编码，请先等它完成」。
- **刷新页面会丢编码中的任务**（不做断点恢复）。这与现在上传中刷新的行为一致，页面里不特别提示。

### 8.3 实现难点与风险

1. **CORS（与截取帧同源问题）**：素材在对象存储时 `/files/` 会 302 到跨域地址，Mediabunny 的 `UrlSource` 用 `fetch` + Range 读取，需要存储允许跨域读取并放行 `Range`、暴露 `Content-Range`。用户已确认对象存储配置了 CORS，但 `Range` 相关的头**未验证，实现时用真实桶实测一次**。本地存储同源不受影响。
2. **缓存污染**：同一地址若先被"不带 crossOrigin"的播放器加载过，浏览器可能复用没有跨域头的缓存。截取帧分支的做法是给截帧请求追加 `cap=1`；本设计同样需要一个 `trimUrl(src)`（**该函数在本分支不存在，需新写或等截取帧合并后共用**）。
3. **音频编码器**：AAC 编码在部分平台（如部分 Linux Chrome）不可用，Mediabunny 的自动选择是否足够要实测。
4. **预览与编码的缩略图**：缩略图用 Mediabunny `CanvasSink` 或隐藏 `video` + `canvas` 各有利弊，建议先用 `CanvasSink`（同一依赖，按需解码，不会反复 seek）；实现时对比一次。
5. **videoSlots 名额池**：见 §6.4，要核对不会被回收。
6. **内存**：结果整段放内存，几百 MB 的素材在低内存设备上可能失败，已有"预估超 200MB 拦截"兜底，但不能完全避免。
7. **进度精度**：Mediabunny 的进度值与"已处理时长 / 选区时长"是否一致，需要实测；参考图里会停在 100% 一小会儿再出现上传中。

- **没有在浏览器里验证任何界面或交互**（按项目约定不使用端到端自动化）：手柄拖动手感、预览跳转、胶片条缩略图、编码进度、新节点出现与上传，都需要用户打开页面确认。

### 遗留事项

1. **必须真机验证**：Mediabunny 的实际 API 行为（`Conversion` 的 `trim` 与 `onProgress`、`UrlSource` 的 `requestInit`、`CanvasSink.canvasesAtTimestamps`）只做了类型检查，没有真实视频跑过。
2. 对象存储下 `Range` / `Content-Range` 是否放行、302 与 `trim=1` 缓存隔离是否生效，需用真实存储桶实测。
3. 编码后的画质、体积、进度精度、AAC 可用性未实测。
4. 画布被他人锁定（只读）时功能区是否已禁用，未核实。
5. 编码失败后"选区保留"依赖仓库里的 `start / end`，已有测试覆盖；但"编码中取消选中再选回来能接上进度"只靠仓库设计保证，没有组件级测试。
6. 浏览器支持检测用 `VideoEncoder` / `VideoDecoder` 是否存在，**没有**调用 `isConfigSupported()` 检查具体编码配置；真正的编码器缺失会在 `Conversion.init` 时以 `isValid=false` 暴露，并翻成"当前浏览器无法编码"。
