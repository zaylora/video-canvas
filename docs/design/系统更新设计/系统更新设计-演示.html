系统更新 · 设计演示

在后台看版本、读日志，一键更新，不满意退回去

管理员现在要登录服务器跑 update.sh 才能更新，后台里连当前版本都看不到。这个设计分两期补上：一期只读，显示版本、提示新版本、展示版本日志；二期才能执行，由宿主机上的 Host Updater 完成更新和回退。回退会把数据库一起还原到更新前，更新之后产生的数据会丢，且只能退回最近一次更新。

阅读说明。本页是设计提案，尚未实现，对应 Markdown 设计文档（系统更新设计.md）。版本号、时间、耗时、磁盘大小都是示意数据；参考项目的做法来自 2026-10-12 读到的源码和文档。原型里的更新、回退都在浏览器内存里模拟，刷新复原，不会碰任何服务器。

一次更新怎么走

从点击到恢复可用，谁在做什么。顺序是备份 → 拉镜像 → 停服，与 open-ai-canvas 一致。

1 后台点更新只有 super_admin；backend 做权限和并发检查
2 前置检查 + 备份应用还在运行；失败了服务毫发无损
3 拉取镜像应用仍在运行；拉不下来就停在这，服务不受影响
4 停服停服窗口从这里开始；PG、Redis 保持运行
5 切换 + 启动改镜像版本，新 backend 启动时自动迁移数据库
6 健康验证通过后才算成功；不通过自动回退
设计：backend 容器自己重建不了自己，也不能持有 docker.sock（它面向公网，还跑用户上传的插件）。所以第 2~6 步全部由宿主机上的 Host Updater 做，backend 只通过带 token 的 Unix Socket 下达命令、读取状态。状态存在 Updater 一侧，backend 被停掉期间页面断线也不影响。放弃：让 backend 直接调 docker。
兜底与边界。第 2、3 步失败（备份、拉镜像）：应用一直在运行，状态 failed。第 4 步停不掉容器：用旧镜像重新拉起，状态 failed。第 5、6 步失败：自动还原备份并启动旧版本，状态 rolled_back，但备份之后到停服之前的写入会丢；回退也失败则进入 manual_intervention，页面给出备份文件名和排查命令，不伪造成功。 提案

分两期交付

一期没有任何特权组件，上线后管理员马上有用；二期的安全面（Socket 鉴权、Docker 调用、备份还原）单独评审。

一期 · 检查与日志只读

后台新增「系统更新」页：当前版本、最新版本、版本日志，侧栏有新版本时出现“新”。要更新时页面给出可复制的 update.sh --tag 命令，仍需在服务器上执行。

二期 · 一键更新与回退需装 Updater

宿主机装 Host Updater，页面上开始更新和回退由它执行；更新前自动备份 PostgreSQL，失败自动回退。未安装时按钮禁用并写明原因。

设计：一期价值不依赖二期。放弃：一期就做完整闭环（Updater 的安全面会和页面一起评审，出问题难定位）。

更新后发现有问题，点回退，会发生什么

管理员最担心的是“退回去”到底退了什么。

  1. 点“回退到 v0.3.0”只有最近一次更新成功、备份已通过校验时才可点；否则按钮禁用并写原因
  2. 确认框写明会丢什么“将还原到 10-14 03:05（备份时刻）的数据库，此后产生的画布、任务、积分变动都会丢失”，并要求填写原因
  3. 停应用、还原备份、切回旧镜像校验备份的 SHA-256 后才开始；校验失败直接停，进入人工介入
  4. 健康验证通过，状态变为“已回退”回退入口消失，不能连续回退；下次更新会生成新的备份
边界和后果。① 从备份时刻起到回退之前新增的数据全部丢失，包括拉镜像期间、更新之后用户新建的画布。② 素材文件不在数据库里，不会被还原，期间新上传的素材会变成没有记录的孤儿文件，占空间但不影响使用。③ 只能回退最近一次，不能回到更早的版本。
设计：为什么不只切镜像不动库？启动即自动迁移，迁移里有 DROP COLUMN（v0.3.0 就删过一列），旧代码遇到被删的列可能起不来，健康检查也发现不了。放弃：不丢数据的回退。

交付时要提前告知：备份只含 PostgreSQL；回退窗口只有最近一次；更新前建议通知用户暂停使用。

状态机（二期）

与 open-ai-canvas 的阶段名和顺序一致，去掉 migrating（迁移随新 backend 启动完成，合并进 switching）。

阶段含义进行中转到
idle无操作否preflight
preflight前置检查是backing_up / failed
backing_uppg_dump + 校验，应用仍在运行是pulling / failed
pulling拉取目标镜像，应用仍在运行是draining / failed
draining停 backend、web、plugin-runner；PG 和 Redis 保持运行是switching / failed
switching改 .env、启动新版本（含启动期迁移）是verifying / rolling_back
verifying健康验证 + 稳定窗口是succeeded / rolling_back
succeeded更新成功，回退可用否idle
rolling_back还原备份并启动旧版本是rolled_back / manual_intervention
rolled_back已回到更新前否idle
failed切换前失败，旧版本在运行，库未改动否idle
manual_intervention回退也失败，不再自动操作否人工处理后复位
  • 同一时间只允许一个操作；进行中再点任何操作返回 63002。
  • Updater 重启后发现停在进行中阶段：按 manual_intervention 处理，不自动续跑。
  • preflight / backing_up / pulling 失败：应用从未停过，终态 failed，库未改动。draining 失败：用旧镜像重新拉起，终态 failed。
  • 进入 switching 之后失败才会 rolling_back。备份之后到停服之前的写入，自动回退和手动回退都会丢，丢失起点都是备份时刻。

func normalize(v string) (string, bool) {
    v = "v" + strings.TrimPrefix(strings.TrimSpace(v), "v")
    return v, semver.IsValid(v)          // dev、sha-xxxx 不合法 → 不可比较

func latestStable(releases []Release) *Release {
    var best *Release
    var bestVer string
    for i := range releases {
        r := &releases[i]
        v, ok := normalize(r.Tag)
        if !ok || r.Draft || r.Prerelease { continue }
        if best == nil || semver.Compare(v, bestVer) > 0 { best, bestVer = r, v }
    }
    return best
}

已确认的决定

  1. 更新由宿主机 Host Updater 执行：backend 只通过 Unix Socket 通信，不碰 Docker。搁置：独立 updater 容器（要挂 docker.sock）、只检查不执行。
  2. 回退 = 还原更新前备份：连数据库一起还原。搁置：只回退镜像（旧代码遇到被删列可能起不来）、按迁移是否可逆自动选。
  3. 只备份 PostgreSQL：不含素材卷。后果：回退后可能有孤儿素材文件。搁置：备份带素材、让管理员勾选。
  4. 只回退最近一次更新。搁置：回退到任意保留的备份。
  5. 版本日志用 Release 列表，含新版与历史：GitHub 不可达时只能看缓存。搁置：镜像内置 CHANGELOG 兜底。
  6. 分两期交付：一期检查 + 日志，二期更新 + 回退。
  7. 引用 golang.org/x/mod/semver：用于版本比较。
  8. 更新顺序：备份 → 拉镜像 → 停服：你看到我最初写的“拉镜像 → 停应用 → 备份”后纠正，与 open-ai-canvas 一致。代价是备份之后到停服之前的写入，回退时会丢，确认框要写明。
  9. 主文档已回写：Markdown 第 5 节原则 3、6.4、7.2、8.5、10、11 已按新顺序改完；其余默认值与待确认问题见第 11 节。
