# 系统更新设计（版本管理与版本日志）

> **范围**：后台管理新增「系统更新」。一期：看当前版本和新版本、读版本日志。二期：一键更新，不满意回退到更新前的版本。
> **日期与状态**：2026-10-12，设计中（未实现）。
> **证据约定**：**事实**附文件路径或来源链接；**推断**是基于事实的判断；**提案**是尚未实现的设计。
> **方案演进**：访谈中方案没有转向。曾比较三种更新执行方式，被搁置的方案见 [9. 方案取舍](#9-方案取舍)。
> **配套演示**：[系统更新设计-演示.html](系统更新设计-演示.html)，建议先读它。
> **命名说明**：本设计叫「系统更新」。`docs/design/版本控制设计/` 讲的是画布项目的版本历史，两者无关。

## 1. 设计摘要

**问题**：管理员要更新系统，得 SSH 登录服务器运行 `scripts/update.sh`。后台看不到当前版本，也不知道有没有新版本。想退回旧版本，只能自己记住旧 tag 再手敲命令。更麻烦的是，旧镜像不一定起得来：应用启动时会自动迁移数据库，v0.3.0 已经删过一列，新版本改过的库，旧代码可能不认。

**目标**：管理员在后台就能（一期）知道现在是哪个版本、有没有新版本、新版本改了什么；（二期）点一下完成更新，不满意再点一下回到更新前的状态。

**推荐结论**：

- 功能叫「系统更新」，放在后台「系统设置」分组。
- 分两期交付。一期只读，不引入任何特权组件；二期新增宿主机上的 Host Updater，负责真正的重建容器。
- 版本来源是 GitHub Release（仓库公开）。版本日志直接用 Release 正文，它本来就取自 `CHANGELOG.md`，不需要另建数据源。
- **回退 = 还原更新前的 PostgreSQL 备份 + 切回旧镜像**。只能回到最近一次更新前；更新之后产生的新数据（画布、任务、积分变动）会丢，确认框必须写明。
- 版本号比较引用 `golang.org/x/mod/semver`（用户已确认）。

## 2. 项目现状

调研日期 2026-10-12，以代码为准。

### 2.1 事实

**部署与更新**

- 生产部署是 `scripts/deploy.sh` 生成的目录（`docker-compose.yml` + `.env`），镜像为 `ghcr.io/zaylora/video-canvas-{backend,web}:${IMAGE_TAG:-latest}`；`plugin-runner` 与 `backend` 用同一个镜像（[docker-compose.yml:31,67,100](../../../docker-compose.yml)）。
- [scripts/update.sh](../../../scripts/update.sh) 已能拉镜像、重建、等服务健康（最多 60 × 3s）、失败时把 `IMAGE_TAG` 改回旧值；`--tag` 可指定版本。**它不备份数据库**。
- `update.sh` 每次都从 `master` 同步 `docker-compose.yml`（update.sh:93-111），不跟随目标版本。
- `update.sh` 头部写明面向 Linux / macOS（update.sh:1-2）；Windows 生产部署没有对应脚本，本设计不覆盖（见 [11. 待确认](#11-待确认与已确认)）。

**版本与发布**

- 版本由 `-ldflags` 注入 `pkg/version`（[backend/Dockerfile:13-19](../../../backend/Dockerfile)、[version.go](../../../backend/pkg/version/version.go)），`GET /health` 已返回 `version` 对象（[health.go:45](../../../backend/internal/handler/health.go)）。
- 推送 `v*` 标签后，[release-docker.yml](../../../.github/workflows/release-docker.yml) 构建并推送镜像，[release-on-tag.yml](../../../.github/workflows/release-on-tag.yml) 用 `CHANGELOG.md` 对应小节创建 GitHub Release，并校验 `VERSION` 与标签一致。
- 仓库公开；最近 5 个 Release 都不是预发布，v0.3.0 正文 1308 字符。GHCR 上 v0.3.0 的标签是 `v0.3.0`、`0.3.0`、`0.3`、`latest`（`gh api` 查询，2026-10-12）。
- `CHANGELOG.md` 的 v0.3.0 小节有固定的 `### 破坏性变更` 标题。

**数据库**

- `config.yaml` 的 `auto_migrate: true`（[config.yaml:27](../../../backend/configs/config.yaml)），compose 没有覆盖它。启动时 `NewDB` 先跑几个手写迁移再 `AutoMigrate`（[db.go:41-72](../../../backend/internal/initialize/db.go)）。

- 没有独立的迁移命令：`cmd/server` 只有 `main.go` 和 `runner.go`（plugin-runner 子命令）。

**后台**

- 角色分 `admin` 和 `super_admin`；后台路由组统一 `RequireAdmin`，写操作加 `superOnly`（[router.go:130-133,245-262](../../../backend/internal/router/router.go)）。

### 2.2 设计约束（推断）

| 约束 | 依据 | 对设计的影响 |
| --- | --- | --- |
| backend 容器自己重建不了自己 | 镜像是 alpine，非 root，没有 docker CLI，也没挂 `docker.sock`（Dockerfile:29-45，compose backend 段） | 二期必须有容器外的执行者 |
| backend 不能持有 `docker.sock` | 它面向公网，还会执行用户上传的 JS 插件；挂上 sock 等于宿主机 root | 排除"backend 直接调 docker"，用户也选了 Host Updater |
| 只切回旧镜像不一定起得来 | 启动即 `AutoMigrate`，迁移含 `DROP COLUMN`；旧代码遇到被删列或新增约束可能报错 | 回退必须连数据库一起还原到更新前 |
| 还原备份会丢更新后的新数据 | 备份是更新瞬间的快照 | 确认框必须写明；回退只开放最近一次更新 |
| 素材文件不在 PG 里 | 素材存本地卷或 S3（[AGENTS.md](../../../AGENTS.md)） | 备份只含 PostgreSQL（用户已确认）；回退后更新期间新传的素材成为孤儿文件 |
| 更新期间页面会断线 | backend 会被停掉重建 | 前端要能"断线后继续查状态"，状态存在 updater 一侧而不是 backend 内存 |
| 一套部署只有一个 backend 实例 | compose 只有一个 backend 服务 | 一期的版本缓存放进程内即可，不依赖 Redis（Redis 在配置里可关闭，见 `APP_REDIS_ENABLED`） |

### 2.3 当前缺口

1. 后台看不到当前版本。
2. 没有"有没有新版本"的检查，也没有地方读版本日志。
3. 更新和回退都要 SSH 到服务器。
4. `update.sh` 不备份数据库，回退只改 tag，遇到破坏性迁移无兜底。
5. 没有记录"谁在什么时候把系统更新到了哪个版本"的审计。

### 2.4 未验证

- 线上镜像里 `version.Version` 是 `0.3.0` 还是 `v0.3.0`。`docker/metadata-action` 的 `steps.meta-backend.outputs.version` 对 tag 触发的构建通常不带 `v`，但本次没有在线上镜像里确认。设计上比较前统一去掉 `v` 再补回（见 8.3）。
- 现有部署的 `.env` 里 `IMAGE_TAG` 可能是 `latest`（`update.sh` 不带 `--tag` 时会写入 `latest`）。此时无法从 `.env` 得知"当前版本"，只能靠 `version.Version`。二期要处理这个情形（见 7.2）。
- GHCR 镜像的 digest 固定方式没有调研到本仓库的实际值。

## 3. 用户与场景

- **谁**：自托管本产品的运维 / 管理员，通常就是 `super_admin`（users 表为空时首个注册者自动成为 `super_admin`，见 [model/user.go:9](../../../backend/internal/model/user.go)）。`admin` 是运营角色，只管模型。
- **触发场景**：
  1. 在 GitHub 看到发布了新版，想知道自己是不是落后了。
  2. 想更新前先看看改了什么，有没有破坏性变更。
  3. 更新后发现某个功能有问题，想退回去。
  4. 排查问题时需要确认线上跑的到底是哪个版本和哪个提交。
- **主任务**：打开后台 → 看到有新版本 → 读日志 → 决定更新 → 等待完成 → 确认可用；或更新后点回退。
- **成功指标（提案）**：
  - 一期：管理员无需 SSH 就能说出当前版本、最新版本和差异；
  - 二期：从点击"更新"到服务恢复可用，管理员全程不需要登录服务器；更新失败时服务停在可用状态（旧版本）或明确进入"需人工介入"，不出现"页面一直转圈却不知道结果"。

## 4. 调研范围

用户指定参考两个项目。访问日期均为 2026-10-12，读的是各仓库默认分支（`main`）当天的内容，没有固定到某个 commit。

### 4.1 sub2api（Wei-Shaw/sub2api）

来源：<https://github.com/Wei-Shaw/sub2api>，重点文件 `backend/internal/service/update_service.go`、`backend/internal/handler/admin/system_handler.go`、`frontend/src/components/common/VersionBadge.vue`。

**观察到的事实**

- **更新对象是二进制，不是镜像**。`PerformUpdate` 从 GitHub Release 下载当前平台的压缩包，校验 `checksums.txt` 的 SHA-256，解压后用"当前改名为 `.backup`、新文件改名为当前"的方式原子替换，失败则恢复备份；临时目录建在可执行文件同目录，保证同一文件系统内 `rename` 原子。
- **Docker 部署不走后台更新**。README 写明 Docker Compose 部署的升级是 `docker compose pull` 再 `up -d`，后台一键更新对应的是脚本安装（systemd + 二进制）。
- **版本检查**：结果走 `UpdateCache` 接口缓存，TTL 20 分钟（具体用 Redis 还是别的实现，本次未确认）；GitHub 失败时回退到缓存并带 `Warning`，没有缓存则返回"无更新"加警告。`build_type` 区分 `source`（手动构建）与 `release`（CI 构建）。
- **下载安全**：只允许 `github.com` 与 `objects.githubusercontent.com`；最大 500MB；校验 checksum。
- **回退有两种**：不带版本号 = 恢复上次更新留下的 `.backup`；带版本号 = 下载指定旧版本安装，且只开放"比当前旧的最近 3 个非预发布版本"。
- **操作保护**：更新/回退/重启共用一个系统操作锁，并做幂等；更新上下文与 HTTP 请求生命周期解耦（15 分钟超时），注释说明这是为了避免浏览器或 nginx 在 30–60 秒后断开请求导致下载中途取消（issue #4504）。更新完成后返回 `need_restart: true`，由管理员再点"重启"。
- **前端入口**：顶栏的 `VersionBadge`。有新版本时徽标变琥珀色并带呼吸圆点；点开是下拉卡片，里面有当前版本、最新版本、刷新、更新、回退面板，更新失败有红色错误块。仅管理员可见完整版。
- **接口**（`system_handler.go`）：`GET /admin/system/version`、`GET /admin/system/check-updates?force=true`、`POST /admin/system/update`、`GET /admin/system/rollback-versions`、`POST /admin/system/rollback`、`POST /admin/system/restart`。

**对本项目的启发**

- 版本徽标 + 红点/琥珀点是成熟的"发现新版本"入口，成本低。
- 把长耗时操作和请求生命周期解耦、加操作锁、做幂等，是必须学的。
- 回退限定在"最近几个版本"，避免管理员退回一个与当前数据库差得太远的版本。

**不适合本项目的地方**

- 二进制替换对 Docker 部署无意义，我们的运行单元是 compose 的多个服务（backend、plugin-runner、web 共用镜像版本）。
- 它没有在读到的代码里出现数据库备份或还原步骤（未逐文件确认）。我们的启动期自动迁移含 `DROP COLUMN`，回退不处理数据库会有风险。
- 更新完成后要管理员再点"重启"，容器场景应由更新器自己完成。

### 4.2 open-ai-canvas（ddcat-ai/open-ai-canvas）

来源：<https://github.com/ddcat-ai/open-ai-canvas>，重点文件 `docs/content/docs/backend/system-update.mdx`、`backend/internal/hostupdate/types.go`、`backend/internal/handler/admin_update.go`、`web/src/pages/admin/settings/system-update-page.tsx`。

**观察到的事实**

- **架构**：浏览器 → Backend 管理 API → 带 Token 的 Unix Socket → 宿主机 Host Updater（systemd 服务）→ Docker Compose。Backend 不挂 Docker Socket。
- **更新顺序**（文档原文的 8 步）：读 GitHub Releases 取最高语义版本并与 `.env` 的 `CANVAS_IMAGE_TAG` 比较（`sha-*` 这类非正式标签视为低于正式版）；下载目标版本的 compose 文件并 `config --quiet` 校验，检查磁盘空间；生成 `backup-YYYYMMDD-HHMMSS.zip.partial`（PG custom-format dump + 数据目录 tar + 元数据），`fsync` 后原子改名并复核 SHA-256；拉取目标镜像并要求有 `sha256` digest，任何失败都在停服前中止；停 web/backend（PG 和 Redis 保持运行）；用目标镜像单独执行迁移命令，整批在事务和 advisory lock 内；原子更新 `.env` 和 compose，固定为 `image@sha256:...`；连续检查就绪接口，过了稳定窗口才算成功。
- **自动回退**：停服后的迁移、启动或健康验证失败时，恢复更新前的 compose 与 `.env`，再校验备份，用 `pg_restore --clean --if-exists` 还原数据库，启动旧服务并再次验证。任一步失败则状态进入 `manual_intervention`，"不伪造成功"。
- **人工回退**：后台仅在"存在旧版本和已校验备份"时开放回退按钮，请求必须带 `reason`。
- **状态机**（`types.go`）：`idle / checking / ready / no_update / preflight / backing_up / pulling / draining / migrating / switching / verifying / succeeded / rolling_back / rolled_back / failed / manual_intervention`，其中 8 个是"进行中"。状态写在宿主机 `/var/lib/open-ai-canvas-updater/state.json`，所以 Backend 或浏览器断线不会终止操作。
- **接口**（`admin_update.go`）：`GET /admin/system-update`、`POST /admin/system-update/check`、`POST .../start`（`targetVersion`）、`POST .../rollback`（`reason`）。请求体限制 16KB。
- **前端页面**：`system-update-page.tsx`。进行中每 2.5 秒轮询；轮询失败且进行中时显示"服务正在切换，等待重新连接"；`supported=false` 时显示"当前部署不支持后台在线更新"并禁用操作；`manual_intervention` 单独红色告警；有"前置检查"列表，`blocking` 项失败时禁用"开始更新"。
- **版本日志**：这个项目的"更新公告"是另一个功能（管理员自定义公告，存在 `system_settings`），文档明确"后台系统更新继续使用真实程序版本和官方 Release"。也就是说它的系统更新页展示的是官方 Release 说明。

**对本项目的启发**

- 宿主机执行者 + Unix Socket + Token 的权限边界，正好是本项目要的。
- 状态存在更新器一侧，断线后能恢复展示，是必需的。
- "停服前把能失败的事做完"（检查、备份、拉镜像、校验），把不可逆窗口压到最小。它的顺序是备份 → 拉镜像 → 停服，本项目采用同一顺序（用户确认）。
- `supported` / 前置检查 / `manual_intervention` 这三个状态，让页面在各种部署形态下都不撒谎。

**不适合本项目的地方**

- 它备份"PG + 数据目录"，本项目用户已确认只备份 PostgreSQL。
- 它有独立的 `migrate-schema` 命令；本项目没有，迁移在 `NewDB` 里跟着服务启动执行，见 8.4。
- 它回退到任意历史备份的能力更强，本项目用户已确认只回退最近一次。
- digest 固定、ARM64 原生构建、多阶段质量门禁属于它的发布体系，本项目不需要照搬。

### 4.4 依赖框架调研

**版本比较：`golang.org/x/mod/semver`**

- 来源：<https://pkg.go.dev/golang.org/x/mod/semver>，仓库 <https://go.googlesource.com/mod>。访问日期 2026-10-12。
- 当前稳定版本：`v0.42.0`，2026-10-09 发布（`proxy.golang.org` 查询）。
- 能覆盖：`Compare`、`IsValid`、`Prerelease`、`Canonical`；足以满足"判断新旧、过滤预发布、校验版本串"。要求版本串带 `v` 前缀，所以比较前要统一补 `v`。仍需自研：从 `0.3.0` / `v0.3.0` / `sha-xxxx` / `dev` 里识别"是否正式版本"的小函数，约 10 行。
- 许可证：Go Authors 的 BSD 风格许可（读到 `LICENSE` 文件开头的"Redistribution and use in source and binary forms…"，未逐条核对条款）。
- 维护：Go 官方子库，最近一次发布在 2026-10-09（距调研日 3 天）。star / 下载量本次未核对。
- 匹配度：纯函数，无运行时依赖。`go.sum` 目前没有它，引用会在 `go.mod` 新增一条依赖。
- 风险：几乎没有；API 稳定。
- 取舍结论：**引用**。用户已确认。
- 接口行为（`Compare` 对非法版本小于合法版本等）来自对该包的已有了解，**本次未运行验证**，实现时用单元测试固定。

**其他依赖：Docker 控制、迁移工具**

- 未发现需要引入的库。Host Updater 直接调 `docker compose` / `docker exec` 命令即可，不引入 Docker SDK，理由见 8.5。
- 其他 semver 库（Masterminds/semver、hashicorp/go-version）未深入调研，因为本场景不需要版本约束表达式，且 x/mod 已经满足。

## 5. 设计原则

1. **先只读，再特权**。一期不引入任何能改服务器的组件；能力边界随期次扩大，每期可单独评审安全。（依据：用户选择两期交付；backend 不能持有 `docker.sock`。）
2. **页面不撒谎**。部署不支持就说不支持并禁用，不能让按钮看起来能点、点了再报错。（依据：open-ai-canvas 的 `supported` / 前置检查；本项目有开发环境、非 compose 部署等多种形态。）
3. **能失败的事先做，备份在拉镜像之前**。顺序是：前置检查 → 备份 → 拉镜像 → 停服。拉镜像和校验失败时应用从未停止，服务毫发无损。备份放在最前面，是因为它最可能因磁盘不足失败，失败了应用还在运行，不需要任何恢复动作。（依据：open-ai-canvas 的顺序，用户确认。）**代价**：备份时应用仍在运行，备份之后到停服之前的写入，在回退（含自动回退）时会丢。这段窗口等于"拉镜像耗时 + 停服耗时"，通常是几分钟；确认框要写明。
4. **回退要对得上数据库**。回退的是"镜像 + 更新前的数据库快照"这一对，不单独切镜像。（依据：启动期 `AutoMigrate` 与 `DROP COLUMN`；用户确认。）
5. **丢数据要说在前面**。任何会丢数据的操作，确认框写明丢什么、从什么时候起。（依据：还原备份的本质。）
6. **状态不能只活在 backend 里**。backend 在更新中会被停掉，状态必须在它之外落盘。（依据：sub2api 的请求解耦、open-ai-canvas 的 `state.json`。）

## 6. 推荐方案

### 6.1 一句话

后台「系统设置」下新增「系统更新」页：一期读 GitHub Release 展示版本与日志；二期加 Host Updater，页面上"开始更新"和"回退"通过 Unix Socket 交给它执行。

### 6.2 信息架构

- **入口**：侧栏「系统设置」分组下新增条目「系统更新」，路径 `/admin/settings/update`。有新版本时条目右侧出现标记（默认"新"，提案）。`admin-nav.ts` 的 `badge` 现在是写死的字符串，需改成可由运行时状态决定（见 8.6）。
- **页面分区（自上而下）**：
  1. 版本卡片：当前版本、提交、构建时间；最新版本；状态；按钮。
  2. 前置检查（二期）：磁盘空间、Updater 连接、部署文件、当前版本是否正式版。
  3. 更新进度（二期）：阶段步骤条 + 日志。
  4. 版本日志：Release 列表，当前版本标"当前"，比当前新的高亮。
- **不做顶栏版本徽标**。sub2api 的徽标适合"随处可见"，但本项目后台顶栏没有现成位置，且一期价值已被侧栏标记覆盖；放到后续（见 10）。

### 6.3 一期：核心流程

1. 管理员进后台，侧栏已按缓存状态显示"新"标记（若有）。
2. 点「系统更新」，页面请求 `GET /api/v1/admin/system/update`，拿到当前版本、最新版本和最近 10 个 Release。
3. 点「检查更新」触发强制刷新（`POST .../check`），成功后更新卡片。
4. 读版本日志（Markdown 渲染）。有"破坏性变更"小节时，在该版本旁加醒目标签（提案：按 `### 破坏性变更` 标题识别）。
5. 想更新：页面给出可复制的命令 `./update.sh --tag <版本>`，并提示"更新前请备份数据库"。

### 6.4 二期：更新与回退

**更新**

1. 点「开始更新」，弹确认：目标版本、将先自动备份数据库、预计停服时间（示意）。若目标版本日志含"破坏性变更"，在确认框里再列一遍。**确认框要写明：备份之后产生的数据，若更新失败回退或之后手动回退，都会丢失。**
2. backend 做权限和并发检查，通过 Unix Socket 把 `{targetVersion}` 交给 Updater。
3. Updater 按阶段执行：前置检查 → 备份 → 拉镜像 → 停服 → 切换并启动 → 健康验证，状态每步落盘。**备份和拉镜像都在应用运行时完成**，这两步失败服务毫发无损；从"停服"起才是停服窗口。**备份时刻到停服之间的写入，回退时会丢**，确认框里要写明。
4. 页面每 2.5 秒轮询；backend 被停掉期间轮询失败，显示"服务正在切换，等待重新连接"，恢复后继续显示最终结果。
5. 成功：状态 `succeeded`，页面显示新版本，并出现"回退到 vX"入口（仅此一次更新有效）。

**回退**

1. 点「回退到 v{旧版本}」。入口只在"存在最近一次更新前的备份，且备份已校验"时可用，其他情况显示为禁用并写明原因。
2. 确认框明确写：**将还原到 {备份时间} 的数据库，此后产生的画布、任务、积分变动都会丢失**（含备份之后、停服之前的那段写入）；要求填写原因（审计用）。
3. Updater：停服 → 还原备份 → 切回旧镜像 → 启动 → 健康验证。成功后状态 `rolled_back`。
4. 回退完成后"回退"入口消失（只能回退最近一次），再次更新会生成新的备份。
5. 回退本身失败：状态 `manual_intervention`，页面显示备份文件路径与排查命令，不伪造成功。

**自动回退**：停服后的迁移、启动或健康验证失败时，Updater 自动执行与人工回退相同的步骤，状态记为 `rolled_back` 且标记 `automatic=true`。

### 6.5 备份保留（用户确认"只回退最近一次"所附带）

磁盘上保留最近 3 份备份文件，仅供出事时人工还原；页面只能用最近一次。备份范围只含 PostgreSQL（`pg_dump` custom format + SHA-256），不含素材卷。

## 7. 状态与异常

### 7.1 页面状态（一期）

| 状态 | 触发 | 页面表现 |
| --- | --- | --- |
| 加载中 | 首次进入 | 版本卡片骨架屏；日志区骨架屏 |
| 已是最新 | 当前版本 ≥ 最新正式版 | 绿色"已是最新"；日志仍可看 |
| 有新版本 | 最新正式版 > 当前版本 | 琥珀色"可更新到 vX"；侧栏条目出现"新" |
| 版本无法比较 | 当前版本不是合法语义版本（如 `dev`、`sha-abc`） | 灰色"开发版本，无法比较"；不显示"有新版本"；日志仍可看 |
| GitHub 不可达（有缓存） | 请求失败，进程内有上次结果 | 显示缓存结果，卡片上方黄条"{时间} 的数据，GitHub 暂不可达" |
| GitHub 不可达（无缓存） | 首次请求就失败 | 版本卡片只显示当前版本；日志区显示"暂时无法读取版本日志"和重试按钮 |
| GitHub 限流 | 返回 403 / 429 | 同"不可达"；提示"请求过于频繁，稍后再试" |
| 无权限 | 非 admin 访问 | 复用现有后台路由守卫，不新增逻辑 |

### 7.2 更新状态机（二期，提案）

沿用 open-ai-canvas 的阶段名和顺序，删去本项目用不到的 `migrating`：本项目没有独立迁移命令，迁移随新 backend 启动完成，合并进 `switching`。

| 阶段 | 含义 | 是否进行中 | 转到 |
| --- | --- | --- | --- |
| `idle` | 无操作 | 否 | `preflight` |
| `preflight` | 前置检查 | 是 | `backing_up` / `failed` |
| `backing_up` | `pg_dump` + 校验（应用仍在运行） | 是 | `pulling` / `failed` |
| `pulling` | 拉取目标镜像（应用仍在运行） | 是 | `draining` / `failed` |
| `draining` | 停止 backend、web、plugin-runner，PG 和 Redis 保持运行 | 是 | `switching` / `failed` |
| `switching` | 改 `.env`、启动新版本（含启动期迁移） | 是 | `verifying` / `rolling_back` |
| `verifying` | 健康验证 + 稳定窗口 | 是 | `succeeded` / `rolling_back` |
| `succeeded` | 更新成功 | 否 | `idle`（下次操作前） |
| `rolling_back` | 还原备份并启动旧版本 | 是 | `rolled_back` / `manual_intervention` |
| `rolled_back` | 已回到更新前 | 否 | `idle` |
| `failed` | 切换前失败；旧版本已在运行（从未停过，或已被重新拉起），数据库未改动 | 否 | `idle` |
| `manual_intervention` | 回退也失败 | 否 | 人工处理后由 Updater 复位 |

规则：

- `preflight`、`pulling` 失败时应用从未停止，终态是 `failed`，旧版本仍在运行。
- `preflight`、`backing_up`、`pulling` 失败时应用从未停止，终态是 `failed`，旧版本仍在运行，数据库未改动。
- `draining` 失败（停不掉某个容器）时，Updater 先用旧镜像把应用重新拉起并等健康，终态仍是 `failed`；重新拉起也失败则 `manual_intervention`。
- 只有进入 `switching` 之后失败才会 `rolling_back`（还原备份）。**备份之后到停服之前应用仍在写库，所以自动回退也会丢这段时间的写入**；人工回退还会丢"更新成功之后"的全部数据。两种回退的丢失起点都是备份时刻。
- 同一时间只允许一个操作；进行中再点任何操作返回 63002。
- Updater 重启后读取 `state.json`：停在进行中阶段的，按 `manual_intervention` 处理，不自动续跑（避免在不确定状态下继续破坏性动作）。

### 7.3 二期异常处理

| 异常 | 处理 |
| --- | --- |
| 部署不是 compose / 没装 Updater | `supported=false`，页面显示"当前部署不支持后台在线更新"和安装说明，按钮禁用并写原因 |
| Updater 连不上 | `connected=false`，同上，原因写"未连接到 Host Updater" |
| 磁盘空间不足 | 前置检查失败，`blocking=true`，禁用"开始更新"，显示需要的空间 |
| `.env` 里 `IMAGE_TAG=latest` | 前置检查给出警告：无法用 `.env` 确定当前版本，以 backend 报告的版本为准；更新后改写为具体版本号 |
| 目标镜像拉取失败 | `failed`，服务未停，显示失败原因 |
| 备份失败（磁盘写满、`pg_dump` 报错） | `failed`，应用仍在运行，数据库未改动 |
| 新版本启动期迁移失败 | `switching` 失败 → 自动回退 |
| 健康验证超时 | 自动回退；超时阈值待定（见 11） |
| 回退时备份校验失败 | `manual_intervention`，显示备份路径和 SHA-256，禁止继续自动操作 |
| 浏览器断线 / backend 在切换中不可用 | 前端显示"等待重新连接"，轮询直到恢复；Updater 状态不受影响 |
| 有进行中的生成任务 | 更新前提示"{n} 个任务进行中，更新会中断它们"。backend 收到 SIGTERM 会 `Shutdown`（cmd/server/runner.go:63-69），已提交给上游的任务恢复方式本次**未验证**，见 11 |
| 两个管理员同时点更新 | 第二个请求返回 63002 |
| 更新后立即想回退，但还没过稳定窗口 | 回退入口在 `succeeded` 前禁用 |

### 7.4 权限

- 读（状态、版本日志）：`admin` 和 `super_admin`，与现有"读 = admin、写 = super_admin"一致（[router.go:245-262](../../../backend/internal/router/router.go)）。
- 检查更新、开始更新、回退：仅 `super_admin`。检查更新虽然只读，但会向外网发请求并占用 GitHub 额度，收紧到 `super_admin`（**默认值**，用户未单独确认）。
- 所有写操作和检查更新进 `admin_audit_logs`。

### 8.2 一期接口（提案）

响应沿用项目的 `response.Body{code,msg,data}`，字段用 snake_case，与 `version.Info` 一致。

| 方法与路径 | 权限 | 说明 |
| --- | --- | --- |
| `GET /api/v1/admin/system/update` | admin | 返回当前版本、最新版本、版本日志；读缓存，不触发 GitHub 请求（缓存为空时才拉一次） |
| `POST /api/v1/admin/system/update/check` | super_admin | 强制刷新；写审计 `system.update_check` |
| `GET /api/v1/admin/system/update/badge` | admin | 只返回 `{update_available, latest_version}`，供侧栏标记轮询，不带日志正文 |

`GET /admin/system/update` 返回（示意）：

```json
{
  "current": {
    "version": "0.3.0", "git_commit": "3544492", "build_time": "2026-10-12T08:40:00Z",
    "go_version": "go1.27", "comparable": true
  },
  "latest": { "version": "0.3.1", "published_at": "2026-10-14T03:00:00Z", "url": "https://github.com/..." },
  "update_available": true,
  "releases": [
    {
      "version": "0.3.1", "name": "v0.3.1", "body": "## [0.3.1] ...", "url": "...",
      "published_at": "...", "prerelease": false,
      "breaking": false, "is_current": false, "is_newer": true
    }
  ],
  "fetched_at": "2026-10-14T03:05:00Z", "stale": false, "warning": ""
}
```

字段规则：

- `comparable`：`current.version` 是否是合法语义版本。`dev`、`sha-*` 为 `false`，此时 `update_available` 恒为 `false`。
- `latest`：不含预发布和草稿的最高版本；没有则 `null`。
- `releases`：最多 10 个，按语义版本降序，已排除草稿。预发布保留但标记，不参与"最新"。
- `breaking`：Release 正文里存在 `### 破坏性变更` 标题（本仓库 CHANGELOG 的固定写法）。
- `stale` / `warning`：GitHub 失败而返回缓存时为 `true` 并写原因。

业务错误码（新增 63xxx，**提案**）：

| 码 | HTTP | 含义 | 期次 |
| --- | --- | --- | --- |
| 63001 | 409 | 当前部署不支持在线更新 | 二期 |
| 63002 | 409 | 已有更新操作正在进行 | 二期 |
| 63003 | 409 | 已是最新版本 | 二期 |
| 63004 | 400 | 目标版本不存在或不是比当前更新的正式版 | 二期 |
| 63005 | 409 | 没有可回退的更新（无备份或备份未通过校验） | 二期 |
| 63006 | 503 | 无法连接 Host Updater | 二期 |
| 63007 | 502 | 无法读取版本信息（GitHub 不可达且没有缓存，仅用于 `check`） | 一期 |

### 8.2.1 二期接口扩展（提案）

一期 backend 没有 Updater 客户端，`GET /admin/system/update` 不返回下面三个字段，页面据此只显示可复制的命令。二期起这三个字段始终存在：

```json
{
  "deployment": { "supported": true, "connected": true, "reason": "" },
  "checks": [
    { "key": "disk", "label": "磁盘空间", "status": "ok", "detail": "可用 38 GB", "blocking": true }
  ],
  "operation": {
    "id": "op_20261014_0305", "phase": "idle",
    "from_version": "0.3.0", "target_version": "0.3.1",
    "started_at": null, "finished_at": null,
    "error": "", "rollback_error": "", "automatic_rollback": false,
    "logs": [{ "at": "2026-10-14T03:05:12Z", "phase": "backing_up", "message": "…" }]
  },
  "rollback": { "available": false, "to_version": "", "backup_at": null, "reason_unavailable": "" }
}
```

- `deployment.reason`：`supported=false` 时的原因，如 `updater_not_installed`、`not_compose`。
- `checks[].status`：`ok` / `warn` / `failed`；`blocking=true` 且 `failed` 时禁止开始更新。
- `operation.phase`：取值见 7.2；`logs` 最多保留最近 200 条。
- `rollback.available`：仅当最近一次更新 `succeeded` 且备份已通过校验时为 `true`；否则 `reason_unavailable` 写明原因。

| 方法与路径 | 权限 | 请求体 | 说明 |
| --- | --- | --- | --- |
| `POST /api/v1/admin/system/update/start` | super_admin | `{"target_version":"0.3.1"}` | 立即返回 202 和当前 `operation`，实际由 Updater 异步执行；状态靠 `GET /admin/system/update` 轮询。错误：63001 / 63002 / 63003 / 63004 / 63006 |
| `POST /api/v1/admin/system/update/rollback` | super_admin | `{"reason":"…"}`，1~200 字符 | 回退最近一次更新。错误：63001 / 63002 / 63005 / 63006 |

请求体上限 16KB（提案，参考 open-ai-canvas 的做法）。两个接口都先写审计再调用 Updater；Updater 返回"已有操作"时映射为 63002。

**backend 与 Updater 之间的 Socket 接口**（提案，全部要 `Authorization: Bearer <token>`）：

| 路径 | 说明 |
| --- | --- |
| `GET /status` | 返回 `deployment`、`checks`、`operation`、`rollback` |
| `POST /start` | `{"target_version"}`，已有操作则 409 |
| `POST /rollback` | `{"reason"}`，不可回退则 409 |
| `GET /logs?since=<RFC3339>` | 增量日志，供 backend 补充给前端 |

`state.json` 字段：`schema_version`、`operation`（同上）、`last_backup`（`id`、文件名、`sha256`、`size`、`created_at`、`from_version`）、`rollback_available`。只记文件名，不记完整宿主机路径给前端。

### 8.3 版本比较与缓存

- 取 Release 用单个请求 `GET https://api.github.com/repos/{repo}/releases?per_page=10`，一次拿到最新版和历史。
- 版本规整：去掉前导 `v` 后再补 `v` 交给 `semver`。`semver.IsValid` 为假的版本（`dev`、`sha-…`）视为不可比较。
- "最新"：非草稿、非预发布，按 `semver.Compare` 取最大。
- 缓存放**进程内**，TTL 默认 20 分钟（取自 sub2api 的取值，可配置），用 `singleflight` 合并并发刷新；失败时保留旧值并标 `stale`。放进程内而不是 Redis 的原因：Redis 可被关闭，且部署只有一个 backend 实例（见 2.2）。
- 出站请求固定 `api.github.com`，10 秒超时，响应体限 1MB，不跟随跳转到其他主机。
- 仓库名走配置，不写死，避免 fork 部署指向上游：

```yaml
# configs/config.yaml（提案）
update:
  repository: zaylora/video-canvas   # 与 compose 的 IMAGE_OWNER 默认值一致
  cache_ttl: 20m
```

- GitHub 未认证请求的限流是每 IP 每小时 60 次，这是已有认知，**本次未再核实**。20 分钟 TTL 下单实例每小时最多 3 次，远低于该值。
- 解析、比较、`breaking` 判断都做成不依赖网络的纯函数，便于测试。

### 8.4 数据库与回退（核心风险）

- 现状：新 backend 一启动就在 `NewDB` 里跑手写迁移和 `AutoMigrate`（db.go:41-72）；没有独立迁移命令。
- 含义：更新时 **"启动期迁移"就是 `switching` 阶段的一部分**。迁移若中途失败，库可能处于半迁移状态。
- 对策：回退一律 `pg_restore --clean --if-exists` 还原更新前的 dump，这样无论迁移做到哪一步，库都回到确定状态（用户已确认）。
- 不引入独立迁移命令：此刻没有必要。open-ai-canvas 为了"迁移失败时旧服务还没停"才拆出来，我们的做法是接受"迁移失败 = 自动回退"，代价是失败时停服时间更长。这是**有意放弃**，后续如果停服窗口成为问题再拆（见 10）。
- 孤儿素材：回退后更新期间新上传的素材文件还在，但库里没有记录。不会影响使用，会占空间，文档里要告知。

### 8.5 Host Updater（二期，提案）

**形态**：宿主机上由 systemd 运行的 Go 二进制（用户已确认），随 Release 发布 `linux/amd64`、`linux/arm64` 两个文件和 `SHA256SUMS`。由 `deploy.sh` / 单独的安装脚本安装。

**通信**

- Updater 监听宿主机上的 Unix Socket，例如 `/run/video-canvas-updater/updater.sock`，权限只给 root 和 backend 容器用户所属组。
- compose 里把该 Socket 所在目录挂进 backend，且不能设为只读（连接 Unix Socket 需要写权限），并传入 `APP_UPDATE_UPDATER_SOCKET` 与 `APP_UPDATE_UPDATER_TOKEN`。环境变量名是提案，沿用现有 `APP_` 前缀约定。
- 每个请求带 `Authorization: Bearer <token>`，token 安装时随机生成，只存在于宿主机 root 可读的环境文件和部署目录的 `.env` 里。
- Updater 只接受 4 个动作：`status`、`start`、`rollback`、`logs`，没有通用命令执行。
- 为什么用 Unix Socket 而不是 TCP：不暴露端口，权限由文件系统控制。

**Updater 不使用 Docker SDK**，直接调 `docker compose` 与 `docker exec`（`pg_dump` 在 postgres 容器内执行）。原因：命令集很小，少一个依赖；`update.sh` 已经证明这些命令在本项目可用。

**目录与状态**

- 部署目录由安装时写入 Updater 的配置（即 `.env` 与 `docker-compose.yml` 所在目录）；Updater 只在此目录内操作。
- 状态文件 `state.json`、备份目录 `backups/`、日志都在 Updater 自己的目录下，不依赖 backend 存活。
- 备份文件：`backup-YYYYMMDD-HHMMSS-<fromVersion>.dump` 与同名 `.sha256`，先写 `.partial`，`fsync` 后原子改名，再校验。保留最近 3 份。

**更新步骤（`start`）**

1. `preflight`：磁盘空间（至少 2 倍当前库大小，阈值待定，因为 `pg_dump` 要在应用运行时写出备份）、`docker compose config --quiet`、目标版本是正式版且比当前新、没有进行中的操作。
2. `backing_up`：`docker compose exec postgres pg_dump -Fc` → 校验 → 记录 `fromVersion`、`backupId`。此时应用仍在运行，备份是该时刻的一致性快照（`pg_dump` 自身保证事务一致）。失败则停在这里，服务未动。
3. `pulling`：`docker compose pull` 目标 tag 的 backend 与 web。失败则停在这里，服务未动。
4. `draining`：`docker compose stop backend web plugin-runner`，PG 和 Redis 保持运行。从这里起进入停服窗口。失败则用旧镜像 `docker compose up -d` 重新拉起，`failed`。
5. `switching`：保存旧 `.env` 与 `docker-compose.yml` 副本 → 把 `IMAGE_TAG` 改成目标版本 → `docker compose up -d --remove-orphans`。
6. `verifying`：沿用 `update.sh` 的健康判据（所有带健康检查的服务 healthy 且 web 在运行），并要求 backend `/health` 返回的 `version` 与目标一致，再保持稳定窗口（时长待定）。
7. 成功：`succeeded`，记录 `rollbackAvailable = true`。

**回退步骤（`rollback`，也是自动回退的步骤）**

1. 校验备份与 SHA-256。失败 → `manual_intervention`。
2. `docker compose stop backend web plugin-runner`。
3. 恢复旧 `.env` 与 compose 副本。
4. 对 postgres 容器 `pg_restore --clean --if-exists`。
5. `docker compose up -d`，同样的 `verifying`。
6. 成功：`rolled_back`，`rollbackAvailable = false`。

**compose 文件的同步**：`update.sh` 每次都从 `master` 拉最新 compose。Updater 应该改为**拉目标 tag 对应的 compose**（`raw.githubusercontent.com/.../<tag>/docker-compose.yml`），否则新版本若依赖新的服务或环境变量，会与旧 compose 不匹配。这是对现有行为的有意修改，需要在二期实现时同步修正 `update.sh`。

**`IMAGE_TAG` 是 `latest` 时**：Updater 以 backend `/health` 报告的版本作为"当前版本"，更新时把 `IMAGE_TAG` 改写成具体版本号。

**与 `update.sh` 的关系**：`update.sh` 保留，作为无 Updater 时的手动方式，一期页面上给出它的命令。两者都会改 `.env` 的 `IMAGE_TAG`，同时运行会冲突；Updater 开始前检查 `.env` 的修改时间与自己上次记录一致（**待确认**其必要性，见 11）。

3. 同一份 compose 同时被 `update.sh` 和 Updater 改。
4. 测试：Updater 的 Docker 调用要抽成接口，用假实现测状态机；不做真机 Docker 的自动化测试（项目约定不用 Playwright，真机验证留给人工）。

## 9. 方案取舍

### 9.1 更新执行方式

用户已选 **A 宿主机 Host Updater**。下表是我当时给出的比较，**权重是我设的默认值**（用户没有单独给过权重），分数是我的判断，不是测量结果。

| 维度（权重） | A 宿主机 Host Updater | B 独立 updater 容器 | C 只检查 + 看日志 |
| --- | --- | --- | --- |
| 权限边界（30%） | 5：backend 与容器都不碰 `docker.sock` | 3：容器持有 `docker.sock`，等同宿主机 root，只是隔离在小容器里 | 5：无特权组件 |
| 管理员一键完成（30%） | 5 | 5 | 1：仍要 SSH |
| 部署成本（15%） | 2：要 root 装服务、发布二进制 | 4：改 compose 即可 | 5 |
| 实现复杂度（15%） | 2 | 3 | 5 |
| 与参考项目的一致性（10%） | 5：同 open-ai-canvas | 2 | 3 |
| 加权 | 4.10 | 3.65 | 3.60 |

结论：A 在"权限边界 + 一键"两个最重的维度上同时最好，代价是部署成本和复杂度。三者差距不大，分数只用来说明排序依据，不要当作精确度量。C 单独看分数不低，但不满足"一键更新、可回退"的目标，所以作为**一期**吸收，不作为终点。

### 9.2 回退策略

| 策略 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| 回退 = 还原更新前备份 + 切旧镜像 | 旧版本一定跑在它认识的表结构上；与 open-ai-canvas 一致 | 更新后的新数据丢失；回退要停服数分钟 | **采用**（用户确认） |
| 只回退镜像 | 快，不丢数据 | 遇 `DROP COLUMN` 类迁移，旧代码可能起不来或运行时报错，健康检查发现不了 | 搁置 |
| 按迁移是否可逆自动选 | 最灵活 | 要给每个版本维护"是否可逆"标记，容易漏 | 搁置 |

### 9.3 明确放弃

- **回退到任意历史版本**。只能回最近一次更新（用户确认），理由是越远丢得越多、与当前库差得越远。
- **备份素材卷**。体积大、更新前等待久（用户确认只备份 PG）。后果：回退后可能有孤儿素材文件。
- **后台直接调 Docker**。安全边界不接受。
- **独立迁移命令**。本期接受"迁移失败 = 自动回退"，见 8.4。
- **镜像内置 CHANGELOG 兜底**。GitHub 不可达时只能看缓存（用户确认用 Release 列表）。
- **顶栏版本徽标**。见 6.2。

## 10. MVP 与后续

### 一期：检查与日志

范围：后台「系统更新」页（只读）、侧栏新版本标记、`GET /system/update`、`POST /system/update/check`、`GET /system/update/badge`、进程内缓存、`x/mod/semver` 引用、审计 `system.update_check`、可复制的 `update.sh` 命令。

验收条件：

1. `admin` 能看到当前版本、提交、构建时间；`super_admin` 能点"检查更新"。
2. 当前 0.3.0、GitHub 最新 0.3.1 时，页面显示"可更新到 0.3.1"，侧栏出现标记。
3. 当前版本是 `dev` 时，不显示"有新版本"，不报错。
4. GitHub 不可达：有缓存显示缓存和黄条；无缓存显示重试按钮；页面不白屏。
5. 版本日志按版本降序，当前版本标"当前"，更新的版本高亮；含 `### 破坏性变更` 的版本带标记。
6. Release 正文中的 `<script>` 或 HTML 不会被执行。
7. `admin` 调 `POST .../check` 返回 403。
8. 版本比较（`0.3.0` vs `v0.3.1`、预发布、非法串）有单元测试覆盖。

### 二期：一键更新与回退

范围：Host Updater、安装脚本、compose 变更、`start` / `rollback` 接口、状态机、前置检查、进度与日志、断线重连、自动回退、审计。

验收条件：

1. 未安装 Updater 时页面显示"不支持"并禁用按钮，不报错。
2. 从旧版本一键更新到新版本成功，期间管理员不登录服务器；更新后页面显示新版本。
3. 在 `pulling` 阶段让拉取失败：服务保持旧版本可用，状态 `failed`。
4. 让新版本启动失败：自动回退，旧版本可用，数据库与更新前一致，状态 `rolled_back` 且 `automatic=true`。
   - 让备份失败（如磁盘写满）：状态 `failed`，应用一直在运行，数据库未改动。
   - 备份之后、停服之前让数据库写入一条记录，再让新版本启动失败：自动回退后这条记录丢失，确认框事先已写明。
5. 更新成功后点回退：数据库还原到更新前，旧版本可用；确认框写明丢失数据的起点时间。
6. 备份文件损坏时回退进入 `manual_intervention`，不继续执行。
7. 更新期间刷新页面或断网，恢复后能看到最终结果。
8. 两个 `super_admin` 同时点更新，只有一个成功，另一个得到 63002。
9. 状态机用假 Docker 实现做单元测试，覆盖上表所有转移；真机验证由人工完成（**本设计未验证**）。

## 11. 待确认与已确认

### 已确认（用户的回答）

1. **更新执行方式：宿主机 Host Updater**。backend 只通过 Unix Socket 与它通信。
2. **回退 = 还原更新前备份**。回退时连数据库一起还原。
3. **备份范围：只备份 PostgreSQL**，不含素材卷。
4. **回退深度：只回退最近一次更新**。
5. **版本日志：Release 列表，含新版与历史**。
6. **交付节奏：两期**。一期检查 + 日志，二期更新 + 回退。
7. **依赖：引用 `golang.org/x/mod/semver`**。
8. **更新顺序：备份 → 拉镜像 → 停服**（用户看到我最初写的"拉镜像 → 停应用 → 备份"后纠正）。与 open-ai-canvas 一致。代价是备份之后到停服之前的写入，回退时会丢，确认框要写明。

### 已搁置的决定（将来启用时可复用）

- 独立 updater 容器（挂 `docker.sock`）：搁置，原因是权限边界；若将来 Host Updater 的安装成本成为主要阻力可重评估。
- 只回退镜像、不动数据库：搁置，原因见 9.2。
- 镜像内置 CHANGELOG 兜底；回退到任意历史备份；备份带素材卷：搁置，见 9.3。

### 默认值（我设的，不需要用户决定，但可以改）

- 权限：读 = `admin` + `super_admin`；检查更新 / 更新 / 回退 = 仅 `super_admin`。
- 缓存 TTL 20 分钟、进程内缓存（取自 sub2api，见 8.3）。
- 展示最近 10 个 Release。
- 备份保留最近 3 份。这个数字来自访谈时给出的选项说明，不是用户单独回答过的。
- 侧栏标记文字为"新"，路径 `/admin/settings/update`。
- 版本日志里 `### 破坏性变更` 标题触发"破坏性"标签。
- 错误码段 63xxx。
- 页面叫「系统更新」。

### 仍待确认（会影响实现或验收）

1. **健康验证的稳定窗口与超时**。多长算稳定？超时多久触发自动回退？需要真机跑一次得到数据，设计阶段无法定。
2. **磁盘空间前置阈值**。"至少 2 倍库大小"是我的猜测，没有依据。
3. **更新时进行中的生成任务如何处理**。backend 收到 SIGTERM 会 `Shutdown`，但已提交给上游供应商的任务在重启后如何恢复，我没读 worker 代码，**未验证**。是否要在更新前阻止、或提示数量，需要先查清。
4. **`update.sh` 与 Updater 并存**。是否需要"`.env` 被外部修改则拒绝开始"的保护，还是只在文档里写明二选一。
5. **线上镜像的 `version.Version` 带不带 `v`**（见 2.4）。实现时在真实镜像里确认；设计上已两种都兼容。
6. **Windows 生产部署**。`update.sh` 面向 Linux / macOS，本设计只覆盖 Linux。是否需要 Windows，需要用户说明有没有这种部署。
7. **Updater 如何分发**。作为 Release 附件由安装脚本下载，还是由 `deploy.sh` 一并安装；这决定发布工作流要不要新增产物步骤。
8. **回退完成后，被回退掉的版本要不要标记"已知有问题"**，避免管理员马上再次更新到同一版本。当前设计不做。
