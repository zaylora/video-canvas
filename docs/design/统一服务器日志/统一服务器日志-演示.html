统一服务器日志

所有用户运行走同一套日志：一个编号查过程，一个 call_id 查全文

画布生成、短剧、营销、Agent 和同步模型调用，统一打到两个文件：app.log 记过程和结果，每次运行以一行汇总结束；payload.log 记每一次上游调用的请求和响应全文，成功的调用也记。两边用 call_id 对应。 日志不入库、不做后台页面，给运维用 grep / jq 排查。

阅读说明。现状来自读代码核对（Markdown 第 2 节）。日志示例里的编号、时间、耗时、内容都是示意；整套设计尚未实现。完整依据见同目录的 统一服务器日志.md；短剧部分的细节见 ../短剧运行日志/，已并入本方案。

字段名打架

run_id 既指 Agent 运行又指营销环节运行，都是十进制；任务编号有的十六进制、有的十进制。

请求和任务串不起来

request_id 只在 gin 上下文里，service 拿不到；访问日志不带用户。

生产日志不持久

生产 compose 没配日志文件，只写标准输出，容器重建就没了。

有的业务几乎不打

短剧整条链路只有 5 处 Warn，失败原因被吞掉。网关 0 处、插件宿主 0 处。

主线：一行日志怎么产生、怎么被找到

关联字段在入口挂到上下文上，后面每一行自动带上；上游调用在两个统一切点记录。

入口HTTP 中间件 / River 任务中间件把 request_id、user_id、run_kind、run_id 挂到 ctx，自动打开始和重试
业务过程logger.Ctx(ctx) 打 run.* 事件
三个外部调用切点网关（文本模型）、插件宿主（供应商）、统一出站客户端（其他 HTTP）：每次调用生成 call_id
两个文件app.log 元数据 · payload.log 全文
运行汇总终态时一行 run.finish：状态、耗时、调用数、token、积分、失败原因
设计：全文只在两个切点记录，所有业务自动获得，不需要逐个业务改；业务代码只负责「过程」和「汇总」。汇总行借鉴 Stripe 的 canonical log line：一行回答谁、什么、多久、成没成、为什么。
兜底：payload.log 关闭或写失败时，app.log 照常，只是按 call_id 找不到全文；任何写日志的失败都不影响业务。进程崩溃最多丢失 payload.log 约 1 秒或 1MB 的缓冲 提案默认值。

两个文件和其他进程

全文和过程分开，主日志才读得下去。

app.log
标准输出 + 文件保留 30 天

过程事件、运行汇总、访问日志、错误原因。文件里一行一条 JSON；本地开发的终端仍可用彩色 console 格式。

payload.log
只写文件保留 7 天 · 压缩

每次上游调用的请求和响应全文（文本模型、供应商插件的每个 HTTP），成功的也记。Key 遮成 ***，图片 base64 换成摘要占位。

Agent 服务 · plugin-runner
只对齐字段

改成输出 JSON 行，带同样的 request_id / run_id / call_id，同一个编号能在三个进程里 grep 到；Docker 日志驱动加大小上限。

为什么选这个方案

三个候选按「排查完整度」和「主日志可读性」来比。

A 两文件 + 统一切点（推荐，已确认）B 全部进一个文件C 只在失败时记全文
排查完整度成功、失败的调用都有全文同 A结果不好但没报错时看不到输入输出
主日志可读性只有元数据全文淹没错误，滚动快好
磁盘全文单独保留 7 天全部保留 30 天，量最大最小
实现成本中：两个切点 + 上下文 + 各业务事件同 A中：各业务自己判断何时打
结论采用放弃放弃（用户选每次都记）

用户说「Agent 把画布改错了」时，会发生什么

只有用户名，没有编号。

  1. 后台用户管理里查到用户 ID例如 42。
  2. 在 app.log 里找他今天的运行汇总jq 'select(.user_id==42 and .event=="run.finish")'，看到一条 run_kind=agent 的运行。
  3. 按 run_id 展开这次运行每次模型调用一行 llm.call，带 call_id、耗时、token、finish_reason。
  4. 拿 call_id 去 payload.log看到模型当时收到的完整上下文（含工具结果）和它的完整回复（含工具调用参数）。
  5. 判断是模型理解错还是工具执行错需要更细的 Agent 内部过程时，再用同一个 run_id grep Agent 服务的日志。
边界：payload.log 里有用户原文和模型输入输出
  • 日志目录的访问权限要按数据库同级管理。
  • 凭证永不落盘：渠道 Key（三种转义）和 Authorization 等请求头一律 ***。
  • 只保留 7 天：一周前的「结果不好」问题看不到全文。
  • 用户访问平台的 HTTP 请求体不记全文，只记访问汇总行。
  • 日志量估算未实测：Agent 和短剧用量大时 payload.log 增长最快，上线一周后按实际调整。

交付时要告知部署方：新增 ./logs 挂载目录，需要预留磁盘并控制访问权限。

日志长什么样

左边选一种运行，右边上下两个终端分别是 app.log 和 payload.log。输入框同时 grep 两个文件；点 app.log 里任意一个 call_id，就会用它去 grep，看到它在 payload.log 里对应的全文。 编号、时间、内容都是示意，长全文用开头加「全文 N 字」表示。

payload.log 的处理规则

全文原样，只有这几项会被改写。

凭证沿用插件宿主的 redactor：渠道 Key 明文、URL 转义、JSON 转义都换成 ***；Authorization、x-api-key、api-key、x-goog-api-key 请求头整个值换成 ***
二进制data: URI 和超过 1KB 的 base64 换成 <base64 image/png 1.2MB sha256:ab12…>，只为控制体积
上限单字段 4MB，超出截断并标 truncated=true（试跑落库的追踪仍是 8KB，二者分开）
轮询折叠连续多轮请求和响应完全相同，只记首尾，中间一条 {"folded": N}
文本模型响应记拼装后的正文、思考、工具调用；不记 SSE 原始分片；非 2xx 记错误体原文（≤8KB）

已确认的决定

  1. 运行日志入库和后台先不做，先搭服务器统一日志：给运维排查，需要完整记录。访谈中曾定的「PostgreSQL 分区表」「后台只做查看」「与使用记录 / Agent 运行记录并存互跳」都已搁置，将来做时可复用。
  2. 系统日志不入库。
  3. 每次上游调用都记全文，放在单独的 payload.log；app.log 只记元数据和失败原因。
  4. Go 后端为主，Agent 服务和 plugin-runner 只对齐字段和 JSON 格式。
  5. compose 默认挂卷写文件：app.log 保留 30 天，payload.log 保留 7 天并压缩。
  6. 新功能自动纳入：补上 River 任务中间件和统一出站 HTTP 客户端，用编译期类型约束、架构测试和 forbidigo 拦住绕过记录的写法；业务汇总字段和过程事件写进接入清单。主文档 6.12 已回写。
  7. 短剧运行日志并入本方案：主文档已回写（两份 Markdown 都写明了），字段改为 run_kind + run_id，全文改进 payload.log。
