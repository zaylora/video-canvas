## 1. 设计摘要

- **问题**：现在每个业务各打各的日志。字段名不统一（`run_id` 同时指 Agent 运行和营销环节运行；任务编号有的十六进制、有的十进制）。HTTP 请求和后台任务串不起来（`request_id` 到不了 service 层，访问日志不带用户）。最关键的是，**发给上游的请求和上游的回复几乎都没留下**：只有试跑任务有插件追踪，而且截到 8KB；文本模型调用一个字都不记。生产部署只写标准输出，容器重建就丢。
- **目标**：运维拿到用户给的编号，或者只有用户 ID 加时间，就能：
  1. 在 `app.log` 里 grep 出这次运行的全过程，最后一行是运行汇总；
  2. 用汇总行或调用行里的 `call_id`，到 `payload.log` 里取出当时发给上游的**完整请求**和上游的**完整响应**。
- **推荐结论**（均已由用户确认，见第 11 节）：
  1. **两个文件**：`app.log` 记元数据和失败原因，同时写标准输出；`payload.log` 记**每一次**上游调用（文本模型、供应商插件 HTTP）的请求体和响应全文，成功的调用也记，只写文件。
  2. **一套关联字段**：`run_kind` + `run_id`（和界面上显示的编号相同）+ `call_id` + `request_id` + `user_id`，由上下文自动带上，业务代码不用逐处手写。
  3. **两个统一切点**：文本模型调用在 `llmgateway` 统一记录，供应商调用复用现有的 `provider.Trace`。业务代码只负责打运行的过程事件。
  4. **落盘**：`docker-compose` 默认挂载 `./logs`；`app.log` 保留 30 天，`payload.log` 保留 7 天、压缩。
  5. **进程范围**：Go 后端为主；Agent 服务和 plugin-runner 改成输出 JSON 行，并带同样的关联字段。
  6. **新功能自动纳入**（6.12）：HTTP 中间件、**River 任务中间件**、网关、插件宿主、**统一出站 HTTP 客户端**五个挂载点自动记录；CI 里的架构测试拦住「新任务没登记运行信息」和「自己 new `http.Client` 绕过记录」。业务只需要补过程事件和汇总行里的业务字段，漏了也会有一行兜底的汇总。

### 2.2 设计约束

- **C1**：渠道 Key 和其他凭证（`Authorization`、`x-api-key` 等请求头）永远不进任何日志文件。复用宿主 `redactor` 的三种遮法。
- **C2**：日志不入库、不做后台（用户决定）。
- **C3**：写日志不能拖慢或打断业务：写失败只影响日志本身；`payload.log` 用缓冲写入。
- **C4**：不改用户可见的行为和文案。

### 2.3 当前缺口

1. 没有上游请求和响应的全文（F8–F10）。
2. 字段名冲突、编号格式不一（F5、F6、F11）。
3. 请求、任务和用户串不起来（F3、F4）。
4. 生产日志不持久（F2）。
5. 部分业务（短剧）几乎没有过程日志（F15）。

**推断**：运维人少，「有问题才查」，主要用 `grep`、`jq`、`less`、`docker logs`。所以两个文件都必须是**一行一条 JSON**，字段固定。

### 4.1 主流做法

| 做法 | 观察到的事实 | 对本项目的启发 | 不适用之处 |
| --- | --- | --- | --- |
| Stripe canonical log line | 每个请求结束时额外打一行「权威」汇总，带 HTTP、身份、限流、耗时、资源用量等关键维度；在中间件里打，异常时也保证输出，日志失败不影响请求；目的是查询时不用把多行拼起来 | 每次**运行**和每个 **HTTP 请求**结束时各打一行汇总（`run.finish`、`http.request`），其余行是过程 | 它还把日志送进数据仓库，本方案不做 |

## 5. 设计原则

1. **一个编号拉出一次运行**：每行都带 `run_kind` + `run_id`，`run_id` 和界面上显示的编号完全一样。
2. **过程进 `app.log`，全文进 `payload.log`，用 `call_id` 连接**：主日志保持可读，全文不淹没错误。
3. **在切点统一记录，不在业务里散写**：文本模型在网关记，供应商在插件宿主记，HTTP 在中间件记；业务只打自己的过程事件。
4. **每次运行、每个请求都以一行汇总结束**（canonical line）：一行就能回答「谁、什么、多久、成没成、为什么」。
5. **字段由上下文带入**：`logger.Ctx(ctx)` 自动带关联字段，业务代码不手拼编号。
6. **凭证永不落盘，其余按原文**：只遮 Key 和鉴权头；二进制内容换成摘要占位，不算脱敏。
7. **默认被记录，绕过要被拦住**：能自动的放进挂载点；必须由业务提供的信息用类型约束强制；绕开挂载点的写法由 CI 架构测试拦截，而不是靠记性。

## 6. 推荐方案

### 6.1 总体结构

```
HTTP 请求 ──① HTTP 中间件──> ctx 带 request_id、user_id；结束打 http.request
                         │
后台任务 ──② River 任务中间件──> ctx 带 run_kind、run_id、user_id、attempt；
                         │        自动打 run.start / run.retry，业务没收尾时兜底 run.finish
                         │
           业务代码：logger.Ctx(ctx) 打 run.step；终态补 run.finish 的业务字段
                         │                                    ┌──> app.log + 标准输出（JSON 行）
           ③ llmgateway  ④ 插件宿主  ⑤ 统一出站 HTTP 客户端 ──┤
                    每次外部调用生成 call_id                  └──> payload.log（JSON 行，只写文件）
```

①–⑤ 是五个自动挂载点，新功能只要走它们就会被记录；CI 护栏见 6.12。

### 6.2 两个文件

| | `app.log` | `payload.log` |
| --- | --- | --- |
| 内容 | 过程事件、汇总行、错误原因、访问日志、River 日志 | 每次上游调用的请求和响应全文 |
| 输出 | 标准输出 + 文件 | **只写文件**（不进 `docker logs`） |
| 格式 | 文件为 JSON 行；标准输出沿用 `log.format`（本地开发可用 `console`） | JSON 行 |
| 级别 | 沿用 `log.level` | 不分级别，开启即全记 |
| 滚动 | 100MB / 份，保留 30 天，压缩 | 200MB / 份，保留 7 天，压缩 |
| 写入 | 同步（与现在一致） | `BufferedWriteSyncer`：1MB 或 1 秒刷盘，进程退出时 `Stop` |
| 开关 | 始终开启 | `log.payload.enabled`，默认 `true` |

### 6.3 关联字段（每行都有的字段）

由 `logger.Ctx(ctx)` 从上下文自动带入；没有的字段不输出。

| 字段 | 类型 | 来源 | 说明 |
| --- | --- | --- | --- |
| `request_id` | string | HTTP 中间件 | 同步请求才有；后台任务里，如果是由某个请求入队的，入队时把它写进任务参数，执行时还原（提案，见 8.1） |
| `user_id` | uint64 | 鉴权中间件 / 任务参数 | 用户主键 |
| `run_kind` | string | 运行入口 | 见 6.4 |
| `run_id` | string | 运行入口 | **和这次运行在界面上显示的编号相同**：gen / drama / mkt 为 `idcodec` 十六进制，agent 为十进制（F11） |
| `parent_kind` / `parent_id` | string | 运行入口 | 由另一个运行派生时才有：短剧片段出视频、营销出片、Agent `generate_media` 生成的任务指向发起它的运行 |
| `attempt` | int | River | 后台任务第几次执行（从 1 开始） |
| `call_id` | string | 网关 / 插件宿主 | 只在上游调用相关的行出现；12 位十六进制随机值，`app.log` 和 `payload.log` 用它对应 |
| `event` | string | 打点处 | 事件类型，见 6.5；`jq` 按它过滤 |
| `instance` | string | 启动时 | 主机名，多实例部署时区分来源 |

| 值 | 运行 | `run_id` 来源 |
| --- | --- | --- |
| `gen` | 生成任务（画布、营销出片、短剧片段视频、Agent 生成；含后台试跑，另带 `test=true`） | `generation_tasks.task_ref` |
| `drama` | 短剧流水线任务 | `idcodec.Encode(drama_jobs.id)` |
| `mkt` | 营销环节运行 | `idcodec.Encode(marketing_step_runs.id)` |
| `agent` | Agent 运行（Go 侧平台 API 部分） | Agent 运行 ID（十进制，与后台一致） |
| `adapt` | 短剧片段转写（同步） | `idcodec.Encode(segment_id)` |
| `preflight` | 短剧预检判断体裁（同步，未建项目） | 草稿 token 前 12 位 |
| `step_trial` | 后台环节试跑 | `idcodec.Encode(step_trials.id)` |
| `system` | 不属于任何用户的后台任务（清理、通知、周期任务） | River 任务 ID（十进制）；另带 `job_kind` |

旧字段 `task_id`、`drama_job_id`、`run_id`（十进制）、`round_id` 等改为 `run_kind` + `run_id`；只描述对象、不代表运行的字段（`asset_id`、`storage_id` 等）保留。

### 6.4 `logger` 包的新接口（提案）

### 6.5 事件（`event` 字段）

`message` 仍按规范写中文短句；`event` 是稳定的英文取值，用于 `jq` 过滤和计数。

| `event` | 级别 | 在哪打 | 专有字段 |
| --- | --- | --- | --- |
| `http.request` | Info / Warn（4xx）/ Error（5xx） | 访问日志中间件（**请求汇总行**） | method、path、query、status、latency_ms、ip、`user_id`、`run_kind`/`run_id`（请求创建了运行时） |
| `run.create` | Info | 运行入队后 | `step` 等业务字段、`frozen_credits` |
| `run.start` | Info | worker 领到任务、置为执行中 | `resumed`、`queue_wait_ms` |
| `run.step` | Info / Warn | 业务过程节点（短剧的批次、生成任务的提交 / 轮询结果 / 转存、营销的环节层） | 业务自定义 |
| `llm.call` | Info / Warn | **网关**（每次尝试一行） | 见 6.6 |
| `provider.call` | Info / Warn | **插件宿主**（每次 handle：提交 / 一轮轮询 / 转存 / 取消） | `phase`（submit/query/prepare/cancel）、`plugin`、`plugin_version`、`http_count`、`latency_ms`、`result`、`upstream_status`、`error` |
| `ext.call` | Info / Warn | **统一出站 HTTP 客户端**（每个请求） | `purpose`、`method`、`host`、`path`、`status`、`request_bytes`、`response_bytes`、`latency_ms`、`result`、`error` |
| `run.retry` | Warn | **River 任务中间件**（任务返回错误、将重试） | `max_attempts`、`error` |
| `run.finish` | Info / Warn / Error | 运行进入终态（**运行汇总行**）；业务没打时由中间件兜底 | 见 6.7 |

### 6.6 上游调用行（`llm.call` / `provider.call`）与 `payload.log` 记录

`app.log` 里的 `llm.call`：

| 字段 | 说明 |
| --- | --- |
| `call_id` | 对应 `payload.log` 里的同一条 |
| `purpose` | 调用方传入的用途：`drama.scripts`、`mkt.reverse`、`agent.main`、`agent.summary` 等 |
| `call` / `try` | 业务内位置（如 `episode=3`）、业务级第几次（校验失败重写算第 2 次） |
| `net_attempt` | 网关内第几次（空闲超时重试） |
| `model_key` / `channel` / `upstream_model` / `format` | 模型、渠道、上游模型、接口格式 |
| `request_bytes` / `response_chars` | 请求体字节数、回复字数 |
| `input_tokens` / `output_tokens` / `cached_tokens` / `usage_missing` | 用量 |
| `finish_reason` | stop / length / tool_calls 等 |
| `latency_ms` / `ttft_ms` | 总耗时、首字耗时 |
| `result` | ok / failed / canceled / timeout |
| `upstream_status` / `error` | 失败时带；`error` 是完整错误链，已遮 Key |

业务层的结果（如短剧的「输出不合格」）不在网关判断，由业务打 `run.step`（Warn）并带同一个 `call_id` 和校验原因。

`payload.log` 的一条记录（一行 JSON）：

```json
{
  "time": "2026-11-14T17:21:22.950+0800",
  "call_id": "c7e2a91f04b3",
  "kind": "llm",
  "run_kind": "drama", "run_id": "9f3c…", "user_id": 42, "request_id": "…",
  "purpose": "drama.scripts",
  "request":  { "method": "POST", "url": "https://api.example.com/v1/chat/completions",
                "headers": { "Authorization": "***" }, "body": "{…完整请求体…}" },
  "response": { "status": 200, "text": "…完整正文…", "thinking": "…", "tool_calls": [...],
                "error_body": "", "truncated": false },
  "latency_ms": 24548
}
```

- `kind=llm`：一次网关尝试一条；响应记**拼装后的结果**（正文、思考、工具调用），不记 SSE 原始分片；上游非 2xx 时 `error_body` 是错误体原文（最多 8KB）。
- `kind=http`：统一出站 HTTP 客户端的一个请求一条，记请求（方法、URL、请求头、请求体）和响应（状态、响应头、响应体）；规则同下。
- `kind=provider`：一次插件 handle 一条，`steps` 就是现有 `provider.Trace` 的步骤数组（钩子入参、返回值、`utils.log`、每个 HTTP 请求和响应），对 payload 来说请求体 / 响应体上限从 8KB 提高到 4MB。
- **处理规则**：
  - 凭证：沿用 `redactor`，渠道 Key 的明文、URL 转义、JSON 转义都换成 `***`；请求头里的 `Authorization`、`x-api-key`、`api-key`、`x-goog-api-key` 整个值换成 `***`。
  - 二进制：`data:` URI 和长度超过 1KB 的 base64 片段换成 `<base64 image/png 1.2MB sha256:ab12…>`，不是脱敏，只为控制体积（图片原件在素材库里）。
  - 上限：单个字段超过 4MB 时截断并标 `truncated=true`。
  - 连续多轮轮询如果请求和响应完全相同，只记第一条和最后一条，中间记一条 `{"folded": N}`。

### 6.7 运行汇总行（`run.finish`）

每次运行只打一行，所有业务字段名一致：

| 字段 | 说明 |
| --- | --- |
| `status` | succeeded / failed / canceled / expired / paused |
| `duration_ms` / `queue_wait_ms` | 执行耗时、排队耗时 |
| `llm_calls` / `provider_calls` | 本次运行的上游调用次数 |
| `input_tokens` / `output_tokens` | 合计用量 |
| `frozen_credits` / `charged_credits` | 冻结和实扣积分 |
| `error_code` / `error_message` | 写库、给用户看的错误码和文案 |
| `error_type` | 低基数分类：`upstream` / `timeout` / `network` / `invalid_output` / `context_too_long` / `no_model` / `canceled` / `business` / `internal` 等；各业务可加自己的（短剧合成的 `compose_*`） |
| `error` | 完整错误链 |
| `last_call_id` | 失败时，最后一次上游调用的 `call_id` |

级别：成功 Info；业务失败、取消、超时 Warn；`internal` 和需要人处理的失败 Error。

计数（调用次数、token）用挂在 ctx 上的一个计数器累加，由网关和插件宿主写入，汇总行读取。

### 6.8 各业务的接入点

「自动」指由 6.12 的挂载点产生，业务不用写。

| 运行 | `run.create` | `run.start` | 过程 | `run.finish` |
| --- | --- | --- | --- | --- |
| 生成任务（`gen`） | `GenerationTaskService.Create` | 自动（River 中间件） | 提交、每轮轮询结果变化、转存（`run.step`）；`provider.call` 自动 | `finish` 事务提交后补业务字段 |

### 6.9 与短剧运行日志设计的关系

[短剧运行日志](../短剧运行日志/短剧运行日志.md) 并入本方案，有三处调整：

1. 字段：`drama_job_id` 改为 `run_kind=drama` + `run_id`；E1–E11 映射到 6.5 的 `event`（E1→`run.create`，E2→`run.start`，E4→`llm.call` + 业务 `run.step`，E5 / E6 / E7→`run.finish`，E9→`run.retry`）。
2. 全文：提示词和不合格输出的全文**不再打在 `app.log`**，统一在 `payload.log`；`app.log` 的失败行带 `last_call_id`。原来「失败时才打全文」变为「每次调用都记全文，在单独文件」（本次访谈确认）。
3. 不变：失败原因不再被吞（`dramaCallError`、`dramaCause`）、`error_type` 取值、任务条显示任务 ID、网关保留错误体原文。

### 6.10 Agent 服务与 plugin-runner 的对齐（最小改动）

- **输出**：标准输出改为一行一条 JSON，字段至少有 `time`、`level`、`msg`、`service`（`agent` / `plugin-runner`），以及能拿到的 `request_id`、`run_kind`、`run_id`、`call_id`。
- **Agent 服务**：Go 调 Agent 服务时在请求头带 `X-Request-ID`；Agent 服务记日志时带上当前运行的 `run_id`（`run_kind=agent`）；它通过平台 API 回调 Go 时原样带回 `X-Request-ID`。
- **plugin-runner**：Go 发执行请求时带上 `call_id`、`run_kind`、`run_id`；runner 自己的日志（脚本异常、超时、崩溃）带上这几个字段。脚本里的 `utils.log` 仍然经宿主写进 `provider.Trace`，最终进 `payload.log`。
- **落盘**：两个服务仍写标准输出，由 Docker 保存；compose 为它们配置 json-file 的 `max-size: 100m`、`max-file: 5`，避免无限增长。三个进程的日志用同一个编号都能 grep 到。

### 6.12 新功能自动纳入：五个挂载点 + CI 护栏

目标：以后新增工作室或功能时，**不写也会被记录，写错了 CI 会拦住**。能自动的交给挂载点；必须由业务提供的信息（运行编号怎么取、业务成败）用接口强制登记，并用测试检查。

#### 6.12.1 新功能得到什么

| 内容 | 新功能要做什么 | 由谁保证 |
| --- | --- | --- |
| HTTP 访问汇总行（`http.request`） | 什么都不用做 | ① HTTP 中间件 |
| 后台任务的关联字段、`run.retry`、重试用完 / panic 的兜底收尾 | 任务参数实现 `RunArgs` 接口，用 `queue.AddWorker` 注册；真正开始干活时调 `run.Start()` | ② River 任务中间件；**编译期类型约束 + 架构测试**（见 13 节：`run.start` 不由中间件自动打） |

#### 6.12.2 River 任务中间件（提案）

River v0.49 支持 `WorkerMiddleware`（F16），但中间件只能拿到原始任务行。所以在注册 worker 时，一起登记「怎么从参数里取出运行信息」：

```go
// RunArgs 是所有队列任务参数必须实现的接口：告诉日志这次任务属于哪个运行。
type RunArgs interface {
	river.JobArgs
	RunRef() logger.RunRef // {Kind, ID, UserID, RequestID, ParentKind, ParentID}；系统任务返回 Kind="system"
}

// AddWorker 替代 river.AddWorker：注册 worker 的同时登记该任务类型的解码函数。
func AddWorker[T RunArgs](workers *river.Workers, w river.Worker[T]) {
	river.AddWorker(workers, w)
	runRefs[T{}.Kind()] = func(raw []byte) (logger.RunRef, error) {
		var args T
		err := json.Unmarshal(raw, &args)
		return args.RunRef(), err
	}
}

// runLogMiddleware 对每个任务：挂上下文 → run.start → 执行 → 出错打 run.retry → 业务没收尾时兜底 run.finish。
func (m *runLogMiddleware) Work(ctx context.Context, job *rivertype.JobRow, doInner func(context.Context) error) (err error) {
	ref, _ := runRefs[job.Kind](job.EncodedArgs)       // 解不出来时 Kind 记为 job.Kind，不影响执行
	ctx, run := logger.BeginRun(ctx, ref, logger.Attempt(job.Attempt), logger.JobKind(job.Kind))
	defer func() {
		if r := recover(); r != nil {
			run.Fallback("panic", fmt.Sprint(r)) // Error 级，带堆栈；再把 panic 抛回给 River
			panic(r)
		}
		switch {
		case err != nil && job.Attempt < job.MaxAttempts:
			run.Retry(err) // run.retry（Warn）
		case !run.Ended():
			run.Fallback(resultOf(err), "")    // run.finish，finish_fallback=true
		}
	}()
	return doInner(ctx)
}
```

- `logger.BeginRun` 同时给同步运行用（片段转写、预检、Agent 平台 API），返回的 `run` 有 `End(status, fields...)`，`defer` 调用即可保证收尾。
- 兜底的 `run.finish`：任务成功返回但业务没调 `End` 时，`status=unknown`、`finish_fallback=true`、Warn 级，用来提醒开发补上；任务彻底失败（重试用完）时 `status=failed`、`error_type=internal`。
- `run.start` 的业务字段（如短剧的 `resumed`）由业务在领取后用 `run.Set(...)` 补，或者另打一行 `run.step`。

#### 6.12.3 统一出站 HTTP 客户端（提案）

新增 `internal/pkg/outbound`：

```go
// Client 返回带记录的 HTTP 客户端：每个请求在 app.log 打 ext.call，在 payload.log 记请求和响应全文。
// purpose 是用途（如 agent.web_fetch、imageproc.tencent），base 为空时用 netguard 的 SSRF 防护传输层。
func Client(purpose string, opts ...Option) *http.Client

// Transport 给只能传 RoundTripper 的 SDK 用（如腾讯 COS SDK）。
func Transport(purpose string, base http.RoundTripper) http.RoundTripper
```

- 记录规则和 payload 的处理规则一致（6.6）：鉴权头遮掉、base64 占位、4MB 截断。
- 下载类响应（图片、视频文件）只记状态、类型和大小，不记响应体。
- 自动带上 `X-Request-ID`。

现有 10 处直接构造 `http.Client` 的代码（F17）这样处理：

| 文件 | 用途 | 处理 |
| --- | --- | --- |
| `provider/webaccess/client.go` | Agent 联网搜索、抓取网页 | **迁移**到 `outbound.Client("agent.web")` |
| `imageproc/tencent.go` | 腾讯数据万象：用户素材的图片处理、视频截帧 | **迁移**：COS SDK 的 `http.Client` 用 `outbound.Transport("imageproc.tencent", …)` |
| `provider/netguard/netguard.go` | SSRF 防护传输层本身 | 白名单：是被包装的底层；它的调用方各自负责记录 |
| `provider/plugin/runner_client.go` | 宿主 → plugin-runner（内部进程） | 白名单：外部调用已由插件宿主记录；按 6.10 带关联头 |
| `service/agent/notify.go`、`service/agent/observe_remote.go` | Go → Agent 服务（内部进程） | 白名单：内部调用；带 `X-Request-ID` |
| `updater/client.go` | Go → updater（内部进程） | 白名单：运维功能 |
| `release/github.go` | 查 GitHub 新版本 | 白名单：运维功能，不是用户运行 |
| `storage/probe.go`、`service/image_processor_check.go` | 后台检测存储和图片服务配置 | 白名单：后台操作，已有操作审计 |

#### 6.12.4 CI 护栏

放在 `backend/internal/tests/arch/`，随 `bash scripts/check.sh` 一起跑：

1. **任务登记**：两层保证。
   - **编译期**：`queue.AddWorker[T RunArgs]` 带类型约束，任务参数没实现 `RunRef()` 就编译不过。
   - **架构测试**：用 `go/parser` 扫描，`river.AddWorker` / `river.AddWorkerSafely` 只允许出现在 `queue.AddWorker` 的实现里，其他地方直接调用就失败，并提示「请实现 RunArgs 并用 queue.AddWorker 注册」。（River v0.49 的 `Workers` 没有公开方法列出已注册类型，所以不能在运行时比对，改用这两层。）
2. **出站 HTTP 测试**：用 `go/parser` 扫描 `internal/` 下的非测试代码，以下写法只允许出现在白名单文件里，否则失败并给出文件和行号：
   - 构造 `http.Client{}`、`http.Transport{}`；
   - 使用 `http.DefaultClient`、`http.DefaultTransport`、`http.Get`、`http.Post`、`http.PostForm`、`http.Head`；
   - 调用 `netguard.NewClient` / `netguard.NewTransport`（只允许 `llmgateway`、`provider/plugin`、`pkg/outbound`）。

   白名单写在测试文件里，每一项都要写原因（就是 6.12.3 的表）。新增白名单需要在评审里说明。
3. **forbidigo 补充**（编辑器里即时提示）：在 `.golangci.yml` 的 `forbidigo` 里加 `^net/http\.(Get|Post|PostForm|Head)$` 和 `^net/http\.DefaultClient$`，提示「用 outbound.Client（E9）」。`http.Client{}` 这种类型字面量 forbidigo 不好区分「声明类型」和「构造实例」，所以交给第 2 条测试。
4. **字段测试**：扫描非测试代码里 `zap.Uint64("task_id"`、`zap.Uint64("run_id"`、`zap.String("drama_job_id"` 等旧写法，出现就失败（关联字段只能由 `logger.Ctx` 带入）。

#### 6.12.5 新功能接入清单（写进规范 E10，作为评审检查项）

1. 新的后台任务：参数实现 `RunArgs`，用 `queue.AddWorker` 注册；`run_id` 要和界面上显示的编号相同。
2. 新的同步运行（不走队列、但会调模型或外部服务）：`ctx, run := logger.BeginRun(...)` + `defer run.End(...)`。
3. 外部调用：模型走 `llmgateway`；供应商走插件；其他走 `outbound.Client`。
4. 终态调用 `run.End`，补 `status`、积分、`error_code`、`error_message`、`error_type`。
5. 关键过程节点打 `run.step`；失败原因不要吞，通过 error 带到终态。
6. 新的 `run_kind` 或 `error_type` 取值先加进规范的命名表。

## 7. 状态与异常

| 情况 | 日志表现 |
| --- | --- |
| 正常运行 | `run.create` → `run.start` → 若干 `llm.call` / `provider.call` / `run.step` → `run.finish`（succeeded） |
| 网关空闲超时自动重试 | 两行 `llm.call`（`net_attempt` 1、2），两条 payload |
| 业务校验失败重写 | `llm.call`（ok）+ `run.step`（Warn，`invalid_output`，同一 `call_id`）→ 第二次 `llm.call` |
| 上游非 2xx | `llm.call` / `provider.call`（Warn，`upstream_status`、`error`）；payload 里有错误体原文 |
| 基础设施错误、River 重试 | `run.retry`（Warn）→ 下一次 `run.start`（`attempt=2`、`resumed=true`） |
| 进程崩溃 | 已刷盘的行保留；`payload.log` 最多丢失 1 秒或 1MB 的缓冲（提案默认值），`app.log` 不受影响 |
| 用户取消 | 进行中的调用记 `result=canceled`；`run.finish`（canceled，Warn） |
| 写日志失败（磁盘满等） | zap 内部报错写到 stderr，业务继续；lumberjack 下次写入时重试 |
| `payload.log` 关闭 | `logger.Payload` 空操作；`app.log` 里仍有 `call_id`，只是找不到全文 |
| 超大内容 | 单字段 4MB 截断，`truncated=true` |
| 多实例部署 | 每行带 `instance`；各实例写自己的文件，按实例分目录挂卷（`./logs/<hostname>/`） |

**权限与隐私**：`payload.log` 里有用户原文、提示词、模型输出、参考图摘要。日志目录的访问权限等同数据库，部署文档里写明。凭证在任何文件里都不出现。

### 8.4 日志量估算（示意，未实测）

| 内容 | 估算 |
| --- | --- |

### 8.5 测试（TDD，放 `backend/internal/tests/`）

1. `logger.Ctx`：ctx 上挂的 request / user / run / attempt / parent 字段都出现在输出里；没挂的不输出。
2. 两个文件：`logger.Payload` 只写 payload core，不出现在 `app.log` 和标准输出；`payload.enabled=false` 时为空操作。
3. 网关观察者：用 `httptest` 假上游，成功、非 2xx、空闲超时重试三种情况各回调正确次数，`call_id` 唯一，错误体原文保留且 Key 被遮成 `***`（三种转义形式）。
4. 请求头：`Authorization` 等值被换成 `***`。
5. base64 占位：超过 1KB 的 `data:` URI 被替换，带 MIME、大小和哈希。
6. 4MB 截断和 `truncated` 标记。
7. 插件宿主：非试跑任务也写 `provider.call` + payload；试跑任务落库的 `trace_json` 仍是 8KB 截断（回归）。
8. 轮询折叠：连续 5 轮相同结果只写首尾和一条 `folded: 3`。
9. 汇总行：一次短剧运行的 `run.finish` 里 `llm_calls`、token 合计等于各 `llm.call` 之和。
10. 访问日志：带 `user_id`；请求创建任务时带 `run_kind` / `run_id`。
11. River：任务参数里的 `request_id` 在执行时还原；`attempt` 正确。
12. 编号：`run_id` 等于界面编号（gen/drama/mkt 为 `idcodec` 编码）。
13. River 中间件：任务成功且业务调了 `End` → 只有业务的 `run.finish`；成功但没调 → 兜底 `run.finish`（`status=unknown`、`finish_fallback=true`）；返回错误且还会重试 → `run.retry`；重试用完 → 兜底 `failed`；panic → Error 级兜底行并重新抛出。
14. `BeginRun` + `defer End`：同步运行的汇总行在函数返回时打出，`llm_calls` 等计数正确。
15. 出站客户端：`ext.call` 和 payload `kind=http` 各一条；鉴权头被遮；下载类响应不记响应体；带 `X-Request-ID`。
16. 架构测试本身：在临时目录放一个直接 `&http.Client{}` 的样例文件、一个直接 `river.AddWorker` 的样例，测试能报出文件和行号；白名单内的文件不报。

## 9. 方案取舍

| 维度（权重） | A 两文件 + 统一切点（推荐，已确认） | B 全部进一个文件 | C 只在失败时记全文 |
| --- | --- | --- | --- |
| 排查完整度（35%） | 成功和失败的调用都有全文 | 同 A | 「不好但没报错」时没有全文 |
| 主日志可读性（25%） | 主日志只有元数据 | 全文淹没错误，滚动快 | 好 |
| 磁盘（15%） | `payload.log` 单独保留 7 天 | 全部一起保留 30 天，量最大 | 最小 |
| 实现成本（25%） | 中：两个切点 + 上下文 + 各业务事件 | 同 A | 中（各业务要自己判断失败） |
| 结论 | **采用** | 放弃 | 放弃（用户选择每次都记） |

**明确放弃 / 不做**：日志入库、后台查看页面、日志导出、后台调日志级别、外部日志平台、OTel SDK、记录 HTTP 请求体（用户→平台方向的请求不记全文）、Agent 服务和 plugin-runner 内部的全面改造。

## 11. 待确认问题与已确认事项

**已确认（用户回答）**

1. **日志系统要两类**：业务运行日志和系统日志；**系统日志不入库**，给运维排查用。
2. **后台只做查看**（后被第 5 条整体搁置）。
3. **后台与现有页面并存互跳**（后被第 5 条搁置）。
4. **运行日志存 PostgreSQL 分区表**（后被第 5 条搁置）。
5. **运行日志先不做，先搭服务器统一日志**，给运维排查，**需要完整记录**。
6. **完整程度**：每次上游调用都记全文（成功也记），**放在单独的 `payload.log`**；`app.log` 只记元数据和失败原因。
7. **进程范围**：Go 后端为主；Agent 服务和 plugin-runner 只对齐字段和 JSON 格式。
8. **落盘**：compose 默认挂卷写文件；`app.log` 保留 30 天，`payload.log` 保留 7 天并压缩。
9. **新功能自动纳入**：补上 River 任务中间件（自动关联字段、开始 / 重试 / 兜底收尾）和统一出站 HTTP 客户端，并用 CI 护栏（编译期类型约束、架构测试、forbidigo）拦住绕过记录的写法；业务汇总字段和过程事件写进接入清单。（用户回答「可以的」，主文档 6.12 已补）

**已搁置的决定（将来做运行日志入库时可复用）**

- 运行日志写 PostgreSQL，按天分区，过期整天删分区；常用字段单独成列，其余放 jsonb。
- 后台「日志管理 › 运行日志」只做查看：按用户、编号、类型、级别、时间筛选，点开看一次运行的日志流，全文可展开；不做级别控制、保留期设置和导出。
- 与「使用记录」「Agent 运行记录」并存，在各自的详情里加「查看运行日志」按钮互相跳转。
- 访谈中最后一题（入库内容和保留期）没有回答就搁置了。

**默认值（不需要用户决定）**

- 字段、事件、`run_kind` 取值（第 6 节）；`call_id` 为 12 位十六进制。
- `app.log` 文件固定 JSON，标准输出沿用 `log.format`。
- `payload.log` 缓冲 1MB / 1 秒；单字段 4MB 截断；base64 超过 1KB 换成摘要占位；轮询相同结果折叠。
- 用户访问平台的 HTTP 请求体不记全文（只记访问日志汇总行）。
- 后台试跑归在 `gen` 下，另带 `test=true`。

**仍待确认（不阻塞设计，实现前核对）**

1. Agent 服务拆分后，Go 侧能否在平台 API 的每个请求里拿到 Agent 运行 ID（现在由桥令牌解析，见 `CtxAgentRunIDKey`），以及 Agent 运行 ID 在拆分后的格式。
2. 首字耗时在 Gemini 格式下能否逐段拿到（同 [短剧运行日志](../短剧运行日志/短剧运行日志.md) 的未验证项）。
3. 8.4 的日志量是估算，上线一周后按实际调整 `payload.log` 保留期。

**与设计的出入**

1. **`run.start` 不由队列中间件自动打**。生成任务的一生是多次 River 执行（提交后每次轮询前都 `JobSnooze`），闸门满时其他任务也每秒延后一次，中间件在每次执行前打开始行会刷屏。改为：中间件只挂上下文，被延后的执行不打任何日志；开始行由真正开始干活的代码调 `run.Start()`（三期接入）；正常返回时，**本次执行里开始了却没收尾**才兜底打 `unknown`，避免对「任务已是终态、醒来什么都没做」的执行误报。调用计数按单次执行累计。
2. **`request_id` 放进任务 metadata，不放进任务参数**：几种任务都开了 `UniqueOpts.ByArgs`，参数里多一个字段会让不同请求的同一任务不再去重。
3. **compose 用命名卷 `backend_logs:/app/logs`，不用 `./logs` 绑定挂载**：容器以 `app` 用户运行，绑定挂载的宿主目录由 Docker 以 root 创建，写不进去会静默丢日志。查看方式改为 `docker compose exec backend grep … /app/logs/app.log`（镜像是 alpine，有 grep，没有 jq）。
4. **营销的队列任务是轮次**：`run_kind=mkt_round`，`run_id` 是轮次编号；轮次里每个环节运行由业务另开 `mkt` 运行（三期）。
5. **`logger.Ctx` 能读穿 `*gin.Context`**：有 9 个 handler 把 `c` 直接当 ctx 传给 service，gin 默认不回落到请求 context；没有开 `ContextWithFallback`（会改变这些接口的取消行为），改为 logger 自己从 gin 挂着的 `*http.Request` 上取。
6. **删除 `middleware.CtxAgentRunIDKey`**：Agent 拆成独立服务后已没有地方设置它，只剩访问日志在读；Agent 运行改由三期在平台 API 里 `BeginRun`。
7. **队列运行时原有的 `instance` 字段改名 `worker_id`**：和每行都有的 `instance`（主机名）重名，JSON 里会出现两个同名键。
8. River v0.49 的 `Config.WorkerMiddleware` 已弃用，改挂在 `Config.Middleware`。
9. `logger.TaskID` 暂时保留，三期替换完后删除。
