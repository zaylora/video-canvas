01关系总览

一张任务表把用户、画布、积分、素材和 AI 配置串起来

02全库约定

六条约定，所有表都遵守

只支持 PostgreSQL

用到 jsonb、ILIKE、部分索引（WHERE ...）。

数据按用户隔离

用户数据的查询、更新、删除都带 user_id；查不到和不属于自己统一返回“不存在”。

软删除只给用户与画布

users、canvas_projects 嵌入 BaseModel（带 deleted_at）。任务、流水、素材、配置不软删：它们是审计依据。

jsonb 与 json 分开用

画布、任务输入输出用 jsonb；配置正文用 json，因为 jsonb 会重排键，而 input_schema 的键序就是前端渲染顺序。

不可变版本 + 指针

配置、插件都存不可变版本，主表只存“当前指向哪一版”。发布、回滚、升级都是改指针。

逻辑关联，不建外键

表之间靠 id / key 关联，GORM 没有声明关联，所以没有外键约束；归属与引用检查在 service 层做。

迁移：auto_migrate 启动时建表、加列，只加不删。本次改动删表删列，没有真实数据，开发环境清空重建。

09不可变版本与快照

发布、回滚、升级都只是改指针

模型

published_revision_id

编辑写新的 draft；发布把指针指向它；回滚把指针改回旧 revision。旧 revision 永远保留。

渠道

plugin_version_id

插件版本不可改；升级插件 = 上传新版本 + 渠道改指向。有渠道或进行中任务引用的版本不能删。

任务

config_snapshot

提交时把当时的模型正文、渠道配置（不含 Key）、插件版本哈希整份冻结。改指针不影响进行中的任务。

快照里 Key 只存名字 channel:<key>，执行时再解密：换 Key 立即对进行中的任务生效，而换配置不会。

12待确认与未验证

五个会影响建表的问题

01 · 提案

ai_audit_logs 的字段与 action 取值是提案，设计文档里只写了“要记哪些操作”。

02 · 保留期

任务表里的文本产物、审计日志要保留多久？决定要不要按时间分区或定期清理。

03 · 插件代码大小

插件版本不可删（被引用时），每版最多 512KB；长期看要不要清理无引用的旧版本？

04 · 渠道是否要版本

目前渠道改动直接生效、不留历史（快照兜住进行中任务）；是否需要像模型一样做 revision？

05 · 外键

目前全靠逻辑关联。要不要给 ai_channels.plugin_version_id 这类强引用加外键，防止误删？

建议 · 顺手修

idx_task_provider 按代码只有一列；provider 改存渠道 key 时，给它补上索引标签，变成复合索引。未在实际库里核对。
