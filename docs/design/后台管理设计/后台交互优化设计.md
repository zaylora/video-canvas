# 后台交互优化设计

> 范围：AI 配置后台（模型 / 渠道 / 插件三页）的交互逻辑走查、删除能力补齐、整体闭环重设计，以及能不能套用 shadcn-admin 模板。
> 配套演示：[后台交互优化-演示.html](./后台交互优化-演示.html)（可点击的交互原型：总览页、三种删除流程、一屏建渠道、模型“上线 / 下线”）。
> 日期：2026-10-02。状态：分析与设计稿，未改任何代码。

---

## 1. 一句话结论

后台现在是**按数据结构排出来的**（插件 → 渠道 → 模型，各管各的），不是**按运营要完成的事排出来的**（“我要上线一个模型给用户用”）。所以每一步都能做，但用户要自己记住顺序、自己发现哪里坏了、自己跨页找入口，而且东西一旦建错**删不掉**。

优化方向一共四件事：

| #   | 做什么                                                                          | 解决什么                           |
| --- | ------------------------------------------------------------------------------- | ---------------------------------- |
| ①   | **补删除**：插件、渠道、模型都能删，被引用时告诉你被谁引用、给一键处理          | 建错的东西永远留在列表里           |
| ②   | **加总览页**：一个“上线进度 + 待处理问题”首页，每个问题一键去修                 | 不知道先做什么、不知道哪里坏了     |
| ③   | **缩短主流程**：渠道一屏填完（含 Key）自动检查；模型“发布 + 上架”合成一个“上线” | 一个任务要跨 3 个弹窗、记 3 个状态 |
| ④   | **状态往下传**：插件停用 / 渠道缺 Key → 模型行直接显示“不可用（原因）”          | 列表上显示“已上架”，用户其实用不了 |

## 2. 现状：一条完整闭环要走多少步

以“接入一个新平台，上线一个视频模型”为例（super_admin 视角），按现在的代码实际走一遍：

| 步  | 页面                   | 操作                                                               | 问题                                                                                                                                                                            |
| --- | ---------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 插件                   | 点“上传插件” → 选文件 → 上传 → 预检通过                            | ✅ 有“下一步：新建渠道”，这一步做得好                                                                                                                                           |
| 2   | 渠道（抽屉）           | 填名称、key、选插件版本、地址、插件设置、限流、安全开关 → **保存** | Key 不能在这里填，提示“保存渠道后再设置 Key”                                                                                                                                    |
| 3   | 渠道（抽屉内再开弹窗） | 点“设置 Key” → 粘贴 → 保存                                         | 第二个弹窗                                                                                                                                                                      |
| 4   | 渠道（抽屉）           | 点“检查连通性”                                                     | 要手动点；失败了也不拦                                                                                                                                                          |
| 5   | 渠道 → 模型            | 点“去上架模型”                                                     | **断链**：链接是 `/admin/ai/models/new`，没带 `?channel=`，到了模型页还要重新选渠道（[channel-sheet.tsx:678](../../../web/src/pages/admin-ai/channels/channel-sheet.tsx#L678)） |
| 6   | 模型（大弹窗）         | 三个页签填基本信息、能力参数、定价                                 | key、上游模型 ID、展示名称三个“名字”要分别填                                                                                                                                    |
| 7   | 模型（弹窗套弹窗）     | 点“测试模型” → 填示例输入 → 试跑                                   |                                                                                                                                                                                 |
| 8   | 模型（确认框）         | 点“保存并发布” → 确认                                              | 用户以为发布完就上线了                                                                                                                                                          |
| 9   | 模型（弹窗底栏）       | **再**打开“在画布中上架”开关                                       | 真正对用户可见是这一步，很多人会漏                                                                                                                                              |

**9 步、跨 3 页、开 5 个浮层、要理解 4 个状态（草稿 / 已发布 / 上架 / 启用）**。设计目标是压到 **4 步、1 条向导路径**（见 §5）。

## 3. 问题清单

按严重程度排序。每条都标了代码位置，方便对照。

### 3.1 致命：删不掉（用户点名的问题）

| 对象 | 现在能做什么                                             | 后端                                     | 前端                                                                                                        |
| ---- | -------------------------------------------------------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 插件 | 只能**逐个删版本**；删到最后一个版本时后端顺手删掉插件行 | `DELETE /plugins/:key/versions/:version` | [plugin-detail.tsx](../../../web/src/pages/admin-ai/plugins/plugin-detail.tsx) 版本时间线里的“删除这个版本” |
| 渠道 | **不能删**，只能停用                                     | 无接口                                   | 无入口                                                                                                      |
| 模型 | **不能删**，只能下架                                     | 无接口                                   | 无入口                                                                                                      |

后果：测试时建的 `test-xxx` 渠道、配错的模型、废弃的上传插件全部永久留在列表里，列表越用越乱；模型 key 被占用，想用同名重建也不行。

### 3.2 严重：闭环断裂

1. **没有起点**。后台默认进“模型”页，但一个空系统必须先有插件和渠道。模型页的空状态只给“新建模型”，点进去渠道下拉是空的，用户不知道要先去渠道页。
2. **渠道创建拆成三段**：保存 → 设 Key（另开弹窗）→ 检查连通性。Key 是渠道能用的必要条件，却被放在“保存之后”。
3. **“去上架模型”链接丢了渠道参数**（见 §2 第 5 步），渠道页另一个入口“用这个渠道新建模型”是带参数的，两个入口行为不一致。
4. **发布 ≠ 上架**。“保存并发布”之后模型对用户仍不可见，还要再开“上架”开关；反过来，从没发布过的模型“上架”开关是禁用的，只有鼠标悬停才有 title 提示。两个概念对运营没有区别，只是让人多点一下、漏点一下。
5. **admin 角色遇到死胡同**。admin 能编辑模型，但渠道没设 Key 时发布被拦，提示“请联系运维在渠道页设置 Key”——页面上没有任何能把这件事交给运维的东西（复制链接、@ 某人都没有）。
6. **导入模型是一个一个过**。从渠道导入后进入“待处理草稿 N 个”队列，只能逐个打开编辑器、逐个保存，不能在一个列表里勾选要哪些、批量设好渠道和价格后一起保存。

### 3.3 严重：状态看不见

7. **状态不向下传播**。插件停用 → 所有用它的渠道不接新任务 → 这些渠道下的模型实际不可用；但渠道列表仍显示“启用”，模型列表仍显示“已上架 ✓”。运营要逐层点进去才能发现。
8. **没有“健康”汇总**。“未设 Key”“插件可升级”“有未发布草稿”“发布被阻断”这些信号分散在各页的小字里（列表项右下角、卡片 Notice、弹窗头部），没有一个地方能一眼看到“现在有几件事要处理”。
9. **渠道页选中项不在 URL 里**。左栏选中用的是组件内 state（[channel-master.tsx](../../../web/src/pages/admin-ai/channels/channel-master.tsx) 的 `selectedKey`），而抽屉用 `?edit=`。从插件页点“在用渠道”链接过来，抽屉打开了，左栏却还停在第一个渠道；刷新页面也会丢选中。插件页用的是 `?key=`，两页不一致。

### 3.4 中等：操作一致性

10. **危险操作确认不一致**。停用渠道有确认框；停用插件（影响面更大，波及所有渠道）**直接拨开关就生效**，没有确认，也没有成功提示（[plugin-detail.tsx](../../../web/src/pages/admin-ai/plugins/plugin-detail.tsx) 的 `toggle`）。
11. **同一个操作多个入口、位置不同**。回滚：模型行“更多”菜单里有，模型弹窗“更多 → 回滚到历史版本”子菜单里也有，展示格式还不一样（`v3 已归档 回滚` vs `第 3 版 · 历史`）。测试：行菜单、弹窗头部预览卡片、弹窗底栏三处。
12. **整行可点 + “编辑”按钮**，两个都是打开编辑弹窗，按钮是冗余的，反而挤掉了更常用的“测试”。
13. **插件升级只能一个渠道一个渠道切**。插件页显示“可升级到 v1.3”，但要进每个渠道的编辑抽屉手动换版本。
14. **弹窗套弹窗**。模型编辑是 1000px 大弹窗，里面再开测试弹窗、发布确认框、回滚确认框、放弃修改确认框。

### 3.5 轻微：信息过载

15. **插件详情对运营太技术**：sha256、契约版本、`allowedHosts`、轮询间隔占了大半屏，运营真正关心的只有“支持哪些生成方式、几个渠道在用、能不能导入模型”。
16. **渠道表单的“高级与安全”默认展开**。“允许访问内网”“允许插件读取 Key”对新手是噩梦开关；其中“允许插件读取 Key”在插件声明 `auth: custom` 时是**必须**开的，完全可以自动处理。
17. **三个名字**：产品模型标识（key）、上游模型 ID、展示名称。key 可以由“展示名称”自动生成（可改），导入时上游模型 ID 已知，运营只需要关心展示名称。

## 4. 删除设计（重点）

### 4.1 统一规则

所有删除走同一个模式，用户只需要学一次：

1. **入口**：详情 / 行的“更多”菜单最底部，红色“删除…”，与其他操作用分隔线隔开。
2. **先算影响**：打开对话框时调后端的“删除预检”，列出谁在引用它。
3. **有阻断 → 不让删，但给出路**：每一类引用旁边放一键处理按钮（“把 3 个模型迁到其他渠道”“停用后再删”），处理完对话框自动刷新，变成可删除状态。
4. **无阻断 → 确认**：模型直接确认；渠道和插件要**输入名称**才能点删除（影响面大）。
5. **结果**：toast“已删除「xxx」”，列表自动选中下一项。

### 4.2 三种对象各自的规则

|            | 模型                                                | 渠道                                                                     | 插件（整个）                                                    |
| ---------- | --------------------------------------------------- | ------------------------------------------------------------------------ | --------------------------------------------------------------- |
| 阻断条件   | 仍在上架 → 先下架（对话框里给“下架并删除”一键完成） | ① 有模型引用（任一版本正文里 `channels[].channel` 指向它）② 有非终态任务 | ① 内置插件不能删（只能停用）② 任一版本被渠道固定 ③ 有非终态任务 |
| 一键处理   | “下架并删除”                                        | “把这些模型迁到…”（选目标渠道，复用批量修改的“统一切换渠道”）            | “查看在用渠道”跳转；渠道都删掉/切走后可删                       |
| 确认方式   | 普通确认                                            | 输入渠道名                                                               | 输入插件 key                                                    |
| 一起删掉的 | 草稿、所有历史版本                                  | 渠道 Key（`ai_secrets` 里的 `channel:<key>`）、连通性记录                | 所有版本代码                                                    |
| 不影响的   | 历史任务：任务表存了 `ConfigSnapshot`，结果照常可看 | 历史任务（同上）                                                         | 历史任务（同上）                                                |
| 批量       | 模型列表批量栏加“批量删除”                          | 不做                                                                     | 不做                                                            |

### 4.3 模型彻底删除（2026-10-02 改）

最初设计为软删除、key 不能复用。实际使用中“删掉重新导入”很常见，而历史任务只存 `model_id`、没有按 key 回查模型名的地方，软删除的顾虑不成立。改为**硬删除**：模型连同全部历史版本一起删掉，不能恢复，同一个 key 之后可以重新新建 / 导入（版本号从 1 开始）。

开发期已经软删除过的模型由一次性迁移清掉（连同历史版本），并删掉 `deleted_at` 列。

渠道和插件**硬删除**即可：任务快照里已经冻结了渠道配置和插件版本哈希，删除不影响历史。

### 4.4 后端接口

| 接口                                       | 权限        | 说明                                                                           |
| ------------------------------------------ | ----------- | ------------------------------------------------------------------------------ |
| `GET /admin/ai/models/:key/delete-check`   | admin       | 返回 `{ blocked, reasons: [{type:"enabled"}] }`                                |
| `DELETE /admin/ai/models/:key`             | admin       | 彻底删除（含全部历史版本）；仍上线返回 409                                     |
| `GET /admin/ai/channels/:key/delete-check` | super_admin | 返回引用它的模型列表、非终态任务数                                             |
| `DELETE /admin/ai/channels/:key`           | super_admin | 事务内重新统计引用（同插件版本删除的加锁写法），连同 secret 一起删；记审计日志 |
| `GET /admin/ai/plugins/:key/delete-check`  | super_admin | 返回各版本被哪些渠道固定、非终态任务数                                         |
| `DELETE /admin/ai/plugins/:key`            | super_admin | 内置返回 409；删除全部版本与插件行；记审计日志                                 |

> 预检只是给界面看的，**真正的判断以 DELETE 事务内为准**（并发下预检结果可能过期），与现有 `DeleteVersion` 的做法一致。

## 5. 傻瓜式闭环设计

### 5.1 新增“总览”页（后台首页）

侧栏第一项。分两块：

**上线进度**（系统还没跑通时显示，跑通后收起成一行）：

```
① 接入平台（插件）  ✓ 2 个     →  ② 配置渠道  ⚠ 1 个缺 Key  →  ③ 上线模型  0 个在线
                                       [去设置 Key]                    [新建模型]
```

每一步只看“够不够用”，不看细节；当前卡住的那一步高亮，给一个主按钮。

**待处理**（按严重度排序，每条一个修复按钮，修复动作就地完成或深链到对应位置）：

| 信号               | 文案                                                  | 按钮                 |
| ------------------ | ----------------------------------------------------- | -------------------- |
| 渠道缺 Key         | 渠道「NewAPI 主线」还没设置 Key，2 个模型因此无法上线 | 设置 Key（就地弹窗） |
| 插件停用但仍有渠道 | 插件「Kling」已停用，1 个渠道、3 个在线模型实际不可用 | 查看 / 启用插件      |
| 连通性检查失败     | 渠道「备用线路」上次检查失败：401                     | 重新检查             |
| 有未上线的修改     | 4 个模型有改动还没上线                                | 去查看               |
| 插件可升级         | Kling v1.3 可用，2 个渠道还在 v1.2                    | 一键升级             |

### 5.2 状态模型简化

对运营只露出**一个状态**，其余变成“附注”：

| 用户看到                 | 对应现在的组合                                |
| ------------------------ | --------------------------------------------- |
| **在线**                 | 已发布 + 上架 + 渠道启用 + 插件启用 + Key 齐  |
| **不可用**（红，带原因） | 已发布 + 上架，但渠道 / 插件 / Key 任一不满足 |
| **已下线**               | 已发布 + 未上架                               |
| **未上线**               | 从没发布过                                    |
| 附注：**有未上线的修改** | `has_unpublished_draft`                       |

按钮也随之合并：

- 弹窗主按钮从“保存并发布”改成 **“上线”**（= 保存 + 发布 + 上架，一步）；已在线的模型改完后按钮叫 **“更新上线版本”**。
- 次按钮“保存草稿”保留。
- 底栏的“在画布中上架”开关去掉，**下线**放到“更多”菜单和列表行开关里。
- 发布确认框里如果用户只想发布不上架（灰度场景），给一个“暂不对用户开放”的勾选，默认不勾。

### 5.3 渠道一屏建完

新建渠道抽屉改成三段，从上到下就是顺序：

1. **选插件**：卡片选择（图标 + 名称 + 支持的生成方式），默认最新版本，版本号收进“高级”。
2. **连接**：地址（插件可在 meta 里给默认值，选了插件就预填）、**Key**（直接在这里填，插件 `auth.type = none` 时整段隐藏）、插件设置。
3. **名称**：显示名，key 由显示名自动生成（可改）。

底部只有一个主按钮 **“保存并检查”**：保存渠道 → 写 Key → 跑连通性检查，结果在抽屉内显示。成功后给两个下一步：**“从这个渠道导入模型”**（插件支持导入时）/ **“用这个渠道新建模型”**（带 `?channel=`）。

“限流”“允许访问内网”收进折叠的“高级设置”；“允许插件读取 Key”在插件声明 `auth: custom` 时自动打开并显示一行说明，不再让用户决定。

### 5.4 导入改成批量勾选

导入对话框返回草稿后，不再逐个进编辑器，而是在对话框里显示一个表格：勾选要的模型 → 统一设能力类型 / 默认价格 → **“全部保存为草稿”** 或 **“全部上线”**。单个模型需要细调时再点进编辑器。

### 5.5 一致性修正（小改动，收益大）

| 现在                      | 改成                                                           |
| ------------------------- | -------------------------------------------------------------- |
| 插件启停直接拨开关        | 停用要确认，写明“N 个渠道、M 个在线模型会不可用”；成功后 toast |
| 渠道页选中项在组件 state  | 改成 `?key=`，与插件页一致；`?edit=` 打开抽屉时同步选中        |
| 模型行“编辑”按钮          | 去掉（整行可点），换成“测试”按钮                               |
| 回滚两处、格式不同        | 统一成“版本历史”抽屉：时间线 + 每个版本可查看差异 / 回滚       |
| 插件“可升级到 vX”只是提示 | 加“升级全部 N 个渠道”按钮，确认后批量切版本                    |
| 插件详情一屏技术字段      | sha256、契约版本、allowedHosts、轮询参数收进“技术详情”折叠     |
| admin 遇到缺 Key 死胡同   | 提示里加“复制给运维”按钮（复制渠道深链 + 一句话说明）          |

## 6. 能不能套用 shadcn-admin 模板

[satnaing/shadcn-admin](https://github.com/satnaing/shadcn-admin)（MIT）。

### 6.1 结论：不整套替换，继续“按件移植”

**现在的后台本来就是照着它做的**。代码里已经移植了它的 `NavGroup`、`NavUser`、`AppTitle`、`DataTablePagination`、`DataTableBulkActions`，配色 token 命名也一致（见 [components/admin-ui/](../../../web/src/components/admin-ui/) 的注释和 [AI配置管理-演示.html](./AI配置管理-演示.html)）。视觉上已经是它的样子。

不建议整套替换的原因：

|          | shadcn-admin                                        | 本项目                                | 影响                                                           |
| -------- | --------------------------------------------------- | ------------------------------------- | -------------------------------------------------------------- |
| 路由     | TanStack Router（文件路由）                         | react-router 8                        | 整套替换要改路由体系，和画布前台不一致                         |
| 组件底层 | Radix UI                                            | shadcn `base-nova` 风格，底层 Base UI | 两套组件 API 不同（`asChild` vs `render`），混用会出现两种写法 |
| 定位     | 作者自己说“不是 starter 模板”，是一个独立 Vite 应用 | 后台是主应用里的一组路由              | 没法“装”进来，只能抄                                           |
| 内容     | 用户、任务、聊天、设置等演示页                      | AI 配置三页                           | 业务页面一个都用不上                                           |

**交互问题不在模板**：§3 列的问题（删不掉、闭环断裂、状态不传播）换了模板一个都不会消失。模板管“壳”，这些是“流程”。

### 6.2 值得从它那里继续搬的

| 模板里的东西                                              | 用在哪         | 说明                                                                                                                       |
| --------------------------------------------------------- | -------------- | -------------------------------------------------------------------------------------------------------------------------- |

## 8. 已确认（2026-10-02）

1. **范围**：先做 P0 + P1，验收后再做 P2 / P3。
2. **模型彻底删除，key 可以复用**（最初定为软删除、不能复用，用户试用后改为：删掉就彻底不用，不考虑恢复，之后导入同名模型不受影响）。
3. **不保留“发布但不对用户开放”**：上线 = 发布 + 上架，一步完成；想停用就下线。
4. **公共弹窗全站通用**：`store/dialog.ts`（全局弹窗 store）+ `components/dialog-host.tsx`（挂在路由根布局）+ `confirm()`（`components/admin-ui/confirm-dialog.tsx`）。页面级弹窗都走它；从弹窗 / 抽屉**里面**打开的子弹窗仍是受控弹窗，留在原组件树里（否则按 Esc 会连外层一起关）。
5. 渠道删除时“有模型引用”的口径：最新草稿 + 已发布版本，已归档的历史版本不算。
6. 总览页作为后台默认落地页。
