## 1. 设计摘要

**问题**：现在的「编辑模型」弹窗骨架已经和设计稿对齐（三页签、版本徽章、发布前待办、左表单右预览、底栏上架），但内容差了一大截：

- 基本信息缺 Logo、展示标签、描述字数限制，选择器预览缺价格与标签。
- 「能力与参数」页签是通用的 `input_schema` 编辑器，不是面向运营的结构化表单：没有生成方式、上下文能力、参考素材数量与大小上限、「开放给用户」、可选值勾选、范围滑块、固定系统提示。
- 「积分定价」页签只有统一的按次价格，按秒、Token、规格价格、成本与利润率都是禁用占位。

**目标**：运营在弹窗里只靠表单就能完整配置一个模型，不需要手写 JSON；画布端按配置渲染节点并实时显示价格；扣费与配置一致。

**推荐结论**（均来自本次访谈的确认）：

| 决策 | 结论 |
|---|---|
| 范围与节奏 | 全部设计，分三期实现：① 基本信息 ② 能力与参数 ③ 积分定价 |
| 模型 Logo | 新增 `vendor` 字段；前端 `bun add @lobehub/icons`，按需深引入厂商图标组件；选不到回退首字头像 |
| 结构化数据 | 新增顶层 `capabilities` 块作为**唯一来源**，`input_schema` 废弃，画布、下单校验、任务快照全部改读 `capabilities` |
| 旧数据 | 现有模型配置**丢弃重建**，不写兼容适配器（前提：确认库里没有线上真实数据，见 §11） |
| 生成方式 | 视频：文生 / 图生 / 全能参考，**不做首尾帧**；图片：**只有**文生图 / 图生图（已确认）。视频**可以要参考视频**（参考视频自己的秒数不单独计费，已确认先不做）。**全能参考不区分素材类型**：已开启的素材都能引用，具体类型由上游节点决定 |
| 档位与时长 | 图片 1K / 2K / 4K、视频 720P / 1080P / 4K 是**清晰度档位**，不同档位价格不同；视频时长**不是点选**，是在「最小 – 最大」之间可拖动的滑块；去掉「提示词相关性」 |
| 生成数量 | 画布参数面板里的「生成数量」（1 / 2 / 4）：**像「复制节点」一样，复制出 N 个一模一样的节点**（提示词、模型、参数、生成方式、引用的素材和上游连线都相同），后端对应拆成 N 个独立任务（均已确认）。**点发送的瞬间 N 个节点就已经在画布上**；每个节点绑定自己的任务，各自冻结、各自结算、互不影响；**哪个节点失败，就哪个节点显示自己的错误，失败的节点不删除**（均已确认）；底栏显示的积分 = 每个任务的积分 × N |
| 计费方式 | 每个模型自己配置：视频**按秒**（档位 × 音频开关等用规格价格表达）；图片**按次**（档位定价）；文本**按 Token**。对照了 token.xinhankr.com 的视频模型计价（见 §4.1）；**视频 Token 计费本版不做**（已确认） |
| 文本参数 | 文本模型**没有**发散度、Top P 等采样参数（已确认），画布文本节点底栏只有模型、积分、发送 |
| 节点版式 | 画布节点底栏参考用户给的 LiblibTV 截图：模型 → 生成方式 → 参数摘要（点开是参数面板）→ 积分 → 发送 |
| 能力从哪来 | **运营在后台手动填**，不由插件声明（已确认）。插件协议只负责对接平台，一个插件对应的模型太多，不管模型的具体能力。后端只用固定的合理上下限兜底，新建时按 kind 预填默认值（参考影策的做法，见 §4.1） |
| 价格精度 | **整数积分，最小 1 积分，没有小数**（已确认）：所有价格输入都是整数；只有文本 Token 计费会因 `Token 数 × 单价 ÷ 100 万` 出现小数，向上取整 |
| 计价位置 | 定价规则下发给前端本地计算；后端下单时以自己算的为准并冻结 |
| Token 计费 | 按上限预冻结，完成后按实际用量多退少补（退到不超过预冻结） |

### 2.2 设计约束

1. 配置发布后不可变，回滚只是改指针。新结构要保持这点。
2. 积分账务是「先冻结再执行」，用户不能欠费。任何新计费方式都要落到这个模型里。
3. 画布端不能拿到成本价。
4. 管理端仍保留「编辑 JSON」模式；JSON 与表单读写同一份正文。
5. 管理端组件按 `components/admin-ui` 的 shadcn 风格平铺可组合，页面直接用（项目记忆里的既有约定）。

### 2.3 当前缺口

见 §1 的三条问题；此外还有两处**设计稿没画、但实现必须补**的缺口：

- 画布节点没有「生成方式」切换，也没有按素材数量 / 大小上限约束连线。
- 任务结果里没有 Token 用量，插件契约也没要求回传，Token 计费无从结算。

## 3. 用户与场景

| 角色 | 场景 | 频率 |
|---|---|---|
| 运营（`admin`） | 接入一个新模型：选能力和渠道，配展示信息、素材与参数、定价，测试，发布上架 | 每周数次 |
| 运营 | 调价、调整开放哪些参数 | 偶尔 |
| 运维（`super_admin`） | 在渠道/插件页配置 Key 与插件；模型页同样可写 | 低 |
| 创作端用户 | 在画布节点上选模型、选生成方式、拖素材、调参数、看到价格再点生成 | 高频 |

**主任务（运营）**：新建模型 → 基本信息 → 能力与参数 → 积分定价 → 测试模型 → 保存并发布。弹窗顶部「发布前待办」负责引导漏项。

**成功指标**（可验收）：

1. 新建一个视频模型并发布，全程不打开 JSON 模式。
2. 画布上选的模型头像是厂商 logo，价格随时长/分辨率实时变化。
3. 配置里的价格与下单实际冻结的积分逐笔一致（有共用测试向量覆盖）。
4. 运营看不到的字段（成本价）不出现在 `GET /models` 响应里。

**对本设计的影响**（均已落到下文）：

1. 计费方式是模型自己的属性：视频「按秒」，图片「按次」，文本「Token」。
2. 对照目录里有一半视频模型按 Token 计费，但**本版不做视频 Token 计费**（已确认，见 §9.2）；视频先按秒，将来要做时在 `pricing` 里加一种计费方式即可。
3. 规格价格的条件维度扩展为：枚举参数（清晰度）、**布尔参数（音频开 / 关）**、**生成方式**、**参考素材里有没有视频**。

### 4.2 方案比较：结构化配置怎么存

| 维度 | A. 扩展 `input_schema` + 顶层补字段 | B. 新增 `capabilities` 为唯一来源（**采用**） | C. 只用现有字段 |
|---|---|---|---|
| 与设计稿贴合 | 中 | 高 | 低 |
| 数据模型清晰度 | 中（两处来源） | 高（单一来源） | 低 |
| 改动面 | 小 | 大（下游全改） | 最小 |
| 旧数据 | 无需迁移 | 需丢弃重建 | 无需迁移 |
| 满足缺失项 | 全部 | 全部 | 缺 MB 上限、生成方式、上下文、系统提示 |

采用 B 的原因：用户明确选择；且现有模型很少、可以重建（§11 待确认没有线上数据），一次性换成单一来源比长期维护两套读法更干净。放弃的是「向后兼容」。

## 5. 设计原则

1. **表单是正文的读写，不是另一份数据**：弹窗里每个控件都映射到 JSON 里的一个确定字段，「编辑 JSON」始终可用（来自 §2.2-4）。
2. **能力由运营手填，后端兜底**：模型能支持什么由运营在后台决定，插件不声明；后端只用固定的合理上下限拦住手误（来自访谈「插件不需要管模型的内容」与影策的做法）。
3. **所见即所得**：左边改一项，右边预览（选择器、画布节点、价格）立即变化。
4. **价格先看见再点击**：画布按钮上永远显示将要冻结的积分；后端下单仍以自己算的为准（来自访谈「计价位置」）。
5. **账务不欠费**：所有计费方式都落在「先冻结再结算」里，Token 计费按上限预冻结（来自 §2.2-2 与访谈）。
6. **敏感字段分级**：成本价只存在于管理端正文，画布接口一律不下发（来自 §2.2-3）。

## 6. 推荐方案

**与旧结构的差异（破坏性）**

| 旧 | 新 |
|---|---|
| `credits` | `pricing`（`pricing.unit` 即旧 `credits`） |
| `input_schema` | `capabilities`（`prompt` + `refs` + `params` + `ops`） |
| 无 | `vendor`、`tags` |

**字段规则**

- `ops`：video 取值 `t2v / i2v / omni`；image 取值 `t2i / i2i`（已确认只有这两种）；text、audio 不允许有 `ops`。至少保留一种。
- 各生成方式能引用的素材由**代码常量**决定（不进配置），**全能参考不区分素材类型**：

  | 方式 | 提示词 | 可引用素材 |
  |---|---|---|
  | `t2v` / `t2i` 文生 | ✅ | 无（只有文字） |
  | `i2v` / `i2i` 图生 | ✅ | 图片 |
  | `omni` 全能参考 | ✅ | **不限类型**：`refs` 里 `on=true` 的素材类型都可以引用（图片、音频、视频…），连什么上游节点就是什么 |

  `refs.<类型>.max` 和 `max_mb` 约束每种素材的数量与单个大小。`refs.<类型>.on = false` 表示不接收这种素材，即使该方式本来允许。
- `params.*.open`：`true` 出现在画布节点的参数面板里；`false` 不出现，按 `default` 发送。`open=false` 的字段必须有 `default`。
- `params.*.options`（enum）：运营在后台勾选 / 输入的**可用值**（界面给常用预设，也能自己输入），`default` 必须在其中。
- `params.*.type = number`：用户在画布上**拖动滑块**选择，范围是 `min`–`max`（运营自己填，后端要求 1 ≤ 最小 ≤ 默认 ≤ 最大 ≤ 3600，步长 ≥ 1），`step` 为步长，`default` 在范围内。**时长就是这种参数**，不再是点选。
- `params.*.spec`：`true` 表示可作为规格价格的条件维度。**enum**（清晰度 / 档位）和 **boolean**（生成音频开 / 关）可以设 `spec`；number（时长）不能——时长对价格的影响用「按秒计费」表达，而不是按区间分段。
- `params.*.fanout`：`true` 表示这个参数是「生成数量」：一次提交**拆成 N 个独立任务**（N = 参数的值），每个任务各自按单次价格冻结和结算，互不影响。一个模型至多一个 `fanout` 参数，且必须是 enum（取值是正整数）。
- **所有价格都是整数积分**（≥ 0，发布时当前计费方式下的价格必须 > 0）。
- `pricing.tiers[].when`：键可以是 `spec=true` 的参数名（enum 值必须在 `options` 里，boolean 取 `true` / `false`）、`op`（生成方式，必须在 `ops` 里）、`ref_video`（布尔：本次请求的参考素材里是否有视频，仅当 `refs.video.on` 时可用）。至少要有一个条件，否则无效。参考视频自己的时长**不单独计费**（已确认先不做），`ref_video` 只用来让「有参考视频」时的每秒单价不同。多个条件同时满足时取条件最多的一条，条件数相同取排在前面的——所以「4K + 有参考视频」这类组合要**显式写成一条两个条件的规格价格**，否则会落到先写的那条上。
- `pricing.billing`：`per_call` 任何 kind 都可以；`per_second` 要求有名为 `duration` 的 number 参数；`token` 仅 text（用 `token.in` / `token.out`），**video 不支持 `token`（本版不做）**。
- 文本模型的 `params` 可以为空：发散度、Top P 等采样参数不做（已确认）。
- `context`、`system`：仅 text。

### 6.2 能力的默认值与固定上下限（不依赖插件）

**不再让插件声明能力**（已确认）。插件协议只对接平台（请求怎么发、结果怎么取），不关心模型能做什么；模型的能力、可选值、素材数量、参数范围，都是运营在后台手动填。所以本设计**不改插件 `meta`，不升级 `newapi.js`**。

**新建时按 kind 预填默认值**（放在前端 `templates.ts`，运营可改；后端不依赖它）：

| kind | 预填内容（提案，均可改） |
|---|---|
| video | `ops` 文生 / 图生 / 全能参考；参考素材：图片 4 张 × 10 MB、音频 1 个 × 15 MB、视频 1 个 × 100 MB；参数：比例（Auto 等）、清晰度（720P / 1080P / 4K）、时长（5 – 10 秒滑块）、生成音频、生成数量（1 / 2 / 4）；按秒计费 |
| image | `ops` 文生图 / 图生图；参考素材：图片 4 张 × 10 MB；参数：比例、清晰度（1K / 2K / 4K）、生成数量；按次计费，按清晰度分档 |
| text | 上下文窗口 / 最大输出；没有生成参数；按 Token 计费 |

**后端固定上下限**（只拦手误，不代表某个平台的真实上限；数值参考影策，**是提案**）：

| 字段 | 允许范围 |
|---|---|
| `refs.<类型>.max` | 0 – 50 |
| `refs.<类型>.max_mb` | 1 – 500 |
| `prompt.max_length` | 1 – 1,000,000 |
| 时长 `duration`（number） | 1 ≤ 最小 ≤ 默认 ≤ 最大 ≤ 3600，步长 ≥ 1，`(默认 − 最小)` 是步长的整数倍 |
| enum 可选值个数 | 1 – 20；`fanout`（生成数量）的值为 1 – 8 的正整数 |
| `context.window` | 1 – 10,000,000 |
| `context.output` | 256 – 1,000,000，且小于 `context.window` |
| `tags` / `hint` / `vendor` | 见 §6.1 |
| 价格 | 整数，0 – 1,000,000 |

> 说明：运营填的能力和上游平台实际能力不一致时（比如填了 15 秒、平台只支持 10 秒），问题在**运行时**由上游报错暴露，测试模型（测试弹窗）就是用来在发布前发现这类问题的。这是放弃「插件声明上限」的代价，已由你确认接受。

### 6.4 画布端

**模型选择器**：行内容 = 厂商 logo + 名称 + 价格 + 标签 + 描述。无 `vendor` 时回退首字头像。

**节点版式**（参考用户给的 LiblibTV 视频节点 / 图片节点截图；这是用户提供的素材，不是我的外部调研）。从上到下三层：

1. **参考素材行**：当前生成方式能引用的素材类型，每种一个方块，角标显示「已连接 / 上限」。文生方式只显示一句「只用文字」。
2. **提示词区**：右下角 `0 / N`（N = `capabilities.prompt.max_length`）。
3. **底栏**（从左到右）：**模型**（厂商 logo + 名称 + 下拉）→ **生成方式**下拉（`ops` 多于一个时才显示）→ **参数摘要**按钮（如 `Auto · 720P · 5秒 · 🔊 · 1个`，点开是参数面板）→ **⚡ 积分** → **发送**（圆形箭头）。

**参数面板**（点参数摘要展开，在底栏下方；只渲染 `open=true` 的参数，按书写顺序）：

| 参数类型 | 控件 |
|---|---|
| enum `ratio`（比例） | 带比例图形的网格按钮 |
| 其他 enum（清晰度、生成数量） | 等宽分段按钮；只显示勾选后的 `options` |
| number（视频时长） | **滑块 + 数字输入框 + 单位**，滑块下标注「最短 / 最长」；拖动时积分实时变化 |
| boolean（生成音频） | 「开启 / 关闭」两个按钮 |

`open=false` 的参数不出现，由前端在提交时按 `default` 填入。

**生成方式切换**：切换后上方参考素材行跟着变化；已连线但新方式不允许的素材，**保留连线但标红提示「当前方式不使用」**，提交时忽略，不自动删连线；素材数量达到 `refs.<类型>.max` 后该口不再接受新连线。**全能参考不按类型过滤**，所有已开启的类型都能连。

**生成数量 N > 1：复制出 N 个一模一样的节点**（已确认）：点发送后，**像画布上「复制节点」一样**，当前节点保留，再复制出 N − 1 个副本，共 N 个节点（例：生成数量 3 → 画布上有 3 个一模一样的节点）。

| 复制什么 | 做法 |
|---|---|
| 节点内容 | 提示词、模型、生成方式、全部参数、手动选的参考素材（`prompt` / `model` / `params` / `paramAssets`）都原样复制；节点标题沿用建节点的编号规则（视频节点 2、视频节点 3 …） |
| 引用（上游连线） | 当前节点**所有进来的连线**都为每个副本各复制一份（同样的上游节点、同样的连接口），所以副本引用的文字 / 图片 / 音频 / 视频和原节点完全一样 |
| 不复制 | 生成结果（`src`、`assetId`、`text`、`status`、`error`、`taskId`）——副本从干净状态开始，等自己的任务回填；**出去的连线**（下游节点）也不复制，下游仍然只连原节点 |

**什么时候出现、失败怎么显示**（已确认）：

1. **点发送的瞬间**，N 个节点就已经在画布上了（不等服务端返回），都处于「提交中」。
2. 服务端按节点逐个返回结果：成功的节点记下自己的任务 id（`node.data.taskId`），进入「生成中」；失败的节点直接显示它自己的错误。
3. **失败的节点不删除**，和单个节点失败一样留在画布上，**报什么错就显示什么错**（「积分不足，无法生成」「并发已满」「上游返回…」等），用户改完可以重新生成。
4. **哪个节点失败，就哪个节点报错**，其余节点不受影响。两种失败都一样处理：**提交时就失败**（积分不够、并发已满、参数不合法…，这个任务没建出来，没冻结，不用退）；**任务执行中失败**（上游报错、超时，退还该任务自己的积分）。
5. 例：生成数量 4、余额只够 2 个 → 节点 1、2 正常生成，节点 3、4 显示「积分不足，无法生成」。

**这几件事我按默认做了，有异议告诉我**：

| 事情 | 默认做法 | 为什么 |
|---|---|---|
| 副本摆在哪 | 按「复制节点」的习惯，在原节点附近错开摆放，并自动避开重叠；副本创建后一起被选中，方便用户一次拖开 | 不是排成一列，也不是接在原节点右边的下游 |
| 原节点算不算 N 个里的一个 | 算。生成数量 3 = 原节点 + 2 个副本，共 3 个节点、3 个任务 | 节点和任务一一对应 |
| 防止重复扣费（幂等键） | 点一次发送生成一个 key；重试（网络抖动）复用同一个 key；N 个任务用「key + 序号」 | 网络抖动重发时，不会创建出 2N 个任务、扣两遍积分 |
| N 个结果会不会一样 | 每个任务带自己的随机种子（插件决定怎么传给上游） | 否则可能出 N 个一模一样的结果，「生成数量」就没意义了 |

**积分与发送**：底栏上的 ⚡ 数字由前端本地计价（§6.5），随清晰度、音频、时长、数量实时变化，是**所有任务合计**要冻结的积分；Token 计费显示 `≤N`（按估算 / 上限冻结）。点发送后，选了生成数量 N 就提交 N 个任务。

### 6.5 计价与扣费

**下发**：`GET /models?kind=` 返回 `vendor / tags / hint / capabilities / pricing`，其中 `pricing` **去掉 `cost`**，`capabilities` 去掉 `params`（固定参数）与 `system`（系统提示）。

**公式**（Go 与 TS 各实现一份，共用同一份测试向量，见 §8）：

```
选定规格 spec = { op, ref_video, <全部参数名>: 值 }   // 取用户当前选择，未开放的参数取 default
                                                      // ref_video = 参考素材里是否连了视频（且当前方式允许）

匹配规格价 tier：
  候选 = tiers 中 on=true 且 when 的每一项都等于 spec 对应值的条目
  取条件项最多的一条；条件项数相同取书写顺序靠前的；没有候选则为空
  （没有任何有效条件的规格价格视为无效：不参与匹配，且发布被待办拦住）

n = spec[fanout 参数] ?? 1                            // 生成数量；没有 fanout 参数则为 1

每个任务的积分 one：
  per_call:   one = tier ? tier.unit : pricing.unit                        // 整数
  per_second: rate = tier ? tier.unit : pricing.per_second
              one  = rate × duration                                    // duration 取用户拖动的整数秒
  token(文本): one = max(1, ceil( (in_est × in + max_out × out) / 1,000,000 ))
              in_est = 提示词字数 + 系统提示字数（保守按 1 字 = 1 Token）
              max_out = min(context.output, params.max_tokens 若有)
              // 只有这里会出现小数（Token 数 × 单价 ÷ 100 万），所以才需要 ceil

底栏显示 / 一次提交总共要冻结 = one × n        // 价格和时长都是整数，所以 one 本身就是整数
```

> 例（与演示一致）：视频按秒，1080P、开音频、5 秒 → 规格价格 `{1080P, audio}` 5 积分/秒 → one = 25；生成数量 4 → 一次提交 4 个任务，共冻结 100。


**生成数量 = 复制出 N 个节点 = N 个任务**（均已确认）：一次请求（带 `count` 与 `node_ids`）**按节点顺序逐个创建任务，每个任务各自一个事务、各冻结 `one` 积分**，任务 i 绑定第 i 个节点（原节点或它的副本）。某个任务创建失败（例如冻结到第 K 个时余额不够、并发已满）只让这个节点得到错误，**不回滚已经创建成功的任务**；响应按节点逐项返回「任务」或「错误」（见 §8.1）。每个任务有自己的 `frozen_credits`、状态、结果和积分流水；某一个失败、超时只退它自己的积分。

**冻结与结算**（每个任务各自执行）：

| 计费方式 | 下单冻结 | 完成时 | 失败时 |
|---|---|---|---|
| 按次 / 按秒 | `one` | settle：扣冻结额 | refund：全退 |
| Token（仅文本） | `one`（按 `max_out` 算的上限，即先冻结全额） | settle：按插件回传的 `usage` 算实际消耗 `ceil(usage.in × in + usage.out × out)`，**扣 `min(实际, 冻结额)`，差额退回**，写一笔 settle + 一笔 refund 流水（已确认） | refund：全额退回（已确认） | refund：全退 |

- 任务快照里同时存 `frozen_credits`（冻结额）与定价规则（来自模型 revision 快照），保证「运营中途调价不影响进行中的任务」。
- 实际用量超出冻结额时仍只扣冻结额（用户不被多扣；平台承担偏差）。
- 失败 / 超时 / 取消的退款路径不变。

**成本与利润率**：只用于管理端展示，不参与扣费，也不入快照给画布。

## 7. 状态与异常

| 场景 | 行为 |
|---|---|
| 弹窗加载中 | 保持现有「正在加载…」 |
| 草稿保存中 / 失败 | 沿用现有 `busy` 状态与错误 Notice；保存失败不丢本地编辑 |
| 发布前待办 | 沿用 `modelChecks`；新增检查项：至少一种生成方式、至少一个开放参数不强制；价格 > 0；规格价格条件合法；`open=false` 的参数有默认值 |
| 超出固定范围 | 控件上直接标红提示「允许范围 …」，同时作为 `issues`（`capabilities.refs.image.max` 等路径）出现在待办里，可点击定位 |
| 填的能力和上游平台实际不符 | 发布前后端查不出，运行时由上游报错；用「测试模型」在发布前发现 |
| 能力/渠道已保存后不可改 | 沿用现状；设计稿里「能力变更提醒」不需要 |
| 厂商 logo 加载失败 | 回退首字头像 |
| 配置版本冲突 | 沿用现有 revision 机制，本次不改 |
| 切换计费方式（按次↔按秒） | 规格价格的单位不同，**切换时清空全部规格价格**并提示 |
| 规格价格没有任何条件 | 不参与匹配，发布被待办拦住（否则它会盖掉默认价） |
| 规格价格条件失效（参数的可选值被取消勾选） | 该条规格价格标红「条件里的 1080p 已不可选」，发布被待办拦住；不自动删除 |
| 画布：方式切换后连线不再适用 | 保留连线、标红提示、提交时忽略 |
| 画布：价格不一致（前端算的 ≠ 后端冻结的） | 以后端为准；任务视图展示实际冻结额。出现时前端上报日志（暴露两份算法漂移） |
| 画布：积分不足 | 沿用 402 提示；按钮价格已提前展示 |
| 生成数量 N > 1：余额只够 K 个（K < N） | 前 K 个节点正常生成，其余节点各自显示「积分不足，无法生成」（没有冻结，不用退），节点保留；底栏积分已显示合计，提交前就能看到 |
| 生成数量 N > 1：其中某个任务失败 | 对应的那个节点显示失败，只退这个任务自己的积分，其余节点照常完成 |
| 生成数量 N > 1：请求本身就失败（未登录、参数不合法、模型已下线…） | N 个节点都显示这条错误，节点保留，用户改完重新生成 |
| 生成数量 N > 1：进行中任务数超限 | 沿用「进行中任务上限」，N 个任务各占一个名额，放不下的节点各自显示「并发已满」 |
| Token：插件没回传 usage | 按**冻结额**扣并记日志（默认做法，你没有特别说明；要改告诉我）。正常路径是已确认的「先冻结全额、按实际结算、失败全额退」 |
| 权限 | admin / super_admin 都能改模型（沿用）；成本价对两者可见，对 `user` 不可见 |

## 9. 方案取舍

### 9.1 决策矩阵

权重来自本次访谈暴露的优先级（用户选择了最完整的路径）：数据清晰度与一致性 > 与设计稿贴合 > 实现成本。

| 方案 | 数据清晰度 (0.4) | 贴合设计稿 (0.3) | 改动成本 (0.2，越小越高分) | 风险 (0.1，越低越高分) | 加权 |
|---|---|---|---|---|---|
| **B. capabilities 唯一来源 + 丢弃重建（采用）** | 5 | 5 | 2 | 3 | 4.2 |
| A. 扩展 input_schema + 补顶层字段 | 3 | 4 | 4 | 4 | 3.6 |
| C. 只用现有字段 | 2 | 1 | 5 | 5 | 2.6 |

> 评分是 1–5 的主观分，仅用于显式化取舍，不代表量化结论。

### 9.2 明确放弃的

- 向后兼容旧 `input_schema`（用户选择丢弃重建）。
- 首尾帧生成方式（用户明确本版不做）。
- 视频 Token 计费（Seedance 类；对照网关目录发现有一半视频模型这样计费，用户确认本版先不做）。
- 文本的发散度、Top P 等采样参数（用户确认不要）。
- 错峰折扣（`time_multipliers`）、缓存价、按提示词长度分层的 Token 价、按像素分层的图片价（对照网关目录看到了，本版都不做）。
- 把时长按区间分段做规格价格（时长用「按秒计费」表达，number 参数不能做规格价格维度）。
- 「提示词相关性」等不常用的专业参数（用户明确不要）。
- 运营上传自定义 logo（用户选择内置厂商 logo）。
- 前端防抖调报价接口（用户选择本地计算）。
- 插件声明模型能力（用户确认：插件只管对接平台，能力由运营手填）。
- 价格带小数 / 微积分（用户确认最小精度 1 积分）。
- 下单不冻结、完成后实际扣费的 Token 计费（会产生欠费）。

## 10. MVP 与分期

### 第一期 · 基本信息（+ 公共基础）

**范围**：`vendor`、`tags`、`hint` 上限；`bun add @lobehub/icons` 与 `vendors.ts`、`VendorAvatar`；选择器预览改版（logo、标签、价格）；画布模型下拉同步改版；新结构里**先只带 `vendor / tags / hint`**，`capabilities` 与 `pricing` 在第二、三期落地。

> 说明：因为决定了「丢弃重建」，第一期可以和第二期**同时切换到新正文结构**（`credits`、`input_schema` 暂时保留到各自被替换那一期）。第一期不删旧字段，只加新字段，不破坏当前系统。

**验收**：
1. 新建模型可选厂商、加 ≤ 5 个标签（超出被拒）、描述计数到 500 字截止。
2. 管理端预览与画布下拉都显示 logo 与标签；未选厂商显示首字头像；logo 加载失败回退。
3. `GET /models` 返回 `vendor`、`tags`；`go test` 与前端测试通过。

### 第二期 · 能力与参数结构化

**范围**：`capabilities`（ops、refs、prompt、params、context、system）；固定上下限校验与按 kind 的默认模板；管理端能力与参数页签重做；画布生成方式切换、素材约束、开放参数渲染；下单校验改读 `capabilities`；**此期删除 `input_schema`**，同时丢弃现有模型配置。

**验收**：
1. 新建视频模型：勾选三种方式、配图片/音频上限、设置时长的最小/最大/默认、勾选可用清晰度，全程不开 JSON；新建图片模型同理（1K/2K/4K）。
2. 配置超出固定范围（如参考图 99 张）时发布被拒，待办里点击可定位到对应控件。
3. 画布：底栏是「模型 / 生成方式 / 参数摘要 / 积分 / 发送」；切换方式更新参考素材行（全能参考不按类型过滤），素材数量到上限后不能再连；时长是可拖动滑块（范围 = 配置的最小–最大）；`open=false` 的参数不出现在参数面板，且提交时用默认值。
4. 文本模型：上下文与系统提示可配置，系统提示不出现在 `GET /models`。

### 第三期 · 积分定价

**范围**：`pricing`；`Quote` 与前端同算法及共用向量；按次 / 按秒 / 规格价格（含音频、有无参考视频、生成方式条件）先上线；**生成数量 = 复制出 N 个节点 + N 个任务**；成本与利润率；文本 Token 计费与 `usage` 回传、`frozen_credits`、多退少补；**此期删除 `credits`**。

**验收**：
1. 画布底栏积分与任务实际冻结额逐笔一致（向量测试 + 一次端到端），覆盖：按秒 × 清晰度 × 音频开关 × 时长 × 生成数量，按次 × 档位 × 数量，并覆盖「先取整再乘 N」的边界（小数价格）。
2. 规格价格并列时取条件最多者；条件失效时发布被拦。
3. `GET /models` 不含任何 `cost` 字段（有测试断言）。
4. 文本 Token 任务：完成后扣 `min(实际, 冻结)`，差额以 refund 流水退回；失败全退；缺 `usage` 按全额扣并有日志。
5. 生成数量 4：画布上有 4 个一模一样的节点（提示词、模型、参数、上游连线都相同，结果不复制），一次提交创建 4 个任务、各冻结一次、各绑定一个节点；点发送的瞬间 4 个节点就都在画布上（提交中）；余额只够 2 个时，节点 1、2 正常生成，节点 3、4 显示「积分不足，无法生成」且保留；其中 1 个任务执行失败，只有对应节点显示它自己的错误、只退它自己的积分，节点不删除。
6. 运营中途调价，不影响进行中任务的冻结额（快照）。
