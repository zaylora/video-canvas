一次排查怎么走

四个节点用用户名和任务编号串起来，不需要离开后台。

用户反馈「我的视频一直没出来」
用户 › 使用记录搜用户名，看他最近任务，打开失败的那条

日志管理 › 操作审计需要时看是否有人改过渠道 / 配置
设计：以排查路径而不是以数据表来分页——用户不关心有几张表，只关心「谁、什么时候、出了什么事」。任务编号 task_ref 本来就在界面和日志里（task_id），所以不需要新增关联字段。
没有新数据时（老任务）：日志功能上线前的任务没有状态时间线和上游错误，抽屉里明确写「创建于日志功能上线前，没有记录」，其余字段（基础信息、输入、产物、积分）照常显示。

当运营收到「我的视频没出来」时，会发生什么

这是最主要的使用路径，一分钟内要能给用户一个交代。

  1. 在「用户 › 使用记录」搜用户名默认近 7 天；顶部摘要条立刻显示他的总数 / 成功 / 失败 / 实扣积分
  2. 点失败的那一行，右侧抽屉滑出列表和筛选条件保持原样，关掉抽屉就回到刚才的位置
  3. 看「失败原因」和「状态时间线」用户文案、错误码、上游错误原文；时间线看到在哪一步停下
  4. 看「积分」块确认已退款freeze / settle / refund 流水一目了然，直接回复用户
边界：时间线和上游错误只对「上线之后」的任务有效
  • 老任务只能看到基础信息、输入、产物和积分。
  • 上游错误和提示词都是原文：不脱敏、不截成摘要（只遮渠道 Key，另有 16KB 大小上限）。不记录「发给上游的实际请求 / 响应」，这块已按你的意见撤掉。
  • 抽屉不带 URL 参数：不能把「这一条任务」的链接发给同事，只能发任务编号让对方搜索。
  • admin 与 super_admin 都能看到用户的提示词和上游错误，且不记「谁看过」的审计（这是你的选择，见「数据与接口」页末）。
  • 没有系统日志页：系统报错只在服务器控制台，后台看不到（你已撤回这一块）。

交付时需要提前告知运营：老任务查不到时间线是正常的，不是 bug。

状态迁移与事件写入规则

哪些迁移会产生事件，写入失败怎么办。

迁移事件备注
（创建）→ pendingcreated在 Create 的事务内写
pending → queued / runningsubmitted表示上游已受理
queued → running不记对运营没有判断价值，且是轮询得来的，噪声大
running → finalizingfinalizing平台已出片，正在转存
→ succeededsucceeded与积分结算同一事务（finish）
→ failedfailed带 class / code / upstream
→ canceled / expiredcanceled / expired带 reason（user_cancel / deadline）
进度变化（状态不变）不记避免噪声

事件与状态迁移同一事务：事件写失败则迁移整体失败并重试，因为事件是时间线的唯一来源。目前 transit 不开事务，需要改为 WithTx。

接口（全部 GET，RequireAdmin，admin 与 super_admin 同权）

响应沿用 {code, data, msg}；游标分页沿用 {items, next_cursor}；limit 默认 20，最大 100；from/to 为 RFC3339。

方法与路径参数返回业务错误
GET /admin/usageq（≤64；32 位十六进制按 task_ref 精确，否则用户名 / 邮箱 ILIKE）、user_id、status（all / active / succeeded / failed / canceled / expired）、kind、model、from/to（默认近 7 天，最大跨度 90 天）、include_test（默认 false）、cursor、limititems:[{id, task_ref, user:{id,username}, kind, model_key, model_name, status, credits, charged_credits, error_code, error_message, duration_ms, created_at}]ErrInvalidParams：游标 / 时间 / 状态不合法，跨度 > 90 天
GET /admin/usage/summary同上筛选，无分页{total, succeeded, failed, canceled, expired, active, charged_credits}同上
GET /admin/usage/:ref路径 ref：先查 task_ref 唯一索引，找不到再试 idcodec.Decode{task, user, input, outputs, error:{code,message,upstream}, events:[…], ledger:[…], trace?}（trace 仅试跑，沿用现有 trace_json）；老任务 events=[]、error.upstream=nullErrTaskNotFound（40004，已存在）
GET /admin/logs/auditsactor（用户名或 id）、module、action、from/to（默认近 30 天）、cursor、limititems:[{source:"admin|ai", id, actor_id, actor_name, action, target_type, target_ref, target_name, summary, detail_json, created_at}]ErrInvalidParams
两个实现要点
  • 审计游标：两张表主键空间不同，游标 = base64url(<unix_micro>:<source>:<id>)，排序键 (created_at DESC, source, id DESC)；UNION ALL 各取 limit+1 再合并裁剪。
  • 全站按状态 / 模型过滤没有组合索引，靠时间范围收窄走 idx_task_created。近 7 天内应够用，未验证 · 需在有量数据上实测；慢了二期补 (status, created_at)。

核心流程伪代码

一处新逻辑：任务事件随状态迁移写入，失败原因带上游错误原文。

// service/generation_task_store.go —— finish 内（提案）
tx.WithTx(func(tx) error {
    t := tx.UpdateIf(id, from, fields, bump=true)           // CAS 迁移
    tx.InsertEvent(Event{TaskID: t.ID, Event: target,
        From: oldStatus, To: target, Detail: detailOf(extra)}) // 同一事务
    if !t.IsTest { settleLedger(tx, t, target) }
    return nil
})

// worker_errors.go —— fail（提案）
detail := {class: f.class, code: f.code,
           upstream: truncate(f.raw, 16*1024)}               // 原文；渠道 Key 已由宿主在构造 f.raw 时遮掉
finish(ctx, t.ID, active, TaskFailed, {event_detail: detail})
设计：任务事件和状态迁移同一事务——时间线是事件的唯一来源，不允许状态变了事件没有。这与审计「写失败不回滚业务」的取舍不同，因为这里的事件是业务数据，不是旁路日志。

已确认的决定

  1. 入口：「使用记录」放进「用户」分组，「操作审计」放进新的一级菜单「日志管理」。先选的是「一个日志菜单 + 标签页」，评审时改为现在的结构；因此没有标签页。主文档已回写。
  2. 「生成记录 / 生成任务」统一改名「使用记录」，含用户详情抽屉里原有的「生成记录」页签（默认值，要改告诉我）。
  3. 任务详情含：基础信息 + 状态时间线 + 上游错误原文。因此新增 generation_task_events；只对新任务生效。
  4. 上游错误不需要脱敏（评审时更正）。追问渠道 API Key 时选择「只遮住 Key，其余全量原文」：上游错误、提示词原样保存和展示；渠道 Key 仍然只写不读。此项与后端规范 E9 冲突，实现时要补一条后台日志接口的例外。主文档已回写。
  5. 不要「发给上游的实际请求 / 响应」这一块（评审时撤回）。本期不新增请求追踪表，也不让所有任务开追踪；试跑任务的追踪保持现状。主文档已回写。
  6. 不要「系统日志」（评审时撤回）。不做系统日志页，也不做日志入库、日志表和任务 ↔ 日志互跳；系统报错仍只在服务器控制台。主文档已回写，思路留在「已搁置」。
  7. admin 与 super_admin 都能看全部。含提示词和上游错误；渠道 Key 永不展示。
  8. 使用记录默认是全站任务流水 + 用户筛选。
  9. 详情用右侧抽屉，不带 URL 参数。你先选了独立详情页，随后更正为抽屉；独立页和可分享链接已搁置。主文档已回写。
  10. 一期两个入口全做，任务事件只记新任务；不做日志量直方图和导出。
