# 后台使用记录与日志管理

> **范围**：后台新增两处入口：（1）**用户分组下的二级菜单「使用记录」**——按人、按条件查看全站生成任务并打开详情（原名「生成任务」）；（2）**一级菜单「日志管理」下的二级菜单「操作审计」**——浏览后台操作审计。（原本还有「系统日志」，评审时撤回，见 §11。）
> **日期 / 状态**：2026-10-18 · 设计中（访谈已完成，等待用户评审后实现）。
> **证据约定**：**事实**附文件路径或来源链接；**推断**是基于事实的判断；**提案**是尚未实现的设计。没有标注的描述性句子均指现状。
> **方案演进**：（1）访谈中详情形式曾选「独立详情页」，随即改为「**右侧抽屉，不带 URL 参数**」，以后者为准；（2）任务详情深度原选「基础 + 时间线 + 脱敏截断的上游错误摘要」，评审阶段用户先更正为「不需要脱敏，要看到发给上游的实际请求内容」，随后**撤回了「实际请求追踪」这一块**，最终保留「**上游错误不脱敏（只遮渠道 Key）**」；（3）原有的第三个标签页「系统日志」（Warn / Error 入库）评审时也被**撤回**，一期只有「生成任务」「操作审计」两个标签页（见 §11）。（4）入口结构最后定为：**「使用记录」放进「用户」分组、「操作审计」放进新的一级菜单「日志管理」**，不再是「一个日志菜单 + 标签页」，也就没有标签页了。

## 1. 设计摘要

- **问题**：运营想知道「某个用户都生成了什么、为什么失败」，运维想知道「谁改了配置」。现在这些数据一部分在库里但没有入口（审计），一部分只在服务器控制台（上游原始错误），一部分只能在单个用户的抽屉里翻（「生成记录」，且没有详情）。
- **目标**：两个入口分别回答两个问题：**谁用了什么、结果如何**（用户 › 使用记录）；**谁改了什么**（日志管理 › 操作审计）。并且能用任务编号和用户快速定位，把一次失败从用户现象查到上游原因。
- **推荐结论**（均已由用户在访谈中确认，见 §11）：
  1. 侧栏「用户」分组新增二级菜单**「使用记录」**（`/admin/usage`）；新增一级菜单**「日志管理」**，里面是二级菜单**「操作审计」**（`/admin/logs/audits`）。
  2. 使用记录默认展示**全站任务流水**，用户只是筛选条件之一；用户详情抽屉里原来的「生成记录」页签同步改名为「使用记录」。
  3. 任务详情含：基础信息、输入、产物、积分流水、**状态时间线**、**上游错误原文**（不脱敏，只遮渠道 Key）。
  4. `admin`、`super_admin` 都能看全部内容；所有接口只读。
  5. 详情用**右侧抽屉**，不带 URL 参数。
  6. 一期两个入口全做；任务时间线和上游错误原文**只对上线后的新任务生效**；不做图表和导出。

### 2.2 设计约束

- **C1**：渠道 Key 在系统里**只写不读**，必须保持：任何落库内容和接口响应里都不得出现 Key 明文（URL 转义、JSON 转义形式同样）。除 Key 外，上游错误原文、提示词按**原文**保存和展示（用户 2026-10-18 确认），不做内容脱敏。此项与规范 E9「平台返回的原始错误信息不得出现在返回前端的响应里」有冲突：本功能的接口只对后台 admin / super_admin 开放，实现时需在 [02-错误处理与日志.md](../../../backend/docs/standards/02-错误处理与日志.md) 的 E9 里补一条后台日志接口的例外。
- **C2**：审计表只增不改不删，浏览功能只能读（F11）。
- **C3**：后台组件各自维护，新行为放 `admin-ui`，**不改共享的 `components/ui`**（用户记忆，2026-10-05）。所以抽屉要在 `admin-ui` 新增同 API 的 `sheet.tsx`。
- **C4**：分页沿用其他后台列表的页码分页（`page` / `page_size`，响应 `{list,total,page,page_size}`，前端 `DataPanelPagination`）；用户详情抽屉里的三个游标列表（F17）不改。审计要合并两张表，靠 `UNION ALL` + 稳定排序实现（见 §8.3）。
- **C5**：任务事件必须与状态迁移同事务写入（时间线的唯一来源）；审计写入沿用现有取舍：失败不回滚业务（见 `adminAudit` 注释）。
- **C6**：任务表已有 `created_at` 单列索引，但**没有**「状态 / 模型 + 时间」的组合索引（F5）；全站按状态过滤依赖时间范围收窄。

### 2.3 当前缺口

1. 没有跨用户的任务视图；没有任务详情（F2、F3）。
2. 任务没有「状态变化时间线」：只知道 `created_at / submitted_at / finished_at` 三个时刻，中间卡在哪看不出（F6）。
3. 失败原因只有用户文案，真正的上游原因在控制台里（F8）。
4. 审计写了没人看（F12）。
5. 系统日志只在控制台 / 文件，后台看不到（F14）。**本期不做**（用户评审时撤回）。

## 3. 用户与场景

| 角色 | 典型触发 | 主任务 | 成功标准 |
| --- | --- | --- | --- |
| 运营（admin） | 用户反馈「我的视频一直生成不出来 / 扣了积分没结果」 | 搜用户 → 看他最近的任务 → 打开失败任务 → 看状态走到哪、积分有没有退 | 1 分钟内回复用户原因，不用找开发 |
| 运营 | 巡检「今天哪个模型失败最多」 | 全站任务 → 筛状态=失败、时间=今天 → 看 error_code 分布 | 不依赖运维就能定位到模型 / 渠道 |
| 运维（super_admin） | 怀疑某渠道异常 | 使用记录筛该模型的失败任务 → 看上游错误原文；操作审计看最近是否有人改过渠道 | 能区分是插件、渠道还是用户参数问题 |
| 运维 | 「谁把这个渠道停了」 | 操作审计 → 按操作人 / 操作类型筛 | 看到操作人、时间和前后值 |

**推断**：运营和运维是同一批少量后台账号，使用频率是「有问题才开」，不是每天盯。所以首屏要能直接给出结论（状态、原因），而不是让人先配筛选条件。

## 5. 设计原则

1. **以排查路径组织，而不是以表组织**：「使用记录」回答谁生成了什么、「操作审计」回答谁改了什么，页内用任务编号和用户名串起来。（来自场景 §3）
2. **默认就给结论**：列表第一屏的状态、错误文案、耗时、积分已经能回答大多数问题；详情抽屉解决剩下的。（Replicate 的单对象思路）
3. **Key 永不落库，其余按原文**：渠道 Key 在写入前由宿主替换成 `***`，其余内容（上游错误、提示词）原样保存，因为排查需要看到上游真正说了什么。有大小上限只为保护存储，不是脱敏。（C1，用户确认）
4. **事件写入与状态迁移同事务**：任务事件是时间线的唯一来源，状态变了事件就必须有；写失败整体回滚重试，不留「有状态没事件」的任务。（C5）
5. **只读**：本期所有接口都是 GET，没有任何修改日志的入口。（C2）
6. **不假装有历史**：上线前的任务没有时间线，就明确写「无时间线」，不编造。

### 6.2 使用记录（用户 › 使用记录）

**列表**（每行一个任务，按 id 倒序，页码分页，每页 20，可选 10 / 20 / 30 / 40 / 50，页码、搜索和筛选放进 URL，刷新不丢；详情抽屉不进 URL）：

| 列 | 内容 |
| --- | --- |
| 任务编号 | `task_ref` 前 8 位 + 复制按钮（沿用现有 `task-id-tag` 的样式思路） |
| 用户 | 用户名；点击 = 把该用户加入筛选 |
| 类型 / 模型 | 类型图标 + 模型展示名（快照里的 label，回落 model key） |
| 状态 | 状态点 + 文案（进行中 / 成功 / 失败 / 已取消 / 已超时） |
| 积分 | 冻结 → 实扣（如 `20 → 20`；失败显示 `20 → 0`） |
| 耗时 | `finished_at - created_at`；进行中显示「已 2m10s」 |
| 创建时间 | 相对时间 + 悬停绝对时间 |

**筛选条**（顶部）：用户（输入用户名 / 邮箱 / 任务编号一个搜索框，见下）、状态（全部 / 进行中 / 成功 / 失败 / 已取消 / 已超时）、类型（视频 / 图片 / 音频 / 文本）、模型（下拉，来自 `GET /admin/ai/models/options`，已存在）、时间范围（默认 **近 7 天**，可选今天 / 近 24 小时 / 近 7 天 / 近 30 天 / 自定义）、「包含试跑任务」开关（默认关）。

**搜索框规则**：输入 32 位十六进制 → 按 `task_ref` 精确找；否则按用户名 / 邮箱模糊（ILIKE）匹配用户后筛该用户的任务。

**摘要条**（列表上方一行）：当前筛选下的 总数 · 成功 · 失败（含超时、取消）· 进行中 · 实扣积分合计。选了某个用户时这一行就是「他的任务概况」。摘要由单独接口按同一组筛选条件做一次分组统计得到（§8.3）。

**行点击** → 右侧抽屉。

**任务详情抽屉**（宽约 560px，自上而下）：

1. **头部**：任务编号（完整，可复制）、状态标签、用户（用户名 · id）。
2. **基础信息**：类型、模型（展示名 + key）、渠道 key、插件 key@版本、画布 id、节点 id、创建 / 提交 / 完成时间、排队时间（`submitted_at - created_at`）、执行时间（`finished_at - submitted_at`）、截止时间、是否试跑。
3. **失败原因**（仅失败 / 超时 / 取消）：用户文案（`error_message`）+ 统一错误码；其下是**上游错误原文**（折叠代码块，原样，上限 16KB，仅 Key 被遮）。老任务显示「此任务创建于日志功能上线前，没有上游错误记录」。
4. **状态时间线**：每个状态变化一行（时间、从 → 到、距上一步耗时、备注）。老任务显示「无时间线」。
5. **输入参数**：`input_json` 的格式化展示（提示词、参考素材、尺寸、时长等），长文本折叠。
6. **产物**（实现后按评审意见改为真正渲染，见 §11 已确认 13）：图片显示缩略图（点击在新标签页开原图）；视频显示可播放的 `<video controls>`（首帧当封面）；音频显示 `<audio controls>`；文本直接显示正文。没有访问地址（素材已被清理等）时退回图标卡片并写明原因。尺寸 / 时长和素材编号留在下方小字。
7. **积分**：冻结额、实扣、该任务的 freeze / settle / refund 流水（来自 `credit_ledger`，F10）。
8. **试跑追踪**（仅 `is_test`）：沿用 `trace_json`，用现有 `pages/admin/ai/trace` 组件展示。

## 7. 状态与异常

- **保存 / 冲突 / 撤销**：本功能全部只读，没有保存、revision 冲突和撤销问题。
- **任务事件写失败**：事件和状态迁移**同一事务**，写失败则迁移整体失败并重试（事件是时间线的唯一来源，不允许状态变了事件没有）。
- **用户被删 / 改名**：列表里用户显示取当前用户名；用户不存在显示「已删除用户 #id」（**推断**：现有系统没有硬删用户入口，属防御性处理，待实现时核实）。
- **权限**：admin 与 super_admin 同权（F18）。所有 `/admin/usage/*` 与 `/admin/logs/*` 都是 GET，挂 `RequireAdmin`。

`detail_json` 约定（均可选，**提案**）：

### 8.2 写入路径

1. **任务事件**：在 `Create`、`transit`、`finish`（F9）里，状态真正变化时于**同一事务**插入一行事件。`transit` 目前不开事务，需要改成 `WithTx`。进度类 `bumpVersion` 变化（状态不变）和 `queued → running`（轮询得来，对运营无判断价值）**不记事件**，避免噪声。
2. **上游错误原文**：`worker.fail` 已拿到 `failure.raw`（F8），现在只写日志。改为同时经 `finish` 的 `extra` 通道写入 `failed` 事件的 `detail_json.upstream`：**原文，上限 16KB（只为保护存储），仅渠道 Key 被遮**。Key 由宿主构造 `failure.raw` 时用现有 `redactor` 遮掉（F7a），worker 不另做脱敏。**不新增任务表字段，也不新增追踪表**：本期**不记录发给上游的请求 / 响应**（用户评审后撤回，见 §11）。

### 8.3 新增接口（全部 GET，`RequireAdmin`）

响应沿用统一包装 `{code, data, msg}`；页码分页沿用其他后台列表：请求 `page`（从 1 起）、`page_size`（缺省 20，最大 100），响应 `{list, total, page, page_size}`（`pkg/pagination`）；id 字段为数字，`task_ref` 为 32 位十六进制。

| 方法与路径 | 说明 | 业务错误 |
| --- | --- | --- |
| `GET /admin/usage` | 任务流水。参数：`q`（≤64）、`user_id`、`status`（`all|active|succeeded|failed|canceled|expired`，其中 `failed` 不含取消与超时，与摘要口径一致见下）、`kind`、`model`、`from`/`to`（RFC3339，默认近 7 天，跨度最大 90 天）、`include_test`（默认 false）、`page`、`page_size`。返回 `list:[{id, task_ref, user:{id,username}, kind, model_key, model_name, status, credits, charged_credits, error_code, error_message, duration_ms, created_at}]` | `ErrInvalidParams`（时间 / 状态不合法、跨度过大） |
| `GET /admin/usage/summary` | 与上同一组筛选参数（无分页），返回 `{total, succeeded, failed, canceled, expired, active, charged_credits}` | 同上 |
| `GET /admin/usage/:ref` | 任务详情：`{ task: {…基础信息…}, user, input, outputs, error:{code, message, upstream}, events:[…], ledger:[…], trace? }`；`ref` 先查 `task_ref` 唯一索引，找不到再尝试 `idcodec.Decode` | `ErrTaskNotFound`（40004，已存在） |
| `GET /admin/logs/audits` | 合并审计。参数：`actor`（用户名或 id）、`module`、`action`、`from`/`to`（默认近 30 天）、`page`、`page_size`。返回 `list:[{source:"admin|ai", id, actor_id, actor_name, action, target_type, target_ref, target_name, summary, detail_json, created_at}]` | `ErrInvalidParams` |

**状态口径**：沿用用户详情的映射习惯（F2 契约）但在这里**分开展示**：摘要里 `failed`、`canceled`、`expired` 分别计数；列表筛选 `failed` 只含 `failed`，另有 `canceled`、`expired` 可选。（用户抽屉里「失败」含取消和超时，是用户抽屉自己的约定，不改。）

**审计排序与分页**：两张表主键空间不同，排序键取 `(created_at DESC, source DESC, id DESC)`，保证两张表交错时翻页顺序稳定、不重复、不遗漏；实现是 `UNION ALL` 子查询加 `OFFSET / LIMIT`，总数用同一份条件 `COUNT`，**不建物化视图**。

**索引评估（C6）**：`GET /admin/usage` 无 `user_id` 时依赖 `idx_task_created` 在时间范围内扫描再过滤状态 / 模型。默认近 7 天范围内可接受（**推断**，需在有量数据上实测）。如实测慢，二期补 `(status, created_at)` 或 `(model_id, created_at)` 索引。**未验证**。

## 9. 方案取舍

### 9.1 决策矩阵

权重来自用户确认的优先级：**能查全站、能看清失败原因、不增加运维负担**（访谈 Q1–Q3）。

| 方案 | 覆盖「按人 + 全站」(30%) | 看清失败原因 (30%) | 不增加运维 (25%) | 实现成本低 (15%) | 加权 |
| --- | --- | --- | --- | --- | --- |
| **A. 使用记录（用户下）+ 操作审计（日志管理下）+ 抽屉（采用）** | 5 | 4 | 5 | 4 | **4.55** |
| B. 只增强用户抽屉 | 3 | 2 | 5 | 5 | 3.5 |
| C. 任务与审计合进一个「日志」菜单的标签页（访谈中曾选，后改） | 5 | 4 | 5 | 3 | 4.4 |
| D. 接 Loki/Grafana | 2 | 5 | 1 | 2 | 2.65 |

（5 分最好。分数为设计判断，**不是实测**。）

### 9.2 明确放弃

- 独立详情页、URL 参数 / 可分享链接（用户选了抽屉且不带 URL）。代价：不能把「这条任务」的链接发给同事，只能发任务编号让对方搜索。
- 外部日志平台。代价：没有强大的查询语言和长期留存。
- 系统日志入库（用户评审时整块撤回，含 Info 级和每个 HTTP 请求入库的想法）。
- 发给上游的实际请求 / 响应追踪（评审时曾要求，随后撤回）：若将来重提，可选的思路是——所有任务开 `provider.Trace`、每次处理落一行、连续相同的轮询折叠、单个请求 / 响应体 64KB 与单任务 1MB 上限、30 天保留；宿主 `redactor` 已只遮渠道 Key（F7a）。
- 日志量直方图、CSV 导出（二期）。
- 查看提示词不加遮罩也不记查看审计（用户确认两角色看全部）。

### 已确认（用户在访谈中的回答）

1. **入口结构（评审时调整）**：「使用记录」是「用户」分组下的二级菜单；「日志管理」是一级菜单，里面是二级菜单「操作审计」。原先「一个日志菜单 + 标签页」的方案废弃。
2. **任务详情深度**：基础 + 状态时间线 + 上游错误原文（需新增 `generation_task_events`）。原选「脱敏截断的摘要」，评审时更正为不脱敏（第 8 条）。
3. **（已撤回）系统日志来源**：原选 Warn / Error 级日志入库，评审时撤回，见第 10 条。
4. **权限与隐私**：admin 与 super_admin 都能看全部（含提示词、上游错误）。
5. **任务默认视角**：全站任务流水 + 用户筛选。
6. **详情形式**：右侧抽屉，**不带 URL 参数**（先选了独立详情页，后更正为此）。
7. **MVP 范围**：使用记录与操作审计两个入口全做，任务事件只记新任务；不做图表和导出。
8. **（评审时更正）上游错误不需要脱敏**；追问「渠道 API Key 怎么处理」时选择**只遮住 Key，其余全量原文**（上游错误、提示词、参数、日志字段原样保存与展示）。
9. **（评审时撤回）不要「发给上游的实际请求 / 响应」这一块**：本期不新增请求追踪表，也不让所有任务开追踪；试跑任务的追踪保持现状。
10. **（评审时撤回）不要「系统日志」**：不做第三个标签页，也不做 zap 日志入库、`system_logs` 表、日志清理器和任务 ↔ 日志的互相跳转。
11. **（评审时调整）「生成记录 / 生成任务」改名为「使用记录」，放进「用户」分组**；审计单独放在一级菜单「日志管理」里。
12. **（实现后评审）使用记录与操作审计要做页码分页**，参照其他后台页面：接口改成 `page` / `page_size`，响应 `{list,total,page,page_size}`，前端用 `DataPanelPagination`，页码 / 搜索 / 筛选进 URL（详情抽屉仍不进 URL）。原先实现的是游标分页 +「加载更多」，已替换。
13. **（实现后评审）任务详情里的产物要渲染出来**，不能只显示图标和素材编号。

### 已搁置的决定

- **发给上游的请求 / 响应追踪**：见 §9.2 末项，用户评审时撤回。
- **系统日志（Warn / Error 入库）**：用户评审时撤回。若将来重提，思路是——给 zap 加一个异步批量写库的 core（`>= Warn`，满则丢、失败只写 stderr），表含 level / message / caller / request_id / task_ref / user_id / fields_json / stack / instance，保留 30 天，访问日志中 4xx 不入库，并在任务抽屉与日志页之间按 `task_ref` 互跳。
- 独立详情页与可分享链接：将来若需要，抽屉内容组件可原样搬进页面，路由上加 `?task=`。
- 提示词查看审计 / 遮罩：用户选「都能看全部」后搁置。
- Info 级入库：见 §9.2。
