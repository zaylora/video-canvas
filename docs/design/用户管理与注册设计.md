# 用户管理与注册设计

> 设计面:导航与信息架构(后台管理)+ 登录注册流程。
> 状态:设计稿,尚未实现。访问日期统一为 2026-10-04。

## 1. 设计摘要

**问题**:管理后台只管 AI 配置和系统设置,没有任何"人"的管理;登录页没有注册入口。运营无法控制单个用户的并发、积分和账号状态,也没法让新用户自助加入。

**目标**:

1. 登录页提供注册(用户名 + 密码 + 邮箱验证码),可由后台开关关闭。
2. 后台新增「用户管理」:积分调整与流水、单用户并发上限、封禁/启用、角色调整、重置密码、操作审计。
3. 首个注册账号自动成为 `super_admin`,免去用 SQL 提升。

**推荐结论**:列表 + 弹窗详情;封禁在鉴权层实时生效;积分调整复用现有账户行锁与流水表(扩展 type,放宽 `task_id`);注册走"先验证邮箱再建号",**SMTP 在后台「邮件服务」页配置并加密存储**(复用存储配置的"密钥只写不读"做法)。

### 2.2 设计约束

- 积分的冻结/结算必须与管理员调整互斥:调整必须在 `LockCredit` 行锁事务内做,否则会与任务结算并发丢更新。
- 封禁要"即时",所以不能只靠 JWT 过期(默认 72 小时)。
- 项目没有邮件发送能力,邮箱验证意味着新增 SMTP 依赖;已确认 SMTP 由后台配置,密码需加密存储,加密主密钥沿用 `APP_AI_SECRET_KEY`。
- **引导问题**:后台要超管才能进,超管要靠注册产生,而注册要邮件。现在没启用邮件服务就不验证,所以首个账号无需先配 SMTP 就能建出来(见 6.1)。
- 后端分层必须遵守 `router → middleware → handler → service → repository`;新增测试放 `backend/internal/tests/`、`web/src/tests/`。

### 2.3 当前缺口

1. 注册:前端缺失;后端缺邮箱、验证码、开关、首个超管逻辑。
2. 用户:缺状态、单用户并发覆盖、邮箱唯一约束、最近登录时间。
3. 积分:缺管理员调整入口与可追溯流水。
4. 安全:`/users` 列表对所有登录用户开放(现有缺口,本方案顺带收口)。
5. 审计:缺用户类审计动作。

## 3. 用户与场景

- **运营 admin**:查用户、看积分、调整积分、封禁。
- **运维 super_admin**:额外调整角色、重置密码、改注册开关。
- **新用户**:自助注册后立即进入画布使用赠送积分。
- **成功指标**(提案):新用户从打开登录页到进入首页不超过 90 秒(含收验证码);运营处理一次"加积分"不超过 3 次点击;封禁后该用户下一个请求即被拒。

## 5. 设计原则

1. **积分只经一条路径改**:所有余额变化(任务冻结、结算、退款、管理员调整)都在 `LockCredit` 行锁内,并写流水。
2. **封禁即时生效**:状态在鉴权层查,不等 token 过期。
3. **能自助的不找管理员**:注册、首个超管都不再依赖 SQL。
4. **危险操作留痕**:积分调整、封禁、改角色、重置密码都写审计,调整积分必须填备注。
5. **复用优先**:沿用现有角色模型、审计表、`admin-ui` 组件和 `NewCachedRoleLookup` 的缓存做法。

## 6. 推荐方案

### 6.1 注册流程(登录页)

```
登录页 ── 底部「没有账号?注册」 ──▶ 同页切换为注册表单(登录/注册 Tab,同一左侧品牌区)
注册表单: 用户名 / 邮箱 / 验证码[发送] / 密码 / 确认密码
  1. 填邮箱 → 点发送 → POST /auth/register/code (限频:同邮箱 60s 一次,同 IP 每小时 N 次)
  2. 填 6 位码(10 分钟有效,错误 5 次作废)→ 提交 POST /auth/register
  3. 服务端事务内:校验码 → 查用户名/邮箱唯一 → 判断 users 表是否为空 → 建号(为空则 role=super_admin)
  4. 成功后直接返回 token,自动登录进首页
```

- 注册关闭时:登录页不显示入口;`GET /auth/config` 返回 `{register_enabled, email_verify_required}` 供前端判断;接口返回业务错误"注册已关闭"。
- **邮件服务未启用时(2026-10-05 调整)**:是否验证邮箱完全由后台「邮件服务」页的启用开关决定。未启用时,注册表单隐藏验证码,只填用户名、邮箱、密码(邮箱仍必填,但不验证、不写 `email_verified_at`),**任何人**都可注册,表为空时第一个账号成为 `super_admin`;启用后,除首个账号外都要填邮件验证码。原方案是"表非空且未配 SMTP 时关闭注册",已废弃。风险:没配邮件服务时没有任何防刷号手段,建议先配好邮件服务再对外开放,或关闭「开放注册」。
- 首个账号的免验证注册有被抢注的窗口(部署后到你注册之前)。这与"表为空即超管"的原有风险同源,建议部署后第一时间自己注册;MVP 不加额外保护。
- 首个超管:在注册事务内用 `SELECT count(*) FROM users` 判空(配合表级锁或唯一约束兜底),**仅表为空时生效**,已部署环境不受影响,仍用 SQL 提升。
- 邮箱:新增 `email` 唯一索引。**老用户 email 为空串,需迁移为 NULL 或用部分唯一索引(`WHERE email <> ''`)**,避免违反唯一约束。

| 管控 | 单用户并发上限(留空=使用全局默认,显示当前默认值);封禁/启用;角色(仅 super_admin 可见可改);重置密码(仅 super_admin) |

**权限分层**(沿用现有模型):

| 操作                                | admin | super_admin |
| ----------------------------------- | ----- | ----------- |
| 查看列表/详情/流水                  | ✅    | ✅          |
| 调整积分、改并发、封禁/启用普通用户 | ✅    | ✅          |
| 封禁/改动其他 admin 或 super_admin  | ❌    | ✅          |
| 调整角色、重置密码、改注册开关      | ❌    | ✅          |
| 对自己:封禁、降级                   | ❌    | ❌(防锁死)  |

### 6.3 关键规则

- **积分调整**:事务内 `LockCredit` → 校验调整后 `balance - frozen ≥ 0`(扣减不得扣到低于冻结额)→ `AddCredit` → 写流水(type=`admin_adjust`,`task_id` 为空,附备注与操作人)。
- **并发上限**:`users.max_active_tasks`(可空),`insertAndFreeze` 里取 `COALESCE(用户值, 全局默认)`;调低不影响已在跑的任务,只影响新提交。
- **封禁**:`users.status`(`active/disabled`);登录时拒绝;`JWTAuth` 之后增加状态检查中间件(用带短 TTL 缓存的查询,与 `NewCachedRoleLookup` 同做法,封禁时主动清缓存);封禁弹窗带勾选项「同时取消进行中任务」,**默认不勾**,勾选则走现有取消流程并退还冻结积分。
- **重置密码**:管理员输入新密码或生成临时密码,只展示一次;重置后使该用户旧 token 失效(见 §8,需要 token 版本号)。
- **审计**:新增动作 `user.credit_adjust / user.ban / user.unban / user.role / user.reset_password / user.limit / settings.register`,`target_type=user`,detail 记前后值,不记密码。

## 8. 数据与工程影响(建议,不擅自改代码)

**表结构**:

- `users` 新增:`status`、`max_active_tasks`(可空)、`email_verified_at`、`last_login_at`、`token_version`;`email` 部分唯一索引。
- `credit_ledger`:`task_id` 改为可空,唯一索引改为仅对非空 `task_id` 生效(部分唯一索引);新增 `operator_id`、`note`;type 增加 `admin_adjust`、`initial`(可选,记录赠送)。
- 新增 `system_settings`(键值):`register_enabled`、`initial_credits`、`default_max_active_tasks`。**已确认(2026-10-05):配置文件里的 `ai.max_active_tasks_per_user`、`ai.initial_credits`、`user.login_log_retention_days` 全部删除,默认值(并发 4、初始积分 50、登录记录保留 180 天)写成代码常量,后台库值优先。**
- 新增 `smtp_settings`(单行):host、port、加密方式(none/starttls/tls)、username、`password_enc`(加密)、from 地址与显示名、`enabled`、`last_check_at/last_check_ok/last_check_error`、`updated_by`。密码只写不读,接口只返回"是否已设置"。
- 审计表:沿用 `ai_audit_logs` 并扩展常量,还是新建 `admin_audit_logs`,见待确认问题 1。

**API(建议)**:

```
GET  /auth/config                    {register_enabled}
POST /auth/register/code             发验证码
POST /auth/register                  注册(改:加 email、code,返回 token)
GET  /admin/users                    列表(搜索/筛选/分页)
GET  /admin/users/:id                详情(含积分、并发占用)
GET  /admin/users/:id/ledger         流水分页
POST /admin/users/:id/credits        调整积分
PUT  /admin/users/:id/limits         并发上限
PUT  /admin/users/:id/status         封禁/启用(body 含 cancel_active)
PUT  /admin/users/:id/role           仅 super_admin
POST /admin/users/:id/reset-password 仅 super_admin
GET/PUT /admin/settings/register     注册开关、初始积分、默认并发
GET  /admin/settings/smtp            读 SMTP 配置(密码只回 has_password)
PUT  /admin/settings/smtp            改 SMTP 配置,仅 super_admin
PUT  /admin/settings/smtp/password   替换密码,仅 super_admin
POST /admin/settings/smtp/test       发测试邮件到指定地址,仅 super_admin
```

同时**收口现有 `/users`、`/users/:id`**:移入 admin 组或删除。

**实现难点与风险**:

1. 流水唯一索引改造涉及线上数据,迁移需在 `AutoMigrate` 前后配合(参考 `repository/migrate.go` 的做法),要有可重复执行的迁移测试。
2. 即时封禁每个请求多一次状态查询,依靠缓存控制开销;缓存延迟即封禁生效延迟(建议 ≤ 5–10 秒,封禁时主动清除)。
3. "首个用户为超管"在并发注册下必须原子,需要测试覆盖。
4. 邮件发送是同步外部调用,要设超时,且不能阻塞注册事务。SMTP 地址由管理员填写,**存在 SSRF 风险**(可探测内网端口),应复用 `provider/netguard` 的出站校验思路,默认拒绝内网/回环地址,是否允许内网需单独确认。
5. 加密主密钥 `APP_AI_SECRET_KEY` 缺失时,无法保存 SMTP 密码,页面需明确提示(存储配置已有同样处理,照搬)。
6. 验证码存 Redis;**Redis 关闭时降级为进程内存**,多实例部署下会失效,需在文档中说明(待确认)。
7. 初始积分当前是惰性创建账户时发放;改成注册时发放还是维持惰性,会影响老用户与流水记录(待确认)。

## 11. 待确认问题

**已确认(2026-10-05)**

1. 审计:**新建**通用 `admin_audit_logs`,不扩展 `ai_audit_logs`。
2. 无 Redis 时验证码降级为进程内存:**可以接受**(多实例部署须启用 Redis,在部署文档中写明)。
3. 初始积分:**注册时发放**。注册事务内建 `user_credits` 并写一条 `initial` 流水(`task_id` 为空)。现状是惰性创建(首次 `GET /credits` 或首次提交任务时建账户、不写流水,见 `service/generation_task_query.go:107`、`service/generation_task_create.go:292`);已有但没有账户的老用户**保留惰性兜底**,`EnsureCredit` 真正插入新行时同一事务补写 `initial` 流水。不做存量迁移。
4. debug 模式下把验证码打印到日志:**可以**(仅 `server.mode=debug`,release 模式绝不输出)。
5. 封禁状态检查:**复用 Redis `UserCache`**(`user:<id>`)。封禁 / 启用 / 改角色时主动删除缓存,所有实例下一个请求即生效;无 Redis 时直接按主键查库。封禁时同时断开该用户的全部 WebSocket 连接(WS 建立后不再经过 JWT)。现有 `NewCachedRoleLookup` 的 30 秒内存缓存一并改成这套,降级管理员也立即生效。
6. 邮箱唯一:**同意**用部分唯一索引(`WHERE email <> ''`),老用户空邮箱不冲突。
7. SMTP 地址:**不允许**指向内网 / 回环 / 链路本地地址(含解析后的 IP),复用 `provider/netguard` 的出站校验,保存和发测试邮件时都校验;不提供放开开关。自建邮件服务器场景需走公网地址。
