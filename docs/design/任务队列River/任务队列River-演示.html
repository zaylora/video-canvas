任务队列（River）演示

任务调度换成 River，后台能调并发、看队列

现在的生成任务靠自研代码调度：任务表、抢锁、租约、心跳、定时轮询，全部要自己维护，并发写死在配置文件里，改了要重启。 这次改用开源任务队列 River。它直接用现有的 PostgreSQL，不需要新增中间件。后台可以按阶段调整并发，几秒内生效，并能看到积压、渠道占用、吞吐和实例。 用户超过自己的并发上限时不再被拒绝，而是自动排队，超过排队上限才会被拒绝。 任务状态、积分、前端推送的规则都不变。

一个生成任务怎么走

任务从点击“生成”到产出，会依次经过三个队列，每个队列可以单独调整并发。

创建（一个事务）写任务 + 冻结积分 + 入队 submit，三件事要么都成功，要么都不发生
提交上游先拿用户名额和渠道名额，拿不到就稍后再试（snooze），拿到后提交上游
查询进度每 5–15 秒查一次上游进度；等待期间不占执行槽位
转存产物把产物转存到自己的存储，结算积分，释放名额
推送前端每次状态变化照旧通过 WebSocket 推送，并保留对账兜底（不变）
设计：按阶段拆队列，是因为转存最长要 30 分钟。合在一个队列里，转存慢的时候会把提交和轮询一起堵住。名额检查只放在 submit 入口，这样“用户上限”和“渠道上限”是同一处逻辑、同一个事务。River 的 job 只管“什么时候执行下一步”，任务表仍是唯一的事实来源。
出问题时怎么兜底： 上游临时出错，River 会按现有策略重试（提交 5 次，转存 10 次），用尽后失败并退款。 进程崩溃时，其它在线实例的定时对账会把失联实例正在执行的任务立即放回队列，约 30–60 秒内被接手（River 自带的救回只是 1 小时的兜底）。 排队超过 60 分钟的任务会自动过期并退款，不会无限期排下去。 前端如果漏收推送，靠现有的 HTTP 对账补齐。

三层并发控制

同时生效，任何一层没有名额，任务都会继续排队。

队列并发
新增 · 按实例计后台可调

每个阶段在一台实例上最多同时执行几个。默认 submit 8 / poll 16 / finalize 4，可调范围不超过配置文件里的硬上限。

用户名额
行为变化：429 → 排队

一个用户同时进行中的任务数（默认 4）。超出的部分排队；排队总数超过“并发 × 排队倍数”（默认倍数 5）才返回 429。用户并发不同，排队上限也随之不同。

渠道名额
沿用“最大同时生成数”

一个渠道同时在上游生成的任务数。跨用户先到先得，转存阶段不占这个名额。规则与现状一致。

一个用户一次点了 8 个视频，会发生什么

假设该用户并发上限 4、渠道 max_running 6、排队倍数 5（也就是最多排 20 个）。可以在“排队演示”页自己改参数试试。

  1. 8 个任务全部创建成功（202），积分全部冻结现在的行为是第 5 个起返回 429；新方案会一直接受，直到排队总数超过 4 × 5 = 20
  2. 前 4 个拿到用户名额，开始提交还要同时有渠道名额；拿到名额的那一刻才开始计算生成超时
  3. 后 4 个在节点上显示“排队中”每 2–10 秒检查一次能不能拿到名额，按创建顺序先到先得
  4. 前面每完成一个，就有一个排队的开始转存阶段仍占用户名额，但不占渠道名额
边界：排队不是无限的，后台操作会影响排队任务
  • 排队超过 60 分钟：任务过期并退款，节点提示“排队超时”。
  • 后台暂停 submit 队列期间，排队时间照样累计；暂停太久会导致批量超时。
  • 进程崩溃后，正在执行的任务由其它实例的对账在 约 30–60 秒内接手（心跳 10 秒一次、30 秒没有就算失联）；只有一个实例且它挂了，要等它重启。
  • 队列并发按实例计算：将来部署两台实例时，实际总并发是设置值的 2 倍。

上线时要提前告知用户：429 的含义从“并发超了”变成“排队满了”，前端提示文案会同步修改。

核心流程（伪代码，已实现）

// 创建（已实现）—— 一个 GORM 事务
tx: EnsureCredit → LockCredit(user)
    if CountActive(user) >= effectiveLimit(user) * queue_multiplier { return 429 "排队任务已达上限" }
    InsertTask(status=pending, slot_acquired_at=NULL, deadline_at=now+排队超时)
    freeze credits + ledger
    river.InsertTx(sqlTx(tx), SubmitArgs{task_id})        // 任务、积分冻结、job 要么一起成功要么一起回滚

// 一个 job 被取出后（提交 / 查询 / 转存三个阶段共用）—— provider/queue
work(stage, taskID):
  t := GetTask(taskID)
  if t == nil || t.terminal()        { return nil }                 // 用户取消、超时、别的实例处理完
  if stageOf(t.status) != stage      { return handOff(t) }          // 任务已进入别的阶段：交给那个队列
  if t.next_poll_at - now > 1s       { return JobSnooze(until next_poll_at) }
  if !gate[stage].tryAcquire()       { return JobSnooze(1s..3s) }   // 后台可调的并发闸门（每实例）
  defer gate[stage].release()
  if t.status == pending && t.slot_acquired_at == nil:              // 提交阶段：先排队等名额
    if now > t.deadline_at           { handler.Expire(t); return nil }   // 排队超时：expired + 退款，不请求上游
    switch AcquireSlot(t):           // 用户名额 + 渠道名额，一个事务，先到先得
      gone:                          return nil
      wait_user / wait_channel:      return JobSnooze(2s..6s)
      acquired:                      t = GetTask(taskID)             // deadline 已重置为 现在 + 模型超时
  handler.Handle(t)                  // 提交 / 查询一次 / 转存；结果写在任务行里（含 next_poll_at、poll_attempts）
  t2 := GetTask(taskID)
  if t2.terminal()                   { return nil }
  if stageOf(t2.status) != stage     { return handOff(t2) }         // 入队下一阶段，按 next_poll_at 排期
  if t2.next_poll_at == t.next_poll_at { return JobSnooze(5s) }     // 没有任何变化：避免空转
  return JobSnooze(max(t2.next_poll_at - now, 1s))

// 对账（每个在线实例每 30 秒一次，启动后立即一次）
sweep():
  RecoverOrphanedJobs(在线实例)       // 失联实例正在执行的 running job → 立即放回队列
  for t in UnscheduledTasks():       // 非终态、队列里没有活着的 job（升级前在途、状态迁移后入队前崩溃）
      insert(stageOf(t.status), t.id, at t.next_poll_at)

已确认的决定

  1. 目标是用成熟方案替换自研调度：用户不想自己维护一套调度代码。
  2. 选用 River 开源版：中途选过 RabbitMQ，后来改为 River；Pro 不用，按渠道/用户的限流自研一层薄逻辑。
  3. RabbitMQ 已搁置：将来出现“多个独立消费方订阅任务事件”的需求时，再用它做事件分发，执行调度仍归 River。
  4. 监控 = 自建概览页 + 嵌入 River UI：概览讲业务语言，单个 job 的操作交给 River UI。
  5. 队列按阶段拆分：submit / poll / finalize，各自调整并发。
  6. 修改并发立即生效、按实例计：River MaxWorkers 作为硬上限，实际值由进程内可调信号量控制。
  7. 监控 MVP 四块内容：队列卡片 + 并发调节、渠道占用、近 1h 吞吐与失败率、实例列表。
  8. 用户超出并发改为排队，并保留排队上限：超过排队上限才返回 429。
  9. 排队上限 = 用户生效并发 × 倍数：每个用户的并发不同，全局固定值会出现矛盾；倍数和排队超时放在「注册设置」里，可配置。
  10. 任务队列页不放限流参数：默认并发已在「注册设置」、单用户覆盖值已在「用户管理」，不重复提供入口。
  11. 评审原型后再次确认保持三个队列，不合并。主文档已回写（头部修订说明、§6.4、§6.5、§8.3、§8.4、§11）。
  12. 崩溃救回已解决：改用“实例心跳 + 定时对账”，约 30–60 秒内被接手，不再有约 35 分钟的退化；River 开源版也确认没有运行时改并发的接口，用进程内闸门实现。主文档已回写：与最初提案的出入、验证情况和未验证事项见 Markdown §13。
