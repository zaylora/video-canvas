# Agent 看视频与截帧续镜设计

> **范围**：让画布 Agent 能「看懂」画布上已生成的 AI 短视频，并把关键帧截成图片节点、连到下一镜，保证镜头连续。同时评估火山引擎视频点播「长视频理解」能否承担这件事。
> **日期与状态**：2026-10-23，第一期已实现、未提交、未真机验证（见 §13）。
> **证据约定**：**事实**附文件路径或来源链接；**推断**是基于事实的判断；**提案**是尚未实现的设计；**未验证**需要实现时实测。
> **方案演进**：起点是评估火山「长视频理解」。用户随后澄清真实诉求是「理解已生成的短视频、截图给后一镜当参考」（生成模型不能直接引用上一段视频），结论转为**后端 ffmpeg 抽帧 + Agent 自己的看图能力**，火山长视频理解搁置（见 §9）。
> **配套演示**：[Agent看视频-演示.html](Agent看视频-演示.html)（先读它）。

## 1. 设计摘要

- **问题**：连续镜头靠「上一镜尾帧当下一镜首帧/参考图」衔接，但视频生成模型不接受视频作参考，Agent 现在也看不到视频内容（只有 `canvas_inspect_image` 看图）。
- **目标**：用户说「接着上一段继续拍」，Agent 能看懂上一段视频的内容与结尾状态，截出尾帧（或它挑的关键帧）建成图片节点，连到下一镜的视频节点上，再写出与上一镜衔接的提示词。
- **结论**：
  1. **可行，不需要火山长视频理解**。看生成的短片只需均匀抽几帧交给 Agent 当前的看图模型；火山方案要把视频传进点播空间，且只产出文字总结、不产出截图，对这个场景是绕路（§9）。
  2. **新增两个后端工具**：`canvas_inspect_video`（抽帧给模型看，只读）和 `canvas_capture_frame`（截帧落成图片节点并连线，免费）。
  3. **抽帧在后端用 ffmpeg**（用户已确认），打破原先「后端不装 ffmpeg」的约定，镜像要加 ffmpeg。
  4. 范围只含 AI 生成的短片（约 5–15 秒），不含用户上传的长视频。

### 设计约束

- Agent 工具跑在服务端，**没有浏览器**，不能复用前端 Mediabunny 取帧。
- 素材归属必须校验到用户（沿用 `AssetStore` 的做法）。
- 看图内容属于用户素材，不进历史、不进日志。
- `canvas_apply_ops` 写不了 `assetId`，所以「截帧建节点」不能靠它完成，要由新工具直接写节点。

### 当前缺口

1. Agent 看不到视频内容。
2. 后端没有抽帧能力、镜像没有 ffmpeg。
3. Agent 没有「由素材建出上传型图片节点」的写入路径。
4. 视频节点的当前产物解析（对应 `ImageRefs` 的视频版）。

## 3. 用户与场景

- **用户**：在画布上用 AI 做分镜、连续出片的创作者。
- **场景**：上一镜视频生成完，下一镜要接着拍——人物位置、动作、光线、运镜方向要衔接，而生成模型只吃文字和图片参考。
- **主任务**：对 Agent 说「接着这段继续」→ **由 Agent 自己判断**要不要看、要不要截、截几张 → 需要的帧建成图片节点，认为该当参考的再连到下一镜 → 写衔接提示词 → 走原有生成确认。
- **成功指标（提案）**：① 一句话完成「看 + 截 + 连线」，不需要用户手动点截取帧；② 截帧不扣积分；③ 抽帧失败时 Agent 能说明原因并让用户改用手动「截取帧」。

### 4.2 方舟（豆包）原生视频理解（调研检索，未逐页复核）

来源：<https://docs.volcengine.com/docs/ark/video-understanding?lang=zh>、<https://docs.volcengine.com/docs/ark/file-api?lang=zh>，检索于 2026-10-23。

- Chat API 的 `video_url` 支持 `url` 或 `file_id`，`fps` 默认 1.0；Base64 传视频 ≤50MB，Files API ≤512MB（存 TOS 可到 2GB）。
- 这条路是「模型直接看视频」，仍不产出截图；且只适用于方舟的豆包模型，Agent 当前模型不一定是它。**未验证**：项目 Agent 模型的渠道是否支持 `video_url`。

### 4.3 行业做法（未验证，来自常识）

主流视频生成产品普遍用「上一段尾帧 → 下一段首帧/参考图」做镜头衔接。本次未逐个产品核实，**不作为依据**，仅说明该做法是通行路径；项目自己的「截取帧」设计（§2）已把「拿尾帧接下一段」列为首要场景。

## 5. 设计原则

1. **看和写分开**：看视频是只读、不落库、不扣费；截帧是写画布但免费、可撤销。
2. **截帧按需调用**：系统提示词里写明什么时候该截（需要参考图、用户明确要求），什么时候不该截（只是了解内容），避免过度调用刷屏、占存储。
3. **复用看图链路**：抽出的帧就是图片，走现有 `ToolImage`（URL 或 base64）进模型，不另造模型接入。
4. **用户素材不留痕**：看到的帧不进历史、不进日志，与 `canvas_inspect_image` 一致。
5. **失败要可退**：抽帧失败时返回人话原因并引导手动「截取帧」，不阻塞 Agent 其他工作。
6. **后端对外部二进制设防**：超时、并发、输入协议白名单，不信任视频内容。

## 6. 推荐方案

### 6.1 一句话

Agent 新增两个后端工具，后端用 ffmpeg 抽帧：`canvas_inspect_video` 抽几帧让模型看懂；`canvas_capture_frame` 把指定帧存成素材、建图片节点。**两个工具是各自独立、按需调用的：看视频不等于截帧，截帧只在 LLM 判断「需要把某帧留下来」（典型是要当下一镜的参考图）时才调用，绝不是每次看视频后的固定动作。要不要用这两个工具、截多少帧（一次最多 6 帧）、每张帧要不要连线当参考，都由 LLM 自己决定**，后端只校验上限和合法性，不规定流程。

### 6.2 主流程（续镜，典型路径而非固定流程）

**截帧是可选的工具，不是流程的一环**：用户问「这段拍了什么」「帮我看看有没有穿帮」，只用 `canvas_inspect_video` 或根本不用工具；只有「接着拍」「把这帧当参考」这类需要留下画面的诉求才会调 `canvas_capture_frame`，也可以不看直接截（如用户明说「截尾帧」）。

**LLM 的三个自主决定**：① 要不要看视频、要不要截帧（用户只问「这段拍了什么」就只看不截）；② 截几张、截哪些时间点（一次最多 6 张）；③ 截出的每张帧**是否作为参考**连到下一镜（不连则只是放在画布上备用）。系统提示词只描述这些工具的用途和续镜的常见做法，不写成必须执行的步骤。

典型的续镜路径（**第 3–4 步的截帧仅在需要参考图时发生**）：

1. 用户：「接着上一段继续，镜头往前推。」（可 `@` 引用视频节点）
2. Agent 调 `canvas_inspect_video`（`nodeId`、可选 `count`）→ 后端按时间均匀抽帧，附带每帧时间戳，交给模型看。
3. Agent 判断结尾状态（人物位置、动作、光线、运镜），自己决定要截哪些帧、几张。
4. Agent 调 `canvas_capture_frame`（`nodeId`、`frames`，每项含 `at` 与可选 `connectTo`）→ 后端逐帧存素材，在视频节点右侧建图片节点；只有写了 `connectTo` 的帧才连到对应下一镜视频节点作参考。
5. Agent 用 `canvas_apply_ops` 给下一镜写提示词（有参考帧就写衔接，没有就按文字写）。
6. Agent 调 `generate_media`，走原有确认卡片与积分预估。

### 6.3 工具契约（提案）

**`canvas_inspect_video`**（只读，需要模型支持看图，所有任务模式可用）

| 参数 | 说明 |
| --- | --- |
| `nodeId` | 视频节点 id，必须已有产物 |
| `count` | 抽几帧，由 LLM 决定，默认 6，范围 1–6（超过 6 返回错误并说明上限） |
| `start` / `end` | 可选，秒；只看一段。第一版接口保留，便于以后扩展到更长视频 |

返回：文字（节点名、时长、每帧时间戳）+ 图片（JPEG，长边 ≤1024，**示意值，待实测**）。帧均匀取点；`count` ≥2 时**包含首帧与尾帧**。

**`canvas_capture_frame`**（写画布，免费）

| 参数 | 说明 |
| --- | --- |
| `nodeId` | 视频节点 id |
| `frames` | 要截的帧，**1–6 项**，超出返回错误并说明上限 |
| `frames[].at` | `"first"`、`"last"` 或秒数 |
| `frames[].connectTo` | 可选，下一镜节点 id 列表；**写了才连线作为参考**，不写则只建节点；连线方向为帧图 → 目标 |

行为：逐帧抽取（PNG，原分辨率）→ 经素材服务存为用户素材 → 建 `uploaded: true` 的图片节点（放在视频节点右侧 80 像素处、垂直居中；与已有节点重叠就整体下移「节点高 + 40」，最多试 60 次，即**同一列向下依次避让**，规则与前端 `placeBeside` 一致）→ 与视频节点连来源线（`video → image`，不符合生成依赖规则，所以由后端受信任的建图函数 `canvasgraph.AddFrameNodes` 直接建，不走 `connect` 操作） → 有 `connectTo` 的再连到目标。返回各帧的新节点 id 与时间戳。同一时间点重复请求时去重。

**帧图留在画布上**：它们是 `uploaded: true` 的普通图片节点，不是只给 Agent 用的临时数据。不连线也保留，用户可以像对待上传图片一样拖动、预览、拿去做图生图/局部重绘，或手动连给任意节点；删除、撤销与其他节点一致。

### 6.4 抽帧实现要点（提案，均需实测）

- **输入**：素材在对象存储时用签名 URL 直接交给 ffmpeg；本地磁盘存储时落临时文件再取（尾帧要 seek）。
- **取尾帧**：`-sseof` 从末尾回退一小段再取最后一帧；不要正好取总时长（浏览器方案已踩过「等于时长取不到画面」的坑，ffmpeg 同类问题**未验证**）。
- **取点**：先 `ffprobe` 读时长，再对每个时间点单独取帧（输入侧 `-ss`），保证速度。
- **设防**：协议白名单（只允许 `file`、`https`，对象存储 URL 走现有 `netguard`）；单次超时；全局并发上限；输出大小上限；临时文件用后即删。具体数值待实测。

### 6.5 AI 行为与审批

- 看视频：无需确认。
- 截帧：不弹确认卡片（用户已选择「直接建节点并连线」），靠撤销兜底；一次最多 6 张，节点数量有上限所以不会刷屏；在时间线显示工具名「截取视频帧」。
- 真正花积分的仍是 `generate_media`，确认卡片不变。

## 7. 状态与异常

| 情形 | 行为 |
| --- | --- |
| 当前模型不能看图 | 不给 `canvas_inspect_video`；仍可用 `canvas_capture_frame`（不需要看）。提示词里说明可建议用户换支持看图的模型 |
| 节点不是视频、没有产物、产物还在生成 | 工具返回人话原因，与 `ImageRefs` 风格一致 |
| 素材不属于该用户/已删除 | 「视频素材不存在或已删除」 |
| ffmpeg 不存在（镜像未更新） | 工具返回「当前环境不能处理视频」，并让 Agent 引导用户用手动「截取帧」；服务启动时检测一次并记日志（提案） |
| 抽帧超时/并发已满/视频损坏 | 返回具体原因，可重试一次；不影响 Agent 继续其他步骤 |
| 视频格式 ffmpeg 无法解码 | 同上，提示手动截取帧 |
| 画布 revision 冲突 | 沿用 Agent 写画布的现有冲突处理（**需实现时核对**） |
| 撤销 | 截帧建的节点和连线走 Agent 写画布的统一撤销（**需核对撤销粒度**） |
| 剧本创编、提示词优化模式 | `canvas_inspect_video` 可用（只读）；`canvas_capture_frame` 不可用（这两个模式本来就不允许新建图片节点），直接调用返回「当前是 X 模式，不能使用」。全能创作、分镜搭建两个模式都可用 |

## 8. 数据与工程影响

- **后端镜像**：`alpine` 阶段加 `ffmpeg`（含 `ffprobe`）；开发镜像 `Dockerfile.dev` 同步；本机 Windows 开发需要本地装 ffmpeg 或跳过相关测试。
- **新增代码**：`service/agent` 下新增视频工具（解析视频节点产物、抽帧、建节点）；`canvasgraph` 增加视频节点产物解析（`VideoRefs`）和「建上传型图片节点」的图操作；`tool_decls.json` 新增两个声明；`tool_registry.go` 登记（`inspect_video` 带 `needsVision`）。
- **复用**：`AssetStore.Open`（取视频）、`AssetService.Upload`（存帧，需确认能否不经 HTTP 直接用）、`ToolImage`（给模型图）、前端 `uploaded: true` 节点形态。
- **不改**：`payload_json` 结构、`revision` 机制、`generate_media`。
- **前端**：节点和时间线展示工具名；新建节点由现有画布同步机制展示（**需核对**）。
- **提示词/技能**：Agent 系统提示要教会「续镜流程」；可新增一条技能（提案）。
- **观测**：工具调用要进 Agent 运行记录，但**图片不记**。

## 9. 方案取舍

| 决策项（权重：贴合需求 40、实现成本 25、运行稳定 20、合规与出站 15） | A ffmpeg + 看图 | B 方舟 video_url | C 火山长视频理解 |
| --- | --- | --- | --- |
| 贴合「看懂 + 截图续镜」 | 5 | 3 | 2 |
| 实现成本 | 3 | 3 | 1 |
| 运行稳定（依赖少） | 4 | 3 | 2 |
| 合规与出站 | 4 | 3 | 2 |
| 加权 | **4.1** | 3.0 | 1.9 |

权重为默认权重（用户未单独排序），打分是主观判断，仅用于说明倾向。

**放弃的东西**：
- 火山长视频理解（暂搁置）：对短片过重；以后若要分析用户上传的**数分钟以上长片**、需要语音转写（ASR）时可重启，届时需视频入点播空间。
- 前端回传抽帧：Agent 离线时不可用，旧设计已明确不做。
- 自动挑最佳帧的专门算法：第一版由模型看帧后自己选。

## 10. MVP 与后续

**第一期（MVP）**：
- 镜像加 ffmpeg；抽帧工具函数（首帧、尾帧、指定秒、均匀 N 帧）。
- `canvas_inspect_video`、`canvas_capture_frame` 两个工具及声明、注册。
- 系统提示增加「续镜」流程。
- 验收：① 对一个已生成的 10 秒视频，Agent 能描述内容并截出尾帧节点，连到下一镜；② 截帧不扣积分；③ 不能看图的模型不出现看视频工具；④ 他人素材、非视频节点、无产物节点都返回明确原因；⑤ ffmpeg 超时或缺失时返回可读错误；⑥ 看到的帧不出现在历史与日志；⑦ 一次请求超过 6 帧时返回明确的上限错误；⑧ 不写 `connectTo` 的帧只建节点不连线，写了的才连到目标；⑨ 用户只问「这段拍了什么」时，Agent 不会多余地截帧（靠提示词与实测评估，非硬性校验）。

**第二期（可选）**：`start`/`end` 分段翻查、一次截多帧、截帧后自动给下一镜写衔接提示词的专用技能。

**第三期（视需求）**：用户上传的长视频理解（重评火山点播/方舟 `video_url`）。

## 11. 待确认问题与已确认事项

**已确认（用户回答）**
1. 真实诉求：理解已生成的视频，并把截图交给后续镜头做参考，因为生成模型不能引用视频。
2. 抽帧位置：**后端装 ffmpeg**。
3. 落帧方式：**Agent 直接建图片节点**，不弹确认卡片。
4. **是否截帧、截几张（一次最多 6 张）、哪些帧作为参考（连线），全部由 LLM 自己决定**，后端不写死流程。
5. **截好的帧放在画布中**，作为可继续使用的图片节点；是否连线当参考另由 LLM 决定。
6. 视频范围：**只看 AI 生成的短片**。

**已搁置的决定**
- 火山长视频理解、方舟 `video_url` 直传：见 §9，需要分析长片时复用 §4 调研。

**默认值（无需用户决定，实现时可调）**
- 看视频默认抽 6 帧、范围 1–6；看图用 JPEG 长边 1024，落帧用 PNG 原分辨率；Agent 用自己当前的看图模型理解视频，不额外调模型。

**仍待确认**
1. （已按默认处理，仅记录）截帧只在「全能创作」「分镜搭建」可用，与 `generate_media` 同级；剧本创编、提示词优化模式不放行。若要放开，改 `tool_registry.go` 里的 `modes`。
2. Alpine 的 ffmpeg 包许可证与镜像体积是否可接受？（影响发布）
3. 截出的帧图是否要标明来源（节点标题带「某视频 · 尾帧」）？默认带，需 UI 确认。

## 13. 实现记录

> 2026-10-23，分支 `worktree-agent-video-frames`（worktree），**已实现、未提交**。

**已实现**
- `backend/internal/pkg/videoframe`：`os/exec` 调 ffmpeg / ffprobe 的抽帧器（`Duration`、`Frame`、`Sample`、`LastAt`）；协议白名单、单次超时 30 秒、并发上限 2（超出返回 `ErrBusy`，不排队）、ffmpeg 输出只进日志不透给模型。
- `canvasgraph`：`VideoRef`（取视频节点素材）、`AddFrameNodes`（受信任建帧图节点 + 来源线 + 可选参考线，整批原子）、`FrameSpec`。
- 服务层：`AgentCanvasService.VideoRef / CheckFrames / AddFrames`；`MutationFrames = "frames"`（改动日志的种类，「撤销本轮」按改动内容倒回，不区分种类）；`canvas_inspect_video`、`canvas_capture_frame` 两个工具，登记在 `tool_registry.go`，声明在 `tool_decls.json`；`BridgeDeps` 新增 `Frames`、`FrameStore`（接口声明在 `service/agent/video.go`）。
- 装配：`initialize/agent.go` 创建抽帧器（找不到 ffmpeg 只记警告），`assetFrameStore` 把 `AssetService.Upload` 包成 `FrameStore`。

- 前端：`timeline.ts` 的 `WRITE_TOOLS` 加入 `canvas_capture_frame`（让只截帧的一轮也有改动摘要和「撤销本轮」）；名称由后端下发，前端不用加常量。
- 镜像与 CI：`Dockerfile`（Alpine 运行阶段）、`Dockerfile.dev`、`ci.yml`、`release-docker.yml` 装 ffmpeg。

**与设计的出入**
- 帧图摆放由「横向排开」改为「同一列向下依次避让」：与现有手动「截取帧」一致，也不会压到右侧的下一镜节点。
- 视频节点在组里时，帧图仍放在画布顶层（按绝对坐标），不加入该组。
- 多个帧图与连线：连线目标校验用 `canLink(image, 目标种类)`，即只能连到图片或视频节点。
- 校验失败先于抽帧、存素材：`CheckFrames` 先干跑一遍，所以不合法的请求不会留下孤儿素材；但「素材已存、最后写画布失败」（如版本冲突重试三次仍失败）仍会留下用户素材，目前不清理。
