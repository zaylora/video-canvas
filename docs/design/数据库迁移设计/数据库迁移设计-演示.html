数据库迁移 · 设计演示

改了模型就自动生成迁移 SQL，启动时安全地执行它

现在的迁移是“启动时 AutoMigrate 自己决定改什么”，改了什么看不到，也没有版本和校验。新方案让 Atlas 从 GORM 模型生成 SQL 文件，由项目自带的 小型迁移器在事务里加锁执行。老用户必须先经过一个“过渡版本”才能接管，否则迁移器会拒绝启动。

阅读说明。这是设计提案，尚未实现，对应 Markdown 设计文档（数据库迁移设计.md）。所有“实测”都是我在临时目录和临时 Postgres 16 里跑原型得到的，仓库没有被改动；原型本身没有单元测试。页面里的原型在浏览器内存中模拟，不会连接任何数据库，耗时数字是示意。

一次迁移怎么走

从改模型到上线，谁在什么时候做什么。

1 改 GORM 模型开发者在 internal/model 里加字段
2 生成 SQLloader 输出 schema.sql，Atlas migrate diff 写出迁移文件
3 人工评审看到 DROP 就要停：社区版没有 lint 帮你拦
4 提交并编进二进制SQL 文件 //go:embed，CI 查漂移
5 启动时执行事务内加锁、校验、执行；生产由 migrate 服务先跑
设计：生成和执行分开。Atlas 只在开发机和 CI 里出现，不进镜像；运行时只有项目自己约 155 行的迁移器（实测原型）。放弃：让 Atlas 在生产执行（镜像要装二进制，并发时其余进程直接报错退出）。
兜底与边界。任何一步失败，整批事务回滚，库回到迁移前，没有“半迁移”状态（已实测）。已发布的迁移文件被改动（哪怕一个空格）→ 启动即拒绝；旧程序连新库 → 拒绝。但大表加索引不能用 CONCURRENTLY，会锁表（已实测），目前没有解法。

分三步落地：老用户必须先经过“过渡版本”

这是实测得出的硬约束，不是偏好。直接从很旧的版本跳到有增量迁移的版本，迁移器会拒绝。

过渡版本 N只含基线

迁移计划只有一个基线文件；接管老库时先跑旧的全部逻辑（5 个手写函数 + AutoMigrate），再记录基线。落后的老库在这里被补齐。

版本 N+1 起增量时代

只执行新增的迁移文件。遇到未接管的老库（计划里已有多个迁移）→ 迁移器拒绝启动，库不动，提示先升级到 N。

清理需确认无人停在 N 之前

删除 5 个手写函数、钩子里的 AutoMigrate 和对应 552 行测试。前提是确认没有用户停在旧版本。

设计：为什么不一步到位？实测两个反例：①钩子里留着 AutoMigrate 而计划里已有增量 → 增量报“列已存在”，整批回滚，老库升级失败；②钩子里去掉 AutoMigrate → 落后的老库缺表缺列却被悄悄放过，verify 还通过。过渡版本同时避开这两个问题。

开发者把列名改了，会发生什么

社区版没有 migrate lint，这是日常最容易踩的坑。

  1. 把 PhoneNo 改名为 Mobile只改了 Go 字段名和 json 标签
  2. 运行 make migrate-diffAtlas 无法区分“改名”和“删一列再加一列”
  3. 生成的 SQL 是“删列 + 加列”控制台没有任何警告（实测）
  4. 评审或 CI 发现 DROP COLUMN手改成 RENAME COLUMN，再运行 make migrate-hash 重算 atlas.sum
边界和后果。如果没人发现，上线后该列全部数据丢失。CI 里“含 DROP COLUMN / DROP TABLE 则失败，除非显式标注”是社区版缺 lint 的替代，检查方式是提案，尚未实现。
设计：为什么不自己做 rename 检测？可以做，放在“后续”。放弃：自动判断改名（误判风险，且 GORM 字段改名不一定是数据库列改名）。

开发流程原型

模拟开发者的一次完整迭代：选一个模型改动 → 生成迁移 → 评审 → 提交 → CI 检查。数据在内存里，刷新复原；不会运行 Atlas，也不会碰数据库，生成的 SQL 是照实测输出写的示意。想看失败：选“改列名”后直接点提交，或选“忘了生成迁移”。

迁移器接口

签名来自实测原型。lock_timeout、日志、Status 还没写进原型，实现时补。

// 提案，签名来自实测原型
type Migration struct {
    Version  int64
    Name     string
    Checksum string // 文件内容 SHA-256，换行已统一
    SQL      string
}

func Load(fsys fs.FS, dir string) ([]Migration, error)      // 命名不合法 / 版本重复 / 空目录都报错
type Hook func(tx *sql.Tx) error                              // 接管时代替"执行基线 SQL"，同一事务内
func Run(db *sql.DB, plan []Migration, probeTable string, takeoverHook Hook) error
func Verify(db *sql.DB, plan []Migration) error               // 只读：过旧 / 过新 / 名称或校验和不一致都报错

Run 的执行顺序

全部在一个事务里；任一步失败整体回滚。

  1. 拿锁SELECT pg_advisory_xact_lock(<固定键>)，事务级，随事务结束自动释放。原型还没加 lock_timeout：默认一直等（实测另一会话持锁 8 秒就等 8 秒），SET LOCAL lock_timeout 对 advisory lock 有效（实测设 2 秒，2 秒后报错）。设计里的默认值 10 分钟是我设的，非实测
  2. 锁内检测接管probeTable（如 users）存在且 schema_migrations 不存在 → 待接管的老库。检测在锁内，所以多个实例不会同时判定
  3. 计划里多于一个迁移就拒绝报“老库只能由过渡版本接管”，回滚，库不动
  4. 建记录表，逐个应用已有记录则比对名称与校验和，不一致报错；没有记录则执行。接管时基线不执行 SQL，改调 takeoverHook 后记录
  5. 提交

已确认的决定

  1. 用 Atlas 生成 SQL，使用社区版：用户在我给出“标准版 + goose”后选定“Atlas 生成 + goose 执行 + 和社区版本”。
  2. 开发和生产最好一样：用户的要求，所以开发和生产跑同一批嵌入的文件。
  3. 对混合方案的探索与要求重写：用户让我实测混合方案并重写设计。这不等于已决定采用混合方案，见下。
