## 1. 设计摘要

**问题**：

1. **迁移内容看不到**。启动时 `AutoMigrate` 自己决定改什么，评审、Release 说明、更新器的前置检查都拿不到"这次升级会执行哪些 SQL"。
2. **`AutoMigrate` 做不了的事靠手写函数**。仓库里已有 5 个，每个都带"必须在 AutoMigrate 之前/之后调用"的顺序约束（[migrate.go](../../../backend/internal/repository/migrate.go)）。
3. **模型之外还有手写 DDL**。`idx_task_poll` 是 [db.go:68-71](../../../backend/internal/initialize/db.go) 里手写的 `CREATE INDEX`，不在 GORM 模型里。
4. **没有版本、没有校验**。库停在哪个版本、已执行的迁移是否被改过，都无从得知；旧程序也可以连新结构的库。

**目标**：开发和生产用**同一批可审查的 SQL 文件**；SQL 由工具从 GORM 模型自动生成；失败时库保持干净；旧程序不能连新库；老用户自动接管。

**推荐结论**：

- **生成**：Atlas 社区版 v1.3.0 + 一个约 20 行的 loader（`cmd/migrate-schema`），从 GORM 模型生成纯 SQL 迁移文件。
- **执行**：项目自带的迁移器（实测原型 155 行），读取 `//go:embed` 的 SQL 文件，用**文件内容的真实 SHA-256**做校验和，整批放在一个事务里，事务内先拿 advisory lock。
- **部署**：生产由 compose 里的一次性 `migrate` 服务先跑，backend 只做版本校验；开发保持启动时自动迁移。做法参考 open-ai-canvas，见 [4.1](#41-open-ai-canvas-的自研迁移器)。
- **老库接管**：必须经过一个**只含基线迁移的过渡版本**，否则迁移器拒绝启动（实测）。这是本方案最重要的约束。
- 不登录 Atlas，不引入 goose，Atlas 不进镜像。

**必须知道的代价**：

- 社区版**没有 `migrate lint`**，Atlas 会把"改列名"生成成"删列 + 加列"（实测，会丢数据），控制台无警告。只能靠 CI 检查加人工评审。
- 整批一个事务，所以**不能用 `CREATE INDEX CONCURRENTLY`**（实测），大表加索引会锁表。
- 开发者改模型后**必须先生成迁移文件**，否则开发库和生产库结构对不上。这是日常流程的变化。

## 2. 项目现状

调研日期 2026-10-13，以代码为准。

### 2.1 事实

**迁移入口**

- `NewDB` 在 `cfg.AutoMigrate` 为真时，按固定顺序执行：`MigrateLegacyAIConfig` → `MigrateUserManagement` → `MigrateConversationDefault` → `MigrateChannelTrustedInternal` → `db.AutoMigrate(model.All()...)` → `MigrateModelSingleConfig` → 手写 `CREATE INDEX idx_task_poll`（[db.go:41-72](../../../backend/internal/initialize/db.go)）。
- `auto_migrate` 在 [config.yaml:27](../../../backend/configs/config.yaml) 与 `config.local.yaml:25` 都是 `true`；`docker-compose.yml` 没有覆盖它，所以生产也开着。
- `NewDB` 只有一个调用方：[app.go:54](../../../backend/internal/initialize/app.go)。
- `model.All()` 有 33 个类型，一一对应 33 张业务表（[model/base.go](../../../backend/internal/model/base.go)）。
- `repository/migrate.go` 有 5 个手写迁移函数，加上 `EnsureBuiltinStorage`（只插数据，不改结构，在 `app.go:584` 调用，不属于本设计的迁移范围）。对应测试 5 个文件共 552 行；另有 11 个测试文件用 `AutoMigrate` 建测试库。
- 后端镜像只构建 `./cmd/server` 一个二进制（[Dockerfile:19](../../../backend/Dockerfile)）。

**5 个手写迁移函数，各自的前提**

| 函数 | 做什么 | 与 AutoMigrate 的顺序 | 对全新库 |
| --- | --- | --- | --- |
| `MigrateLegacyAIConfig` | 删 `ai_providers` 表、`ai_models.provider_key` 与 `deleted_at` 列；删 `target='provider'` 的 revision | 之前 | 无意义 |
| `MigrateUserManagement` | `credit_ledger.task_id` 放开非空；删旧的全量唯一索引 `uk_ledger_task_type`，让 AutoMigrate 重建成部分索引 | 之前 | 无意义 |
| `MigrateConversationDefault` | 删 `conversations.is_default` 列和 `uk_conversations_default` 索引 | 之前 | 无意义 |
| `MigrateChannelTrustedInternal` | 删 `ai_channels.trusted_internal` 列，对仍开着的渠道打 WARN | 之前 | 无意义 |
| `MigrateModelSingleConfig` | 把模型多版本数据收敛成每个模型一份配置（**改数据**，不只改结构） | 之后 | 无意义 |

**模型之外的手写 DDL**：`idx_task_poll`（`CREATE INDEX IF NOT EXISTS ... WHERE status IN ('pending','queued','running','finalizing')`）。注释写明原因：GORM 的 `where` 标签不方便写 `IN` 列表，所以迁移后补建（[db.go:66-71](../../../backend/internal/initialize/db.go)）。Atlas 只读 GORM 模型，不读这条语句，**实测基线里 `idx_task_poll` 为 0 次**。

**分层规则**（[backend/AGENTS.md](../../../backend/AGENTS.md)、[.golangci.yml](../../../backend/.golangci.yml)）：`repository` 不 import `service`、`handler`；`service` 不 import `gorm.io/gorm`；依赖只在 `initialize/app.go` 手动组装；新增外部依赖前先确认必要性；提交前 `make fmt`、`make lint`、`make test` 必须全过。

### 2.2 设计约束（推断）

| 约束 | 依据 | 影响 |
| --- | --- | --- |
| 老用户库由 `AutoMigrate` 建出，没有版本表 | 现状 | 必须有"接管"机制 |
| 老用户库可能停在比当前更早的结构 | 5 个手写函数就是为此存在 | 接管前必须先让库达到基线结构，见 6.5 |
| 只支持 PostgreSQL | AGENTS.md | 迁移文件可以直接写 PG 方言 |
| 多实例可能同时启动 | 无法排除手动多开 | 必须加锁，且接管检测要在锁内 |
| `idx_task_poll` 不在模型里 | 2.1 | 要进模型标签，见 6.6 |
| 部分索引里的多值 `IN` 会被 Atlas 误报 | 实测，见 2.3 | 模型里要改写法 |
| 镜像里没有 Atlas | Dockerfile | 执行必须是自带代码，不能调用 Atlas |

### 2.3 实测结论（2026-10-12/13，临时目录 + 临时 Postgres 16，仓库未改动）

**Atlas 部分**

| 项 | 结论 |
| --- | --- |
| provider 加载全部模型 | 通过：33 张表 |
| 社区版 `data "external_schema"` | **不支持**：报 `not supported by the community version of Atlas` |
| 社区版 + loader 输出 `schema.sql`，`src = "file://schema.sql"` | 通过；基线 31,295 字节、33 条 `CREATE TABLE` |
| 社区版默认输出（`format` 不指定） | 纯 SQL 文件，无 goose 标记，另生成 `atlas.sum` |
| 无变更再 `migrate diff` | 产出 0 个文件（前提：把多值 `IN` 改成 `OR`，见下） |
| 标准版 Atlas 未登录 | `migrate diff` 能出文件，但每次提示 `requires 'atlas login'`；`migrate lint` 报仅限 Pro |
| **改列名** | 生成 `DROP COLUMN "phone_no", ADD COLUMN "mobile" ...`，**会丢数据**，控制台无警告 |
| 漂移检测 | 无漂移 0 个文件；改模型不生成迁移时检出 1 个 |

**`IN` 谓词误报的根因（黑盒定位，未读 Atlas 源码）**：

| 谓词写法 | 无变更再 diff |
| --- | --- |
| `status IN ('a','b')`、`status = ANY(ARRAY[...])` | 误报，每次想重建索引 |
| `status = 'a'`、`status <> ''`、`a OR b OR c` | 不误报 |

PG 把 `IN` 存成 `ANY(ARRAY[...])`，Atlas 读回的形态与它解析 SQL 的形态不一致。项目里只有 `uk_agent_runs_active`（[agent.go:108](../../../backend/internal/model/agent.go)）用了多值 `IN`。改成 `OR` 后，`idx_task_poll` 写进模型标签（也用 `OR`）也不误报。

**执行器部分（自研原型 155 行）**

| 项 | 结论 |
| --- | --- |
| 空库执行基线（33 张表） | 通过，约 12 秒；再执行 25~100 毫秒无事可做 |
| 基线 + 由 Atlas 生成的增量 | 通过 |
| 4 实例并发（空库） | 全部 `err=nil`，最终 1 条记录、33 张表 |
| 4 进程同时接管同一个老库 | 通过：1 条记录、33 张表，无重复 |
| 多语句文件中途失败 | 整批回滚：先建的表、加的列都不存在 |
| 基线已应用后增量失败 | 只回滚增量，已有记录不动 |
| 改已发布文件（加一个空格） | 拒绝：校验和不一致 |
| 旧程序（只有基线）连新库（有增量） | 拒绝：版本高于程序支持 |
| CRLF 与 LF 的校验和 | 一致（读入后统一换行再哈希） |
| `CREATE INDEX CONCURRENTLY` | **失败**：`cannot run inside a transaction block`，且整批（含基线）回滚 |
| 老库（旧逻辑建，有数据）接管 | 通过：基线只记录，数据保留，后续增量只执行新增 |
| 带 v0.2 残留（`trusted_internal` 列、`ai_providers` 表）的老库接管 | 通过：残留被清理，结构与全新库一致 |
| 接管钩子里失败 | 整体回滚，库回到接管前，`schema_migrations` 表都不留 |
| 接管后的老库 vs 全新库 | 仅 2 个索引的谓词写法不同（`idx_task_poll`、`uk_agent_runs_active`，老库是 `ANY(ARRAY[...])`），功能等价 |

**接管的关键发现（实测，会让第一版实现出错）**：

1. 接管钩子里如果跑 `AutoMigrate(model.All()...)`，它按**当前模型**建结构。当程序里同时有"基线 + 后续增量"时，钩子已经把增量要加的列加好了，随后的增量报 `column "phone_no" already exists`，整批回滚，**老库升级失败**。
2. 如果钩子里去掉 `AutoMigrate` 来绕开问题，那么**停在更早版本的老库（缺基线里有的表和列）会被悄悄放过**：实测接管后 `conversations` 表和 `users.avatar_key` 仍然缺失，`verify` 却通过。
3. 两者的解法是同一个：**接管只能由一个只含基线迁移的过渡版本完成**，此时钩子里的 `AutoMigrate` 等于基线，不会和增量冲突，落后的库也被补齐（实测：接管后 `conversations=1`、`avatar_key=1`、`idx_task_poll=1`）。迁移器在检测到"老库 + 计划里多于一个迁移"时直接拒绝启动（实测，库未被改动）。

## 3. 用户与场景

这是内部工程设计，"用户"是三类人：

- **开发者**：改了 GORM 模型，想自动得到迁移 SQL，不想手写 `ALTER TABLE`。
- **部署者 / 运维**：升级时希望迁移自己完成，失败了库别坏；多开实例别互相踩；旧版本别连新库。
- **老用户**：库是 `AutoMigrate` 建出来的，升级到新机制不能丢数据、不能被要求手工操作。

触发场景：

1. 开发者给 `User` 加字段 → 一条命令生成迁移，评审时看得到 SQL。
2. 开发者删字段或改列名 → 想知道会不会丢数据。
3. 部署者升级 → 迁移先于服务执行，失败则服务不启动、库保持原样。
4. 老用户第一次升级到新机制 → 自动接管，不报"表已存在"。
5. 旧版本镜像误连新库 → 被拒绝，而不是在运行时报错。
6. CI → 发现"改了模型忘了生成迁移"、"改了已发布的迁移文件"。

成功指标（**提案**，除标注外均已在原型里实测）：

- `make migrate-diff` 一条命令得到迁移文件。
- 全新库与接管后的老库结构一致（差异仅 2 个索引的谓词写法，见 2.3）。
- 并发启动 4 个实例，最终只有一份迁移被执行。
- 迁移文件中途失败，库回到迁移前状态。
- 已发布的迁移文件被改动，启动即拒绝。
- 旧程序连新库被拒绝。

### 4.1 open-ai-canvas 的自研迁移器

来源：<https://github.com/ddcat-ai/open-ai-canvas>（Go 模块名 `yingce`），重点文件 `backend/internal/database/migrations.go`（596 行）、`backend/cmd/migrate-schema/main.go`、`docker-compose.deploy.yml`、`docs/content/docs/backend/backend-database.mdx`、`backend/internal/database/migrations_test.go`。**只读了源码和文档，没有运行过它的迁移器。**

**观察到的事实**

- 迁移清单是 Go 切片，每项 `{version, name, checksum, apply func(*gorm.DB)}`，当前到 v50。迁移内容是 Go 函数：多数是 `tx.AutoMigrate(&model.Xxx{})`，也有 `HasColumn` + `AddColumn`，复杂的是独立函数（含数据回填）。
- 版本表 `schema_migrations`（version、name、checksum、applied_at）。**校验和是手写字符串常量**（如 `"sha256:channel-presentation-v9-20260908"`），我没有在代码里找到计算哈希的逻辑。
- 整个迁移在一个事务里，开头 `pg_advisory_xact_lock`。失败整体回滚，有测试覆盖。
- 已应用版本的名称或校验和不一致就拒绝；库版本高于程序也拒绝（"拒绝旧程序连接新数据库"）。
- 独立命令 `migrate-schema`：`up`、`status`、`verify`，另有数据修复命令。
- **生产部署里迁移是独立的一次性服务**：`docker-compose.deploy.yml` 有 `migrate` 服务（`entrypoint: migrate-schema`），backend 用 `depends_on: migrate: condition: service_completed_successfully`。`CANVAS_AUTO_MIGRATE=false` 时 backend 启动只调 `RequireSchemaVersion`，不自己迁移；开发环境默认启动时自动迁移。
- 文档明确："后续迁移必须新增版本，不得修改已经发布迁移的实现或校验和"；"此修复不提供降级迁移……应恢复匹配的备份和版本"。
- 它遇到过真实的迁移编号冲突（v6/v7 顺序），写了专门逻辑：只在名称和校验和都精确匹配历史记录时才采用历史顺序，否则拒绝（`migrationsForDatabase`）。
- 测试覆盖：`CurrentSchemaVersion` 与清单一致、失败迁移回滚、校验和不一致被拒、逐版本的"升级已有库"，CI 起真实 Postgres 16，并有一步检查"依赖服务的测试没被跳过"。

**对本项目的启发**：生产迁移作为部署编排的独立一步（只有一个执行者）；库版本高于程序则拒绝；版本 + 名称 + 校验和三重校验；"只增不改"的约定与测试。

**不照搬的部分**：迁移是手写 Go 函数，没有自动生成 SQL，没有漂移检测；迁移里嵌了大量数据修复，难以审查；同时支持 SQLite 与 PG，要兼顾两种方言。

| 新增运行时依赖 | 无（只在开发/CI） | goose + pgx | golang-migrate + 驱动 | **pgx（已在主模块）** |

### 4.3 Atlas 的版本与许可边界

来源：[社区版说明](https://atlasgo.io/community-edition)、[功能页](https://atlasgo.io/features)、[定价页](https://atlasgo.io/pricing)。

- 源码 Apache-2.0（仓库 `LICENSE` 已核对）。官方二进制有两种：**标准版**与**社区版**（`atlasgo.sh -- --community`，或 Docker 镜像 `arigaio/atlas:latest-community`）。

- 社区版**支持**：`migrate diff/apply/status`，PostgreSQL 的表/列/索引/约束（页面对 PG 核心对象没有逐项列出，以上为实测可用的部分）。

**对本项目**：模型里没有视图、触发器、函数，社区版够用；`external_schema` 用 loader 绕开。

### 4.4 Atlas GORM provider

来源：<https://github.com/ariga/atlas-provider-gorm>，v0.6.1（2026-05-26），Apache-2.0，未归档。

## 5. 设计原则

1. **开发和生产跑同一批文件**。迁移 SQL 提交进仓库、编进二进制，没有"开发靠 AutoMigrate、生产靠迁移"的两条路。（依据：用户要求"开发和生产一样"；实测 embed 执行可行。）
2. **SQL 由工具生成，但人必须看**。社区版没有 lint，改列名会被生成成删列加列（实测）。评审生成的 SQL 是流程的一部分。
3. **失败时库保持干净**。整批一个事务，任何一步失败都回滚到迁移前（实测）。
4. **已发布的迁移不可改，只能新增**。运行时用文件内容的真实哈希校验，改一个空格也拒绝（实测）。
5. **旧程序不能连新库**。库的最高版本高于程序已知版本，启动即拒绝（实测）。
6. **老库自动接管，但只能经过过渡版本**。迁移器只在"程序里只有基线迁移"时才接管；否则拒绝并不动库（实测）。这是为了避免"落后的老库被悄悄放过"和"接管钩子与增量冲突"两类问题，见 2.3。
7. **回退靠备份，不靠 Down**。本方案不提供 Down；回退仍按系统更新设计走"还原备份"。
8. **生产的迁移是部署编排的一步**。参考 open-ai-canvas：compose 里一次性 `migrate` 服务先跑，backend 只校验版本，只有一个执行者。（依据：4.1。）

## 6. 推荐方案

### 6.1 一句话

开发时：改 GORM 模型 → loader 输出 `schema.sql` → Atlas 社区版 `migrate diff` 生成纯 SQL 迁移 → 评审后提交。运行时：迁移器读取嵌入的 SQL，在事务内加锁、校验、执行；生产由 compose 的 `migrate` 服务先跑，backend 启动只做版本校验。

### 6.2 目录结构（提案）

```text
backend/
├── migrations/                      # 迁移文件，提交进仓库
│   ├── 20261013030847_baseline.sql  # 基线：当前全部 33 张表 + idx_task_poll
│   ├── 2026xxxxxxxxxx_xxx.sql       # 之后的增量，由 atlas 生成
│   ├── atlas.sum                    # Atlas 目录完整性校验，必须一起提交
│   └── embed.go                     # //go:embed *.sql，导出 embed.FS
├── cmd/
│   ├── server/                      # 现有
│   ├── migrate/                     # 新增：一次性迁移命令（up / status / verify）
│   └── migrate-schema/              # 新增：loader，加载 model.All()，输出 schema.sql 到 stdout
├── atlas.hcl                        # env "gorm"：src=file://schema.sql，dir=file://migrations
└── internal/
    └── migrator/                    # 新增：迁移器（实测原型 155 行）
```

说明：

- `migrations/` 放在 `backend/` 根而不是 `internal/`，因为 Atlas 要按路径读它，`embed.go` 必须与 `*.sql` 同目录。
- `migrations/embed.go` 的 `//go:embed *.sql` 不会把 `atlas.sum` 嵌进去（实测原型使用该写法）。
- loader 放在 `cmd/migrate-schema/`，属于主模块。**独立模块方案已实测否决**（4.4）。
- `cmd/migrate` 要新增进 Dockerfile 的构建（现在只构建 `./cmd/server`，[Dockerfile:19](../../../backend/Dockerfile)），否则 compose 的 `migrate` 服务没有可执行文件。**这是对 Dockerfile 的修改**。也可以让 `migrate` 作为 `server` 的子命令（`server migrate`），做法与现有的 `server plugin-runner` 一致（[main.go:17](../../../backend/cmd/server/main.go)），这样不用改 Dockerfile，**两种都可行，待确认**。
- 分层：`internal/migrator` 只依赖 `database/sql`，不 import gorm，不属于 service 层，符合 depguard 规则。接管钩子（需要 gorm 和旧的 repository 函数）由 `initialize` 提供并传入。

### 6.3 迁移器的行为（提案，除标注外均已实测）

**`Run(db *sql.DB, plan, probeTable, takeoverHook)`** 在一个事务里依次：

1. `SELECT pg_advisory_xact_lock(<固定键>)`。事务级锁，随事务结束自动释放，进程崩溃也不会残留。
2. **锁内**检测：`probeTable`（如 `users`）存在，且 `schema_migrations` 不存在 → 判定为"待接管的老库"。
3. 若待接管且计划里迁移数 > 1 → **返回错误并回滚**（不动库）。
4. `CREATE TABLE IF NOT EXISTS schema_migrations (version, name, checksum, applied_at)`。
5. 逐个迁移：已有记录则比对名称与校验和，不一致即报错；没有记录则执行。接管时第一个迁移（基线）不执行 SQL，改为执行 `takeoverHook`，然后记录。
6. 提交。

**`Verify(db, plan)`** 只读：库里最高版本 < 程序最高版本 → 过旧；> → 过新，拒绝；相等则逐条比对名称与校验和。

**文件加载（`Load`）**：文件名必须匹配 `^\d{14}_[A-Za-z0-9_\-]+\.sql$`，版本重复报错；读入后统一 `\r\n → \n` 再算 SHA-256（实测 CRLF 与 LF 校验和一致，避免 Windows 检出后哈希变化；仓库 `.gitattributes` 本就设了 `* text=auto eol=lf`，是双保险）。

**版本号**：直接用 Atlas 的 14 位时间戳（`20261013030847`）作为 `version`（`bigint`）。

### 6.4 部署形态（提案，参考 open-ai-canvas，本项目**未实测 compose 编排**）

| 环境 | 谁迁移 | backend 启动时 |
| --- | --- | --- |
| 开发（`auto_migrate: true`） | backend 启动时调用 `Run` | 随后已是最新 |
| 生产（compose） | 新增一次性 `migrate` 服务，`depends_on: postgres(healthy)` | `Verify` 通过才继续；版本不符直接退出 |

compose 草案：

```yaml
migrate:
  image: ${IMAGE_REGISTRY:-ghcr.io}/${IMAGE_OWNER:-zaylora}/video-canvas-backend:${IMAGE_TAG:-latest}
  entrypoint: ["/app/server", "migrate"]   # 或独立二进制，见 6.2
  environment:
    APP_DATABASE_DSN: ...                  # 与 backend 相同
  depends_on:
    postgres: { condition: service_healthy }
  restart: "no"

backend:
  depends_on:
    migrate: { condition: service_completed_successfully }
  environment:
    APP_DATABASE_AUTO_MIGRATE: "false"     # 生产只校验，不自己迁移
```

- `restart: "no"`：迁移失败不能无限重启重试。失败后 `backend` 因依赖未成功而不会启动，旧 backend 容器若还在运行则由更新器处理（见 8.8）。
- 现状 `auto_migrate` 在 `config.yaml` 默认 `true`，compose 没覆盖；改成生产 `false` 后，**直接 `docker compose up` 的老用户**（没有 `migrate` 服务的旧 compose）会因 backend 校验失败而无法启动。`update.sh` 每次会同步 compose（[update.sh:93-111](../../../scripts/update.sh)），所以走脚本升级的用户会拿到新 compose；手动改了 compose 的用户不会。**这是一个升级兼容性风险，待确认**。

### 6.5 发布与老库接管（核心风险，提案）

**发布分两个版本**（这是实测得出的硬约束，见 2.3）：

| 版本 | 内容 | 目的 |
| --- | --- | --- |
| **过渡版本 N** | 迁移计划**只有基线**；接管钩子 = 旧 `NewDB` 的全部逻辑（5 个手写函数 + `AutoMigrate` + 其余旧步骤）；之后不再有 `AutoMigrate` 以外的结构变更 | 把所有老库带到基线结构并记录版本 |
| 版本 N+1 起 | 允许有增量迁移；迁移器拒绝接管 | 之后只走增量 |

**为什么必须这样**：

- 在计划含增量时，钩子里的 `AutoMigrate` 按**当前模型**建结构，会把增量要加的列提前加好，随后的增量报"列已存在"并整批回滚（实测）。
- 如果去掉钩子里的 `AutoMigrate`，落后的老库缺表缺列却被放过，`verify` 还通过（实测）。
- 在过渡版本里，钩子里的 `AutoMigrate` 等于基线，落后的老库被补齐，结果与全新库一致（实测）。

**老库升级路径**：

```text
任意老版本 ──▶ 过渡版本 N（接管：旧逻辑 + 记录基线）──▶ N+1 ──▶ ...
                  ▲
                  └─ 如果直接从很旧的版本升到 N+1：迁移器拒绝，提示先升级到 N
```

**对用户的影响**：必须逐步升级经过 N。`update.sh --tag` 可以直接指定任意版本，所以**文档和 Release 说明必须写明**；系统更新设计的前置检查也要加一条（见 8.8）。

**接管钩子的实现方式（原型）**：在迁移器的事务上用 `postgres.New(postgres.Config{Conn: tx})` 套一层 GORM，把旧函数原样调用。实测可用，且钩子内失败会整体回滚。

**第二步（清理）**：确认没有用户停在 N 之前后，删除 5 个手写函数、钩子里的 `AutoMigrate` 与对应 552 行测试，接管逻辑只保留"记录基线"。

### 6.6 基线怎么生成（提案，两处模型改动已实测）

1. 把 `uk_agent_runs_active` 的 `where:status IN (...)` 改成等价的 `OR` 写法（[agent.go:108](../../../backend/internal/model/agent.go)）。
2. 把 `idx_task_poll` 写进 `GenerationTask.NextPollAt` 的标签：`index:idx_task_poll,where:status = 'pending' OR status = 'queued' OR status = 'running' OR status = 'finalizing'`。实测 loader 输出了它，基线里出现，且无变更再 diff 不误报。同时删除 [db.go:66-71](../../../backend/internal/initialize/db.go) 的手写语句。
3. 运行 loader + `atlas migrate diff baseline`，得到约 31 KB 的基线。
4. **老库里这两个索引仍是 `IN` 的形态**（`ANY(ARRAY[...])`），与新库只差谓词写法，功能等价，**不额外写迁移**（实测差异仅此二处）。

## 7. 状态与异常

### 7.1 启动时的状态（提案）

| 状态 | 判定 | 行为 | 依据 |
| --- | --- | --- | --- |
| `auto_migrate=false`，生产 | 配置 | backend 只调 `Verify`，不迁移 | 参考 4.1 |
| 全新库 | 没有业务表，没有 `schema_migrations` | 从基线开始建 | 实测 |
| 老库，计划只含基线（过渡版本） | 有业务表，无 `schema_migrations` | 钩子（旧逻辑）→ 记录基线 | 实测 |
| 老库，计划含增量 | 同上，但计划里迁移数 > 1 | **拒绝，库不动** | 实测 |
| 已接管，有待执行迁移 | 记录最大版本 < 目录最大版本 | 执行差额 | 实测 |
| 已接管，已是最新 | 版本一致且校验和全对 | 立即继续启动 | 实测 |
| 库版本**高于**程序 | 记录最大版本 > 目录最大版本 | **拒绝**：旧程序连新库 | 实测 |
| 已应用的迁移被改 | 名称或校验和不一致 | **拒绝** | 实测 |
| 其他实例持锁 | `pg_advisory_xact_lock` 阻塞 | 等待至对方提交，再检测 | 实测并发：4 实例正常 |

### 7.2 迁移失败（实测）

| 情形 | 结果 |
| --- | --- |
| 多语句文件中第 3 条语句出错 | 整批回滚；前两条的效果不残留；该版本不记录；返回 `执行迁移 <版本>（<名称>）：<PG 错误>`。库里 `schema_migrations` 视情况也不存在（空库首次运行时一并回滚） |
| 基线已应用后，增量失败 | 只回滚增量，已有记录不动 |
| 接管钩子内失败 | 整体回滚，库回到接管前，`schema_migrations` 表都不留 |
| 重试 | 修好后重新运行即可，没有 `dirty` 状态 |
| 容器重启策略 | `migrate` 服务应 `restart: "no"`；backend 因依赖未成功不启动（提案） |
| 事务内不能执行的语句（`CREATE INDEX CONCURRENTLY`） | **失败并整批回滚**（实测），见 7.3 |

### 7.3 异常与边界

| 异常 | 处理 | 状态 |
| --- | --- | --- |
| 并发启动 | 事务级 advisory lock，一个执行其余等待 | 实测 |
| 并发接管同一个老库 | 锁内检测，只接管一次 | 实测 |
| 持锁进程崩溃 | 事务级锁随连接断开自动释放 | PG 语义；**未测** |
| 锁等待时间 | 默认无超时：实测另一会话持锁 8 秒，等待方就等 8 秒。解法：在事务里先 `SET LOCAL lock_timeout = '<时长>'` 再拿锁；实测设 2 秒时，等待方 2 秒后报 `canceling statement due to lock timeout`，对 advisory lock 有效 | 已实测；默认时长（建议 10 分钟）是**我设的值**，非实测；迁移器原型**还没加这一步** |
| 大表加索引 | 默认 `CREATE INDEX` 阻塞写入；`CONCURRENTLY` 在整批事务里不可用 | 实测限制，**未解决**，见 11 |
| 迁移耗时过长导致健康检查超时 | 生产迁移独立成 `migrate` 服务，不占 backend 的健康检查窗口 | 推断；compose 编排**未实测** |
| 迁移文件版本号冲突（两分支同秒生成） | `Load` 报"版本重复"；`atlas.sum` 在合并时会冲突，强制重新生成 | `Load` 的重复检测代码有，**未单独测**；`atlas.sum` 冲突是 Atlas 设计行为，未实测 |
| 手改了迁移文件但没重算 `atlas.sum` | Atlas 报校验失败 | Atlas 设计行为，**未实测** |
| 回滚到旧版本镜像 | 旧镜像不带迁移器；库结构若已被新迁移改过，旧代码的 `AutoMigrate` 可能遇到被删列 | 推断；回退靠备份还原，见 8.8 |
| 迁移里写了依赖当前模型的代码 | 禁止：基线与增量都是纯 SQL，不引用 Go 模型；接管钩子是唯一例外且仅存在于过渡版本 | 约定 |

### 7.4 日常开发的异常

| 情形 | 处理 |
| --- | --- |
| 改了模型没生成迁移 | CI 的 `migrate-check` 失败（实测漂移检测可用） |
| 改列名 | Atlas 生成"删列 + 加列"（实测，**会丢数据**）。评审时手改为 `ALTER TABLE ... RENAME COLUMN`，然后运行 `make migrate-hash` 重算 `atlas.sum` |
| 删字段 | 生成 `DROP COLUMN`。评审确认数据可丢 |
| 手改了迁移文件 | 已发布的文件不得修改；未发布的可改，改完重算 `atlas.sum` |
| 在多值 `IN` 上建部分索引 | Atlas 会每次误报重建（实测）；用 `OR` 写法，约定写进开发规范 |
| 数据回填（`UPDATE`/`INSERT`） | 写进迁移 SQL 文件（纯 SQL），不要写 Go；复杂回填的做法**未设计**，见 11 |

### 8.2 `schema_migrations` 表（实测原型）

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `version` | `bigint` 主键 | Atlas 的 14 位时间戳 |
| `name` | `varchar(160)` | 文件名中的名称部分 |

### 8.3 迁移器接口（提案，签名来自实测原型）

```go
package migrator

type Migration struct {
    Version  int64
    Name     string
    Checksum string // 文件内容 SHA-256（换行已统一）
    SQL      string
}

// Load 读取目录下所有迁移，按版本升序；命名不合法、版本重复、目录为空都报错。
func Load(fsys fs.FS, dir string) ([]Migration, error)

// Hook 在接管时代替"执行基线 SQL"，与记录基线在同一事务内。
type Hook func(tx *sql.Tx) error

// Run：事务内 xact lock -> 锁内检测接管 -> 建记录表 -> 逐个应用 -> 提交。
// 接管时（有 probeTable、无 schema_migrations）：计划多于一个迁移则报错；否则基线不执行 SQL，改调 takeoverHook。
func Run(db *sql.DB, plan []Migration, probeTable string, takeoverHook Hook) error

// Verify 只读校验：过旧、过新、名称或校验和不一致都返回错误。
func Verify(db *sql.DB, plan []Migration) error
```

**还没写进原型的部分（实现时补）**：`SET LOCAL lock_timeout`；日志（每个迁移一条：版本、名称、耗时）；`Status` 只读查询（供 `status` 命令）；对 `Hook` 的 `*gorm.DB` 包装放在 `initialize`，不放在 `migrator`。

### 8.4 `initialize/db.go` 的新结构（提案）

```go
func NewDB(cfg config.Database) (*gorm.DB, error) {
    db, err := gorm.Open(...)
    // 连接池设置同现状

    sqlDB, _ := db.DB()
    plan, err := migrator.Load(migrations.FS, ".")
    if err != nil { return nil, err }

    if cfg.AutoMigrate {
        // 开发与旧部署：启动时迁移。老库接管钩子只在过渡版本里存在。
        if err := migrator.Run(sqlDB, plan, "users", legacyTakeover(db)); err != nil {
            return nil, fmt.Errorf("migrate: %w", err)
        }
    } else {
        // 生产：迁移由 migrate 服务完成，这里只校验。
        if err := migrator.Verify(sqlDB, plan); err != nil {
            return nil, fmt.Errorf("数据库结构不匹配：%w", err)
        }
    }
    return db, nil
}
```

注意：`legacyTakeover` 要在 `*sql.Tx` 上重新构造 GORM（原型 `postgres.New(postgres.Config{Conn: tx})`），**不能**直接用传入的 `db`，否则钩子里的语句不在迁移器的事务里，回滚保证就没了。

**这对系统更新是净改善**：迁移失败时数据库保持干净（实测），不需要还原备份，也不会丢"备份之后的写入"。这修正了系统更新设计里"自动回退也会丢备份之后的写入"的结论，**仅对迁移失败这一种触发有效**。启动失败、健康验证失败仍需要还原备份。

另有两条新增前置检查（提案）：

1. 目标版本是**过渡版本之后的版本**，而当前库是未接管的老库 → 前置检查失败，提示先升级到过渡版本（对应 6.5）。
2. 目标版本的迁移目录包含 `DROP COLUMN` / `DROP TABLE` → 确认框里提示"含删除数据的迁移"。

### 8.9 实现难点

1. **接管钩子的事务包装**：`*sql.Tx` 上套 GORM，钩子里所有语句必须在同一事务内（8.4 的注意事项）。
2. **过渡版本的发布节奏**：用户可能直接跳版本。靠迁移器拒绝加文档，没有别的兜底。
3. **老库没有真实验证**（2.4）。
4. **大表加索引**与整批事务的冲突（7.3），目前无解。
5. **compose 变更的升级兼容**（6.4）：手动改过 compose 的用户升级时可能 backend 校验失败。
6. **Windows 开发机装 Atlas** 未验证；`make` 在 Windows 上本就不一定可用（AGENTS.md 提到"没装 make 时直接运行注释里的命令"）。
7. **提交前检查**：`make lint` 的 `depguard`、`funlen` 对新代码生效。

## 9. 方案取舍

### 9.1 方案演进

| 阶段 | 方案 | 为什么被改 |
| --- | --- | --- |
| 1 | GORM + Atlas 一把梭（生成与执行都用 Atlas） | 用户最初设想。Atlas 没有应用内执行的 Go 库，社区版又不支持 `external_schema` |
| 2 | Atlas 标准版 + goose | 标准版未登录每次提示登录，`lint`/`down` 仍是 Pro |
| 3 | Atlas 社区版 + loader + goose | 实测可行，但：goose 的锁不覆盖"接管检测"；goose 不校验已发布文件；版本过新需自己加 |
| 4 | **Atlas 社区版 + loader + 自研执行器**（本设计） | 研究 open-ai-canvas 后，用户提出"按它的方法自研"，我实测了混合方案（Atlas 生成 SQL + 自研执行器），补上了 goose 的几个缺口 |

### 9.2 执行器

权重是**我设的默认值**，用户没有给过；分数是我的判断，不是测量结果。

| 维度（权重） | 自研（本方案） | goose | golang-migrate |
| --- | --- | --- | --- |
| 失败后库可恢复（25%） | 5：整批回滚，无 dirty（实测） | 5：每文件回滚，可重试（实测） | 2：回滚但标 dirty，重启拒绝运行（实测） |
| 老库接管（20%） | 5：锁内检测，4 进程同时接管正常（实测） | 3：手工插基线可行，检测与锁不衔接（设计上） | 3：未测，按 goose 估 |
| 校验已发布文件被改（15%） | 5：真实哈希（实测） | 1：不校验 | 1：不校验（未核实） |
| 旧程序连新库（10%） | 5：内建拒绝（实测） | 2：要自己加 | 2：要自己加 |
| 大表加索引（10%） | 1：整批事务，CONCURRENTLY 不可用（实测） | 4：`NO TRANSACTION` 可用 | 4：推断可行 |
| 维护成本（10%） | 2：自己维护约 200 行 | 5：开源维护 | 5：开源维护 |
| 新增运行时依赖（10%） | 5：pgx 已在主模块 | 3：goose | 3：golang-migrate + 驱动 |
| 加权 | 4.30 | 3.40 | 2.65 |

分数是我按上面权重算的，仅用于说明排序依据，不是精确度量。**自研方案最大的失分点是大表加索引**，这是真实的代价，不要被分数掩盖。

### 9.3 SQL 生成器

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| Atlas 社区版 + loader | 免费，不登录；自动 diff；漂移检测可用 | 无 lint；改名生成删列加列；多一步 loader | **采用** |
| Atlas 标准版 | `external_schema` 一步到位 | 每次提示登录；`lint` 需 Pro；账号依赖 | 搁置 |
| 手写 SQL | 零依赖 | 要靠人记住每个模型改动 | 搁置：违背"自动生成" |
| GORM `AutoMigrate` 的 `DryRun` 打印 SQL | 不引入外部工具 | 不会生成完整 DDL 序列；**未实测** | 搁置，未验证 |

### 9.4 明确放弃

- **用 Atlas CLI 在生产启动时执行**：镜像要装二进制；并发时其余进程直接报错退出（实测）。
- **golang-migrate**：失败后 `dirty` 让服务卡死（实测）。
- **goose**：在本项目的接管与校验两点上不如自研（实测）；但它在大表索引上更灵活，这是放弃它的真实代价。
- **依赖 Atlas 的 lint 与 down**：社区版没有。
- **独立 Go 模块隔离 provider**：实测被 `internal` 规则否决。
- **一次性删掉 5 个手写函数**：没有真实历史库验证，先在过渡版本里保留。
- **提供 Down 迁移**：不提供；回退靠备份还原。
- **每文件独立事务**：自研版整批一个事务，换来"失败时连基线都回滚、库回到空"的强保证，代价见大表索引。

## 10. MVP 与后续

### 第一步：过渡版本 N（新机制上线，旧路径只用于接管）

范围：基线迁移（只有一个文件）、`internal/migrator`、`cmd/migrate-schema`、`cmd/migrate`（或 `server migrate`）、`atlas.hcl`、`NewDB` 改造、接管钩子（旧逻辑）、`make` 目标、CI 漂移检测与破坏性变更检查、`agent.go` 与 `generation_task.go` 的两处模型改动、文档。

验收条件：

1. 全新空库启动：建出 33 张业务表与 `schema_migrations`，含 `idx_task_poll`，与旧机制建出的库相比，结构差异仅限已知的 2 个索引谓词写法。
2. 老库（`AutoMigrate` 建出，无版本表）启动：自动接管，不报"表已存在"；数据保留；第二次启动无事可做。
3. **停在更早版本的老库**（缺表缺列）：接管后补齐，与全新库一致。**需要用真实旧 tag 验证**，不能只靠手工删表模拟。
4. 同时启动 4 个实例：只有一个执行迁移，`schema_migrations` 记录唯一。
5. 迁移文件中途出错：服务不启动，库回到迁移前，修好后重启成功。
6. 已发布的迁移文件被改动（含一个空格）：启动即拒绝。
7. 旧程序（版本低于库）连新库：被拒绝。
8. 改模型后不生成迁移，CI 失败；生成后 CI 通过；未改模型时 `migrate diff` 产出 0 个文件。
9. 迁移含 `DROP COLUMN` 时 CI 失败，除非显式标注。
10. 生产 compose：`migrate` 服务成功后 backend 才启动；`migrate` 失败时 backend 不启动。**需要实际跑 compose 验证**。
11. 镜像大小与构建不因 Atlas 变大；`make fmt`、`make lint`、`make test` 全过。

### 第二步：增量迁移时代（版本 N+1 起）

范围：之后的模型变更都走"生成 → 评审 → 提交"流程；迁移器拒绝接管未接管的老库。

验收条件：

1. 从过渡版本 N 升级到 N+1：只执行新增文件。
2. 从未接管的老库直接升级到 N+1：被拒绝，提示先升级到 N，库未被改动。
3. 文档与 Release 说明写明升级路径。

### 第三步：清理旧路径

前提：确认没有用户停在过渡版本 N 之前。

范围：删除 `repository/migrate.go` 中 5 个函数、钩子里的 `AutoMigrate`、对应 552 行测试；接管逻辑只保留"记录基线"。

验收条件：全量测试通过，无引用残留。
