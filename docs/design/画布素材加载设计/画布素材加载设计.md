# 画布素材加载设计（大画布首次打开提速）

> 范围：画布节点很多、且浏览器没有缓存时，图片和视频节点加载极慢。本文给出图片“懒加载 / 缩略图”和视频“更快加载”两个方向的结论与落地方案。
> 日期：2026-10-04。状态：**已按本设计实现**（后端、后台页面、画布前端；见第 13 节“实现记录”）。**第 0 步的三家实测还没做**，所以文中凡写“未验证”的点仍然成立。
> 证据约定：**事实**附文件路径或来源链接；**推断**是基于事实的判断；**提案**是尚未实现的设计。外部来源由调研子任务检索，Cloudflare 的三个关键页面我另行打开核对过；版本号、体积和部分价格来自 npm registry、bundlephobia 或第三方汇总，未逐条独立复核，已在第 12 节标出。
> 方案演进：本文经历过两次大的转向。①最初设计为“后端生成缩略图”，核对服务器规格和带宽后搁置（保留在第 9 节）；②评估第三方处理服务后改为**用云厂商自带的图片 / 视频帧处理**；③需求方进一步要求在后台新增独立模块「**图片处理服务管理**」，支持 **Cloudflare R2、腾讯云数据万象、阿里云 OSS** 三家（AWS 不做），其中腾讯云、阿里云的处理服务绑定自家存储。配套的可点击演示见 [图片处理服务管理-演示.html](./图片处理服务管理-演示.html)。

## 1. 设计摘要

**问题**：画布缩到 14% 时，上百个图片 / 视频节点同时进入视口，浏览器一次性请求所有原图（图片几 MB、视频几十 MB），首次（无缓存）打开极慢。

**两个原始问题的回答**：

| 问题                     | 结论                                                                                                                                                                                                                    |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 图片能不能懒加载？       | **能，但只靠 `loading="lazy"` 不够。** Chrome 的触发距离约为视口外 1250px，缩到 14% 时所有节点都落在这个范围内，等于没有懒加载。必须按**缩放级别**决定加载哪一档图，并提供**缩略图**。                                  |
| 视频有没有更快的播放器？ | **没有。** 对几秒到十几秒的单个 mp4，换播放器库不会更快；hls.js / Shaka / dash.js 的收益只来自 HLS/DASH 切片转码，Plyr / Vidstack / media-chrome 只是换皮肤。真正有效的是：**平时只显示封面图，点击才挂载 `<video>`**。 |

**已与需求方逐题确认的决定**：

| #   | 决定                                                        | 一句话                                                                                                           |
| --- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| D1  | **低缩放显示小缩略图**                                      | 缩小后仍能认出每张图和每个视频，不是纯占位                                                                       |
| D2  | **缩略图 / 封面交给云厂商自带处理，不在后端生成**           | 图片用厂商的图片处理，视频首帧用厂商的截帧；后端只负责把变体地址 302 到处理 URL，不读原图、不占 CPU、不装 ffmpeg |
| D3  | **R2 桶绑自定义域名并公开读**                               | Cloudflare 处理需要源在同一 zone；素材 key 含随机 UUID，和现有 `/files` 不鉴权、靠 key 不可猜测的模型一致        |
| D4  | **视频点击播放才挂载 `<video>`**                            | 首屏零视频流量，也不碰 Chrome 的 WebMediaPlayer 数量上限                                                         |
| D5  | **没有处理服务的存储回退原图 / 占位**                       | 本地磁盘、AWS S3、以及未配置处理服务的存储：图片照旧加载原图，视频显示占位                                       |
| D6  | **一次交付完整方案**                                        | 变体地址、后台模块、前端 LOD 和视频 facade 一起上线                                                              |
| D7  | **后台新增「图片处理服务管理」模块**                        | 管理“哪套存储用哪家处理服务”；沿用模型配置的草稿 → 校验 → 试跑 → 发布 / 回滚流程                                 |
| D8  | **一个存储同时只有一个已发布的处理服务**                    | 需要换厂商时先停用旧的，或发布新的时自动替换旧的（可回滚）                                                       |
| D9  | **本期支持三家：Cloudflare R2、腾讯云数据万象、阿里云 OSS** | 腾讯云、阿里云的处理服务**绑定自家存储**；Cloudflare 只支持 R2                                                   |
| D10 | **引入 COS Go SDK 与 OSS Go SDK**                           | 需求方明确同意；用于私有读桶的带处理参数签名，以及阿里云视频首帧（S3 协议不支持 `video/`）。版本、许可证见 4.4   |
| D11 | **AWS 动态图片转换不做**                                    | 它需要客户自部署，官方文档也没查到视频首帧支持                                                                   |
| D12 | **不提示“未覆盖素材”，不做存储迁移**                        | 处理服务只对它绑定的存储里的素材生效，这个边界写在文档里，后台不再展示覆盖统计（需求方：“不用管”）               |

我自己的结论（不属于“引入依赖”，不需要单独征求意见）：**不引入任何视频播放器库**，理由见第 4.4 节。**前端不新增依赖；后端新增两个厂商 SDK（D10，已获同意）。**

### 2.2 设计约束

1. 画布 payload 里的 `src` 是持久化的稳定地址，**不能改格式**，否则所有老画布都要迁移（见存储配置设计 D2）。
2. 素材可能在本地磁盘，也可能在 S3 兼容存储；**线上用的是 Cloudflare R2**（需求方确认）。
3. **部署约束（需求方确认）**：后端服务器带宽小，对象存储在外部。
4. **服务器规格（需求方提供的控制台截图）**：腾讯云轻量应用服务器（首尔二区），2 核 CPU、4GB 内存、60GB SSD 系统盘、流量包 1536GB/月、**峰值带宽 30Mbps**。含义：① 30Mbps 约 3.75MB/s，一张 3MB 的图约要 1 秒、一个 30MB 的视频约要 8 秒，素材一旦经过后端带宽就是瓶颈；② `docker-compose.yml` 里 postgres、redis、backend、plugin-runner、web 看起来都在这一台上（推断，我没有确认线上拓扑），不适合再叠加图片解码和 ffmpeg；③ 这 30Mbps 是否同时限制入站，我没有核实。
5. 项目约定：先写失败测试再实现；后端测试放 `backend/internal/tests/`，前端放 `web/src/tests/`；不使用 Playwright 做端到端。

### 2.3 当前缺口

- 没有任何“小图 / 封面”这一档资源，前端想省流量也无从下手。
- `/files` 对每个请求都查一次库；上百个请求就是上百次查询。
- 节点不知道自己当前缩放级别，也没有视口内 / 视口外的概念。
- 视频没有首帧占位，只能靠 `<video>` 自己拉元数据。

### 2.4 现象的归因（推断）

截图右下角计数显示 `12 / 40`，我推测是连线数 / 节点数（未验证）。素材体积的量级由需求方确认为“图片几 MB、视频几十 MB”，40 个节点按 3MB 算就是约 120MB。**线上已有 Caddy + TLS，浏览器到站点大概率已是 HTTP/2，“每个 host 约 6 个并发连接”的排队更可能只出现在本地开发或没走 TLS 的访问里，不是线上的主因**（这一条是我前面判断错的地方，已修正）。线上的主要成本是字节数本身，再加上每张图一次 `/files` 查库和一次 302 跳转到存储域名。

## 3. 用户与场景

- **用户**：在画布上编排 AI 图片 / 视频生成的创作者，一张画布里有几十到上百个素材节点（角色设定图、道具、场景、生成的视频）。
- **触发场景**：打开一张已有的大画布；清缓存或换设备后首次打开；缩小到全局视图找某个素材。
- **主任务**：打开后先全局浏览，找到目标区域，放大，再点开某个视频播放。
- **成功指标（提案，基线待测）**：
  1. 无缓存、DevTools 限速 Fast 4G、参考画布缩放 14% 时，**图片总传输字节下降到原来的约 1/10**。
  2. 首屏**不产生任何视频文件请求**（只有封面图请求）。
  3. 从“画布数据到达”到“可见缩略图基本加载完”的时间，具体目标待测出基线后再定。

| Chrome 的 WebMediaPlayer 数量 | 约 Chrome 92 起每帧桌面 75、移动 40，超出报 `Blocked attempt to create a WebMediaPlayer`（[Chromium 评审记录](https://groups.google.com/a/chromium.org/g/feature-media-reviews/c/ej_x3Ovqltw)）                                                                                                                                                   | 缩小后几十个 `<video>` 同时存在已接近上限，D4 的“点击才挂载”也规避了它                                                                                                |

AI 视频供应商是否返回封面：Seedance 只查到尾帧 `last_frame_url`（来自第三方网关文档，官方未核实），可灵返回 id / url / watermark_url / duration 没有封面，Sora 的视频接口曾提供 thumbnail 但该页同时写明 Sora 2 视频 API 已下线，Veo **未查到**。**结论：封面要自己产出，不能依赖供应商。**

## 5. 设计原则

1. **稳定地址不变**：payload 里的 `src` 一个字节都不改，老画布无需迁移就能受益。
2. **按需分档**：什么缩放级别看什么分辨率；没人看的东西不下载。
3. **永远能回退**：缩略图或封面缺失、处理失败、存储不支持时，体验退回到今天的样子，而不是坏掉。
4. **视频是重资源**：首屏零视频文件请求，点击才加载。
5. **后端不碰字节**：缩略图的读取、缩放、缓存都在后端之外完成；后端只做地址解析。
6. **选中就看原图**：用户正在操作的节点不降级。

## 6. 推荐方案

### 6.1 一句话

后端为素材提供**变体地址** `/files/<key>?v=thumb|poster`：先找到素材所在的**存储**，再找到该存储绑定的**已发布的图片处理服务**（后台「图片处理服务管理」里配置，目前支持 Cloudflare R2、腾讯云数据万象、阿里云 OSS），由对应厂商的适配器拼出处理 URL（私有读桶带签名）并 302；没有处理服务时图片回退原图、视频回退占位。前端按缩放级别决定节点用变体还是原图，视频平时只显示封面，点击才挂载 `<video>`。

### 6.2 后端：变体地址与图片处理服务

**变体地址（提案）**

- 原地址 `/files/<key>` 不变。新增查询参数：
  - `?v=thumb`：图片缩略图。
  - `?v=poster`：视频封面（首帧）。
- 前端从节点现有的 `src` 推出变体地址，不需要读 `assetId`、不需要改 payload，也不需要新接口。
- 其他取值返回 400 或按不存在处理；`thumb` 只对图片、`poster` 只对视频有意义（按素材 `kind` 判断），音频没有变体。

**图片处理服务（提案，替代之前的存储接口方案）**

处理服务是后台管理的一个实体，和存储是**多对一的绑定**关系：

| 厂商（`vendor`）                        | 允许绑定的存储                            | 需要的前置条件                                                                 |
| --------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------ |
| `cloudflare`                            | `r2`，且已设置公开域名（`PublicBaseURL`） | 域名在同账号的 Cloudflare zone；启用 Transformations                           |
| `tencent_ci`（腾讯云数据万象）          | `tencent_cos`                             | 为桶开通数据万象；要视频封面需另外开通媒体处理                                 |
| `aliyun_oss_img`（阿里云 OSS 图片处理） | `aliyun_oss`                              | 建议绑定自定义域名（默认域名下图片预览会变成下载）；视频封面要求 H.264 / H.265 |

- **绑定规则**：一个处理服务只绑定一个存储；一个存储**同时只有一个已发布**的处理服务（D8）。后台新建时，只有厂商匹配的存储可选，其余灰掉并写明原因。
- **凭证不重复存**：腾讯云、阿里云私有读桶的签名直接使用存储配置里已有的 AccessKey；Cloudflare 公开读不需要密钥。因此这个模块**没有新的密钥字段**（AWS 签名密钥那一项随 D11 一起去掉）。
- **生命周期**：草稿 → 校验 → 试跑 → 发布 / 回滚 / 停用，和模型配置一致；发布才对线上生效，已发布的版本不会被直接修改。

**数据（提案；项目已用 GORM AutoMigrate，把两个新模型加进 `model.All()` 即可建表）**

| 表                         | 关键字段                                                                                                                                                             |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `image_processors`         | `id`、`name`、`vendor`、`storage_id`、`status`（`draft` / `published` / `disabled`）、`draft_json`（草稿配置）、`published_version`、`version`（乐观锁，同存储配置） |
| `image_processor_versions` | `processor_id`、`version`、`config_json`（发布时的配置快照）、`trial_json`（试跑结果）、`published_by`、`published_at`                                               |

- 约束：`storage_id` 在 `status='published'` 时唯一（部分唯一索引）；这套存储若有素材引用，存储的定位字段本来就锁定，处理服务跟着存储走。
- `素材 → 存储 → 处理服务`：`assets` 表**不需要新字段**，仍然只靠 `storage_id` 找到存储。

**适配器接口（提案）**

```go
// imageproc 包：每个厂商一个适配器。
type Provider interface {
    Capabilities() Caps // 是否支持 thumb / poster
    Validate(ctx context.Context, st *storage.Handle, cfg Config) error
    // VariantURL 返回变体处理地址；不支持这个变体时 ok=false。
    VariantURL(ctx context.Context, st *storage.Handle, key, variant string) (url string, ok bool, err error)
}
```

- 运行时按存储 id 缓存“已发布的处理服务 + 适配器”，版本变了才重建；本实例发布 / 停用时立刻失效，多实例部署时其他实例最多等缓存 TTL（和存储 Registry 同一套思路）。
- **适配器之外不出现厂商分支**：`ResolveFile`、handler、前端都只认“有 / 没有处理 URL”。

**R2 的变体 URL（提案）**

设 `PublicBaseURL = https://assets.example.com`，`源 = PublicBaseURL + "/" + 转义后的对象路径`（也就是 `Storage.URL` 现在返回的那个公开地址），`ZONE = https://assets.example.com`：

| 变体             | URL                                                                                      |
| ---------------- | ---------------------------------------------------------------------------------------- |
| `thumb`（图片）  | `ZONE/cdn-cgi/image/width=512,fit=scale-down,format=auto,quality=75,onerror=redirect/源` |
| `poster`（视频） | `ZONE/cdn-cgi/media/mode=frame,time=0s,width=512,format=jpg/源`                          |

说明：

- `fit=scale-down` 是默认值，小于 512 的图原样返回，不放大。
- `onerror=redirect`：图片处理遇到致命错误时，Cloudflare 把用户重定向到原图；它只对同 zone 的源有效，我们的源正好在同一个域名下。
- `time=0s` 是初值。AI 视频的第一帧可能是黑帧或渐入帧，需要实测后调整（比如 0.5s）。
- 源用**绝对 URL**，因为官方明确写了绝对 URL 可作源；绝对路径在 R2 自定义域名上是否可用，官方页面没有说明，不依赖它。
- 签名：公开读，没有签名参数，**URL 永久稳定**，所以 Cloudflare 边缘缓存和浏览器缓存的命中都比现在的每小时变化的预签名地址好。

**腾讯云数据万象的变体 URL（提案；官方文档格式，我没有实测）**

设桶域名 `HOST`（COS 默认域名，或绑定的 CDN 域名），对象路径 `KEY`：

| 变体     | URL（私有读桶在最前面加 COS 签名参数，处理参数建议一并签入）       |
| -------- | ------------------------------------------------------------------ |
| `thumb`  | `https://HOST/KEY?imageMogr2/thumbnail/512x512%3E/format/jpg`      |
| `poster` | `https://HOST/KEY?ci-process=snapshot&time=0&width=512&format=jpg` |

- 处理参数里的 `>` 要编码成 `%3E`；`512x512>` 表示只缩小、等比放入 512×512 框内，等价于长边 512。
- 转 JPG 时透明处填白。想保留透明就要输出 PNG / WebP，列入待验证。
- 视频封面要求桶已开通数据万象的**媒体处理**（单独开通、单独计费，约 0.1 元/千次，官方页给的数字请到价格页核对）；后台里用一个开关“已开通媒体处理”表示，没开通时 `poster` 不可用，回退占位。
- 私有读：使用 COS Go SDK 生成带签名的 URL，并把处理参数签入，防止别人去掉参数拿原图；公开读桶不需要签名。S3 V4 预签名能否带数据万象参数，官方没说明，**不依赖它**。
- 可加 `/ignore-error/1`，让超大文件或参数越界时返回原图而不是报错。

**阿里云 OSS 的变体 URL（提案；官方文档格式，我没有实测）**

设自定义域名 `HOST`，对象路径 `KEY`：

| 变体     | URL（私有读桶需要 V4 签名，且 `x-oss-process` 必须签入）               |
| -------- | ---------------------------------------------------------------------- |
| `thumb`  | `https://HOST/KEY?x-oss-process=image/resize,l_512/format,jpg`         |
| `poster` | `https://HOST/KEY?x-oss-process=video/snapshot,t_0,f_jpg,w_512,m_fast` |

- 私有读：使用 OSS Go SDK v2 的预签名，把 `x-oss-process` 签入；**不能在已签好的 URL 后面追加参数**。官方示例统一用 V4，预签名有效期最长 32400 秒。
- 视频截帧只支持 H.264 / H.265，不支持杜比视界；webm 若是 VP9 / AV1 可能不被支持，需实测。S3 协议下 `x-oss-process` 只支持 `image/` 和 `style/`，所以视频首帧必须走原生 SDK 签名，这是引入 OSS SDK 的原因。
- 默认域名下图片预览会变成下载，所以后台校验时提示“建议绑定自定义域名”。
- 转 JPG 时透明处填白；原图 ≤ 20MB（可申请调整）、宽高 ≤ 30000px、总像素 ≤ 2.5 亿，超限会失败并回退。

**`ResolveFile` 的变体逻辑（提案）**

`FileResolver.ResolveFile(ctx, key)` 增加一个变体参数，handler 从 `c.Query("v")` 读取。找到素材和存储之后，再找存储绑定的已发布处理服务：

| 情况                                             | 行为                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 有处理服务且适配器返回 `ok=true`                 | `302` 到处理 URL。**公开读**（R2、公开域名的 COS / OSS）：`Cache-Control: private, max-age=86400`；**私有读**（带签名）：沿用签名跳转的规则，`max-age` 不超过签名有效期的 1/4，（服务端不缓存签名结果：SDK 的预签名只在本地计算 HMAC、不发网络请求，成本很低；重复请求靠浏览器的 `max-age` 命中） |
| 请求 `thumb` 但没有处理服务 / `ok=false`         | `302` 到原图地址（走现有逻辑），`max-age` 不超过 60 秒，以便处理服务发布后尽快生效                                                                                                                                                                                                                |
| 请求 `poster` 但没有处理服务 / `ok=false`        | `404`；前端显示占位                                                                                                                                                                                                                                                                               |
| 素材 `kind` 与变体不匹配（如对视频请求 `thumb`） | `404`                                                                                                                                                                                                                                                                                             |
| 适配器返回错误（签名失败等）                     | 记录日志，按“没有处理服务”回退，不让画布坏掉                                                                                                                                                                                                                                                      |

**素材覆盖范围（D12）**：处理服务只对它绑定的存储里的素材生效。例如素材原本在 R2，客户新建 COS 并设为默认存储：新素材写进 COS，走数据万象；R2 里的老素材仍由 R2 绑定的处理服务（或回退原图）。**后台不展示覆盖统计，也不做存储迁移**（需求方：“不用管”）；这个边界只写在文档里，运维交接时要说明。

**R2 的老素材自动受益**：只要把 R2 存储的 `PublicBaseURL` 设成自定义域名并发布处理服务，这套存储里**所有已有素材**都会立刻走公开域名和缩略图，**不需要回填**。

**Cloudflare 侧配置清单（运维，非代码；需求方执行；其余两家的前置条件见上表和演示页）**

1. 域名加入 Cloudflare 账号，成为**同账号下的 zone**。官方说 DNS 不必托管在 Cloudflare，可以走 partial（CNAME）接入，但该页没写套餐要求，我没核实。
2. R2 桶绑定这个自定义域名并公开读；**关闭 `r2.dev` 公开 URL**（官方提示不关的话桶仍会通过它公开访问）。
3. 在该 zone 的 Transformations 页面启用图片和媒体变换。
4. 后台存储配置里把该 R2 存储的 `PublicBaseURL` 设为这个域名（现有字段，无需改存储配置页）；再到「图片处理服务管理」新建并发布 Cloudflare 处理服务。
5. 直传不受影响：直传仍走 R2 的 S3 端点（预签名 PUT），读取才走公开域名；浏览器的 `<img>` / `<video>` 读取不需要额外 CORS。

**`/files` 本身的减负（提案，可选）**

- 对 `key → asset` 的查询加一层进程内短缓存（上百个同画布请求不再各查一次库）。这与缩略图方案独立，可后做。

### 6.3 前端：按缩放分档加载图片

**判定（提案）**

- 节点用一个窄选择器订阅缩放，**只返回布尔值**，例如 `useStore((s) => s.transform[2] < LOD_ZOOM)`。React Flow 官方性能页也提醒不要订阅会频繁变化的整块状态；返回原始 zoom 会让每次滚轮都重渲染所有节点。
- 阈值初值取 `LOD_ZOOM = 0.6`（提案，需用真实素材调参）。接近阈值时加一点滞回（如 0.55 / 0.65），避免来回抖动反复切换。
- 三个默认值配套：缩放 < 0.6 用缩略图，缩略图长边 512px，质量 75。缩放 60% 时，默认 384 宽的节点在屏幕上约 230px，在 2 倍屏上约 460 个物理像素，512 宽刚好够用。三个数做成常量，用真实画布看清晰度再调。

**一个 `MediaPreview` 组件统一出口（提案）**

| 条件                      | 加载                                 |
| ------------------------- | ------------------------------------ |
| 缩放 < 阈值，且节点未选中 | 缩略图 `?v=thumb`                    |
| 缩放 ≥ 阈值，或节点被选中 | 原图                                 |
| 节点远离视口              | 不挂载 `<img>`，保留固定宽高的占位框 |
| 缩略图请求失败（`error`） | 自动改用原图，仍失败才显示破图占位   |

所有 `<img>` 统一加 `decoding="async"` 和固定宽高比（节点预览框本来就是固定 16:9，不会塌陷）。

这样放大时会出现“缩略图 → 原图”的替换：原图用同一个 `<img>` 叠在缩略图上，加载完成后再淡入，避免闪白。

**对非 R2 存储**：`?v=thumb` 会 302 回原图，LOD 不会省流量，但也不会坏。

**对图片懒加载问题的最终答复**：我们不依赖 `loading="lazy"` 解决 14% 的问题，只把它作为“视口外节点”的兜底；真正省流量的是缩略图 + LOD。

### 6.4 前端：视频 facade

**节点平时（D4）**

- 显示封面 `?v=poster` + 居中的播放按钮 + 时长角标（`assets.duration_ms` 已有）。
- 不挂载 `<video>`，**首屏零视频文件请求**。

**点击播放后**

1. 把封面替换成 `<video src controls playsInline autoPlay preload="auto">`。
2. 保留现有的 `nodrag nowheel`，拖进度条不会拖动节点。
3. 并发控制（提案）：同时挂载的 `<video>` 上限先定 4。再点击新的视频时，先把**已暂停**的退回封面；正在播放的不打断。
4. 退回封面或节点卸载时显式释放：`removeAttribute('src')` 后调用 `load()`，否则 WebMediaPlayer 不会释放（`display:none` 不会释放，见 tldraw 的做法边界）。

**封面缺失时**（非 R2 存储、mov / webm 处理失败、首帧提取失败）：显示现有的视频占位图标 + 播放按钮，点击仍可播放。

**波及范围（提案）**：同一套封面逻辑应用到会一次性显示多个视频的位置：素材抽屉 [assets-sheet.tsx](../../../web/src/pages/canvas/chrome/assets-sheet.tsx)、历史条 [node-history-strip.tsx](../../../web/src/components/canvas/node-history-strip.tsx)。参数面板和 mention 只显示选中节点的少量引用，优先级低，可放进同一次交付但不阻塞。

### 6.5 关键流程

```
打开画布
  → 拿到 payload（节点 src 不变）
  → 节点按缩放判定：14% < 阈值 → 请求 /files/<key>?v=thumb
        后端：素材 → 存储 → 已发布的处理服务
        ├─ Cloudflare（R2 公开域名）→ 302 到 /cdn-cgi/image/...
        ├─ 腾讯云 / 阿里云（公开读不签名，私有读带签名）→ 302 到处理 URL
        └─ 没有处理服务 / 不支持    → 302 回原图（照旧）
  → 视频节点：请求 /files/<key>?v=poster
        ├─ 有处理服务且支持封面 → 302 到帧提取 URL → 封面
        └─ 否则                 → 404 → 前端占位
放大到 ≥ 阈值 / 选中节点 → 原图淡入覆盖缩略图
点击视频播放按钮 → 才挂载 <video> 开始拉视频
```

### 6.6 后台模块：图片处理服务管理

可点击原型见 [图片处理服务管理-演示.html](./图片处理服务管理-演示.html)（数据在内存里，试跑结果是示意，没有真实调用厂商）。

**位置**：后台「系统设置」下，和「存储配置」并列，入口名“图片处理服务管理”。

**页面**：

**校验项**：绑定关系匹配；域名可访问；Cloudflare 的域名与存储的公开域名一致；腾讯云媒体处理开关；阿里云是否使用自定义域名；私有读签名可用。**试跑**：用一个真实图片素材和一个真实视频素材各走一遍，返回体积和耗时。

| --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## 9. 方案取舍

| 方案                                | 说明                                                                                             | 优点                                                              | 代价                                                                                                                                                               |
| ----------------------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **A 纯前端占位 / 限流**             | 低缩放只显示占位，或仍加载原图只做排队                                                           | 零后端改动，见效最快                                              | 低缩放认不出内容（与 D1 冲突）；“原图限流”不减总流量                                                                                                               |
| **B 后端生成**（已搁置）            | 后端用 Go + ffmpeg 生成缩略图 / 封面                                                             | 不依赖外部服务；任何存储都有缩略图                                | 在 2 核 4GB、30Mbps、与数据库同机的服务器上：直传文件要从存储读回原图（占入站带宽），解码大图有内存风险，ffmpeg 占 CPU，镜像变大，还要新字段、异步队列、老素材回填 |
| **C 云厂商自带处理（采用，D9）**    | 后台管理“存储 ↔ 处理服务”，后端只 302 到处理 URL；支持 Cloudflare R2、腾讯云数据万象、阿里云 OSS | 后端零读取、零 CPU；老素材自动受益；边缘 / 厂商缓存；三家各取所长 | 依赖厂商；腾讯云、阿里云绑定自家存储；新增后台模块、两张表、两个 SDK；私有读签名和视频格式要实测                                                                   |
| ~~D 其他厂商自带~~                  | 已并入 C                                                                                         |                                                                   |                                                                                                                                                                    |
| **F AWS 动态图片转换（不做，D11）** | CloudFront + Lambda 前置在 S3 之前                                                               | 图片能力完整，支持请求签名                                        | 需客户自部署；官方文档未查到视频首帧；本期不做                                                                                                                     |
| **E 通用图片 SaaS**                 | Cloudinary / imgix / ImageKit                                                                    | 图片和视频首帧都有                                                | 私有桶鉴权困难、用户素材出境与留存风险、大陆节点缺失                                                                                                               |

决策矩阵（权重：首次加载速度 0.3、低缩放可辨识 0.2、后端带宽与 CPU 占用 0.2、实现与运维复杂度 0.2、数据合规与可控 0.1；分数 1–5，是我的主观判断，不是测量值）：

| 维度（权重）               | A   | B   | C       | E   |
| -------------------------- | --- | --- | ------- | --- |
| 首次加载速度（0.3）        | 2   | 5   | 5       | 4   |
| 低缩放可辨识（0.2）        | 1   | 5   | 5       | 5   |
| 后端带宽与 CPU 占用（0.2） | 5   | 2   | 5       | 5   |
| 实现与运维复杂度（0.2）    | 5   | 2   | 4       | 2   |
| 数据合规与可控（0.1）      | 5   | 5   | 4       | 1   |
| **加权得分**               | 3.3 | 3.8 | **4.7** | 3.7 |

**为什么搁置 B**：B 本身可行，也经过了完整设计（见下）。但在你的服务器规格下，它要付出带宽、内存、CPU 和镜像体积的代价，并带来新字段、队列和回填；而线上存储恰好是 R2，C 可以用更少的代码和更低的风险达到同样的前端效果。B 保留为将来要支持非 R2 存储时的备选。

**B 方案的已定设计（保留供将来复用）**：

- 按来源分工：中转上传和 AI 生成产物在 `ingest` 里对已落地的临时文件**同步**生成（零额外下载）；开启直传的上传和老素材走**异步限速队列**，后端从存储读一次原图。
- 带宽控制：队列并发 1，共享令牌桶限速约 1MB/s（约占 30Mbps 峰值的 27%），新上传优先于回填；图片整份读取，视频由 ffmpeg 读后端签名的存储地址只发 Range 请求。
- 资源保护：`image.DecodeConfig` 先读宽高，超过 5000 万像素直接放弃；ffmpeg `-threads 1`，单任务超时 10 秒。
- 其他已定细节：GORM AutoMigrate 加 `thumb_key`、`thumb_status`；单独的有界 goroutine 池，不复用生成任务 worker；有透明通道的输出 PNG，其余 JPEG；采用 `golang.org/x/image`；ffmpeg 用 Alpine `apk` 包，GPL 构建可接受。
- 曾评估并否决：直传文件由浏览器生成缩略图再提交（省入站带宽，但多前端逻辑、提交接口和客户端小图的信任问题）。

**明确放弃的东西**：

- 不引入任何视频播放器库。
- 不做 HLS/DASH 转码切片。
- 不用通用图片 SaaS（私有桶鉴权、出境合规）。
- 本期不做后端生成（B），不装 ffmpeg。
- 本期不重写老视频原文件做 faststart。
- 本期不启用 `onlyRenderVisibleElements`。
- 本期不改 Caddy / nginx 的 http2 配置（线上已有 TLS）。
- 不做 AWS 动态图片转换（D11）；Cloudflare 只支持 R2，不处理其他来源的素材。
- 不做“未覆盖素材”统计和存储迁移（D12）。

### 11.4 仍待确认 / 实现阶段验证

1. **哪个域名接入 Cloudflare**：素材域名要成为同账号下的 zone；官方说可以走 partial（CNAME）接入，套餐要求我没核实，需要你确认当前账号和域名的情况。
2. **透明图**：Cloudflare 的 `format=auto` 是否保留透明文档没说；腾讯云、阿里云转 JPG 时透明处填白。第 0 步用真实透明 PNG 验证；不保留就改输出格式（webp / png）。
3. **视频格式**：Cloudflare 官方只保证 H.264 + AAC 的 MP4；阿里云只支持 H.264 / H.265。你的素材里 mov、webm、HEVC 的占比如何？不支持时返回什么需要实测；失败时前端显示占位，不会坏。
4. **首帧是否黑帧**：AI 视频的第 0 秒可能是黑帧或渐入帧，`time` 做成可配置，默认 0，需要实测后调整。
5. **并发 / 速率限制**：大画布首次打开 40 个变体同时现算，三家有没有限制，我没查到（腾讯云只查到“海外媒体处理并发默认 10 QPS”）。
6. **用户所在地**：用户主要在大陆吗？Cloudflare 没有 ICP 备案时，大陆用户由境外节点服务，速度没有官方数据。
7. **私有读签名是否通过**：腾讯云带处理参数签入、阿里云 V4 签 `x-oss-process`，官方文档都有说明，但我没有实测；第 0 步必须验证，失败的话适配器要调整签名方式。
8. **两个 SDK 的 API 与构建**：我没有读 SDK 源码，具体用哪个函数生成预签名、是否纯 Go（`CGO_ENABLED=0` 构建）、对二进制体积的影响，实现时先验证。
9. **防盗链**：R2 公开读后原图地址永不过期、无法撤销，是否需要尽早加 WAF 规则限制外链。
10. **发布的灰度**：发布处理服务会让这套存储下所有素材的 `/files` 跳转行为同时改变，先在自己的画布验证，再对所有用户生效。

### 13.2 与设计的出入

1. **签名地址服务端不缓存**：设计写“按存储 id / key / 变体缓存签名 URL”。实现里没做：两个 SDK 的预签名都只在本地算 HMAC，不发网络请求，成本低；浏览器侧靠 `Cache-Control: max-age = 签名有效期 / 4` 命中。
2. **校验与试跑合并成一个接口 `/check`**：设计里 validate 和 trial 是两个接口，实现合并为一次调用，结果一起存进 `check`，前端更简单。
3. **缩放订阅没有用 `useStore` 选择器**：选择器拿不到“滞回的前一状态”，改用 `store.subscribe` 加本地 `useState`，只有滞回后的布尔值翻转才触发重渲染。
4. **视频名额全在播放时**：允许超过 4 个（软上限），不打断、不拒绝用户刚点的播放，已暂停的会在下一次点击时被回收。
5. **前端对域名更严格**：后端 `Normalize` 容忍带协议或路径的域名并自动清洗，前端表单直接拒绝。

### 13.4 遗留事项

1. **存储删除不检查处理服务引用**：把一套没有素材、但绑定了处理服务的存储删掉，处理服务会变成“孤儿”（视图里存储名为空）。建议在存储删除预检里加上这一项。
2. **画布前端**：`NodeImageBody`（出图动画 `GridReveal`）仍直接加载原图；视频时长角标不显示，因为节点数据里没有 `durationMs`（需要时再扩展 payload，当前按设计不改 payload）。
3. **第 0 步实测**（见第 10 节）仍是上线前必须做的事：透明 PNG、mov / webm / HEVC、首帧黑帧、首次并发、COS 带处理参数签名、OSS V4 签 `x-oss-process`。
4. **运维配置**：Cloudflare 域名接入、R2 绑域名公开读、启用 Transformations；腾讯云开通数据万象与媒体处理；阿里云绑定自定义域名。
