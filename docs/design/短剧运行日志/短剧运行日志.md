## 1. 设计摘要

- **问题**：短剧运行失败时，服务器日志里基本什么都没有。`failDrama` 把错误转成用户文案落库后返回 nil，原始错误既不往上抛也不打日志；内部错误在库里只剩「服务内部错误」；输出不合格时，模型写了什么、哪条校验没过都被丢弃；整个短剧链路只有 5 处 Warn。用户在任务条上也看不到编号，运维没有抓手。
- **目标**：运维拿到用户反馈后，**用一个编号 grep 一次**，就能回答四个问题：这次运行跑了哪些步骤和批次；卡在哪一次模型调用；为什么失败（上游原文 / 校验原因 / 内部错误链）；当时发了什么提示词、模型回了什么。
- **推荐结论**（均已由用户确认，见第 11 节）：
  1. 服务器日志覆盖**全流程**：任务创建、开始、每次模型调用、检查点恢复、终态（成功 / 失败 / 取消 / 暂停）都打一行，所有行带同一组关联字段，`drama_job_id` 和前端显示的编号是同一个值。
  2. **失败时打全文**：失败那一行带完整错误链、上游错误原文（只遮渠道 Key）、校验原因，以及那次调用的**提示词全文**；输出不合格的那次尝试带**模型输出全文**。成功的调用只打元数据，不打全文。
  3. 短剧任务条失败时显示**任务编号**（可复制），复用画布已有的 `TaskIdTag`。
  4. 不做后台页面、不建表、不引入新依赖；日志继续用现有 zap。

### 2.2 设计约束

- **C1**：渠道 Key 永远不进日志（E9）。提示词里不含 Key；上游错误原文必须先遮 Key（网关已有 `redactErr` / `upstreamMessage` 的遮法可复用）。
- **C2**：日志只在边界记一次（E7）。失败详情由 `failDrama` 这个边界统一打，`callDrama` 不能「打一行再 return」。每次模型调用的那一行是**过程事件**，不是错误日志，不违反 E7，但要在规范里写明（见 8.4）。
- **C3**：不改用户可见的失败文案（`error_message`），只补服务器日志和前端编号。
- **C4**：不加后台页面、不建表（用户决定）。

### 2.3 当前缺口

1. 失败原因被吞（F3、F4、F5、F8），服务器日志里没有任何失败记录。
2. 成功的运行也没有过程记录：不知道调了几次模型、哪次慢、用了多少 token。
3. 上游错误体原文被网关丢弃（F11）。
4. 用户看不到编号，日志里的 `drama_job_id` 又是十进制，两边对不上（F1、F14）。

## 3. 用户与场景

| 角色 | 触发 | 主任务 | 成功标准 |
| --- | --- | --- | --- |
| 运维 | 用户反馈「剧本一直写不出来」，附上任务条里复制的编号 | `grep <编号>` → 看到这次运行的全部行 → 定位到失败那次调用 → 读原因和全文 | 不读代码、不复现，5 分钟内说清原因 |
| 运维 | 用户只说「昨天下午短剧失败了」，没有编号 | 按 `user_id` + 时间段 grep `短剧任务失败` | 能找到候选运行，再按编号展开 |
| 运维 / 开发 | 巡检：今天短剧失败多不多、是哪一类 | grep `短剧任务失败`，按 `error_type` 计数 | 能区分上游故障、输出不合格、内部错误 |
| 开发 | 模型总输出不合格，要改内置提示词 | 从失败行拿到提示词全文和不合格输出全文 | 不用复现就能看到当时的输入输出 |

**推断**：运维是少数几个人，「有问题才查」，主要用 `grep` / `docker logs` / `less`。所以字段名要固定、可 grep，一行一事件，不依赖日志平台。

### 4.2 依赖框架调研

| 候选 | 能覆盖什么 | 结论 |
| --- | --- | --- |
| OpenTelemetry Go（Apache-2.0，Traces 已稳定，Logs 为 RC） | 结构化 span、上下文传递 | **不引入**。需要额外部署 Jaeger / Tempo 或自写导出器；本方案只要日志行，现有 zap 已够用 |

## 5. 设计原则

1. **一个编号串起整次运行**：所有行都带 `drama_job_id`，值和用户界面上显示的编号完全一致，`grep` 一次拿全。（场景 §3，F13）
2. **一次模型调用一行，一次尝试一行**：重试也单独成行，带 `attempt` 序号。（Inngest、OTel）
3. **失败详情只在边界打一次**：失败原因和提示词全文由 `failDrama` 统一打印；下层只负责把上下文带在 error 里往上传。（规范 E7）
4. **全文只在失败时打**：成功的调用只打元数据，日志量可控；失败时打全，排查不用复现。（用户决定，OTel「内容默认不记」）
5. **Key 永不进日志，其余按原文**：遮 Key 用网关现有的方法，其他内容（用户原文、模型输出、上游错误）不做脱敏。（C1，[日志管理](../日志管理/日志管理.md) 的同一取舍）
6. **字段名固定、可 grep**：message 用中文短句且固定不变，字段名用英文 snake_case，不拼进 message。（规范 E7、E8）

不打的：进度变化（`dramaProgress` 每 10%）、WebSocket 推送、只读接口。

### 6.2 公共字段

挂任务的行（E1–E9）都带这一组，由一个辅助函数 `dramaJobFields(j *model.DramaJob) []zap.Field` 生成，保证每行一致：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `drama_job_id` | string，32 位十六进制 | `idcodec.Encode(j.ID)`，**和任务条上显示的编号相同**。不用 `task_id`：短剧任务和生成任务是两张表、各自的主键，同一个编号可能两边都有，字段名区分来源 |
| `drama_id` | string，32 位十六进制 | 短剧项目编号，与前端地址里的一致 |
| `user_id` | uint64 | 用户主键（后台用户列表显示的就是它） |
| `step` | string | analyze / plan / outline / scripts / breakdown / asset_prompts / storyboard / compose |
| `lane` | string | `user`（用户手动发起）/ `pipeline`（自动规划） |
| `episodes` | []int | 本次涉及的集数 |
| `batch` | string | 自动规划的批次范围，如 `"11-20"`；没有批次时不带 |

E10、E11 不挂任务，带 `user_id`、`drama_id`（有项目时）、`segment_id`（转写时）。**`request_id` 带不上**（F15），本期不改中间件，属已知限制。

### 6.3 模型调用行（E4 / E10 / E11）

| 字段 | 类型 | 含义 / 来源 |
| --- | --- | --- |
| `call` | string | 本次调用在运行里的位置，由调用方传入：`episode=3`（scripts 每集）、`batch=1-5`（breakdown 每批）、空串（单次步骤） |
| `attempt` | int | 1 或 2（校验失败重写的那次是 2） |
| `prompt_step` | string | 用的哪套提示词模板（`callDrama` 的 `step` 参数） |
| `prompt_source` | string | `builtin` / 用户自写 / 技能，来自 `cfg.Prompt.Source` |
| `model_key` | string | 模型 key |
| `channel` | string | 渠道 key |
| `upstream_model` | string | 实际调用的上游模型 |
| `prompt_chars` | int | 提示词字数 |
| `output_chars` | int | 模型输出字数（失败且无输出为 0） |
| `input_tokens` / `output_tokens` | int | 上游用量 |
| `usage_missing` | bool | 上游没给用量 |
| `finish_reason` | string | stop / length 等；`length` 意味着输出被截断，是「输出不合格」的常见原因 |
| `latency_ms` | int | 从发出到收完 |
| `ttft_ms` | int | 首字耗时；`streamText` 的事件回调里记第一个 text 事件的时间，没收到为 0 |
| `result` | string | `ok` / `invalid`（解码或校验没过）/ `failed`（上游或网络失败）/ `canceled` |
| `error_type` | string | `result` 不是 ok 时带，取值见 6.5 |
| `error` | string | `result=failed` 时带完整错误链（`err.Error()`，已遮 Key） |
| `upstream_status` / `upstream_body` | int / string | 上游非 2xx 时带 HTTP 状态和**错误体原文**（遮 Key，最多 8KB，见 8.2） |
| `validation_error` | string | `result=invalid` 时带：解码或校验的原因原文 |
| `output` | string | **仅 `result=invalid` 时带模型输出全文**；其余情况不带 |

**级别**：`result=ok` 为 Info；`invalid`、`failed` 为 Warn；`canceled` 为 Info。第 1 次 invalid 后会重写，所以同一个 `call` 会出现 attempt=1（Warn）和 attempt=2 两行。

### 6.4 失败行（E6）

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `error_code` | int | 写进 `drama_jobs.error_code` 的值 |
| `error_message` | string | 写进库、给用户看的文案（运维对照用户截图） |
| `error_type` | string | 见 6.5 |
| `error` | string | **完整错误链** `cause.Error()`：内部错误不再只剩「服务内部错误」 |
| `call` / `attempt` | string / int | 失败发生在哪次调用；非模型调用失败时不带 |
| `prompt` | string | **那次调用的提示词全文**；非模型调用失败时不带 |
| `duration_ms` | int | 从开始执行到失败 |
| `refunded` | int | 退回的积分（等于 `frozen_credits`） |
| `paused` | bool | 自动规划因此暂停 |

**级别**：`error_type=internal`、`compose_*` 用 **Error**（需要人处理，自动带堆栈）；其余（上游、超时、输出不合格、上下文过长、自定义提示词不合格）用 **Warn**（用户重试或换模型可能自愈）。

**全文分布**：提示词全文只在失败行打一次；不合格输出全文在对应的 E4 行里。两行都带 `drama_job_id` + `call` + `attempt`，grep 编号时会一起出来。这样一次失败最多打印「1 份提示词 + 2 份输出」，不会重复打印同一份内容。

### 6.5 失败分类 `error_type`

低基数枚举，便于按类型计数（参照 OTel `error.type`）：

| 值 | 含义 | 判定 |
| --- | --- | --- |
| `upstream` | 上游返回非 2xx 或流里的 error | `errors.As(err, *llmgateway.UpstreamError)` |
| `timeout` | 超过模型 deadline 或空闲超时 | `context.DeadlineExceeded` 且任务仍有效 |
| `network` | 连接失败、读流中断等 | 其余网关错误 |
| `invalid_output` | 两次都解码或校验不过 | `ErrDramaOutputInvalid` |
| `custom_prompt` | 自定义提示词或技能导致不合格 | `ErrDramaCustomPrompt` |
| `context_too_long` | 提示词超过模型上下文 | `ErrDramaContext`、`ErrDramaEpisodeSourceTooLong` |
| `no_model` | 渠道 Key 读取失败或没有可用文本模型 | `ErrDramaNoTextModel` |
| `canceled` | 用户取消导致上游中断 | `ensureDramaActive` 返回的错误 |
| `compose_download` / `compose_transcode` / `compose_store` | 合成三个阶段的失败 | `renderCompose` 各分支 |
| `business` | 其他业务错误（如分镜提交时的校验） | 其余 `errcode.Error` |
| `internal` | 其余所有错误 | 兜底 |

### 6.7 运维排查手册（写进 backend README 的「排查」小节，提案）

```bash
# 用户给了编号：看整次运行
grep '<编号>' logs/app.log            # 或 docker logs <容器> 2>&1 | grep '<编号>'

# 只有用户 ID：找他今天的失败
grep '短剧任务失败' logs/app.log | grep '"user_id": 42'

# 巡检：按失败类型计数
grep '短剧任务失败' logs/app.log | grep -o '"error_type": "[a-z_]*"' | sort | uniq -c

# 慢调用：模型调用耗时超过 60 秒
grep '短剧模型调用' logs/app.log | grep -E '"latency_ms": [0-9]{5,}'
```

`console` 格式下字段是一段 JSON，配置 `log.format: json` 后整行是 JSON，可直接 `jq`。**建议生产配 `log.filename`**，否则日志只在容器标准输出里，容器重建就没了（F12，属部署建议，不改默认配置）。

## 7. 状态与异常

| 情况 | 日志表现 |
| --- | --- |
| 正常成功 | E1 → E2 → E4×N（全 ok）→ E5 |
| 第 1 次输出不合格、第 2 次成功 | E4（attempt=1，Warn，带 `validation_error` 和 `output` 全文）→ E4（attempt=2，Info）→ … → E5 |
| 两次都不合格 | E4×2（Warn，各带输出全文）→ E6（Warn，`invalid_output`，带提示词全文） |
| 上游报错 | E4（Warn，`failed`，带 `upstream_status` 和 `upstream_body`）→ E6（Warn，`upstream`，带提示词全文） |
| 内部错误（如提示词渲染失败） | E6（Error，`internal`，带完整错误链和堆栈；没有 `prompt`） |
| scripts 第 3 集失败（前 2 集已保存） | E4（episode=1、2 ok）→ E4（episode=3 failed）→ E6（`call=episode=3`） |
| 用户取消 | 运行中的 E4（`canceled`，Info）+ E7；`failDrama` 看到已非活跃状态，不打 E6 |
| 自动规划失败暂停 | E6（`paused=true`）+ E8（`reason=failure`） |
| 数据库错误，River 重试 | E9（Warn，带 `attempt`），下一次执行再出现 E2（`resumed=true`） |
| 进程崩溃后恢复 | E2（`resumed=true`）→ E3（检查点命中，不再调模型）→ E5 |
| 重复投递已终态的任务 | `startDrama` 返回 nil，不打任何行（与现在一致） |
| panic | River 捕获并经 `zapSlogHandler` 输出 Error（F16），本方案不另处理 |
| 合成下载失败 | E6（Error，`compose_download`，`error` 带存储层原因；用户仍看到「下载失败：无法读取采用视频」） |
| 写日志失败 | zap 忽略写失败，不影响业务（与现在一致） |

**权限与隐私**：日志里会出现用户的小说原文片段（提示词全文）和模型输出。这是用户为排查明确选择的（第 11 节）。服务器日志文件的访问权限等同于数据库，部署文档里写明。渠道 Key 在任何字段里都不出现。

### 8.2 网关改动（`llmgateway`，影响 Agent 等所有文本调用方）

`UpstreamError` 增加一个只给日志用的字段：

```go
type UpstreamError struct {
	Status    int
	Message   string // 给用户看的说明（不变）
	Retryable bool
```

### 8.4 规范补充

在 [02-错误处理与日志.md](../../../backend/docs/standards/02-错误处理与日志.md) 补一条：

- **E7 例外：长流程运行的过程事件**。后台长流程（短剧任务、Agent 运行）可以对每次模型调用打一行过程事件（Info，失败的尝试打 Warn），它记录的是「这一步做了什么」，不是「这个错误发生了」。最终失败仍只由边界记一次。
- **E9 补充：用户内容**。短剧任务失败时，日志里会打出提示词全文和模型输出全文（含用户原文），用于运维排查。渠道 Key 仍然不能出现。

### 8.5 日志量估算（示意）

- 成功运行：每次模型调用一行，约 600 字节。一部 60 集的小说完整跑一遍，模型调用大约 60–120 次，合计不到 100KB。
- 失败运行：多出一份提示词全文（受模型上下文上限约束，最多约几十万字，即几百 KB 到 1MB 级）和最多两份输出全文（受 `max_tokens` 约束）。
- **推断**：失败是少数，按 lumberjack 100MB × 7 份的默认滚动足够；失败率异常高时日志会涨得快，这时本来就需要人介入。

## 9. 方案取舍

| 维度（权重） | A 本方案：全流程 + 失败打全文 | B 每次调用都打全文 | C 建表 + 后台时间线 |
| --- | --- | --- | --- |
| 运维能否 grep 一次定位（40%） | 能 | 能 | 能，但要进后台 |
| 失败原因完整度（30%） | 完整（错误链、上游原文、提示词、不合格输出） | 完整，且成功调用也有全文 | 完整 |
| 日志量 / 存储（15%） | 成功运行 <100KB | 一部小说可能几十 MB，淹没其他日志 | 需要表、清理任务 |
| 实现成本（15%） | 小：集中在 `callDrama`、`failDrama` 两个出口 | 小 | 大：迁移、接口、页面 |
| 结论 | **推荐，已确认** | 放弃：日志量不可控 | **用户撤回**：不加后台 |

权重来自用户确认的目标：给运维排查用，不加后台。

**明确放弃**：后台页面和数据表；成功调用的全文；`request_id` 透传到 service；OTel / Langfuse 接入；日志内容开关（失败全文始终打印，没有配置项）。

- 不新增日志开关配置。

- 无。实现时如发现 `ttft_ms` 需要改网关事件回调以外的代码，可以先不带这个字段。
