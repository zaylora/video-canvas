短剧运行日志

用户给一个编号，运维 grep 一次就能看清整次短剧运行

现在短剧工作室跑失败了，服务器日志里几乎什么都没有：原始错误被吞掉，输出不合格时模型写了什么也没留下。这份设计给每次运行补齐服务器结构化日志：从创建到终态每个节点一行，失败时打出完整原因、提示词全文和不合格输出全文。任务条失败时显示编号，运维拿编号直接 grep。 不做后台页面，不建表，不引入新依赖。

阅读说明。现状来自读代码核对，见 Markdown 第 2 节。日志示例里的编号、时间、耗时、字数都是示意；整套设计尚未实现。完整依据和来源见同目录的 短剧运行日志.md。

今天缺在哪

读代码确认的四个缺口 已核对代码

失败原因被吞

failDrama 把错误转成用户文案落库后返回 nil，不打日志。不是业务错误的，库里只剩「服务内部错误」；合成的下载、ffmpeg、存储错误也都换成了固定文案。

不合格输出被丢掉

callDrama 校验不过会重写一次，但两次的校验原因和模型输出都没留下。

成功的运行也没有过程

整条短剧链路只有 5 处 Warn，看不到调了几次模型、哪次慢、用了多少 token。网关还把上游错误体原文丢了，只留 300 字说明。

编号对不上

任务条失败时不显示编号；仅有的一行队列日志用的是十进制主键，和前端的十六进制编号对不上。

主线：一次排查怎么走

从用户看到失败，到运维读到原因。

任务条失败原因 + 任务 ID，点一下复制
用户发给运维附上编号
grep 编号所有行都带同一个 drama_job_id
读时间线创建 → 开始 → 每次模型调用 → 终态
读失败行错误类型、完整错误链、提示词全文
设计：所有失败详情由 failDrama 这一个出口统一打印，下层只把上下文带在 error 里往上传，符合规范 E7「只在边界记一次」。每次模型调用的那一行是过程事件，不是错误日志。
用户没有编号时（兜底）：每行都带 user_id，运维按用户 ID + 大致时间 grep 短剧任务失败，先找到候选运行，再按编号展开。同步接口（片段转写）带不上 request_id，这是已知限制，本期不改。

三类运行，日志各打多少

全文只在失败时打，日志量才可控。

成功的运行
只打元数据示意：一部 60 集 <100KB

创建、开始、每次模型调用、完成各一行：模型、渠道、耗时、首字耗时、token、积分。

失败的运行
打全文

另外多出：不合格那次的模型输出全文（最多 2 份）、失败行里的提示词全文（1 份）、上游错误体原文、完整错误链。

不挂任务的调用
预检判断体裁 · 片段转写

每次尝试一行，字段和任务里的模型调用一致；用 user_id、drama_id、segment_id 关联。

为什么选这个方案

三个候选按「运维能不能 grep 一次定位」来比。

A 全流程 + 失败打全文（推荐，已确认）B 每次调用都打全文C 建表 + 后台时间线
grep 一次定位能能要进后台看
失败原因完整度错误链、上游原文、提示词、不合格输出完整，成功调用也有全文完整
日志量成功运行很小一部小说可能几十 MB，淹没其他日志要表和清理任务
实现成本集中在 callDrama、failDrama 两个出口小迁移 + 接口 + 页面
结论采用放弃用户撤回（不加后台）
核实度提案 日志量为 未验证未验证调研检索

外部参考：OpenTelemetry GenAI 约定默认不记录提示词和输出内容、错误类型用低基数枚举；Inngest、Trigger.dev 把每次重试单独记一条。调研检索，未逐条复核

用户说「剧本一直写不出来」时，会发生什么

以「写剧本」第 3 集两次输出都不合格为例。

  1. 第 1、2 集正常写完并保存两行 短剧模型调用，call=episode=1/2，result=ok。
  2. 第 3 集第 1 次输出不合格一行 Warn：attempt=1，带 validation_error 和输出全文，然后带着原因重写。
  3. 第 3 集第 2 次还是不合格又一行 Warn：attempt=2，带原因和输出全文。
  4. 任务失败、退款短剧任务失败（Warn）：error_type=invalid_output、call=episode=3、提示词全文、退回积分。
  5. 用户在任务条看到失败和任务 ID文案不变；新增的只是编号。
边界：日志里会出现用户的小说原文和模型输出
  • 失败时的提示词全文含用户原文，最多到模型上下文上限（几百 KB 级，未验证）。
  • 服务器日志文件的访问权限要按数据库同级管理。
  • 渠道 Key 在任何字段里都不出现：上游错误体先遮 Key 再打。
  • 默认配置只写标准输出，容器重建日志就没了；生产建议配 log.filename。

交付时要告知：部署方需配日志文件并控制访问权限；这是用户为排查明确选择的取舍。

日志长什么样

左边选一个场景，右边是这次运行打出的服务器日志（zap console 格式）。在顶部输入框里输入任意文字就是在 grep，比如 短剧任务失败、attempt、error_type。 编号、时间、耗时、全文内容都是示意，全文用一段开头加「全文 N 字」表示。

grep
设计：message 是固定的中文短句，变量全部放进字段，所以 grep 消息名能数出某类事件，grep 编号能拉出一整次运行。绿色的是只在失败时出现的全文字段。

字段与改动（提案）

下面都是设计提案，尚未实现。没有数据表和接口，「数据模型」就是日志字段。对应 Markdown 第 6、8 节。

日志事件清单

每次运行按时间顺序产生这些行。message 固定不变。

#message级别什么时候打专有字段

公共字段

挂任务的行都带这一组，由 dramaJobFields(j) 统一生成。

drama_job_id32 位十六进制，idcodec.Encode(j.ID)，和任务条上的编号相同。不用 task_id：短剧任务和生成任务是两张表，同一个编号可能两边都有，用字段名区分来源
drama_id短剧项目编号（十六进制，与前端地址一致）
user_id用户主键（uint64）
stepanalyze / plan / outline / scripts / breakdown / asset_prompts / storyboard / compose
laneuser 用户手动发起 / pipeline 自动规划
episodes本次涉及的集数 []int
batch自动规划的批次，如 "11-20"；没有批次时不带

模型调用行字段（E4 / E10 / E11）

每次尝试一行。级别：ok 为 Info；invalid、failed 为 Warn；canceled 为 Info。

call本次调用在运行里的位置：episode=3（scripts 每集）、batch=1-5（breakdown 每批）、空串（单次步骤）。由调用方传给 callDrama
attempt1 或 2（校验失败重写的那次是 2）
prompt_step / prompt_source用的哪套模板；builtin / 用户自写 / 技能
model_key / channel / upstream_model模型、渠道、实际上游模型
prompt_chars / output_chars提示词字数、输出字数
input_tokens / output_tokens / usage_missing上游用量；上游没给用量时 usage_missing=true
finish_reasonstop / length 等；length 说明输出被截断
latency_ms / ttft_ms总耗时、首字耗时（首字耗时 未验证：Gemini 格式是否逐段回调需实测）
result / error_typeok / invalid / failed / canceled；不是 ok 时带错误类型
errorfailed 时带完整错误链（已遮 Key）
upstream_status / upstream_body上游非 2xx 时带 HTTP 状态和错误体原文（遮 Key，最多 8KB）
validation_errorinvalid 时带：解码或校验原因原文
output仅 invalid 时带模型输出全文

失败行字段（E6）与失败分类

内部错误和合成失败用 Error（自动带堆栈）；其余用 Warn。

error_code / error_message写进库、给用户看的错误码和文案（对照用户截图）
error_type见右表
error完整错误链，不再只剩「服务内部错误」
call / attempt失败在哪次调用；非模型调用失败时不带
prompt那次调用的提示词全文；非模型调用失败时不带
duration_ms从开始执行到失败
refunded退回的积分
paused自动规划因此暂停
error_type含义级别
upstream上游非 2xx 或流内 errorWarn
timeout超过模型 deadline 或空闲超时Warn
network连接失败、读流中断Warn
invalid_output两次都解码或校验不过Warn
custom_prompt自定义提示词或技能导致不合格Warn
context_too_long提示词超过模型上下文Warn
no_model渠道 Key 读取失败或没有文本模型Warn
canceled用户取消导致上游中断Info（不打 E6）
compose_download / _transcode / _store合成三个阶段Error
business其他业务错误Warn
internal兜底Error

// dramaCallError 把失败那次模型调用的上下文带到 failDrama，由边界统一打印（规范 E7）。
type dramaCallError struct {
	Call    string // episode=3 / batch=1-5 / 空
	Attempt int
	Prompt  string // 那次调用的提示词全文
	Err     error
}
func (e *dramaCallError) Error() string { return e.Err.Error() }
func (e *dramaCallError) Unwrap() error { return e.Err }

// callDrama（节选）
for attempt := 1; attempt <= 2; attempt++ {
	...
	start := time.Now()
	result, ttft, e := s.streamDramaText(ctx, j, snap, prompt)
	fields := append(dramaJobFields(j), dramaCallFields(call, attempt, step, snap, prompt, result, start, ttft)...)
	if e != nil {
		logger.Warn("短剧模型调用", append(fields, callFailure(e)...)...)   // result=failed, error_type, error, upstream_*
		return nil, 0, &dramaCallError{Call: call, Attempt: attempt, Prompt: prompt, Err: e}
	}
	decoded, e := drama.DecodeOutput(step, []byte(result.Text))
	if e == nil && validate != nil { e = validate(decoded) }
	if e != nil {
		logger.Warn("短剧模型调用", append(fields, zap.String("result", "invalid"),
			zap.String("validation_error", e.Error()), zap.String("output", result.Text))...)
		invalid, lastPrompt = e, prompt
		continue
	}
	logger.Info("短剧模型调用", append(fields, zap.String("result", "ok"))...)
	return decoded, cost, nil
}
return nil, 0, &dramaCallError{Call: call, Attempt: 2, Prompt: lastPrompt, Err: errcode.ErrDramaOutputInvalid}

测试与验收

后端用 zaptest/observer 断言打出的行和字段，放 backend/internal/tests/。

  1. 成功：E1、E2、E4（ok）、E5 齐全，drama_job_id == idcodec.Encode(job.ID)，E4 不带 output、prompt。
  2. 第 1 次不合格、第 2 次成功：attempt=1 为 Warn 且带 validation_error、output；attempt=2 为 Info。
  3. 两次都不合格：E6 为 Warn，error_type=invalid_output，带 prompt；库里 error_message 不变。
  4. 上游 400：E4 带 upstream_status、upstream_body，Key 被替换成 ***。
  5. 内部错误：E6 为 Error，error 是原始错误文本。
  6. 用户取消：有 E7，没有 E6。
  7. scripts 第 3 集失败：E6 的 call=episode=3。
  8. 合成 ffmpeg 失败：E6 为 Error，compose_transcode，用户文案不变。
  9. 网关：UpstreamError.Body 遮 Key、≤8KB，Error() 不含 Body。
  10. 前端：失败任务显示「任务 ID：…」，运行中不显示。

人工验收：渠道指向只回 hello 的假服务，拿任务条编号 grep，能看到两行不合格调用（各带输出全文）和失败行（带提示词全文）；把渠道 Key 改错，能看到 401 和上游错误体原文，原文里没有 Key。最后 bash scripts/check.sh 通过。

已确认的决定

  1. 主要用途是运营 / 运维排查用户反馈：服务器日志一起补齐，不以调优提示词为主要目标。
  2. 不加后台页面，只在服务器日志里打完整：运维查日志排查。推翻了此前「并入使用记录、加来源筛选」的回答，那个决定已搁置，将来做后台时可复用。
  3. 全流程都打，失败时打全文：失败行带完整错误、上游原文、校验原因和提示词全文，不合格那次带输出全文；成功的调用不打全文。
  4. 任务条失败时显示任务编号：可复制，和画布生成任务一致。
  5. 默认值（不需要用户决定）：字段命名、级别、error_type 取值；预检判断体裁和片段转写也纳入；不新增日志开关配置。
