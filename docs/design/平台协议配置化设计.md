# 生成平台协议配置化设计

> 状态：设计稿 · 2026-09-29 · 依赖：[长任务生成设计](./长任务生成设计.md) · 首个平台：RunningHub

## 1. 设计摘要

**问题**：画布要接入多家生成平台（RunningHub、可灵、火山方舟…），而且运营会频繁上架新的模型或工作流。不能每接一家平台、每上架一个工作流都改代码发版。

**结论**：

1. 把“不硬编码”拆成三层配置，全部存 DB，**发布后热生效**：
   - **Provider（平台协议）**：鉴权、提交、查询、上传、取消、状态映射、错误分类。用声明式 DSL 描述。
   - **Model（模型 / 工作流）**：画布用户选的那一项。包括输入 `input_schema`、到平台请求的映射 `mapping`、输出选择、积分。
   - **Secret（凭证）**：加密存储，只能写入，永远不下发。
2. 代码里只有**一个通用执行引擎**：解析 DSL → 渲染请求 → 发 HTTP → 用表达式提取字段 → 映射状态。表达式用 [`expr-lang/expr`](https://github.com/expr-lang/expr)：无副作用、保证终止、编译期类型检查。
3. DSL 表达不了的东西（签名算法、multipart 上传）做成代码里的**有限枚举**，配置只负责选用哪一种。这是 DSL 唯一需要写代码扩展的地方。
4. 配置有**草稿 → 校验 → dry-run → 试跑 → 发布**的流程。发布版本不可变，**任务创建时对配置做快照**，运营改配置不影响进行中的任务。
5. 前端参数面板按 `input_schema` 动态渲染。上架新工作流时，前后端都不用发版。
6. RunningHub 支持**按 webappId 自动导入**节点列表，生成映射草稿，运营只需要确认字段含义。

### 2.2 RunningHub 协议形态

来源：官方 API 页面，以及本机 `runninghub` skill 的调用脚本（`scripts/runninghub.py`、`scripts/runninghub_app.py`）。

| 操作 | 形态 |
|---|---|
| 鉴权 | `Authorization: Bearer <32 位 API Key>`（旧版接口把 `apiKey` 放在请求体里） |
| 提交 AI 应用 / 工作流 | `POST /openapi/v2/run/ai-app/{webappId}`，请求体 `nodeInfoList: [{nodeId, fieldName, fieldValue}]`，可选 `instanceType`（default / plus / ultra）、`webhookUrl` |
| 提交响应 | `taskId`、`status`、`errorCode`、`errorMessage`、`promptTips`（JSON 字符串，内含 ComfyUI 的 `node_errors`） |
| 查询 | `POST /openapi/v2/query {taskId}` → `status: QUEUED / RUNNING / SUCCESS / FAILED`，`results: [{url, nodeId, outputType, text}]`，`usage.consumeMoney / taskCostTime` |
| 上传素材 | `/openapi/v2/media/upload/binary`（multipart），返回的文件名作为 `fieldValue` 使用 |
| 获取可改节点 | `GET /api/webapp/apiCallDemo?webappId=…` → `nodeInfoList` 模板 |
| Webhook | `POST {event: "TASK_END", taskId, eventData}` |
| 结果 URL | **24 小时有效，过期后永久失效** |

**关键观察**：RunningHub 是聚合平台，**一套协议下有成千上万个工作流**。每个工作流的 `nodeId` 和 `fieldName` 都不一样。所以变化最多的是 Model 层的映射，而不是 Provider 层的协议。只要把 Model 层做成配置，接 RunningHub 的新工作流就是零代码。

## 3. 调研

| 方案 | 做法 | 启发 | 不适用之处 |
|---|---|---|---|
| RunningHub nodeInfoList | 用 `nodeId + fieldName` 覆盖工作流参数 | 天然适合“映射即配置”，可以按 webappId 自动发现节点 | 节点语义（哪个是提示词）只能人工确认 |
| n8n declarative-style node | 用 JSON 描述 `requestDefaults`、`routing.request / send / output`，配合表达式 | 证明“HTTP 调用 + 表达式映射”这个边界是可行的 | n8n 自己也把复杂鉴权和多步流程留给 programmatic 节点：**DSL 必须有边界** |
| One API / New API | 每种渠道类型一个代码适配器，模型名映射和渠道都是配置 | 大部分价值在模型层配置 | 协议层仍然硬编码，不满足本次要求 |
| LiteLLM | provider 用代码实现，`model_list` 用 YAML 配置 | 同上 | 同上 |
| expr-lang/expr | Go 表达式引擎：内存安全、无副作用、保证终止、编译期类型检查，Google、Uber、Argo 等在用 | 直接作为 DSL 的表达式层，不用自己造解释器 | 表达能力有限。这正好是优点 |

## 4. 设计原则

1. **DSL 只描述“HTTP 调用 + 数据映射”**：没有循环、没有变量赋值、没有任意代码。表达式只从输入计算输出。
2. **能力枚举化**：鉴权方式、请求体编码、上传方式都是代码里的有限枚举，配置负责选用和传参。新增一种签名算法需要发版，这是有意保留的边界。
3. **凭证不进表达式**：表达式上下文里没有任何 secret，只有 `auth` 块能按名字引用凭证。这样模板写错、日志、dry-run 都不会泄露 Key。
4. **发布即不可变，任务带快照**：进行中的任务不受配置修改影响，出了问题也能按快照复现当时的请求。
5. **保存时就失败**：所有表达式在保存时编译，并校验引用的字段是否存在。错误精确到 JSON 路径，不留到运行时。
6. **默认拒绝出网**：每个 Provider 声明 `allowed_hosts`，请求、重定向、结果下载都要校验，防止配置被用来发起 SSRF。

## 5. 推荐方案

### 5.1 三层配置的关系

```text
┌──────────────── Provider（平台协议，少、慢变）────────────────┐
│ key: runninghub                                               │
│ base_url / allowed_hosts / auth(→secret) / rate_limit / poll  │
│ operations: upload · submit · query · cancel                  │
│ status_map · error_rules · webhook                            │
└───────────────────────────▲───────────────────────────────────┘
                            │ provider: runninghub
┌──────────────── Model（模型/工作流，多、常变）────────────────┐
│ key: rh-wan-i2v · kind: video · credits · deadline            │
│ params: {webappId, instanceType}      ← 给 Provider 模板用    │
│ input_schema: prompt / image / duration  ← 前端渲染 + 后端校验 │
│ mapping: {nodeInfoList: [...]}         ← 输入 → 平台字段      │
│ output: 从 outputs 中选出视频                                  │
└───────────────────────────────────────────────────────────────┘
┌──────────────── Secret ───────────────────────────────────────┐
│ runninghub_api_key = AES-GCM 密文，只写不读                     │
└───────────────────────────────────────────────────────────────┘
```

### 5.2 表达式约定

- 模板里任意 JSON 字符串值写成 `"${ expr }"` 时，求值后**保留类型**（可以得到数组或对象）。写成 `"前缀-${ expr }"` 这种嵌在文本里的形式时，做字符串插值。
- 纯表达式字段（`success`、`extract.*`、`when`）直接写 expr 源码。
- 可用的上下文变量：

| 变量 | 内容 | 可用阶段 |
|---|---|---|
| `input` | 已按 `input_schema` 校验过的用户输入 | 全部 |
| `files` | 上传步骤的结果，按输入名索引（如 `files.image`） | submit 及之后 |
| `model` | `model.params`、`model.mapping`（mapping 已先按 input 渲染） | 全部 |
| `task` | `id`、`provider_task_id` | query / cancel |
| `ctx` | `webhook_url`、`now` | 全部 |
| `resp` / `status` | 响应 JSON / HTTP 状态码 | 响应处理 |
| `req` | 回调请求体 | webhook |

- 自定义函数（代码注册，有限集合）：`parseJSON`、`matches`（正则）、`coalesce`、`toString`、`toInt`。

### 5.3 Provider 示例：RunningHub

```jsonc
{
  "dsl": 1,
  "key": "runninghub",
  "name": "RunningHub",
  "base_url": "https://www.runninghub.cn",
  "allowed_hosts": ["www.runninghub.cn", "*.runninghub.cn", "*.runninghub.ai"],
  "auth": { "type": "bearer", "secret": "runninghub_api_key" },
  "rate_limit": { "rps": 5, "max_concurrency": 20 },
  "poll": { "first_delay": "10s", "interval": "5s", "max_interval": "15s", "jitter": 0.2 },

  "operations": {
    "upload": {
      "method": "POST",
      "path": "/openapi/v2/media/upload/binary",
      "encoding": { "type": "multipart", "file_field": "file" },
      "success": "status == 200 && resp.code == 0",
      "extract": { "ref": "resp.data.fileName" }
    },
    "submit": {
      "method": "POST",
      "path": "/openapi/v2/run/ai-app/${ model.params.webappId }",
      "encoding": { "type": "json" },
      "body": {
        "nodeInfoList": "${ model.mapping.nodeInfoList }",
        "instanceType": "${ model.params.instanceType ?? 'default' }",
        "webhookUrl":   "${ ctx.webhook_url }"
      },
      "success": "status == 200 && resp.taskId != nil && len(parseJSON(resp.promptTips ?? '{}').node_errors ?? {}) == 0",
      "extract": { "provider_task_id": "resp.taskId" }
    },
    "query": {
      "method": "POST",
      "path": "/openapi/v2/query",
      "encoding": { "type": "json" },
      "body": { "taskId": "${ task.provider_task_id }" },
      "success": "status == 200",
      "extract": {
        "status":        "resp.status",
        "outputs":       "map(resp.results ?? [], {url: .url, type: .outputType, node: .nodeId, text: .text})",
        "error_code":    "resp.errorCode",
        "error_message": "resp.errorMessage",
        "provider_cost": "resp.usage?.consumeMoney"
      }
    },
    "cancel": null
  },

  "status_map": {
    "QUEUED": "queued", "RUNNING": "running",
    "SUCCESS": "succeeded", "FAILED": "failed",
    "_default": "running"
  },

  "error_rules": [
    { "when": "status == 429 || status >= 500",                                  "class": "retryable" },
    { "when": "matches(toString(resp.errorMessage), '(?i)balance|insufficient|余额')", "class": "provider_balance" },
    { "when": "matches(toString(resp.errorMessage), '(?i)sensitive|nsfw|审核|违规')",  "class": "moderation" },
    { "when": "true",                                                            "class": "terminal" }
  ],

  "webhook": {
    "verify": { "type": "path_secret" },
    "task_id": "req.taskId"
  }
}
```

说明：

- `cancel: null` 表示平台不支持取消，引擎自动走软取消（长任务设计 7.4 节）。RunningHub 是否有取消接口需要核实，见第 10 节。
- 统一错误分类 `retryable / terminal / moderation / provider_balance / submit_unknown` 由 worker 消费。`provider_balance` 表示**平台账户**余额不足，要触发告警通知运维，并提示用户“服务繁忙”，不把原因透给用户。
- 上面的响应字段路径（比如提交响应里 `taskId` 在顶层还是 `data` 下面）以试跑结果为准。这正是 dry-run 和试跑要解决的问题。

### 5.4 Model 示例：你给的 RunningHub 工作流

```jsonc
{
  "key": "rh-2093984571330498561",
  "kind": "video",
  "provider": "runninghub",
  "label": "（运营填写）",
  "hint": "（下拉里的一行小字）",
  "credits": 10,
  "deadline": "30m",
  "enabled": true,
  "sort": 100,

  "params": { "webappId": "2093984571330498561", "instanceType": "default" },

  "input_schema": {
    "prompt":   { "type": "text",  "label": "提示词", "required": true, "max_length": 2000, "port": "text" },
    "image":    { "type": "image", "label": "首帧",   "required": true, "port": "image" },
    "duration": { "type": "enum",  "label": "时长",   "options": [{"value": 5, "label": "5 秒"}, {"value": 10, "label": "10 秒"}], "default": 5 }
  },

  "mapping": {
    "nodeInfoList": [
      { "nodeId": "6",  "fieldName": "text",   "fieldValue": "${ input.prompt }" },
      { "nodeId": "12", "fieldName": "image",  "fieldValue": "${ files.image }" },
      { "nodeId": "30", "fieldName": "length", "fieldValue": "${ input.duration * 16 + 1 }" }
    ]
  },

  "output": { "select": "filter(outputs, .type in ['mp4', 'webm', 'mov'])", "media": "video" }
}
```

- 节点号和字段名是示意，实际值用自动导入获取（5.7 节）。
- `input_schema` 字段类型只有一个小集合：`text / number / enum / boolean / image / video / audio`。可选属性有 `required / default / min / max / max_length / options / port / advanced`（advanced 表示折叠到“高级”里）。
- `port` 表示这个字段可以由画布上游连线提供，比如上游图片节点接进来填 `image`。前端据此生成节点的输入口。
- 映射里可以写表达式做换算，比如秒数换算成帧数。这样运营不需要让工作流作者改工作流。

### 5.5 执行引擎（代码里唯一的实现）

```text
Submit(task):
  snap  := task.config_snapshot                 # 创建任务时冻结的 provider + model 发布版本
  input := validate(task.input, snap.model.input_schema)   # 已在 API 层校验过，这里防御性再校验
  files := for each 媒体类型输入:
             asset := 读取自有存储（校验 asset.user_id == task.user_id）
             upload op 存在 ? 调用 upload → extract.ref : 生成签名 URL
  model.mapping := render(snap.model.mapping, {input, files, model.params})
  req := render(snap.provider.operations.submit, {input, files, model, ctx})
  resp := http(apply_auth(req))                 # host 白名单、超时、响应体上限
  eval success → extract → 返回 provider_task_id，或按 error_rules 分类后的错误

Query(task):
  render query → http → extract.status → status_map → 统一状态
  succeeded 时对 outputs 执行 model.output.select → 交给转存流程
```

**枚举能力（代码实现，配置选用）**：

| 类别 | MVP | 预留 |
|---|---|---|
| `auth.type` | `none`、`bearer`、`header`（自定义头名）、`query`、`body_field`（RunningHub 旧版） | `jwt_hs256`（可灵 AK/SK）、`hmac_v4`（火山签名） |
| `encoding.type` | `json`、`multipart` | `form` |
| 媒体入参方式 | provider `upload` 操作、自有存储签名 URL | 平台预签名直传 |
| `webhook.verify` | `path_secret` | `hmac_header` |

**安全**：

- 每次请求、每次重定向、每次结果下载都校验 `allowed_hosts`。禁止访问内网 IP 段；DNS 解析后再校验一次，防 DNS rebinding。
- 响应体大小上限（比如 5MB，下载结果另有单独上限），超时按操作可配置（默认 30s）。
- 表达式在编译时限制最大节点数。上下文里没有 secret，日志和 dry-run 输出统一脱敏。

**缓存与热更新**：发布时编译所有表达式，按 `revision_id` 缓存编译结果。单实例下，发布接口直接刷新内存注册表；多实例时通过 Redis 广播失效消息，这跟长任务设计里的 `Broadcaster` 共用同一条通道。

### 5.6 版本与快照

```text
ai_providers        key PK, name, published_revision_id, updated_at
ai_models           key PK, kind, provider_key, enabled, sort, published_revision_id, updated_at
ai_config_revisions id, target(provider/model), target_key, revision_no, body_json,
                    status(draft/published/archived), created_by, created_at, note
ai_secrets          name PK, ciphertext, nonce, key_version, updated_by, updated_at
```

- 编辑时写 `draft`。发布时校验通过，把 `published_revision_id` 指向这条 revision。回滚就是把指针改回旧的 revision。
- `generation_tasks` 新增 `config_snapshot jsonb`，内容是创建任务时 provider 和 model 的发布版本正文，每个几 KB。worker 只读快照，不读当前配置。
- Secret 用 AES-256-GCM 加密，主密钥来自环境变量 `APP_AI_SECRET_KEY`，不进配置文件。`key_version` 用于以后轮换密钥。快照里只存 secret 的**名字**，执行时再解密，所以轮换 Key 能立即对进行中的任务生效。

### 5.7 运营工作流与管理 API

用户表新增 `role`（`user` / `admin`），加一个 `RequireAdmin` 中间件。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET / POST / PUT | `/api/v1/admin/ai/providers[/:key]` | 读取或编辑草稿 |
| GET / POST / PUT | `/api/v1/admin/ai/models[/:key]` | 同上 |
| POST | `/admin/ai/:target/:key/validate` | 用 JSON Schema 校验结构，编译表达式，检查引用。错误带 JSON 路径 |
| POST | `/admin/ai/models/:key/dry-run` | 传示例 `input`，返回渲染后的上传和提交请求（method、url、headers 脱敏、body），**不发送** |
| POST | `/admin/ai/models/:key/test-run` | 用草稿真实跑一次，创建 `is_test` 任务，不扣用户积分。返回每一步的原始请求、响应和提取结果 |
| POST | `/admin/ai/:target/:key/publish`、`/rollback` | 发布或回滚 |
| POST | `/admin/ai/import/runninghub` | `{webappId}` → 调用 `apiCallDemo` → 返回 Model 草稿，映射里的值预先填成 `${ input.xxx }` |
| PUT | `/admin/ai/secrets/:name` | 只写。GET 只返回“是否已设置”和更新时间 |

**上架一个 RunningHub 工作流的流程**：

```text
粘贴 webappId → 自动导入（得到所有可改节点，以及 fieldName / 当前值 / 描述）
  → 运营勾选要暴露给用户的节点，给每个节点起输入名、选类型、写 label
    （自动推断：fieldName 为 text/prompt → text；image → image；数字 → number）
  → 未暴露的节点保留工作流原值，不写进 mapping
  → 填 label / credits / deadline → validate → dry-run 看请求体
  → test-run 用示例图跑通 → 发布 → 画布模型下拉里立即出现
```

前端 MVP 做一个 JSON 编辑页（可以用 Monaco，加载 DSL 的 JSON Schema 做补全），右侧放 dry-run 和试跑的结果面板。

### 5.8 面向画布的 API 与前端

- `GET /api/v1/models?kind=video`：只返回 `key / label / hint / credits / kind / input_schema`，**不含** `params / mapping / provider` 细节。
- `POST /generation-tasks` 的 `input` 按 `input_schema` 校验：必填项、枚举、长度、媒体 asset 归属当前用户。校验失败返回 400，并附上字段级错误。
- **节点数据**：新增 `params?: Record<string, unknown>`，按 `input_schema` 的字段名存用户填的值。已有的 `prompt` 字段映射到 `params.prompt`，保持兼容。
- **参数面板**：根据 `input_schema` 渲染控件。有 `port` 的字段在节点上生成输入口：连线接入时显示“来自：某某节点”，并禁用手填。
- **切换模型**：保留同名同类型的参数，其余丢弃，丢弃前给提示。
- **模型下线**：已有节点里记录的 model key 在清单里找不到时，节点显示“模型已下线”，禁用生成，引导用户换一个模型。

## 6. 状态与异常

| 场景 | 处理 |
|---|---|
| 配置保存时表达式编译失败 | validate 返回错误和 JSON 路径，不允许发布 |
| 发布后才发现平台字段路径写错 | 试跑应该已经暴露。线上出现时，任务以 `terminal` 失败并退积分；管理员回滚配置 |
| `extract.status` 取到 status_map 里没有的值 | 按 `_default` 处理，并记录告警日志 |
| 进行中任务所用的模型被下线或修改 | 任务按快照继续跑完；新任务不能再选这个模型 |
| Secret 未设置 | 发布时校验失败；运行时遇到则 `terminal`，同时告警 |
| 平台账户余额不足（`provider_balance`） | 任务失败并退积分，提示“服务繁忙，请稍后再试”，告警给运维 |
| 工作流节点被作者改掉（`promptTips.node_errors`） | 提交判为失败，错误信息附上节点错误，方便运营重新导入 |
| 用户传入的 asset 不属于自己 | 400，不创建任务 |

## 7. 对现有设计的影响

- 长任务设计里的 `Provider` 接口保留，唯一实现是 `declarative.Engine`。7.3 节的 YAML 模型配置改为 DB 配置（见本文 5.6 节）。
- `generation_tasks` 新增 `config_snapshot`、`is_test`，`model_id` 改为保存 model key。
- 新增表：`ai_providers`、`ai_models`、`ai_config_revisions`、`ai_secrets`；`users` 新增 `role`。
- 新增依赖：`github.com/expr-lang/expr`，以及一个 JSON Schema 校验库（用来校验 DSL 自身的结构）。
- 前端：`MODEL_LIBRARY` 改为读取接口；节点新增 `params`，参数面板改成根据 schema 渲染；新增管理员 JSON 编辑页。

## 8. 方案取舍

### 已确认决策

| 分叉 | 决定 | 放弃了什么 |
|---|---|---|
| 维护者 | 运营频繁上架，配置存 DB，热生效 | Git 评审配置变更（用 revision 历史和发布流程来补偿） |
| 声明式程度 | 完全声明式 DSL，能力枚举化 | 签名类的新鉴权方式仍需发版加枚举 |
| 参数面板 | `input_schema` 驱动动态渲染 | 手工精调每个模型的专属 UI |
| 运营工具 | 管理 API + JSON 编辑 + dry-run / 试跑 + RunningHub 自动导入 | 可视化表单后台（放到阶段 2） |

### 主要风险

| 风险 | 缓解 |
|---|---|
| DSL 越长越复杂，逐渐变成编程语言 | `dsl` 版本号；只在真实平台需要时才加特性；新增能力优先做成枚举而不是语法 |
| 运营写错配置导致批量失败 | 发布前强制试跑成功；上线后监控单模型失败率，超过阈值自动下架并告警（阶段 2） |
| 配置被用来发起 SSRF 或窃取凭证 | host 白名单、内网 IP 拦截、表达式上下文不含 secret、只有管理员可以编辑 |
| RunningHub 工作流被作者修改或下架 | 捕获 `node_errors` 时给出明确错误；定期用 `apiCallDemo` 比对节点并告警（阶段 2） |

## 9. MVP 与后续

### 阶段 1（与长任务 MVP 合并交付）

内容：三层配置表加 revision；表达式引擎；枚举能力 `bearer / header / query / body_field` + `json / multipart`；RunningHub Provider 配置；RunningHub 自动导入；validate、dry-run、试跑、发布、回滚；`GET /models`；前端 schema 驱动的参数面板；管理员 JSON 编辑页。

验收条件：

1. 从粘贴 webappId 到画布里能用这个模型，**全程不改代码、不重启**，运营 15 分钟内完成。
2. 进行中的任务在其模型配置修改、回滚或下线后，仍按原配置跑完。
3. 配置里任何表达式写错都会在 validate 阶段报出，错误精确到 JSON 路径。
4. dry-run、日志、试跑结果、`GET /models` 里都看不到 API Key 明文。
5. 把 `base_url` 或结果 URL 指向不在白名单里的地址（包括 `127.0.0.1`、`10.x`、`169.254.x`），会被拒绝。
6. 用户提交缺少必填项或传入他人的 asset 时返回 400，并附字段级错误。
7. 新增第二家平台（比如火山方舟 Seedance，Bearer 鉴权）只需要写 Provider 配置，不改代码。

### 阶段 2

- 可视化表单后台（节点勾选、字段映射拖拽）。
- `jwt_hs256` 接入可灵。
- 动态积分 `credits_expr`（按时长或分辨率计价，提交前询价）。
- 单模型失败率熔断。
- 工作流节点漂移检测。

### 阶段 3

- 同一模型配多个 Provider 做故障切换或按成本路由。
- 配置导入导出，在环境之间迁移。
