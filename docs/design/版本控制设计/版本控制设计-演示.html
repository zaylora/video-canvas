01设计思路

主表继续存“当前画布”，
新增版本表专门负责恢复与审计

保持兼容

不动现有读取逻辑

保留 canvas_projects，payload_json + revision 结构不变，现有接口照常工作。

完整快照

每个版本一份完整 JSON

版本表存整份 payload_json，不做增量。回滚、预览都直接取快照，实现最简单。

前后端分工

撤销重做只在前端

操作级 undo / redo 放浏览器会话里；服务端版本负责跨会话、跨设备的恢复。

回滚本身也是一个新版本——所有历史都不会丢，用户随时可以“回到回滚之前”。

02版本来源与保留策略

自动版本滚动保留，标记过的版本永久保留

autosave

停止编辑后自动保存产生。数量最多，按保留策略滚动清理。

manual

用户主动保存，可命名、加备注，通常会标记为永久保留。

rollback

回滚操作生成的新版本，内容等于被回滚的目标快照。

灰点：未标记的自动版本　·　橙点：命名或标记的版本，不参与清理。示意图，版本间距不代表真实时间。

删除接口只允许删除未标记的自动版本；命名或标记过的版本永久保留。
03保存流程

前端节流提交，后端在一个事务里完成三件事

前端自动保存
每次编辑先写入本地撤销栈
停止编辑 1–3 秒后触发自动保存
请求携带当前 revision 和完整 payload_json
成功后清空已提交的撤销栈，更新本地 revision
后端 · 单事务保存
校验客户端 revision
更新主表当前快照，revision 递增
插入一条 canvas_project_versions 历史版本
按保留策略清理未标记的旧自动版本
主表继续满足现有读取逻辑，版本表负责恢复和审计。

哪些操作入栈

创建 / 删除节点 · 修改节点属性 · 移动节点 · 修改连线 · 修改时间线

连续拖动合并为一步

一次拖动只产生一条历史记录，避免栈被刷满。

刷新页面或更换设备后撤销栈清空；服务端版本仍然可以恢复。
07版本接口

五个接口，覆盖列表、详情、回滚、标记、删除

方法 路径 说明
GET /api/v1/canvas/:id/versions 列表；自动版本折叠后返回关键版本
GET …/versions/:versionNo 详情；返回完整快照
POST …/versions/:versionNo/rollback 回滚；创建新版本
PATCH …/versions/:versionNo 命名、备注、标记永久保留
DELETE …/versions/:versionNo 只允许删除未标记的自动版本
