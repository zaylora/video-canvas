# 协议插件设计

> 状态：设计稿 · 2026-09-30 · 已逐题评审
>
> **关系**：[New API 网关接入设计](./New%20API%20网关接入设计.md)里“项目只认 New API、协议写成 Go 代码、Key 放环境变量”的部分由本文取代：New API 改为**第一个内置插件**。该文的其余结论继续有效：删除 DSL、项目里没有映射、`input_schema` 手写并靠试跑兜底、第一版视频 + 文本、开发数据清空重建。
>
> **沿用**：[长任务生成设计](./长任务生成设计.md)的任务模型、worker、积分、转存、推送；[平台协议配置化设计](./平台协议配置化设计.md)的 Model 层（revision、发布回滚、试跑、快照）与 SSRF 防护、凭证加密。

## 1. 设计摘要

**问题**：New API 只是其中一种协议，以后还要接别的平台。要做到“新增一种协议不发版”，同时不回到“为 DSL 不断加语法”的老路。

**结论**：仿照 New API 的任务插件，做一个**协议插件运行时**。

1. **插件是一个 JS 文件**，由 goja 执行。它只做两件事：**把任务翻译成请求描述**、**把响应翻译成统一结果**。它不能发网络请求、不能读文件，默认也拿不到密钥。
2. **宿主负责其余一切**：发 HTTP、注入鉴权、解析文件引用、SSRF 防护、限流、超时、轮询、重试、错误兜底、积分、转存、脱敏、追踪。这些都是现有代码，大部分只是换个调用方。
3. **三层对象**：插件（协议实现，版本不可变）→ 渠道（选一个插件版本 + 地址 + 加密的 Key）→ 模型（绑定渠道 + 上游模型名 + `input_schema` + 积分）。
4. **权限分层**：新增 `super_admin` 角色（运维），只有它能装插件、管渠道凭证；`admin`（运营）只管模型。
5. **内置插件**：阶段 1 是 `newapi.js`（网关型，按模型名直传）；阶段 2 加 `runninghub.js`（工作流型，一个插件适配任意 RunningHub 工作流）。所有协议只有一条执行路径。
6. **任务快照冻结插件版本**：升级插件不影响进行中的任务。
7. **插件跑在独立的 `plugin-runner` 进程**：生产环境开放在线上传、插件不做代码评审，所以用进程隔离兜底。插件耗尽内存只会让 runner 崩溃并自动重启，主服务不受影响；runner 没有网络，只通过本地 Unix socket 和主服务通信。

## 5. 设计原则

1. **插件描述，宿主执行**：插件没有网络、文件、定时器；所有出网都经过宿主的 SSRF 防护与限流。
2. **密钥默认不进插件**：常见鉴权（Bearer、自定义头、查询参数）由宿主在请求描述返回后注入；只有声明了 `auth: custom` 的插件才拿得到密钥（第一版就支持），由 `super_admin` 在渠道上显式开启。
3. **插件版本不可变**：同一个版本号的代码一旦上传就不能改；任务快照记住版本，出了问题能按原代码复现。
4. **插件的错误是确定性的**：插件抛异常、超时、返回格式不对，都按 `terminal` 失败并告警，不自动重试；重试只针对网络与上游的临时错误。
5. **项目里没有映射**：参数怎么变成上游请求，是插件的事；模型配置只写选哪个渠道、哪个上游模型、给用户看哪些参数。
6. **能力由宿主扩展**：同步、二进制响应、文件上传这些能力加在宿主和契约里，插件按需使用；契约用 `apiVersion` 管理。

## 6. 推荐方案

### 6.1 总体结构

```text
                   ┌──────────── 管理端 ────────────┐
   super_admin ──▶ │ 插件：上传 / 版本 / 启停         │
                   │ 渠道：插件版本 + 地址 + 加密 Key  │
   admin ────────▶ │ 模型：渠道 + 上游模型 + schema   │
                   └───────────────┬────────────────┘
                                   │ 发布（快照冻结：模型 revision + 渠道配置 + 插件版本哈希）
                                   ▼
 画布 ─▶ 任务服务 ─▶ generation_tasks ◀── worker（轮询、转存、积分：不变）
                                           │ provider.Executor
                                           ▼
                   ┌───────────── 插件宿主 PluginExecutor ─────────────┐
                   │ 1. 调插件钩子 build* ──▶ plugin-runner 进程         │
                   │    （goja，沙箱，超时中断；无网络，内存受限）         │
                   │ 2. 校验请求描述：主机白名单、大小                  │
                   │ 3. 解析文件引用、注入鉴权                          │
                   │ 4. 发 HTTP（SSRF 传输层 + 渠道限流 + 超时）         │
                   │ 5. 调插件钩子 parse*，校验结果结构                  │
                   │ 6. 错误兜底分类、脱敏、写追踪                       │
                   └────────────────────────────────────────────────────┘
```

### 6.2 插件文件与 `meta`

一个插件是一个 JS 文件，用 CommonJS 写法（goja 不支持 ES 模块）：

```js
module.exports = {
  meta: {
    apiVersion: 1,
    key: "newapi", // 小写字母、数字、连字符，≤30 字符
    name: "New API",
    version: "1.0.0", // semver，同一 key 下唯一
    description: "自建 New API 网关",
    auth: { type: "bearer" }, // bearer / header / query / custom
    allowedHosts: [], // 结果下载可能要访问的域名；请求本身只能去渠道 base_url
    endpoints: {
      // 这个插件支持哪些生成方式
      text: { mode: "sync" },
      video: { mode: "async" },
      image: { mode: "sync" },
      audio: { mode: "sync" },
    },
    channelSettings: {
      // 渠道上的额外非敏感设置，渲染成表单
      region: { type: "enum", label: "区域", options: ["cn", "global"], default: "cn" },
    },
    import: {
      // 可选：管理端“从渠道导入模型”的参数表单，没有参数就是列出全部
      args: {},
    },
  },

  buildPrepareRequests(ctx) {
    /* 可选：提交前要先发的请求（如上传文件），返回请求描述数组 */
  },
  parsePrepareResponses(ctx, resps) {
    /* 可选：返回 prepared 对象，放进 ctx.prepared 给提交用 */
  },
  buildSubmitRequest(ctx) {
    /* 返回请求描述 */
  },
  parseSubmitResponse(ctx, resp) {
    /* 返回 { providerTaskId, state, immediate } */
  },
  buildQueryRequest(ctx) {
    /* 异步 endpoint 必须实现 */
  },
  parseQueryResponse(ctx, resp) {
    /* 返回统一结果 */
  },
  buildCancelRequest(ctx) {
    /* 可选，没有就走软取消 */
  },
  classifyError(ctx, resp) {
    /* 可选，返回错误分类；不实现就用宿主默认规则 */
  },
  buildCheckRequest(ctx) {
    /* 可选：连通性检查 */
  },
  buildImportRequest(ctx, args) {
    /* 可选：管理端导入模型 */
  },
  parseImportResponse(ctx, resp, args) {
    /* 可选：返回模型草稿数组 */
  },
};
```

**上传时的预检**（任一不通过就拒绝，错误精确到字段）：能在 goja 里编译并执行到导出；`apiVersion` 是宿主支持的版本；`key`、`version` 格式合法且版本未被占用；每个声明了 `async` 的 endpoint 都实现了 query 钩子；`auth.type` 是枚举值；`allowedHosts` 不含 `*` 以外的通配、不含 IP；文件大小不超过上限（提案 512KB）。

### 6.3 钩子契约

**`ctx`**（每次调用新建，JSON 传入，插件拿到的是副本）：

| 字段              | 内容                                                                                     |
| ----------------- | ---------------------------------------------------------------------------------------- |
| `ctx.task`        | `id`、`providerTaskId`（查询时）、`state`（插件上次返回的私有状态）                      |
| `ctx.model`       | `key`、`kind`、`upstreamModel`、`params`（运营在模型上填的固定参数，原样给插件解释）     |
| `ctx.input`       | 已按 `input_schema` 校验与规范化的用户输入；媒体字段是文件引用字符串，如 `"input:image"` |
| `ctx.channel`     | `baseUrl`、`settings`（`channelSettings` 的取值）                                        |
| `ctx.prepared`    | 准备阶段的结果（`parsePrepareResponses` 的返回值），只在 `buildSubmitRequest` 里有       |
| `ctx.credentials` | **只有 `auth: custom` 才有**，含 `apiKey`                                                |
| `ctx.now`         | 当前时间（Unix 秒）                                                                      |

**请求描述**（`build*` 的返回值）：

```js
{
  method: "POST",
  path: "/v1/video/generations",   // 相对渠道 base_url；也可给 url，但主机必须在 allowedHosts 里
  query: { },
  headers: { "Content-Type": "application/json" },
  json: { model: ctx.model.upstreamModel, prompt: ctx.input.prompt,
          image: { __fileRef: "input:image", as: "url" } },
  // 或 form: {...} / multipart: { parts: [{ name: "file", fileRef: "input:image" }] }
  responseType: "json",            // json / text / binary
  timeout: 30,                     // 秒，受宿主上限约束
  auth: { type: "query", name: "apiKey" }   // 可选：本次请求改用别的注入方式，仍由宿主注入
}
```

- 文件引用 `as` 可取 `url`（宿主生成自有存储的签名 URL）、`base64`、`dataUrl`；宿主负责校验素材归属当前用户与大小上限。
- 宿主在插件返回后注入鉴权：`bearer` 加 `Authorization: Bearer <key>`，`header`、`query` 按 `auth.name` 注入。插件自己写的 `Authorization` 头会被拒绝，防止它伪造或泄露。
- 同一平台的不同接口鉴权方式可能不同（RunningHub 的节点查询接口把 Key 放在查询参数里）。请求描述可以用 `auth` 为这一次请求换一种注入方式，Key 仍由宿主注入，插件看不到。`auth.type` 只能是 `bearer / header / query / none`。
- `responseType: "binary"` 时，宿主不把响应体交给插件，而是流式写入素材存储，把 `{ status, headers, asset }` 交给 parse 钩子。语音就走这条路。

**准备阶段**（可选）：有些平台要先把文件传上去，再用返回值提交。流程是：

```text
buildPrepareRequests(ctx) ─▶ 宿主依次执行（通常是 multipart 上传）─▶ parsePrepareResponses(ctx, resps)
      ─▶ prepared 写进任务的 provider_state ─▶ buildSubmitRequest(ctx)，ctx.prepared 可用
```

- 准备请求和提交请求走同样的校验、鉴权注入、SSRF 与限流。
- `prepared` 持久化后，提交阶段重试不会重复上传。
- 每个任务最多 8 个准备请求（提案），防止插件把一个任务变成大量请求。

**导入**（可选）：管理端“从渠道导入模型”时，宿主按 `meta.import.args` 渲染表单，调 `buildImportRequest(ctx, args)`，把响应交给 `parseImportResponse`。返回值是模型草稿数组：`{ upstreamModel, kind, label, params, inputSchema }`。草稿只预填编辑器，运营确认、试跑后才发布。

**统一结果**（`parseQueryResponse` 的返回值，`parseSubmitResponse` 的 `immediate` 同形）：

```js
{
  status: "queued" | "running" | "succeeded" | "failed",
  progress: 40,                                 // 可选，0–100
  outputs: [                                    // succeeded 时必填
    { type: "url",  url: "https://...", mediaType: "video", mime: "video/mp4" },
    { type: "text", text: "..." },
    { type: "asset" }                           // 二进制响应已由宿主落库
  ],
  error: { class: "moderation", code: "...", message: "..." },   // failed 时必填
  state: { },                                   // 可选，≤64KB，宿主持久化
  providerCost: 0.12                            // 可选，只写对账日志
}
```

宿主会校验结构：状态必须是四个值之一；`url` 产物的主机必须在插件的 `allowedHosts` 或渠道 `base_url` 上；`error.class` 只能是 `retryable / terminal / moderation / provider_balance`。不合规就按 `terminal` 失败并告警。

**`utils`**（宿主注入的同步函数）：`uuid()`、`unixNow()`、`base64(s)`、`base64Decode(s)`、`base64URL(s)`、`hmacSHA256(key, msg)`、`jwtSignHS256(claims, secret)`、`sha256(s)`、`log(msg)`（进试跑追踪，不进普通日志，单次调用最多 50 条）。以后新增的函数随 `apiVersion` 登记。

### 6.4 沙箱

| 项     | 做法                                                                                                                                                                                                       |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 进程   | 所有插件钩子都在独立的 `plugin-runner` 进程里执行（与主服务同一个二进制，不同子命令）。主服务按请求把 `ctx` 发过去、拿回结果，runner 不连数据库、不解密凭证、不发 HTTP                                     |
| 运行时 | runner 内每个插件版本一个 goja `Runtime` 池（提案每版本最多 8 个）；`Runtime` 单协程使用，调用前从池里取，用完归还                                                                                         |
| 隔离   | 每次调用的 `ctx`、响应都以 JSON 传入，返回值以 JSON 导出；不把任何 Go 对象暴露给 JS；删除 `eval`、`Function` 构造器等动态执行入口，冻结内置对象                                                            |
| 时间   | 每次钩子调用限时（提案 200ms），用计时器触发 `vm.Interrupt()`；超时后丢弃该 `Runtime`，不再归还池                                                                                                          |
| 大小   | `ctx` 与返回值编码后各 ≤1MB；`state` ≤64KB；插件文件 ≤512KB                                                                                                                                                |
| 内存   | goja 没有内存限制，靠**进程隔离**给出硬边界：生产环境 runner 作为独立容器运行并设 `mem_limit`，超限被系统杀掉后由容器自动重启；主服务不受影响。开发环境（Windows）作为子进程运行，只设 `GOMEMLIMIT` 软限制 |
| 网络   | 生产环境 runner 容器 `network_mode: none`，与主服务通过共享卷上的 Unix socket 通信；即使插件逃出 JS 沙箱，也没有网络可用                                                                                   |
| 能力   | 没有网络、文件、定时器、`require`；只有 `utils`                                                                                                                                                            |

**runner 崩溃时**：正在进行的钩子调用失败，对应任务按 `retryable` 重试一次；同一渠道的崩溃计入“连续插件级失败”，达到阈值自动停用渠道并告警。主服务在 runner 不可用期间，新提交的任务停在 `pending`，runner 恢复后继续。

插件不做代码评审、生产开放在线上传，所以进程隔离是这套设计里防止插件拖垮服务的主要手段。

### 6.5 渠道

| 字段                              | 说明                                                                                             |
| --------------------------------- | ------------------------------------------------------------------------------------------------ |
| `key`、`name`                     | 渠道标识，如 `newapi-main`                                                                       |
| `plugin_key`、`plugin_version_id` | **固定到一个插件版本**；升级插件要显式改这里                                                     |
| `base_url`                        | 插件请求只能去这个地址                                                                           |
| `trusted_internal`                | 是否允许 `base_url` 解析到内网地址（自建 New API 需要）；只有 `super_admin` 能开，开启记审计日志 |
| `allow_credentials`               | 插件声明 `auth: custom` 时必须开启，才会把 Key 放进 `ctx.credentials`；开启记审计日志            |
| `settings`                        | 插件 `channelSettings` 的取值                                                                    |
| `rate_limit`                      | `rps`、`max_concurrency`，复用现有限流组件                                                       |
| 凭证                              | 存 `ai_secrets`，名字固定为 `channel:<key>`，只写不读                                            |
| `enabled`                         | 停用后不再接新任务；进行中的任务按快照继续                                                       |

**连通性检查**：插件实现了 `buildCheckRequest` 时，管理端可以一键调用，确认地址和 Key 可用。

### 6.6 模型

```jsonc
{
  "key": "kling-i2v",
  "kind": "video",
  "channels": [
    // 数组，首期只允许一个元素
    { "channel": "newapi-main", "upstream_model": "kling-v2-master" },
  ],
  "params": { "max_tokens": 2000 }, // 可选，固定参数，原样交给插件
  "label": "（运营填写）",
  "credits": 10,
  "deadline": "30m",
  "enabled": true,
  "sort": 100,
  "input_schema": {},
}
```

- 保存时校验：渠道存在且启用；渠道所用插件版本的 `endpoints` 里有这个模型的 `kind`；`channels` 首期长度必须为 1。
- New API 网关接入设计里写在代码中的“直传规则”和 `limits.max_tokens`，现在都挪进 `newapi.js`：插件读 `ctx.input` 与 `ctx.model.params` 自己组装请求。
- `params` 的结构由插件定义，宿主只存不解释。工作流型插件（如 RunningHub）的节点绑定就放在这里，见 6.10。这是数据，不是表达式：插件按固定规则读取，不做计算。
- **快照**冻结模型 revision、渠道配置（不含 Key）与插件版本哈希。Key 只存名字，执行时解密，所以换 Key 立即对进行中的任务生效。

### 6.7 插件生命周期

```text
上传 plugin.js ─▶ 预检 ─▶ 存为不可变版本（sha256）─▶ 新建或修改渠道时选用这个版本
                                                     │
                                  用 is_test 任务在这个渠道上试跑，确认后发布模型
升级：上传新版本 ─▶ 预检 ─▶ 渠道改指向新版本 ─▶ 新任务用新版本；进行中任务按快照里的旧版本跑完
停用：插件停用 = 所有用它的渠道不再接新任务
删除：只能删除没有渠道引用、也没有非终态任务引用的版本
```

**内置插件**：`backend/plugins/newapi.js`（阶段 1）与 `backend/plugins/runninghub.js`（阶段 2）随仓库发布，启动时按 `key + version` 自动登记为 `builtin` 来源，不能被删除或覆盖；新版本的内置插件随发版登记，渠道仍要显式切换。

**多实例**：插件代码存在 DB，各实例按版本哈希懒加载并缓存，不需要广播代码本身；渠道、模型的变更沿用现有的“发布后刷新内存注册表”，多实例时走 Redis 广播（平台协议配置化设计阶段 2 的同一项）。

| -------------------------------------------------------------------------- | ------------- | ------- |
| 上传、启停、删除插件版本                                                   | ✓             | —       |
| 新建、修改渠道，设置渠道 Key，开启 `trusted_internal`、`allow_credentials` | ✓             | —       |
| 查看插件与渠道（不含 Key）                                                 | ✓             | ✓       |
| 编辑、试跑、发布、回滚模型                                                 | ✓             | ✓       |

- `users.role` 增加 `super_admin`；新增 `RequireSuperAdmin` 中间件，`RequireAdmin` 改为“`admin` 或 `super_admin`”。
- 首个 `super_admin` 只能用 SQL 提升，接口不提供提升自己的途径。
- 插件上传、渠道凭证变更、`trusted_internal` 与 `allow_credentials` 开关都写审计日志：操作人、时间、插件版本哈希或渠道 key。
- 生产环境开放在线上传，插件**不做代码评审**。安全边界靠契约（没有网络与文件）、宿主校验与进程隔离，而不是靠人工审阅代码。

### 6.10 内置插件：RunningHub 工作流（阶段 2）

**目标**：一个 `runninghub.js` 适配任意 RunningHub AI 应用（工作流）。上架一个新工作流只需要新建模型，不写代码、不改插件。

**协议事实**（v2，来源见 12 节）：

| 操作     | 接口                                                                                                                                                                                                             |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 鉴权     | `Authorization: Bearer <32 位 API Key>`                                                                                                                                                                          |
| 提交     | `POST /openapi/v2/run/ai-app/{webappId}`，请求体 `nodeInfoList: [{nodeId, fieldName, fieldValue}]`，可选 `instanceType`（`default / plus / ultra`）、`usePersonalQueue`、`retainSeconds`（10–180）、`webhookUrl` |
| 提交响应 | 顶层 `taskId`、`status`、`errorCode`、`errorMessage`、`results`、`promptTips`（JSON 字符串，含 ComfyUI 的 `node_errors`）                                                                                        |
| 查询     | `POST /openapi/v2/query {taskId}`，`status` 为 `QUEUED / RUNNING / SUCCESS / FAILED`；`results: [{url, nodeId, outputType, text}]`；`usage.consumeMoney`、`taskCostTime`                                         |
| 上传     | `POST /openapi/v2/media/upload/binary`，multipart 字段 `file`，返回 `{code: 0, data: {download_url}}`                                                                                                            |
| 可改节点 | `GET /api/webapp/apiCallDemo?apiKey=…&webappId=…`，返回 `data.nodeInfoList`（`nodeId`、`nodeName`、`fieldName`、`fieldValue`、`description`）                                                                    |
| 取消     | 没有找到，走软取消                                                                                                                                                                                               |
| 结果 URL | 24 小时有效，过期后永久失效                                                                                                                                                                                      |

**模型配置**：`upstream_model` 是 webappId，节点绑定写在 `params`：

```jsonc
{
  "key": "rh-2093984571330498561",
  "kind": "video",
  "channels": [{ "channel": "runninghub-main", "upstream_model": "2093984571330498561" }],
  "params": {
    "instanceType": "default",
    "bindings": {
      // 输入字段 → 工作流节点
      "prompt": { "nodeId": "6", "fieldName": "text" },
      "image": { "nodeId": "12", "fieldName": "image" },
      "duration": { "nodeId": "30", "fieldName": "length" },
    },
    "outputs": { "nodeIds": ["45"], "types": ["mp4", "webm", "mov"] }, // 可选：只取这些节点与类型的产物
  },
  "input_schema": {
    "prompt": { "type": "text", "label": "提示词", "required": true, "port": "text" },
    "image": { "type": "image", "label": "首帧", "required": true, "port": "image" },
    "duration": {
      "type": "enum",
      "label": "时长",
      "options": [
        { "value": 81, "label": "5 秒" },
        { "value": 161, "label": "10 秒" },
      ],
      "default": 81,
    },
  },
}
```

节点号与字段名是示意，实际值由导入得到。

**插件行为**：

| 钩子                                       | 做什么                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `buildImportRequest`                       | `meta.import.args = { webappId }`；请求 `apiCallDemo`，本次请求 `auth: { type: "query", name: "apiKey" }`                                                                                                                                                                                                                                                                         |
| `parseImportResponse`                      | 把 `nodeInfoList` 转成一份草稿：每个节点生成一个 `bindings` 项和一个 `input_schema` 字段；按 `nodeName` / `fieldName` 推断类型（`LoadImage` / `image` → image，`LoadVideo` → video，`LoadAudio` → audio，`text` / `prompt` → text，数字默认值 → number），`fieldValue` 作为默认值，`description` 作为 label。运营删掉不想暴露的字段即可，**没绑定的节点保留工作流原值，不会发送** |
| `buildPrepareRequests`                     | 对 `bindings` 里每个媒体字段，发一次 `media/upload/binary`，`multipart` 的 `file` 用文件引用 `input:<字段名>`                                                                                                                                                                                                                                                                     |
| `parsePrepareResponses`                    | 取每个响应的 `data.download_url`，按字段名放进 `prepared`                                                                                                                                                                                                                                                                                                                         |
| `buildSubmitRequest`                       | 按 `bindings` 生成 `nodeInfoList`：普通字段取 `ctx.input`，媒体字段取 `ctx.prepared`；`instanceType` 等取 `params`                                                                                                                                                                                                                                                                |
| `parseSubmitResponse`                      | `promptTips.node_errors` 非空 → 立即失败（`terminal`，信息带上节点错误，提示运营重新导入）；否则返回 `taskId`                                                                                                                                                                                                                                                                     |
| `buildQueryRequest` / `parseQueryResponse` | 状态映射 `QUEUED→queued`、`RUNNING→running`、`SUCCESS→succeeded`、`FAILED→failed`；产物按 `params.outputs` 过滤，`outputType` 为文本时产出 text 类型；`usage.consumeMoney` 写 `providerCost`                                                                                                                                                                                      |
| `classifyError`                            | 错误信息含 `balance / insufficient / 余额 / credit` → `provider_balance`；`errorCode` 为 `1501`（内容校验不通过）或含审核关键词 → `moderation`；其余交给宿主默认规则                                                                                                                                                                                                              |

**`meta` 要点**：`auth: { type: "bearer" }`；`endpoints` 声明 `video`、`image`、`audio`、`text` 都是 `async`；`allowedHosts` 写 RunningHub 的结果域名（如 `*.runninghub.cn`、`*.runninghub.ai`，以及试跑时观察到的对象存储域名）。渠道的 `base_url` 选 `https://www.runninghub.cn` 或 `https://www.runninghub.ai`。

**放弃了什么**：原来的 DSL 映射能写换算（如秒数换帧数）。现在不行，换算要体现在 `input_schema` 的选项值上：如上例，选项的 `value` 直接是帧数，`label` 写秒数。

## 7. 状态与异常

| 场景                                                    | 处理                                                                                                                                                          |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 插件钩子抛异常                                          | `terminal`，退积分；异常信息进追踪与告警，不直接给用户看                                                                                                      |
| 插件钩子超时（被中断）                                  | `terminal`，退积分，丢弃该 Runtime，告警                                                                                                                      |
| 调用中 runner 进程崩溃（如内存超限）                    | 该任务按 `retryable` 重试一次；计入渠道的连续插件级失败；runner 自动重启                                                                                      |
| runner 不可用                                           | 新任务停在 `pending`，恢复后继续；持续不可用告警运维                                                                                                          |
| 请求描述指向非法主机、写了 `Authorization` 头、超过大小 | `terminal`，退积分，告警                                                                                                                                      |
| 结果结构不合规（未知状态、产物主机不在白名单）          | `terminal`，退积分，告警                                                                                                                                      |
| 上游 429 / 5xx / 网络错误                               | 插件的 `classifyError` 优先；没实现时宿主默认规则（额度不足关键词 → `provider_balance`，429 / 5xx → `retryable`，读超时 → `submit_unknown`，其余 `terminal`） |
| 同一渠道连续多次插件级失败（提案 10 次）                | 自动停用渠道，告警运维                                                                                                                                        |
| 插件或渠道被停用时仍有进行中任务                        | 按快照继续跑完；新任务不能再选用                                                                                                                              |
| 快照里的插件版本被删除                                  | 不允许：有非终态任务引用的版本不能删                                                                                                                          |
| 渠道 Key 未设置                                         | 模型发布校验失败；运行时遇到则 `terminal` 并告警                                                                                                              |
| 上传的插件预检失败                                      | 返回错误与字段位置，不登记版本                                                                                                                                |
| 上传的版本号已存在                                      | 拒绝，要求改版本号（版本不可变）                                                                                                                              |
| 准备阶段请求失败（如 RunningHub 上传失败）              | 按错误分类处理：临时错误重试，已成功的上传结果保留在 `provider_state` 不重复上传；其余失败退积分                                                              |
| RunningHub 工作流被作者改掉（`node_errors`）            | 提交即失败并退积分，错误信息带上节点错误，提示运营重新导入                                                                                                    |

## 9. 方案取舍

### 已确认决策

| 分叉           | 决定                                                                                                | 放弃了什么                                                                                                         |
| -------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 插件形式       | JS 热插件                                                                                           | Go 接口预留 JS：首期更快、不用沙箱，但新增协议要发版                                                               |
| 契约           | 自定契约，形状借鉴 New API                                                                          | 兼容 New API v1：能直接装官方插件，但要跟随对方演进，`ctx.body` 形状没有完整文档                                   |
| 渠道凭证       | 渠道存 DB，Key 加密只写                                                                             | Key 走环境变量：安全边界更简单，但每加渠道都要重启，热插件意义打折                                                 |
| 模型与渠道     | 先单渠道，数据结构预留多渠道                                                                        | 多渠道故障切换：要处理参数差异、可切换的错误、快照记录，复杂度明显上升                                             |
| 安装权限       | 新增 `super_admin`                                                                                  | `admin` 都能装：运营账号被盗就能在服务端跑任意脚本                                                                 |
| 首个插件       | New API 写成 JS 插件随仓库内置                                                                      | Go 内置驱动并存：上线更快，但两条执行路径，契约是否够用要等第二个协议                                              |
| JS 引擎        | goja                                                                                                | moejs：ES 模块写法与 New API 一致，但项目过早期                                                                    |
| 在线上传       | 生产环境开放                                                                                        | 只允许内置插件：攻击面最小，但新增协议要发版                                                                       |
| 代码评审       | 不评审                                                                                              | 强制评审：多一道人工关，但拖慢接入                                                                                 |
| `auth: custom` | 进第一版                                                                                            | 放到阶段 2：第一版只能接 Bearer 类平台                                                                             |
| RunningHub     | 内置 `runninghub.js`，一个插件适配任意工作流，放在**阶段 2**；节点绑定放在模型 `params`，由导入生成 | 与 `newapi.js` 同在阶段 1：契约第一天就被两种协议检验，但阶段 1 范围更大；绑定写进插件：每上架一个工作流都要改插件 |
| 插件执行位置   | 独立 `plugin-runner` 进程，生产无网络、限内存                                                       | 同进程加内存巡检：实现简单，但内存涨得快时拦不住；接受风险：崩溃期间全部接口不可用                                 |

### 相对上一版设计的变化

| 上一版（New API 网关接入设计） | 本版                                                                       |
| ------------------------------ | -------------------------------------------------------------------------- |
| `newapi.Executor` 用 Go 写     | `PluginExecutor` 是宿主，New API 是 `newapi.js`                            |
| Key 放 `APP_AI_NEWAPI_API_KEY` | Key 按渠道存 `ai_secrets`，保留 `APP_AI_SECRET_KEY`                        |
| 删除 `ai_secrets` 与凭证面板   | 保留，改为按渠道                                                           |
| 删除整个 `provider/engine`     | 保留 SSRF 传输层、限流、追踪                                               |
| 服务端配置 `ai.newapi.*`       | 改为渠道记录；`trusted_internal` 从配置文件移到渠道，由 `super_admin` 控制 |

### 主要风险

| 风险                                                     | 缓解                                                                                                                     |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| goja 没有内存限制，有缺陷的插件可能耗尽内存              | 插件跑在独立 runner 进程，生产容器设 `mem_limit`，崩溃只影响插件调用并自动重启；大小上限、超时中断；连续失败自动停用渠道 |
| 插件拿到密钥后外泄（`auth: custom`）                     | runner 没有网络；插件的请求只能去 `base_url` 或 `allowedHosts`；渠道必须显式开启 `allow_credentials`；审计日志           |
| 插件被当成“服务端任意代码执行”的入口（开放上传、不评审） | 只有 `super_admin` 能上传；runner 无网络、不连数据库、没有凭证之外的敏感数据；审计日志记录每次上传的版本哈希             |
| 进程间通信增加延迟                                       | 本机 Unix socket，一次往返预期是毫秒以下；与一次 HTTP 调用相比可以忽略，上线前压测                                       |
| 契约设计不全，第二个协议写不出来                         | New API 作为插件第一天就落地；第二个协议上线前允许 `apiVersion: 1` 做向后兼容的扩展                                      |
| JS 执行的性能开销                                        | 每次钩子调用只做 JSON 组装与解析，预期远小于一次 HTTP；Runtime 池化；上线前压测                                          |
| 调试困难                                                 | 试跑追踪展示每次钩子的输入输出与 `utils.log`；dry-run 展示最终请求                                                       |

## 10. MVP 与后续

### 阶段 1：插件运行时 + New API 插件（视频 + 文本）

内容：`plugin-runner` 进程与 goja 沙箱、契约 v1（同步 `immediate`、异步查询、`state`、文件引用 `url`、`auth: custom`、导入钩子）、插件上传与预检、插件版本表、渠道、`super_admin`、审计日志、内置 `newapi.js`（text、video）、管理页插件与渠道两页、前端文本节点接入。

验收条件：

1. 上传一个新插件（测试用的模拟协议），新建渠道、上架模型、试跑、发布，画布里可用，全程不发版、不重启。
2. 视频节点端到端经 `newapi.js` 跑通：提交、轮询、转存、回填、取消、失败退积分。
3. 文本节点经 `newapi.js` 同步出正文。
4. 升级插件版本并切换渠道后，切换前已提交的任务按旧版本跑完；快照里能看到旧版本哈希。
5. 插件死循环：该次调用在时限内被中断，任务 `terminal` 并退积分，进程不受影响。
6. 插件请求描述指向渠道 `base_url` 以外的主机、写 `Authorization` 头、指向 `127.0.0.1` 或 `169.254.x`：全部被拒绝。
7. `auth: bearer` 的插件在 `ctx` 里拿不到 Key；Key 不出现在追踪、日志、dry-run、`GET /models` 里。
8. `admin` 调用插件上传、渠道凭证接口返回 403。
9. 预检拒绝：语法错误、缺少异步 query 钩子、重复版本号、`apiVersion` 不支持，错误指出具体字段。
10. 仓库里不再有 `expr-lang/expr` 依赖与 DSL 表达式代码。
11. 插件不停分配内存：runner 被系统杀掉并自动重启，主服务的其它接口全程可用，该任务重试一次后失败退积分。
12. 写一个需要 `auth: custom` 签名的测试插件：渠道未开 `allow_credentials` 时 `ctx` 里没有 Key；开启后能签名成功。
13. 管理端“从渠道导入模型”：`newapi.js` 的导入钩子列出 New API 的模型，选中后预填模型草稿。

### 阶段 2：宿主能力补全 + RunningHub 插件

内容：`responseType: binary`（语音）、同步带 URL 产物的 `provider_result`（图片）、准备阶段与 `multipart` 文件引用、请求级 `auth`、`base64` / `dataUrl` 引用、`newapi.js` 补 image 与 audio、内置 `runninghub.js`（6.10）、渠道连续失败自动停用。

验收条件：

1. 真实生成一段配音，经二进制响应直接落素材，节点里可播放。
2. 同步图片返回后、转存前杀掉进程，重启后继续转存，上游只有一次调用。
3. 写一个直连某厂商（例如可灵，需要 `auth: custom` 签名）的插件，不改宿主代码就能真实出片。
4. RunningHub：在管理端填入 webappId `2093984571330498561` 导入，得到草稿；删掉不需要的字段、填 label 与积分，试跑用一张图真实出片，发布后画布里可用，全程不写代码。
5. 再导入一个节点结构不同的 RunningHub 工作流，同一个 `runninghub.js` 不改就能跑通。
6. RunningHub 提交阶段重试时不会重复上传；`node_errors` 非空时任务立即失败并退积分。

## 11. 待确认问题

已于 2026-09-30 确认：生产开放在线上传；`auth: custom` 进第一版；插件不做代码评审；插件跑在独立进程。

**关于许可证**：`newapi.js` 是我们自己写的、按 New API 公开 HTTP 协议调用它的插件，项目不包含也不修改 New API 的代码，不涉及它的 AGPLv3 许可证。唯一要注意的是：写插件时不要照抄 New API 仓库里官方插件的代码（那是 AGPLv3 代码）；借鉴它的钩子命名与边界设计不受影响。

1. **沙箱预算的具体数值**：单次钩子 200ms、`ctx` 1MB、`state` 64KB、插件文件 512KB、每版本 8 个 Runtime，以及 runner 容器的 `mem_limit`，都是提案，压测后定。
2. **（阶段 2）RunningHub 图片字段能否直接填 URL**：v2 工作流接口的图片节点如果接受任意 URL，就能跳过上传、直接用自有存储的签名 URL，省一次请求。旧版接口要求填上传返回的 `fileName`，v2 上传返回的是 `download_url`。先按“上传后填 `download_url`”实现，试跑确认。
3. **（阶段 2）RunningHub 结果与上传文件所在的域名**：决定 `runninghub.js` 的 `allowedHosts`，试跑时记录。
4. **（阶段 2）示例工作流 `2093984571330498561` 的真实节点**：需要用 Key 调一次 `apiCallDemo`（只读、不收费），6.10 的节点号目前是示意。
