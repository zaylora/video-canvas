## 1. 设计摘要

**问题**：后端把 AI 配置改成了“插件 → 渠道 → 模型”三层，权限分成运维（`super_admin`）和运营（`admin`）。管理端现在还是旧的“模型 JSON 编辑器 + 凭证面板”两个标签页，没有插件页、渠道页，也不知道当前用户是谁，旧凭证面板调用的接口后端已经删除。

**目标**：

1. 运维能在页面上完成一次协议接入：上传插件 → 看预检结果 → 建渠道 → 设 Key → 连通性检查。
2. 运营能在不接触插件代码和 Key 的前提下上架模型：选渠道 → 填上游模型（或从渠道导入）→ 试跑看追踪 → 发布。
3. 两种角色看到的界面不同，**危险操作有明确的确认与提示**，无权限的操作不出现而不是点了才报 403。

**推荐方案**：把 `/admin/ai` 拆成 **模型 / 渠道 / 插件** 三个子路由，共用一个带角色的布局；渠道用“列表 + 侧边抽屉”，插件用“主从详情”，模型编辑器保留 JSON 作为唯一事实来源、在上面加一个结构化的“渠道与上游模型”表单；试跑结果面板新增“追踪”标签，把每次钩子与每次 HTTP 摊成时间线。

**最重要的一个前提**：后端的插件、渠道、`/me`、trace 接口**目前都没有**（见后端评审 P0-2）。前端要按 `backend/docs/admin-ai-api.md` 的契约开发，用 mock 起步，不能等后端。

## 3. 用户与场景

| 角色                  | 场景                                                           | 频率                   | 成功标准                                                                                              |
| --------------------- | -------------------------------------------------------------- | ---------------------- | ----------------------------------------------------------------------------------------------------- |
| 运维（`super_admin`） | 接入新协议：传插件、建渠道、设 Key、检查连通                   | 低（每接一个平台一次） | 插件写错时**上传就被拒且指出字段**；Key 设完能立刻看到“已设置”；检查失败能看出是地址、Key 还是 runner |
| 运维                  | 升级插件：上传新版本 → 渠道切过去 → 试跑确认                   | 低                     | 切换前能看到“有新版本”、切换后提示去试跑；进行中任务不受影响这件事在界面上说清楚                      |
| 运营（`admin`）       | 上架模型：选渠道、填上游模型、`input_schema`、积分，试跑、发布 | **高（日常主任务）**   | 一屏内完成“编辑、试跑、看追踪、发布”；不会看到 Key，也不会看到自己做不了的按钮                        |
| 运营                  | 批量起草：从渠道导入模型列表，挑几个预填                       | 中                     | 导入的是草稿，明确不会直接上架                                                                        |
| 运营                  | 试跑失败排查                                                   | 中                     | 一眼看出失败在哪一步（钩子还是 HTTP）、上游返回了什么                                                 |
| 画布用户              | 生成内容                                                       | —                      | 感知不到任何变化                                                                                      |

**主任务路径**：运营的“编辑 → 试跑 → 看追踪 → 发布”。所以模型页是三页里最重的一页，渠道与插件页是低频、重安全的页面。

## 5. 设计原则

1. **看得见的才是能做的**：`admin` 看不到上传、设 Key、开关内网与凭证；只读页仍显示信息，但写操作不渲染。**不靠点了再 403 来教育用户**（403 只作为兜底页）。
2. **危险开关用“后果说明”而不是“确认弹窗”**：`trusted_internal`、`allow_credentials` 的开关旁直接写明它放开了什么、会被审计；确认弹窗留给不可逆的动作（删除版本、覆盖 Key、发布、回滚）。
3. **Key 永远只写**：输入框永远空白，成功后只更新“已设置 · 更新时间”，不缓存、不回显、不进 URL、不进任何 store。
4. **上传即反馈**：预检问题精确到字段路径，和上传文件同屏显示，不靠 toast。
5. **不可变要看得见**：插件版本、`sha256`、“N 个渠道固定在此版本”是一等信息，升级路径清晰。
6. **JSON 仍是模型的事实来源**：`input_schema` 和 `params` 的形状由插件定义，结构化表单只管“选渠道、填上游模型”这类通用字段，不试图为 `params` 造表单。

## 6. 推荐方案

### 6.1 信息架构

```text
/admin/ai                  → 重定向到 /admin/ai/models
├─ /admin/ai/models        模型（admin + super_admin 可写）
│    ├─ ?key=<key>         选中某个模型
│    └─ /new               新建（可带 ?from=import 预填草稿）
├─ /admin/ai/channels      渠道（读：admin；写：super_admin）
│    └─ ?edit=<key>|new    抽屉
└─ /admin/ai/plugins       插件（读：admin；写：super_admin）
     └─ ?key=<key>         主从详情
```

- **布局** `AdminAiLayout`：顶部“返回画布 + 标题 + 三个标签（模型 / 渠道 / 插件）+ 角色徽标”；进入时调用一次 `getAdminMe`，结果放进 `useAdminStore`；`403` 显示 `ForbiddenView`。
- **入口**：画布列表页顶栏增加“AI 配置”入口，只对 `admin / super_admin` 显示。这需要知道角色，所以要在登录后或列表页首次进入时**静默**调用 `getAdminMe`（普通用户得到 403，不弹 toast，见第 8.3 节）。
- **标签顺序**：模型、渠道、插件——与运营的使用频率一致。运维首次接入时的流程是反向的（插件 → 渠道 → 模型），所以在每页顶部放一条**“下一步”提示**：插件页上传成功后提示“去新建渠道”，渠道页 Key 设好后提示“去上架模型”。

### 6.2 角色与权限矩阵

| 操作                                         | `super_admin` | `admin` | 界面表现（`admin`）                    |
| -------------------------------------------- | ------------- | ------- | -------------------------------------- |
| 查看插件、版本、`meta`                       | ✓             | ✓       | 正常显示                               |
| 上传插件、启停、删版本                       | ✓             | —       | 不渲染按钮；页头写“只读，需要运维权限” |
| 查看渠道（不含 Key）                         | ✓             | ✓       | 正常显示，Key 只显示“已设置”           |
| 新建、修改渠道、设 Key、检查、开关内网与凭证 | ✓             | —       | 抽屉以只读模式打开，操作区不渲染       |
| 从渠道导入模型                               | ✓             | ✓       | 可用（后端 admin 可调）                |
| 模型的编辑、校验、试跑、发布、回滚、上下架   | ✓             | ✓       | 可用                                   |
| 普通用户（`user`）                           | —             | —       | 不显示入口；手输 URL 得到 403 页       |

**角色 store**：`useAdminStore`（zustand）持有 `role: 'admin' | 'super_admin' | null`、`status: 'idle' | 'loading' | 'ready' | 'forbidden'`。`utils/admin/role.ts` 已有 `canManageInfra`（仅 `super_admin`）与 `canManageModels`，页面只调用这两个函数，不直接比较字符串。角色变更后端缓存最多延迟一个 TTL，所以 403 兜底页要提示“角色刚变更可稍后重试”。

### 6.3 插件页（主从）

**左栏：插件列表**。每行：名称与 key、来源标签（内置 / 已上传）、启用开关（仅 `super_admin`）、最新版本号、“N 个渠道在用”。顶部搜索与“上传插件”主按钮（仅 `super_admin`）。

**右栏：详情**，从上到下：

1. **头部**：名称、key、来源、启用状态；停用时显示提示“停用后，所有使用它的渠道不再接新任务，进行中的任务不受影响”。
2. **版本表**（新到旧）：版本号、`sha256` 前 8 位（悬停显示全文并可复制）、上传时间、上传人（内置显示“内置”）、“固定在此版本的渠道数”、删除按钮。
   - 删除：内置版本与有渠道引用的版本，按钮禁用并写明原因；其余点击后走 `ConfirmDialog`；后端仍可能因“有非终态任务引用”返回 409，前端把这个原因就地显示在对话框里（全局 toast 照常弹，不重复）。
3. **能力清单**（读 `meta`，不是 JSON 展示）：

   | 区块           | 内容                                                                                              |
   | -------------- | ------------------------------------------------------------------------------------------------- |
   | 鉴权           | `auth.type`；`custom` 时用醒目的警告色写明“需要渠道开启 `allow_credentials`，才会把 Key 交给插件” |
   | 支持的生成方式 | `endpoints` 渲染成 `text / video / image / audio` 四格，每格标同步或异步，没声明的置灰            |
   | 允许访问的域名 | `allowedHosts` 芯片列表                                                                           |
   | 渠道设置项     | `channelSettings` 的字段清单（标题、类型、必填、默认值）——也就是渠道抽屉里会出现的字段            |
   | 导入           | 有 `import` 显示参数表单预览，没有显示“不支持导入模型”                                            |
   | 原始 meta      | 折叠的只读 JSON（`FoldableCode`）                                                                 |

**上传对话框**（仅 `super_admin`）：

```text
┌ 上传插件 ───────────────────────────────┐
│  [ 拖拽或选择 .js 文件 ]  ≤512KB           │  ← 选文件后先做本地检查（扩展名、大小），不通过不发请求
│  已选：kling.js · 18KB                    │
│  ─────────────────────────────────────  │
│  预检结果                                 │
│  ✕ meta.endpoints.video.mode              │  ← 每条问题一行：路径 + 说明，路径可复制
│    异步 endpoint 缺少 buildQueryRequest   │
│  ✕ meta.version   版本号 1.0.0 已存在      │
│                            [取消] [上传]  │
└──────────────────────────────────────────┘
```

- 上传按钮在请求中显示“预检中…”，防止重复提交。
- **预检不通过也是 HTTP 200**（`accepted: false`），所以问题列表在对话框内展示，**不关闭对话框**，用户改文件后可再次选择。
- 通过（`accepted: true`）：对话框切换为成功态，显示新版本号、`sha256`、“下一步：新建渠道”按钮（带上 `plugin_key` 跳到渠道抽屉）。
- 特殊错误：413 文件超限（本地已拦，兜底文案）；503 / 50021 runner 不可用，显示“插件运行器暂时不可用，稍后重试”，保留已选文件。

### 6.4 渠道页（列表 + 抽屉）

**列表**：表格列——名称与 key、插件与固定版本（有新版本时带“可升级”点）、`base_url`、Key（已设置 / 未设置）、标志位（内网 / 凭证）、启用、操作。

- 行内操作：**检查**（`super_admin`）、**导入模型**（都能用）、编辑或查看。
- 空状态：“还没有渠道。渠道把一个插件版本、一个地址和一个 Key 绑在一起，模型通过渠道调用上游。”，主按钮“新建渠道”（`admin` 看不到按钮，只看到说明）。
- 危险标志位在列表里用图标 + 文字标出（不是只有颜色）：`内网` 表示 `trusted_internal`，`凭证` 表示 `allow_credentials`。

**抽屉**（新建 / 编辑；`admin` 打开为只读）：分五个区，从上到下：

| 区         | 字段                                                   | 规则                                                                                                                                                                                                             |
| ---------- | ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 基本       | `key`（新建可填，之后只读）、`name`、启用              | key 用 `CHANNEL_KEY_PATTERN` 实时校验                                                                                                                                                                            |
| 插件       | 插件下拉 → 版本下拉                                    | 版本默认选**最新且启用的**；如果当前渠道固定的不是最新，显示横幅“有新版本 1.1.0，切换后新任务用新版本，进行中的任务按旧版本跑完。切换后建议先试跑”；换插件版本时用 `rebaseSettings` 迁移设置项，被丢弃的项要提示 |
| 连接       | `base_url`                                             | 用 `checkBaseUrl` 校验（http/https、无用户名密码）；**`trusted_internal` 开关**在它下面                                                                                                                          |
| 插件设置   | 按所选版本的 `channelSettings` 渲染（`SettingFields`） | 没有设置项时整区不显示；必填与 enum 取值前端先校验，后端 50013 兜底                                                                                                                                              |
| 限流       | `rps`、`max_concurrency`                               | 0 或留空表示不限                                                                                                                                                                                                 |
| 高级与安全 | `trusted_internal`、`allow_credentials`                | 见下                                                                                                                                                                                                             |

**两个危险开关**（都只有 `super_admin` 能改）：

| 开关                | 旁边的说明文字                                                                                                                                                                                            | 交互                                                                              |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `trusted_internal`  | “允许 `base_url` 解析到内网地址（自建网关需要）。开启后，这个渠道的插件请求可以访问内网。此操作会记入审计日志。”                                                                                          | 从关到开：弹出确认，必须勾选“我确认这个地址是受信任的内部服务”；从开到关无需确认  |
| `allow_credentials` | 仅当所选插件版本 `auth.type === 'custom'` 才可用，否则禁用并解释：“该插件不需要接触 Key。” 开启说明：“开启后，插件代码能读取这个渠道的 Key（用于自行签名）。请确认你信任这个插件。此操作会记入审计日志。” | 同上，需勾选确认；并展示插件版本的 `sha256` 前 8 位，让确认者知道信任的是哪份代码 |

**设 Key**（抽屉内独立分区）：

- 显示“已设置 · 上次更新 <时间>”或“未设置”；输入框永远为空、`type="password"`、`autocomplete="new-password"`。
- 点“设置 / 更新 Key”→ 小对话框：一个输入框 + “保存”。**已设置时保存前确认“将覆盖现有 Key”**。成功后立即清空输入并刷新徽标，**不把输入值放进任何 state 以外的位置**。
- 未设置 Key 的渠道，在列表与抽屉里用警告标出“未设置 Key，模型无法发布”。
- 后端把渠道更新时间与 Key 状态合在同一个 `ChannelView` 里（`secret_set`），前端没有单独的“Key 更新时间”字段；文案里的“上次更新”暂时用渠道 `updated_at`，是否需要独立字段见第 11 节。

**连通性检查**（`super_admin`）：按钮在抽屉与列表行都有；结果内联显示成功或失败、说明、耗时。三种失败要能区分：`ok=false` 且 message 为“插件不支持连通性检查”（中性提示，不是错误）、409 / 50015 Key 未设置（引导去设 Key）、503 / 50021 runner 不可用。

**导入模型**（`admin` 与 `super_admin` 都可）：

```text
渠道行 [导入模型] → 对话框
  1. 参数（插件 meta.import.args 渲染；没有参数则跳过）  [拉取]
  2. 草稿列表：☐ upstream_model · kind · label（可全选）
  3. [带入编辑器] → 跳转 /admin/ai/models/new?from=import，每个选中的草稿依次创建为待保存项
```

- 明确写“导入的只是草稿，不会上架，需要在模型页确认和试跑后发布”。
- 草稿通过 `draftToModelBody` 转成模型正文，`channels[0].channel` 预填为当前渠道；**通过 `sessionStorage` 传递（键带时间戳），不放进 URL**，避免长 JSON 进地址栏。
- 一次选多个时，模型页顶部出现“待处理草稿 3 个”条，逐个编辑并保存；不做批量自动保存。

### 6.5 模型页（三区 + 追踪）

保持现有三栏骨架（列表 / 编辑器 / 结果），改动如下。

**左：模型列表**。行内显示 label（没有则 key）、`kind` 图标、状态（已发布 vN / 有未发布草稿 / 未上架）、渠道名。渠道名依赖后端在列表项里补字段（后端评审第 6 节第 2 点），**补之前前端不显示这一列，也不为它逐个请求详情**。顶部加 `kind` 与状态筛选。

**中：编辑器**。顶部有“表单 / JSON”切换，**JSON 是事实来源**，表单是对 JSON 的一层读写。

| 表单区块           | 字段                                       | 说明                                                                                                                                                                                                                                             |
| ------------------ | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 身份               | `key`（新建可填）、`kind`、`label`、`hint` | `suggestModelKey` 可给建议                                                                                                                                                                                                                       |
| **渠道与上游模型** | 渠道下拉、`upstream_model`                 | 下拉用 `channelsForKind(kind)`：**只列启用且其插件版本 `endpoints` 含该 `kind` 的渠道**；选中后在下方显示“插件 name vX · 鉴权 · Key 已设置 / 未设置”。首期 `channels` 只有一个元素，界面不出现“添加渠道”。改渠道时用 `withModelChannel` 保持键序 |
| 上架               | `credits`、`deadline`、`sort`、`enabled`   | `deadline` 用 `30m` 这种时长串，前端只校验格式                                                                                                                                                                                                   |
| 固定参数           | `params`                                   | **只提供 JSON 编辑框**，标注“由插件定义，宿主只存不解释”                                                                                                                                                                                         |
| 输入定义           | `input_schema`                             | **只提供 JSON 编辑框**（有序对象，书写顺序即画布渲染顺序）；提供“从模板插入”和“预览画布表单”按钮                                                                                                                                                 |

- 保存草稿始终成功（后端保证），返回的 `issues` 显示在问题条里，每条可点击定位到 JSON 行或表单字段（`path` 形如 `channels[0].channel`）。
- 表单与 JSON 切换时，JSON 解析失败则禁止切回表单并提示行列（`parseJsonText` 已有）。
- **发布**：走 `ConfirmDialog`（替换 `window.confirm`），对话框里列出“将发布的渠道、插件版本、积分”，并在渠道 Key 未设置时**直接禁用发布并说明原因**（后端 50015）。回滚同理，展示目标版本。
- 上下架开关：未发布过时禁用（后端要求已发布过）。

**右：结果面板**，标签页化：`问题 / dry-run / 试跑 / 追踪`。

- **dry-run**：展示“插件返回的请求描述（已校验、Key 脱敏）”。标题写“请求描述”，**不要写“最终请求”**（后端目前不含注入后的鉴权头，见后端评审文档不一致第 5 条）。
- **试跑**：沿用现有 3 秒轮询、最长 15 分钟；进度、状态、产物预览、失败原因。试跑完成后自动切到“追踪”标签。
- **追踪**（新增，见 6.6）。

### 6.6 追踪时间线

追踪是运营排错的核心，也是新协议接入时运维验证插件的核心。数据是 `TestRunTrace.steps`，已有 `utils/admin/trace.ts` 转成展示模型。

```text
┌ 追踪 · 试跑 #1821 · 共 6 步 · 4.2s ─────────────────────────────────┐
│ ① ◆ hook  buildSubmitRequest                     12ms  ▏              │
│ ② ● http  POST /v1/video/generations  200        1.8s  ▇▇▇▇▇▇▏        │
│ ③ ◆ hook  parseSubmitResponse                     3ms  ▏              │
│ ④ ● http  GET  /v1/video/generations/abc  200   210ms  ▇              │
│ ⑤ ◆ hook  parseQueryResponse                      2ms  ▏   ← 展开     │
│      输入 ▸   输出 ▸   utils.log（2） ▸                               │
│ ⑥ ✕ hook  parseQueryResponse   插件抛出异常: undefined is not …       │
└───────────────────────────────────────────────────────────────────────┘
```

- **两种步骤两种形态**：`hook`（钩子的输入、输出、`utils.log`）用菱形；`http`（方法、URL、状态、请求与响应）用圆点。**形状加文字标签，不只靠颜色区分**。
- **默认折叠**，只显示一行摘要（序号、类型、名称或 `METHOD path`、状态、耗时）；**失败的步骤默认展开并标红**，并且是列表里被自动滚动到的那一步。
- 耗时条：条形长度按“本次追踪里最长步骤”归一，只用来一眼找慢步骤。
- 展开内容用 `FoldableCode`：长响应体默认折叠，后端在 8KB 处截断时显示“已截断”徽标。
- 所有内容后端已脱敏，界面上固定一行说明“Key 与鉴权头已脱敏”，让运营放心复制分享。
- 步骤数为 0（任务还没有追踪）：显示“任务尚未产生追踪，稍后刷新”，不是错误。
- 提供“复制全部（JSON）”按钮，方便贴到工单里；**不提供下载**（追踪里可能含用户提示词）。

### 6.7 关键流程

**流程 A · 运维接入新协议（首次）**

```text
插件页 → 上传插件 ─(预检失败)→ 看字段路径，改文件重传
                  └(通过)→ “下一步：新建渠道”
渠道页 抽屉：选插件版本 → 填 base_url、插件设置 → 保存
      → 设 Key → 连通性检查 ─(失败)→ 看原因，改地址或 Key
                          └(成功)→ “下一步：去上架模型”
模型页：新建 → 选渠道 → 试跑 → 追踪 → 发布
```

**流程 B · 运维升级插件**

```text
插件页 上传新版本 → 通过 → 渠道抽屉出现“有新版本”横幅
→ 选择新版本、保存 → 到模型页对使用该渠道的模型试跑 → 确认无误
（进行中的任务按快照里的旧版本继续；旧版本在无渠道引用、无非终态任务后才可删）
```

**流程 C · 运营上架**（主路径）

```text
模型页 新建 → 选 kind → 渠道下拉（只列可用渠道）→ 上游模型
→ 编辑 input_schema（可插模板）→ 保存草稿 → 校验 → 试跑 → 看追踪
→ 发布（确认框列出渠道与插件版本）→ 上架
```

**流程 D · 运营批量起草**：渠道行 → 导入模型 → 选草稿 → 带入编辑器 → 逐个保存 → 走流程 C 的后半段。

### 7.3 静默探测角色的 403

入口需要知道“当前用户是不是管理员”，普通用户调用 `/me` 会得到 403，而全局拦截器会弹 toast。这会让每个普通用户登录后看到一条报错。处理方式（二选一，建议方案 1）：

1. **建议**：后端在通用的“当前用户”接口里带上 `role`，前端从登录态拿角色，不再单独探测 `/admin/ai/me`。
2. 备选：拦截器增加一个“此请求不弹 toast”的显式开关，供角色探测使用。这会改动全局约定（规范里明确写了“没有跳过开关”），需要单独评审。

在决定之前，画布列表页的入口先只对“已知是管理员”的会话显示（例如用户主动访问过 `/admin/ai`）。这在第 11 节列为待确认。

### 7.4 撤销与恢复

- 模型正文：草稿版本天然可回退（回滚到历史版本），编辑器内不做多级撤销，交给浏览器的输入撤销。
- 渠道抽屉：关闭时若有未保存修改，提示放弃；不做草稿持久化。
- **不可撤销**的动作：删除插件版本、覆盖 Key、发布、回滚，全部走确认框，文案写清后果。

- 建议在 `api/admin/ai` 里提供一个**环境变量开关的 mock 适配层**（`VITE_ADMIN_AI_MOCK=1`），按契约返回插件、渠道、追踪的固定数据，覆盖“预检失败、预检通过、Key 未设置、runner 不可用、追踪含失败步骤”五类场景。这样后端补齐前，前端可以完整走通流程 A 到 D。
- 纯逻辑继续放 `utils/admin/` 并配 `tests/utils/admin/` 单元测试；**目前只有 `json.test.ts`**，`role`、`plugin`、`channel-form`、`settings-form`、`model-body`、`trace` 都没有测试，接线前先补，这些是页面行为的地基。
- 仓库没有组件测试设施（无 testing-library、jsdom），本期不引入；页面行为用第 10 节的手动验收清单加 Playwright 冒烟。

## 9. 方案取舍

### 9.1 决策矩阵

权重按“运营的主任务最重要、运维操作要安全”设定（没有用户访谈，采用默认权重，见第 11 节）。5 分制。

| 维度（权重）            | A. 三个子路由 + 抽屉（推荐）    | B. 保持单页多标签             | C. 每个对象独立详情页 |
| ----------------------- | ------------------------------- | ----------------------------- | --------------------- |
| 运营主任务效率（30%）   | 5：模型页一屏完成               | 4：同 A，但状态全在一个组件里 | 3：来回跳转           |
| 危险操作安全（25%）     | 5：只读与写入分区清晰           | 4                             | 4                     |
| 可发现性与深链接（15%） | 5：每个对象有 URL               | 2：无法直达某个渠道           | 5                     |
| 实现成本（15%）         | 3：要拆分 `index.tsx`、加路由   | 4：改动最小                   | 2：页面最多           |
| 可扩展性（15%）         | 5：以后加审计页、渠道监控页顺手 | 2：单文件继续膨胀             | 4                     |
| **加权**                | **4.6**                         | **3.3**                       | **3.5**               |

### 9.2 明确放弃的东西

| 放弃                                       | 原因                                                                                     |
| ------------------------------------------ | ---------------------------------------------------------------------------------------- |
| 内置代码编辑器（Monaco 等）                | 大依赖，收益不确定；`textarea` 已有格式化与行列报错                                      |
| 为 `params` 和 `input_schema` 造可视化表单 | 它们的形状由插件定义，宿主不解释，做表单等于重新引入映射层，与“项目里没有映射”的原则冲突 |
| 多渠道选择与故障切换 UI                    | 后端首期只允许一个渠道，数据结构预留即可                                                 |
| 在线编写与调试插件代码                     | 插件在本地写好再上传；页面只做上传、预检、追踪                                           |
| 审计日志页                                 | 后端没有读取接口；写入点也还没有（后端评审 P0-2）。放到后续                              |
| 插件市场、评分、签名校验                   | 设计的后续项                                                                             |
| 渠道 Key 的“查看 / 复制”                   | 与“只写不读”的安全边界冲突                                                               |
| 全局“运行器状态”常驻横幅                   | 容易被误读为全站故障；只在受影响的动作旁提示                                             |

## 10. MVP 与后续

### 阶段 0：地基（前端独立可做）

内容：删除 `secrets-panel.tsx` 与相关 API；新增 `useAdminStore` 与 `getAdminMe` 接线；`AdminAiLayout` 与三个子路由骨架；补 `utils/admin/*` 的单元测试；用 CLI 添加 shadcn 组件；mock 适配层；`index.tsx` 拆成 `models/`。

验收：

1. `/admin/ai` 重定向到 `/admin/ai/models`，三个标签可切换，刷新保持。
2. 普通用户访问得到 `ForbiddenView`，页面无报错弹窗风暴。
3. `utils/admin` 下 7 个模块都有测试，类型检查通过。
4. 仓库里不再有对 `/admin/ai/secrets` 的调用。

### 阶段 1：插件页与渠道页

内容：6.3、6.4 的全部；角色控制的显示与隐藏；预检内联反馈；两个危险开关的说明与确认；Key 只写；连通性检查；导入对话框。

验收（对应后端设计的阶段 1 验收 #1、#8、#9、#12、#13）：

1. `super_admin` 在页面上传一个合法插件，看到版本、`sha256`、能力清单；上传一个缺少异步 query 钩子的插件，看到 `meta.endpoints.video.mode` 一类的具体字段。
2. 上传重复版本号，在对话框内看到 `meta.version` 问题，不是弹窗报错。
3. `admin` 登录：插件页与渠道页只读，看不到上传、设 Key、两个危险开关；手动调用写接口得到 403 不是靠前端隐藏保证的。
4. 新建渠道：Key 输入框永远为空；设置成功后只显示“已设置”；Key 不出现在任何请求 URL、`localStorage`、store、控制台。
5. 所选插件不是 `auth: custom` 时，`allow_credentials` 开关禁用并说明原因。
6. 检查连通性能区分成功、插件不支持、Key 未设置、runner 不可用四种结果。
7. 导入模型：选中若干草稿，带入模型页后不会自动上架。

### 阶段 2：模型页改造与追踪

内容：6.5、6.6 的全部；渠道与上游模型表单；表单与 JSON 双向；发布确认框；试跑后追踪标签。

验收：

1. 模型的渠道下拉只列出启用且插件版本支持该 `kind` 的渠道。
2. 渠道 Key 未设置时，发布按钮禁用并写明原因。
3. 试跑一个会失败的插件（钩子抛异常）：追踪里失败步骤默认展开、标红，且是被自动滚动到的那一步。
4. 追踪里能看到 `utils.log` 输出；响应体被截断时有“已截断”标记；界面显示“已脱敏”说明。
5. 表单与 JSON 来回切换，键顺序不变（`input_schema` 的书写顺序保持）。
6. `window.confirm` 全部替换为确认对话框。

### 阶段 3：打磨

审计日志页（依赖后端读取接口）、键盘与无障碍走查、暗色模式走查、模型列表筛选与搜索、任务详情复用追踪时间线、评估代码编辑器。

- 假设后端会按 `admin-ai-api.md` 补齐管理层，形状不大变；若接口形状改变，前端类型需要跟改。
