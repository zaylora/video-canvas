# 并发控制与沙箱池

本文说明协议插件体系里的三处并发控制各管什么、何时起作用、生命周期如何，业界同类项目怎么做，以及高并发时该怎么调。

> **数据说明**：文中的吞吐数字是按代码参数和假设耗时推算的量级，**没有压测**。上线前请按“八、如何得到真实数字”实测。

## 一、三处并发控制

一次生成任务经过的位置：

```
worker 领取任务 ─→ [① worker 执行池] ─→ 调用插件钩子 ─→ [② 沙箱池] ─→ 钩子返回请求描述
                                   └→ 宿主向上游发 HTTP ─→ [③ 渠道限流] ─→ 上游平台
```

| | ① worker 执行池 | ② 沙箱池（goja Runtime 池） | ③ 渠道限流 |
|---|---|---|---|
| 管的对象 | 任务处理步骤（提交、查询一次、转存） | JS 钩子的执行 | 向上游发的 HTTP 请求 |
| 单次占用 | 一个步骤：毫秒到几十秒，转存最久 | 一次钩子：毫秒 | 一次请求 |
| 所在进程 | 主服务 | plugin-runner | 主服务 |
| 粒度 | 全局共享 | 每个插件版本 | 每个渠道 |
| 实体 | 在途计数器 | 真实 Runtime 对象池 | 令牌桶 + 并发信号量 |
| 默认值 | 8 | 8 | 不限 |
| 配置项 | `ai.worker.concurrency` | `pool_size` | 渠道的 `rate_limit_json`，如 `{"rps":5,"max_concurrency":20}` |
| 代码 | `internal/provider/worker/worker.go` 的 `claimAndRun` | `internal/provider/pluginrunner/server.go` 的 `acquire` / `release` | `internal/provider/plugin/limiter.go`、`executor.go` 的 `limit` |

### 1. worker 执行池

- 每个调度周期（1 秒），领取 `min(并发数 - 在途数, 批量上限 50)` 个到期任务，每个任务起一个协程处理，处理完在途数减一。
- **占用的是一个步骤的时间，不是任务的整个生命周期**：轮询时查询一次，把任务排到下一次轮询时间就释放槽位，上游生成的几十秒等待不占槽位。
- 转存要下载整张图，是占槽位最久的步骤。一个任务里的多张图按顺序下载。
- 只是计数器，随进程启动，随进程结束。

### 2. 沙箱池

- 只在钩子真正执行的几毫秒占用。**沙箱不处理发给上游的 HTTP 请求**：runner 进程没有网络，只通过本地 Unix socket 和主服务通信。插件只负责把任务翻译成请求描述、把响应翻译成统一结果，HTTP 由主服务发。一次提交是“调用钩子（占池）→ 归还 → 主服务发 HTTP（不占池）→ 再调用钩子解析（占池）”。
- 生命周期（按插件版本）：
  1. 装载：版本首次装载时创建池，放入第一个 Runtime。
  2. 调用：`acquire` 先占名额，再取空闲 Runtime，没有就新建。
  3. 归还：正常执行完放回空闲队列复用。
  4. 丢弃：钩子超时，Runtime 被丢弃，不归还。
  5. 销毁：随 runner 进程重启消失。
- 每个 Runtime 只能被一个协程使用、且各自加载一份插件代码占内存，所以要池化并封顶。
- 池满时**无限阻塞**等名额，没有准入超时。

### 3. 渠道限流

- 钩子执行完之后、宿主真正发请求时起作用。先取并发名额再取令牌，这样排队等名额时不会白白消耗令牌。
- 按渠道 key 缓存，参数变化后换新的限流器。不配置就不限。

## 二、上游请求很慢时会怎样

沙箱池不受影响（名额已归还）。被占用的是：

| 层 | 占用方式 | 保护它的超时 |
|---|---|---|
| ① worker 槽位 | 处理任务的协程在等响应，槽位不释放 | 单次提交/查询 `OperationTimeout`，默认 2 分钟 |
| ③ 渠道并发信号量 | 配了 `max_concurrency` 时慢请求一直占名额 | 单个请求 `timeout`，默认 30 秒，上限 120 秒 |

超时后按 `retryable` 重试，不会一直卡住。

## 三、沙箱里唯一的时间限制

钩子执行有 200ms 时限（`defaultHookTimeout`），限制的是 JS 代码本身，不含网络。超时后该 Runtime 被丢弃，任务按插件级失败处理并退积分。goja 是解释执行，逐字符循环处理几百 KB 的大响应很容易超时，应改用原生的正则或内置方法。

## 四、业界对比

调研自 GitHub 源码与文档（子任务读取，出处见各项目仓库；未读到源码的部分在原调研中标为推测）。

| 项目 | 供应商适配方式 | 运行时池 | 默认并发 |
|---|---|---|---|
| **New API**（QuantumNous/new-api） | Go 硬编码 + JS 任务插件（moejs），有沙箱 | **有**：每插件版本一个引擎，信号量 + 实例池 | 默认 8，单次超时 5 秒，池满有准入超时 `ErrCallAdmissionTimeout` |
| One API | Go 硬编码 | 无 | 全局请求速率限流 |
| LiteLLM | Python 硬编码 / `CustomLLM` 子类，同进程 | 无 | 部署级 `max_parallel_requests`，满了返回 429，不排队 |
| Portkey gateway | TS 硬编码，Guardrail 插件编译进网关 | 无 | 开源版未见限流 |
| Kong AI | Lua 驱动硬编码；可扩展 Lua/Wasm/外部进程 | 无（每 nginx worker 一个 VM） | 由 nginx worker 数决定 |
| Higress | Go 编译为 Wasm | 每个 Envoy worker 线程一个 VM | 由 worker 数决定 |
| Tyk（goja） | JS 中间件 | 无池，每次新建 runtime | 网关请求层 |
| KrakenD（gopher-lua） | Lua | 无池，每请求新建 | HTTP server |
| k6（goja 分支） | JS | 每个虚拟用户一个 runtime | VU 数 |
| Redpanda Connect（goja） | JS 处理器 | `sync.Pool` 按需扩张，无上限 | 管道并发 |

要点：

- “业务层 JS 插件 + 固定大小池”只有 New API 是这个形态，且默认值与本项目同为 8，本项目的设计不算异常。
- 池大小通常不是常数，而是跟 worker 数（Envoy）、并发单元数（k6）走，或按需扩张。并发上限一般设在入口/worker/基础设施层，不在脚本池里。
- 可借鉴：池满设准入超时；goja Runtime 被 `Interrupt` 后归还前需 `ClearInterrupt()`（本项目超时后直接丢弃，更稳妥）。
- New API 的异步任务并发：按渠道分协程轮询，渠道内串行，每轮最多取 1000 个任务。

## 五、高并发怎么调

瓶颈排序：① worker 槽位（转存占用最久）> ③ 上游限速 > ② 沙箱池（几乎不会先满）。

| 配置 | 默认 | 建议起点 | 说明 |
|---|---|---|---|
| `ai.worker.concurrency` | 8 | 32 | 最先调这个 |
| `pool_size` | 8 | 32 | 不小于 worker 并发，否则钩子排队 |
| 渠道 `rate_limit_json` | 不限 | 按上游能力设 | 先设 rps 和并发上限，再逐步放大，观察是否出现 429 |

调大时一起检查：

1. **内存**：每个 Runtime 占一份内存，`pool_size` 翻几倍，runner 内存接近翻几倍，注意 runner 容器 `mem_limit`。
2. **数据库**：每个在途步骤都读写库，`database.max_open_conns` 当前为 100，并发不要比它高太多，还要给接口请求留余量。
3. **下载带宽**：并发转存的总流量受服务器带宽限制。
4. **上游**：最终瓶颈通常是上游平台的限速。

## 六、不上消息队列时的并发范围

| 因素 | 现值 |
|---|---|
| 调度周期 | 1 秒 |
| 每批领取上限 | 50 |
| 数据库连接池 | 最大 100 |
| 槽位本身 | 协程，无硬上限 |

- 单实例：worker 并发 **32 到 64** 比较稳，上限大约在 100 出头，再往上会撞数据库连接池和带宽。
- 多实例：任务领取带租约，多个实例可以一起领，吞吐大致按实例数线性增加。**`ClaimDue` 是否用 `FOR UPDATE SKIP LOCKED` 防止重复领取，尚未核实，多实例前必须确认。**
- 几十到上百并发下，数据库领取 + 租约够用；需要单实例几百以上并发，或对丢失/顺序/削峰有严格要求时，再考虑消息队列。

## 七、吞吐估算（concurrency = 32，pool_size = 32）

主服务的提交接口只是把任务写库，不受 worker 限制。这里估算的是后台每秒能处理完多少任务。

假设：提交约 1 秒；出图约 40 秒，轮询约 3 次、每次约 0.3 秒；转存每张图约 3 秒。

| 步骤 | 1 张图 | 4 张图 |
|---|---|---|
| 提交 | 1 秒 | 1 秒 |
| 轮询 3 次 | 约 1 秒 | 约 1 秒 |
| 转存（按顺序） | 3 秒 | 12 秒 |
| 合计占槽位 | 约 5 秒 | 约 14 秒 |

出图的 40 秒等待不占槽位，不计入。吞吐 = 32 ÷ 占用秒数：

| 场景 | 每秒完成任务 | 每分钟 | 每秒出图张数 |
|---|---|---|---|
| 每任务 1 张 | 约 6 | 约 380 | 约 6 |
| 每任务 4 张 | 约 2.3 | 约 140 | 约 9 |

沙箱池 32 不是瓶颈：每个任务约 6 次钩子调用、每次几毫秒，32 个 Runtime 每秒能处理的调用数比上面的任务吞吐高两个数量级。

数字会变的情况：转存平均 10 秒则吞吐降到约三分之一；上游只允许每秒几个提交则上游先到顶；每秒最多领 50 个，在这个规模下不是瓶颈。

## 八、如何得到真实数字

并发提交一批任务（例如 50 张），从日志里取“上游生成成功，开始转存”到转存完成的时间间隔，平均值代入七中的公式。同时观察数据库连接数和上游是否返回 429。

## 九、遗留问题

- 沙箱池满时无限阻塞，建议参考 New API 加准入超时。
- 钩子 200ms 时限偏紧（New API 为 5 秒）；设计文档已把它列为待压测的提案值。
- 池大小、钩子时限等沙箱预算数值均为设计提案，尚未压测（见《协议插件设计》待定事项）。
