01要解决的问题

New API 只是其中一种协议，以后还要接别的平台

老路 · DSL

声明式协议配置

每遇到同步、二进制、签名这类新情况，就要给 DSL 加语法，越来越像一门编程语言。

上一版 · Go 代码

只认 New API

协议写成 Go 代码，最简单；但每新增一种协议都要写代码、发版。

本版 · 插件

仿 New API 任务插件

新增协议 = 上传一个 JS 文件、建一个渠道。不发版、不重启，也不改 DSL。

最值得学的不是 JS，而是边界：插件只描述请求、解析响应，宿主负责执行。
02核心边界

插件描述，宿主执行

插件（JS）

只做翻译，没有副作用
build*任务 → 请求描述
parse*响应 → 统一结果
classifyError可选：错误分类
state可选：私有状态，宿主代存
不能联网、读文件、定时器、拿 Key（默认）

宿主（Go，大多是现有代码）

所有副作用都在这里
发 HTTPSSRF 传输层（已有）
注入鉴权Bearer / 头 / 查询参数
文件引用素材归属校验、签名 URL
限流、超时按渠道（已有组件）
轮询、积分、转存worker（不变）
脱敏、追踪试跑面板（已有）
好处：插件碰不到网络和密钥，SSRF 防护与脱敏只在宿主做一次，每个插件都自动继承。

04已确认决策

七个分叉，每个都写明放弃了什么

分叉决定放弃了什么
插件形式JS 热插件Go 接口预留 JS：更快、不用沙箱，但加协议要发版
契约自定，形状借鉴 New API兼容 v1：能装官方插件，但要跟随对方演进
渠道凭证存 DB，Key 加密只写环境变量：每加渠道都要重启
模型与渠道先单渠道，结构预留多渠道故障切换：参数差异、快照记录复杂
安装权限新增 super_adminadmin 都能装：运营账号被盗即可执行脚本
首个插件newapi.js 随仓库内置Go 驱动并存：两条执行路径
JS 引擎gojamoejs：写法与 New API 一致，但项目过早期
另已确认：生产开放在线上传 · 插件不做代码评审 · auth: custom 进第一版 · 插件跑在独立 plugin-runner 进程
05插件文件

一个 CommonJS 文件：meta + 钩子

module.exports = {
  meta: {
    apiVersion: 1,
    key: "newapi", version: "1.0.0",
    auth: { type: "bearer" },  // bearer/header/query/custom
    allowedHosts: [],          // 结果下载域名
    endpoints: {
      text:  { mode: "sync" },
      video: { mode: "async" }
    },
    channelSettings: { region: { type: "enum", ... } }
  },
  buildPrepareRequests(ctx) { ... },  // 可选：先上传
  buildSubmitRequest(ctx) { ... },
  parseSubmitResponse(ctx, resp) { ... },
  buildQueryRequest(ctx) { ... },   // async 必需
  parseQueryResponse(ctx, resp) { ... },
  buildCancelRequest(ctx) { ... },  // 可选
  classifyError(ctx, resp) { ... },  // 可选
  buildImportRequest(ctx, args) { ... } // 可选：导入
};
为什么是 CommonJS

goja 不支持 ES 模块，宿主包一层函数加载 module.exports。

上传即预检，不通过就拒绝
  • 能编译并执行到导出
  • apiVersion 受支持
  • 版本号未被占用
  • async endpoint 有 query 钩子
  • 文件 ≤ 512KB（提案）

契约为它补的三项（阶段 2）
  • 准备阶段：buildPrepareRequests 先上传，结果存进 provider_state，重试不重复上传

07内置插件 · RunningHub 工作流 · 阶段 2

上架新工作流 = 导入 + 删字段 + 试跑，不写代码

填 webappId→导入钩子调 apiCallDemo→生成 bindings + input_schema 草稿→删掉不暴露的字段→试跑→发布 
// 模型配置：upstream_model 就是 webappId
"upstream_model": "2093984571330498561",
"params": {
  "instanceType": "default",
  "bindings": {             // 输入字段 → 工作流节点
    "prompt":   { "nodeId": "6",  "fieldName": "text" },
    "image":    { "nodeId": "12", "fieldName": "image" },
    "duration": { "nodeId": "30", "fieldName": "length" }
  },
  "outputs": { "types": ["mp4", "webm", "mov"] }
}
// 节点号是示意，实际值由导入得到
绑定是数据，不是表达式

params 的结构由插件定义，宿主只存不解释；没绑定的节点保留工作流原值，不发送。

类型推断

LoadImage → image，LoadVideo → video，text / prompt → text，数字默认值 → number。

放弃了换算

秒数换帧数这类换算写进选项：value 是帧数，label 写“5 秒”。

09沙箱

插件跑在独立进程：超时硬中断，内存由容器兜底

项做法
进程钩子都在 plugin-runner 进程执行；它不连数据库、不解密凭证、不发 HTTP
运行时runner 内每个插件版本一个 goja Runtime 池（提案 8 个）；Runtime 单协程使用
隔离ctx 与返回值都用 JSON 进出，不暴露 Go 对象；删除 eval、Function，冻结内置对象
时间单次钩子限时（提案 200ms），到时 vm.Interrupt()；被中断的 Runtime 丢弃，不再归还
大小ctx 与返回值各 ≤1MB，state ≤64KB，插件文件 ≤512KB
能力没有网络、文件、定时器、require；只有 utils；生产容器 network_mode: none
goja 没有内存限制，所以靠进程隔离：生产 runner 容器设 mem_limit，超限被杀后自动重启，主服务不受影响；该任务重试一次，崩溃计入渠道连续失败。
10鉴权与密钥

密钥默认不进插件，签名类是受控例外

bearer · header · query

宿主注入，插件看不到

插件返回请求描述（不含 Key）
宿主检查：插件自己写了 Authorization 就拒绝
宿主解密渠道 Key，按 auth.type 注入后发送
custom

需要签名时，插件拿到 Key

例如可灵的 AK/SK 签 JWT：插件读 ctx.credentials，调用 utils.jwtSignHS256。

runner 没有网络，请求只能去 base_url 或 allowedHosts，拿到 Key 也发不出去。

第一版就支持；渠道要由 super_admin 开启 allow_credentials，写审计日志。

11插件生命周期

版本不可变，升级是“换指向”

上传 plugin.js→预检→存为版本（sha256）→渠道选用该版本→is_test 试跑→发布模型
升级

上传新版本 → 渠道改指向。新任务用新版本，进行中任务按快照里的旧版本跑完。

停用

用它的渠道不再接新任务，进行中任务继续。

删除

只能删没有渠道、也没有非终态任务引用的版本。

内置

backend/plugins/newapi.js 启动时自动登记，不能删除或覆盖。

多实例：插件代码存在 DB，各实例按版本哈希懒加载；渠道与模型变更沿用发布后刷新，多实例走 Redis 广播。

14状态与异常

插件的错误是确定性的：不重试，直接失败并告警

场景处理
插件抛异常 / 超时被中断terminal，退积分，告警；超时丢弃该 Runtime
请求描述指向非法主机、写鉴权头、超大小terminal，退积分，告警
结果结构不合规terminal，退积分，告警
上游 429 / 5xx / 网络错误插件 classifyError 优先，否则宿主默认规则（额度不足排在 429 前）
同一渠道连续插件级失败（提案 10 次）自动停用渠道，告警运维
插件或渠道停用时有进行中任务按快照跑完；新任务不能再选用
上传的版本号已存在拒绝，版本不可变
15MVP 与验收

先把运行时和 New API 插件跑通，再补宿主能力

阶段 1 · runner + newapi.js（视频 + 文本）
  • 上传模拟协议插件到画布可用，不发版、不重启
  • 视频、文本经 newapi.js 端到端跑通
  • 升级插件后，旧任务按旧版本跑完
  • 死循环被中断，进程不受影响
  • 非法主机、伪造鉴权头、内网地址全部被拒
  • bearer 插件拿不到 Key；Key 不进追踪与日志
  • admin 调插件与凭证接口返回 403
  • 插件耗尽内存：runner 重启，主服务全程可用
  • auth: custom 测试插件能签名
  • 从渠道导入模型：列出 New API 的模型并预填草稿
阶段 2 · 宿主能力补全 + RunningHub
  • responseType: binary：语音直接落素材
  • 同步图片持久化后转存，崩溃重启不重复调用
  • 准备阶段、multipart、请求级鉴权、base64 文件引用
  • runninghub.js：导入两个结构不同的工作流，同一个插件都能真实出片
  • 写一个直连可灵（签名鉴权）的插件，宿主不改代码就能真实出片

后续：多渠道故障切换、Redis 广播、插件签名校验。
