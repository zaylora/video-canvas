01设计摘要 · 结论

六个核心决定

01 · 事实来源

任务状态落库，连接只负责通知

通用 generation_tasks 表是唯一事实来源。任何通道断了都不影响正确性，重新对账就能恢复。

02 · 后端 ↔ 平台

后台 worker 退避轮询

提交拿到 provider_task_id 后轮询。webhook 只触发“立即轮询”，不信任回调内容。

03 · 浏览器 ↔ 后端

202 + WebSocket + 批量对账

POST 立即返回 202 + task；状态走用户级 WS 推送；打开画布或重连时 GET ?ids= 兜底。

04 · 回填

结果由前端写回节点

后端不改 payload_json，不会与现有 revision 乐观锁冲突。

05 · 转存

成功前必须转存

平台视频 URL 一般 24 小时过期。转存到自有存储，节点只引用 assetId。

06 · 计费

冻结 → 结算 / 退回

提交冻结，成功结算，失败 / 取消 / 超时退回。每用户并发上限，支持软取消。

02项目现状 · 约束与缺口

四条硬约束决定了方案的形状

鉴权

浏览器 WebSocket 不能自定义请求头

现有 JWT 请求头鉴权不能直接复用 → 用一次性 ticket 换连接。

超时

60s WriteTimeout 会切断长连接

WS 升级后必须清掉连接 deadline，并用测试锁定这个行为。

并发写

后端写 payload_json 会递增 revision

正在编辑的前端下次自动保存就会 409 → 后端不写画布，结果由前端回填。

降级

Redis 关闭时也要能跑

单实例用内存实现 ticket 存储和推送广播。

当前缺口 —— 以下能力都还没有
任务表平台适配器worker模型清单接口素材存储 /assets积分余额WS 推送

05设计原则

推送可以丢、可以重、可以乱序

01

DB 是唯一事实来源

客户端任何时候都能通过查询恢复一致。

02

推送 = 完整快照 + 版本号

客户端按 version 取最新的，天然幂等，不依赖消息顺序。

03

谁拥有数据谁写

任务结果归任务表，画布结构归前端。后端不跨界改 payload_json。

04

钱和状态在同一个事务里变

冻结、结算、退款与状态迁移同事务；流水表唯一约束保证幂等。

05

平台差异封在适配器里

上层只认统一的状态机和统一的错误分类。

06

单实例落地，多实例接口

worker 用 FOR UPDATE SKIP LOCKED 抢任务，推送走 Broadcaster 接口，加机器不改协议。

07数据与工程影响 · Worker 调度

PostgreSQL 就是任务队列

-- 每秒一次
SELECT … FROM generation_tasks
WHERE status IN ('pending','queued','running','finalizing')
  AND next_poll_at <= now()
ORDER BY next_poll_at LIMIT 50
FOR UPDATE SKIP LOCKED
-- 选中后 lease_until = now()+60s，交给固定大小执行池

新任务创建后通过进程内 channel kick，不等下一个 tick 就立即提交。

轮询节奏（视频）

服务重启

状态全在 DB，重启后调度循环自然接着处理；租约过期的任务会被重新领取。

超时

超过 deadline_at 置 expired 并退积分，先尽力调一次平台 Cancel。

提交幂等风险

平台一般无幂等键。只在连接失败 / 429 / 5xx 重试；读超时直接 failed(submit_unknown) 并退积分 + 告警。

Webhook

校验路径密钥 → 按 provider_task_id 找任务 → next_poll_at = now() → 200。结果仍以 Query 为准。

07数据与工程影响 · WebSocket 协议

用一次性 ticket 建连，不把 JWT 放进 URL

01 · 换票

POST /ws/ticket（带 JWT）→ 一次性 ticket，有效 30s。Redis 开启存 Redis，关闭存内存。

02 · 连接

new WebSocket("wss://…/api/v1/ws?ticket=…")

03 · 绑定

服务端校验并删除 ticket，绑定 user_id，自动订阅 user:{id}，下发 hello。

服务端要点

▸ gorilla/websocket：Upgrade 会清掉 deadline，60s WriteTimeout 不再切连接（需测试锁定）
▸ CheckOrigin 校验白名单，与 CORS 一致，防跨站 WS 劫持
▸ 每连接一个写 goroutine + 有界发送队列，满了断开慢连接，客户端重连后对账
▸ 每 25s ping，60s 没收到 pong 就断开
▸ 同一用户多连接（多标签页）：user_id → set(conn)
▸ 事务提交之后再发布，避免客户端收到推送去查询却读到旧数据

消息格式

// 服务端 → 客户端
{ "type": "task.updated", "channel": "user:12",
  "data": { /* 完整任务快照，含 version */ } }
{ "type": "hello", "data": { "server_time": "…" } }

// 客户端 → 服务端（MVP 只需要 ping）
{ "type": "subscribe", "channel": "canvas:34" }
// ↑ 为协作预留：校验画布访问权限后才允许订阅
07数据与工程影响 · 前端改动

前端拥有画布，所以由前端回填

节点数据

新增 taskId?: string。持久化 DTO 的 status 增加 running，否则刷新后生成中状态会丢。

任务 store（zustand）

tasks: Record<taskId, Task>，由 WS 与对账接口写入，按 version 只保留更新的快照。

回填

终态且节点 taskId 一致时 updateNodeData(id, {status, src, assetId, error})，走现有自动保存；assetId 已相同就跳过。

对账时机

打开画布 → 收集 running 节点 GET ?ids=；WS 重连 → GET ?status=active；切回前台再对一次。

全局连接

登录后在应用根部建一条 WS，列表页也保持连接以弹 toast。重连指数退避 1s → 30s。

模型清单 · 多标签页

MODEL_LIBRARY 改读 /models；视频暂不支持自定义模型。两个标签页同时回填，一个会 409 走重载，结果一致可接受。

08方案取舍 · 为什么不引入 MQ / Kafka

MVP 用 PG 表 + SKIP LOCKED 当队列

量级不需要

1000 活跃用户 × 每人并发 4，也只是几千行、每秒几十次查询。

状态本来就要落库

再加 MQ 就有两份状态；扣积分与发消息要原子还得做 outbox。

核心需求是“定时再查”

Kafka 无延迟消息，RabbitMQ 要插件或死信绕行；一个 next_poll_at 索引即可。

运维成本

现在只有 PG + Redis，加 Kafka 就要再维护一套集群。

什么时候再引入

信号引入什么
多实例部署，WS 连接分布在不同机器Redis Pub/Sub 或 Streams，只广播 task.updated（第一步是它，不是 Kafka）
API 与 worker 拆成独立服务，或 worker 按平台隔离扩容Redis Streams / RabbitMQ 做提交队列，状态仍以 DB 为准
同一事件有多个独立消费方（计费、通知、分析、审计），或提交量上千 / 秒Kafka + outbox：状态迁移事务写 outbox，再投递到 Kafka

Broadcaster 接口与 DB 队列的租约设计已给这些替换留好位置，业务代码不用改。

九条可测的验收标准

01 · 性能

提交接口 p95 < 300ms，不依赖平台响应速度

02 · 关页面

生成中关闭页面，重开画布能看到最终结果并可播放

03 · 重启

生成中重启后端，任务继续完成，积分不重扣不漏扣

04 · 断网

断网 30s 再恢复，5s 内节点状态与服务端一致

05 · 幂等

同一 Idempotency-Key 重复提交，只建一个任务、只冻结一次

06 · 退款

失败 / 取消 / 超时全部退回；credit_ledger 与 user_credits 对账零差异

07 · 长连接

WS 连接保持 > 10 分钟不断（验证绕开 60s WriteTimeout）

08 · 转存

平台 URL 过期（> 24h）后，画布里的视频仍能播放

09 · 并发

超过并发上限返回 429，前端就地提示

通过配置切换；本地磁盘仅用于开发环境。assets 的 URL 策略（公开还是签名）由各存储实现决定。

已确认
03

并发上限 N=4，超时 deadline 30 分钟

即 max_active_tasks_per_user: 4，deadline_at 默认 30 分钟。

已确认

产物进入生成记录，积分照常结算，不自动取消。撤销删除会把节点和 taskId 一起恢复。

已确认

充值本期不做；每个用户初始余额先固定为 50 积分。
