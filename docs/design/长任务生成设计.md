# 长任务生成设计（视频优先）

> 状态：设计稿 · 2026-09-29 · 范围：画布节点选择模型 → 后端调用生成平台 → 结果回填画布

## 1. 设计摘要

**问题**：视频生成一次要 1–5 分钟，有时更久，不可能让一个 HTTP 请求一直挂着等结果。用户还会关页面、切画布、断网、刷新，服务端也会重启。

**结论**：

1. **任务状态落库，连接只负责通知**。新增通用的 `generation_tasks` 表，它是任务状态唯一的事实来源。任何通道断了都不影响正确性，重新对账就能恢复。
2. **后端 ↔ 平台**：提交后拿到 `provider_task_id`，由后台 worker 按退避节奏**轮询**。平台支持 webhook 时可以额外注册 `callback_url` 加速，但 webhook 只用来触发“立即轮询”，不直接信任回调内容。
3. **浏览器 ↔ 后端**：`POST` 提交后立即返回 `202 + task`，状态变化通过**用户级 WebSocket** 推送。打开画布或断线重连时，用 `GET /generation-tasks?ids=` **批量对账**兜底。
4. **结果由前端回填节点**。后端不改 `payload_json`，所以不会跟现有 `revision` 乐观锁冲突。
5. 平台返回的视频 URL 一般 24 小时过期，**成功前必须转存到自有存储**，节点只引用 `assetId`。
6. 积分在提交时冻结，成功时结算，失败、取消、超时时退回。每个用户有并发上限，并支持软取消。

### 设计约束

- 浏览器原生 `WebSocket` **不能自定义请求头**，现有 JWT 请求头鉴权不能直接复用。
- 60 秒 `WriteTimeout` 会切断长连接，WS 升级后必须清掉连接 deadline。
- 后端写 `payload_json` 会递增 `revision`，正在编辑的前端下次自动保存就会 409。
- 需要在 Redis 关闭时降级运行（单实例用内存实现）。

### 当前缺口

任务表、平台适配器、worker、模型清单接口、素材存储（`/assets`）、积分余额、WS 推送，都还没有。

## 3. 用户与场景

- **用户**：在画布上搭分镜流程的创作者，会同时跑多个节点，比如一个场景并发生成 2–4 个视频候选。
- **主任务**：视频节点里写 prompt 或连上参考图 → 选模型 → 生成 → 等待期间继续编辑其他节点 → 结果出现在节点上。
- **关键场景**：
  - 生成中关掉页面，第二天打开，结果还在。
  - 生成中切到别的画布或列表页，也能收到“视频已完成”的提示。
  - 断网或服务重启后，任务不丢、积分不错。

## 4. 调研

### 4.1 视频平台 API 形态（访问日期 2026-09-29）

| 平台 | 提交 | 获取结果 | Webhook | 结果有效期 | 其他 |
|---|---|---|---|---|---|
| Runway | 返回 task `id` | `GET /v1/tasks/{id}`，建议间隔 ≥5s，加抖动和指数退避 | 文档未提及 | 未验证 | 有 cancel 接口；SDK 默认等待 10 分钟后超时 |
| Luma Dream Machine | 返回 generation `id` | `GET /generations/{id}`，状态 `dreaming / completed / failed` | `callback_url`，状态变化时多次 POST，失败重试 3 次，超时 5s | 未验证 | 扩展视频前要求源任务已 completed |
| 可灵 Kling | 返回 `task_id` | 查询接口，状态 `submitted / processing / succeeded / failed` | `callback_url` | **task 24 小时后变成 UNKNOWN** | 查询默认限流 20 RPS，官方建议高频场景用回调 |
| 火山方舟 Seedance | 返回 task id | 查询任务 API，状态 `queued / running / succeeded / failed / expired` | `callback_url`，成功和失败会重试 3 次 | **视频 URL 24 小时有效** | 回调体结构与查询接口一致 |
| 内部 AI 服务（yswg.love） | 返回任务 | WebSocket 推送，失败时回退 HTTP 轮询 | — | — | 与本方案的浏览器侧思路一致 |

**结论**：没有平台提供“同步长连接”。统一的形态是“提交 → 任务 id → 轮询，webhook 可选”。输出物会过期，必须转存。各平台的状态枚举不一样，需要适配层统一。

### 4.2 浏览器 ↔ 后端通道比较

| 维度 | 纯 HTTP 轮询 | SSE | **WebSocket（已选）** |
|---|---|---|---|
| 实现复杂度 | 最低 | 低（单向，走 Gin 中间件链） | 中（要引库，自己做心跳、重连、订阅协议） |
| 完成感知延迟 | +轮询间隔（3–5s） | 实时 | 实时 |
| 离开画布也能收到通知 | 需要全局轮询 | 可以 | 可以 |
| 鉴权 | 复用请求头 | 原生 EventSource 不能带请求头，要改用 fetch 流 | 不能带请求头，要用 ticket |
| 双向能力（协作、订阅） | 无 | 无 | **有** |
| 60s WriteTimeout | 不受影响 | 需要单独放开 | 需要在 Upgrade 后清掉 deadline |
| 多实例 | 天然支持 | 需要 pub/sub | 需要 pub/sub |

**决策**：选 WebSocket（用户确认）。纯任务推送用 SSE 就够了，选 WS 是为了给未来的画布协作（`canvas:{id}` 频道）预留双向通道，代价是多一层连接管理。不管选哪种，**正确性都由 DB 加对账保证**，通道只影响实时性。

## 5. 设计原则

1. **DB 是唯一事实来源**：推送可以丢、可以重复、可以乱序，客户端任何时候都能通过查询恢复一致。
2. **推送消息携带完整快照 + 版本号**：客户端按 `version` 取最新的，天然幂等，不依赖消息顺序。
3. **谁拥有数据谁写**：任务结果归任务表，画布结构归前端。后端不跨界改 `payload_json`。
4. **钱和状态在同一个事务里变**：积分冻结、结算、退款跟任务状态迁移放在同一个 DB 事务里，流水表加唯一约束保证幂等。
5. **平台差异封在适配器里**：上层只认统一的状态机和统一的错误分类。
6. **单实例落地，多实例接口**：worker 抢任务用 `FOR UPDATE SKIP LOCKED`，推送走 `Broadcaster` 接口，以后加机器不用改协议。

## 6. 推荐方案

### 6.1 整体链路

```text
 浏览器                               后端（单进程）                            视频平台
 ──────                              ──────────────                          ────────
 [视频节点] 点生成
   │ POST /generation-tasks  ─────▶  事务：校验模型/并发 → 冻结积分 → 插入 task(pending)
   │ ◀──── 202 {task}                 kick worker
   │ 节点写 taskId, status=running
   │                                 Worker ── Submit ─────────────────────▶  创建任务
   │                                   │  ◀──── provider_task_id              
   │                                   │  status=queued, next_poll_at=+10s
   │  ◀═══ WS task.updated ════════   Hub.Publish(user:{id})
   │                                   │ 循环：到点 Query ─────────────────▶  查询
   │  ◀═══ WS task.updated(running,…)  │  ◀──── running / succeeded
   │                                   │ succeeded → 下载转存 → assets 行
   │                                   │ 事务：status=succeeded + 结算积分
   │  ◀═══ WS task.updated(succeeded)  │
   │ updateNodeData(src, assetId) → 自动保存 payload_json（正常 revision 流程）
   │
 （断线 / 重开画布）GET /generation-tasks?ids=… → 对账补齐
                                     POST /webhooks/:provider ◀────────────  callback（可选）
                                       └─ 只把 next_poll_at 设为 now，不信任回调内容
```

### 6.2 任务状态机

```text
pending ──submit ok──▶ queued ──▶ running ──平台成功──▶ finalizing ──转存成功──▶ succeeded
   │                     │           │                    │
   │ submit 终态错误      │           │ 平台失败            │ 转存重试耗尽
   ▼                     ▼           ▼                    ▼
 failed ◀────────────────┴───────────┴────────────────────┘
 canceled（用户取消，任何非终态都可以进入）
 expired（超过 deadline_at 仍未完成）
```

- 终态：`succeeded / failed / canceled / expired`。进入非成功终态时一律退回积分。
- `finalizing` 表示平台已经出片，正在转存。前端显示“即将完成”。
- 平台状态映射由适配器负责，例如火山方舟的 `queued` 映射成 `queued`，可灵的 `processing` 映射成 `running`，Luma 的 `dreaming` 映射成 `running`。

### 6.3 关键交互（节点侧）

| 状态 | 节点表现 | 可用操作 |
|---|---|---|
| 提交中 | 生成按钮 loading（通常 < 300ms） | — |
| 排队中 `queued` | 骨架屏 + “排队中” | 取消 |
| 生成中 `running` | 骨架屏 + 已耗时计时；平台提供进度时显示百分比 | 取消 |
| 转存中 `finalizing` | “即将完成” | — |
| 成功 | 显示视频，可以播放 | 重新生成（新建任务） |
| 失败 | 失败原因（统一文案，比如“内容未通过审核”“平台繁忙”）+ “积分已退回” | 重试 |
| 取消 / 超时 | “已取消 / 生成超时，积分已退回” | 重试 |
| 积分不足 / 并发已满 | 提交时就地提示，不创建任务 | — |
| WS 断开 | 画布角标“连接中断，正在重连”，节点状态不变 | — |

画布外的反馈：用户在列表页或其他画布时，任务完成弹 toast“《画布名》中的视频已生成”，点击跳转到对应画布。

### 7.4 Worker 调度

- 调度循环每秒执行一次：
  ```sql
  SELECT … FROM generation_tasks
  WHERE status IN ('pending','queued','running','finalizing') AND next_poll_at <= now()
  ORDER BY next_poll_at LIMIT 50 FOR UPDATE SKIP LOCKED
  ```
  选中后写 `lease_until = now()+60s`，交给固定大小的执行池处理。
- 新任务创建后通过进程内 channel **kick** 一下，不用等下一个 tick 就能立即提交。
- 轮询节奏（视频）：提交后第一次查询在 +10s，之后间隔从 5s 起指数增长到上限 15s，再加 ±20% 抖动。每个平台一个令牌桶，避免触发可灵 20 RPS 这类限流。
- 超过 `deadline_at` 就置为 `expired` 并退积分。先调一次平台 Cancel（尽力而为）。
- **服务重启**：任务状态全在 DB 里，重启后调度循环自然接着处理；租约过期的任务会被重新领取。
- **提交幂等风险**：平台一般没有幂等键。提交请求如果读超时，结果未知，盲目重试可能重复扣平台费用。策略：只在连接失败、429、5xx 时重试；读超时直接标记 `failed`（`error_code=submit_unknown`）并退积分，同时记录告警日志供人工核对。
- **Webhook**：校验路径里的密钥后，根据 `provider_task_id` 找到任务，把 `next_poll_at` 设为 `now()`，然后返回 200。结果仍以 `Query` 为准，所以不用对每家平台的签名格式和回调内容做可信解析。

### 7.5 转存

平台返回 `succeeded` 后进入 `finalizing`：下载视频（和封面）→ 写入自有存储 → 插入 `assets` 行 → 在同一个事务里写 `output_json`、置 `succeeded`、结算积分。转存失败按退避重试，必须在平台 URL 的 24 小时有效期内完成，重试耗尽就置 `failed` 并退款。

### 7.6 积分事务

- **提交**：同一个事务里 `SELECT … FROM user_credits WHERE user_id=? FOR UPDATE` → 校验 `balance - frozen >= credits` → 统计进行中任务数不超过上限 → `frozen += credits` → 写 `freeze` 流水 → 插入任务。
- **成功**：`balance -= credits, frozen -= credits`，写 `settle` 流水。
- **非成功终态**：`frozen -= credits`，写 `refund` 流水。
- `UNIQUE(task_id, type)` 保证 worker 重复执行也不会重复扣款或退款。状态迁移用 `UPDATE … WHERE id=? AND status=?` 做 CAS，防止并发迁移。

### 7.7 WebSocket 协议

**建连**：`POST /ws/ticket`（带 JWT）→ 服务端生成一次性 ticket，有效期 30s。Redis 开启时存 Redis，关闭时存进程内存 → `new WebSocket("wss://…/api/v1/ws?ticket=…")` → 服务端校验并删除 ticket，绑定 user_id。不把长期 JWT 放进 URL，避免被写进访问日志。

**服务端实现要点**：

- 库：`gorilla/websocket`。它的 `Upgrade` 会清掉 `http.Server` 设置的 deadline，60s `WriteTimeout` 不会切断连接。需要加一个“连接保持 > 60s”的测试来锁定这个行为。
- `CheckOrigin` 必须校验白名单，和 CORS 配置一致，防止跨站 WebSocket 劫持。
- 每个连接一个写 goroutine 加有界发送队列，队列满时断开慢连接，由客户端重连后对账。
- 服务端每 25s 发一次 ping，60s 没收到 pong 就断开。
- 同一用户允许多个连接（多标签页），Hub 维护 `user_id → set(conn)`。

**消息格式**（JSON）：

```jsonc
// 服务端 → 客户端
{ "type": "task.updated", "channel": "user:12", "data": { /* 完整任务快照，含 version */ } }
{ "type": "hello", "data": { "server_time": "…" } }            // 建连成功
// 客户端 → 服务端（MVP 只需要 ping；subscribe 为协作预留）
{ "type": "subscribe", "channel": "canvas:34" }
```

MVP 建连后自动订阅 `user:{id}`。任务事件发布到任务所属用户的频道。以后协作时增加 `canvas:{id}` 频道，服务端校验画布访问权限后才允许订阅。

**发布时机**：在状态迁移的 DB 事务**提交之后**再发布，避免客户端收到推送后去查询，却读到旧数据。

### 7.8 前端改动

- **节点数据**：新增 `taskId?: string`。持久化 DTO 的 `status` 增加 `running`，否则刷新后生成中的状态会丢。
- **任务 store**（zustand）：`tasks: Record<taskId, Task>`，由 WS 消息和对账接口写入，按 `version` 只保留更新的快照。节点如果有 `taskId`，就优先从这个 store 读进度。
- **回填**：任务进入终态、且节点的 `taskId` 跟任务一致时，调用 `updateNodeData(id, {status, src, assetId, error})`，走现有自动保存。如果节点当前的 `assetId` 已经等于结果，就跳过，保证幂等。
- **对账时机**：打开画布时收集 `status=running` 的节点 → `GET ?ids=`；WS 重连成功 → `GET ?status=active`；页面从后台切回前台时也对账一次。
- **全局连接**：登录后在应用根部建立一条 WS，列表页也保持连接，用来弹完成 toast。重连采用指数退避（1s → 30s）。
- **模型清单**：`MODEL_LIBRARY` 改成读取 `/models` 接口；视频种类暂时不支持自定义模型。
- **多标签页**：两个标签页可能同时回填同一个节点，其中一个会遇到 409，走现有冲突重载逻辑。结果一致，可以接受。

## 8. 方案取舍

### 已确认决策

| 分叉 | 决定 | 放弃了什么 |
|---|---|---|
| 部署 | 单实例落地，接口按多实例设计 | 暂不做 Redis pub/sub、独立 worker 进程 |
| 凭证 | 平台统一托管，后端下发模型清单 | 视频暂不支持用户自带 Key 或自定义模型 |
| 平台结果 | 轮询为主，webhook 只触发立即轮询 | 纯 webhook 带来的最低延迟 |
| 回填 | 任务表为准，前端写节点 | 关页面后 `payload_json` 里的节点不会自动更新（重开画布时对账补齐） |
| 任务范围 | 通用 `generation_tasks`，MVP 只接视频 | 视频专用字段放进 `input_json`，失去列级约束 |
| 计费 | 冻结 → 结算 / 退回 | 更简单的“提交即扣” |
| 通道 | 用户级 WebSocket + 频道 + 对账兜底 | SSE 更低的实现成本 |
| 范围 | 并发上限 + 软取消 | — |
| 素材存储 | 本地磁盘 / S3 / OSS 可配置，磁盘仅开发 | — |
| 删除节点 | 任务继续跑，产物进生成记录，照常结算 | 删除即取消并退款 |
| 积分来源 | 初始余额固定 50，本期不做充值 | 充值与管理员发放入口 |

### 为什么不引入 MQ / Kafka

MVP **不引入**消息队列，用 PostgreSQL 表加 `FOR UPDATE SKIP LOCKED` 当任务队列。理由如下：

- **量级不需要**：任务都是人在画布上点出来的，每个要跑几分钟。即使 1000 个活跃用户、每人并发 4 个，也只是几千行任务、每秒几十次查询，PG 完全承受得住。
- **任务状态本来就要落库**：状态、积分、对账都依赖 DB。再引入 MQ 就有两份状态要保持一致。要保证“扣积分”和“发消息”原子，还得额外做 outbox 模式。
- **核心需求是“定时再查”，MQ 不擅长这个**：worker 要按 `next_poll_at` 退避轮询，本质是延迟调度。Kafka 没有延迟消息；RabbitMQ 要装延迟插件或者用死信队列绕一圈。DB 里一个 `next_poll_at` 索引就能直接解决。
- **运维成本**：现在只有 PG + Redis，加 Kafka 意味着再维护一套集群。

**什么时候再引入**：

| 信号 | 引入什么 |
|---|---|
| 多实例部署，WS 连接分布在不同机器上 | **Redis Pub/Sub 或 Streams**，只用来广播 `task.updated`（第一步就是它，不是 Kafka） |
| API 和 worker 拆成独立服务，或者 worker 要按平台隔离扩容 | Redis Streams / RabbitMQ 做提交队列，任务状态仍然以 DB 为准 |
| 同一个任务事件有多个独立消费方（计费、通知、数据分析、审计），或者提交量达到每秒上千 | Kafka + outbox，由状态迁移事务写 outbox，再投递到 Kafka |

`Broadcaster` 接口（7.3 节）和 DB 队列的租约设计已经给这些替换留好了位置，业务代码不用改。

### 通道决策矩阵（权重：正确性和恢复 35%、实时性 20%、扩展到协作 20%、实现成本 25%）

| 方案 | 正确性和恢复 | 实时性 | 协作扩展 | 实现成本 | 加权 |
|---|---|---|---|---|---|
| 纯轮询 | 5 | 3 | 1 | 5 | 3.80 |
| SSE + 对账 | 5 | 5 | 2 | 4 | 4.15 |
| **WS + 对账** | 5 | 5 | 5 | 3 | **4.50** |

三个方案的“正确性和恢复”得分相同，因为都靠 DB 加对账保证。WS 的优势完全来自协作扩展这一项。如果以后确定不做实时协作，SSE 是更省的替代方案，前端对账和任务 store 都不用改。

## 9. MVP 与后续

### 阶段 1（MVP）

内容：模型清单接口；`generation_tasks` / `user_credits` / `credit_ledger` / `assets` 四张表；接 1 家视频平台的适配器；worker 轮询；转存；WS 推送 + 对账；并发上限；软取消；前端视频节点接入真实任务。

验收条件：

1. 提交接口 p95 < 300ms，而且不依赖平台响应速度。
2. 生成中关闭页面，重新打开画布后能看到最终结果，视频可以播放。
3. 生成中重启后端，任务继续完成，积分不会重复扣或漏扣。
4. 断网 30s 再恢复，5s 内节点状态和服务端一致。
5. 同一个 `Idempotency-Key` 重复提交，只创建一个任务、只冻结一次积分。
6. 失败、取消、超时的任务，积分全部退回。`credit_ledger` 汇总与 `user_credits` 对账零差异。
7. WS 连接可以保持 > 10 分钟不断（验证已绕开 60s `WriteTimeout`）。
8. 平台 URL 过期（> 24h）后，画布里的视频仍然能播放。
9. 超过并发上限时返回 429，前端就地提示。

### 阶段 2

- 配置公网地址后启用 webhook 加速。
- 接入第 2、3 家平台。
- 图片、音频节点迁移到任务体系。
- 增加“生成记录”面板，可以看到节点被删除后留下的产物。
- Redis pub/sub 版 Broadcaster，支持多实例。

### 阶段 3

- `canvas:{id}` 频道：协作时实时同步其他人发起的生成。
- 排队预估时间。
- 优先级队列。
