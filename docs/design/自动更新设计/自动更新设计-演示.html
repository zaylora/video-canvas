01现状

现在升级一个版本，有三件事没人管

迁移

没有迁移记录

启动时 4 个手写 Migrate* → AutoMigrate → 又 1 个 Migrate* → 手建索引。

顺序只靠注释约定；做过哪些变更库里查不到；多实例同时启动没有互斥。

感知

不知道有新版本

后台看不到当前版本和最新版本。

其实 /health 已经返回 version，打 tag 也已经自动建 GitHub Release，只差把它们接起来。

执行

升级全靠手工

登录服务器、改 IMAGE_TAG、pull、up -d。

没有升级前备份提醒，失败了也没有固定的回退步骤。

证据：backend/internal/initialize/db.go:41-82、repository/migrate.go、pkg/version、release-on-tag.yml

02为什么不照搬 sub2api

它换的是「一个文件」，我们要换的是「一组容器」

sub2api：单二进制 + systemd
sub2api（后端 + 内嵌前端 + 内嵌 SQL）替换文件

下载 Release 包 → 校验 SHA-256 → rename 替换 → os.Exit(0) → systemd 拉起新进程。
一个文件就是全部，换完即升级。

video-canvas：Docker Compose 五个服务
backend：/app/server只换这个？
backend：Node + agent/src + node_modules仍是旧的
plugin-runner（同镜像、另一个容器）仍是旧的
web（nginx 前端镜像）仍是旧的
postgres · redis不动

只换容器里的二进制，重建容器就丢，而且前后端版本对不上，比不升级还糟。
→ 借鉴它的迁移器、版本检查、前端交互；执行升级改成「换镜像 tag、重建容器」。

03推荐结论

七个决定

D1
不做二进制自替换升级的单位是镜像，不是文件
D2
生产用 SQL 迁移取代 AutoMigratego:embed SQL + schema_migrations + advisory lock + 每文件一事务
D3
基线 = v0.3.2 的库结构新库执行基线；老库跑冻结的旧链后只记录基线
D4
测试仍可 AutoMigrate结构一致性测试比对「SQL 建出的」与「模型建出的」
D5
只向前，Expand–Contract不写 down；删列改名分两个版本；回退数据库靠备份
D6
检查更新走 GitHub Releases只读、只提示、给命令；内网部署可关闭
D7
一键升级 = 可选的 updater 容器，默认关它挂 docker.sock，负责备份 → 换 tag → 拉镜像 → 重建 → 健康检查 → 失败退回旧 tag；不自动回滚数据库
04一期 · 版本化迁移

迁移器：启动时、HTTP 之前，跑完才放行

backend/migrations/
  embed.go            // go:embed *.sql
  0001_baseline.sql   // v0.3.2 完整结构
  0002_add_xxx.sql
  0003_idx_xxx.notx.sql  // 不包事务

CREATE TABLE schema_migrations (
  filename     TEXT PRIMARY KEY,
  checksum     TEXT,   -- SHA-256
  app_version  TEXT,   -- 谁执行的，回退时要用
  duration_ms  INT,
  applied_at   TIMESTAMPTZ
);
1
固定一条连接，pg_try_advisory_lock 循环等锁（≤10 分钟）
2
建 schema_migrations；判定基线（新库 / 老库 / 已接入）
3
按文件名遍历：已记录且 checksum 一致 → 跳过
!
checksum 不一致 → 中止（已发布的文件被改了）
!
库里有程序不认识的文件 → 中止（旧镜像跑新库）
✓
未记录 → BEGIN；执行；写记录；COMMIT
4
解锁 → 启动 HTTP。任一步失败：进程退出

06一期 · 难点与兜底

老库怎么接进来，模型和 SQL 怎么不跑偏

老库接入
  • 现有 5 个 Migrate* + 手建索引原样搬进 migration/legacy.go，冻结
  • 其中的 AutoMigrate 不用 model.All()，用复制出来的 v0.3.2 冻结模型，否则老库会被建成「未来的结构」
  • 补齐后只记录 0001_baseline.sql，不执行它
  • 旧链永久保留：任何老版本都能一步升到最新
测试
  • 结构一致性：schema A 跑全部 SQL，schema B 跑 AutoMigrate(model.All())，比列和索引；改模型忘写迁移就红
  • 老库升级：冻结模型建库 + 样例数据 → Run → 结构等于 A，数据还在
  • 迁移器行为：幂等、篡改、并发、notx、失败回滚
  • 现有 isolatedDB 不用改
防护
  • CI：对比最近 tag，backend/migrations/ 只许新增
  • 每个迁移事务 SET LOCAL lock_timeout='30s'
  • 大表索引 .notx.sql + CONCURRENTLY IF NOT EXISTS
  • /app/server migrate status 子命令
  • 规则写进 backend/AGENTS.md

退回 0.4.0 安全

09三期 · 一键升级（可选）

谁来「重建自己」？交给一个独立的 updater

浏览器super_admin

unix socket

updaterprofile: updater，默认不启

Docker Engine≈ 宿主机 root

为什么不让 backend 自己做

  • 拿 docker.sock 等于拿宿主机 root，不该给对外服务的进程
  • 重建到一半，发命令的进程自己就没了

updater 只会三件事

  • upgrade（目标必须是 GitHub 正式 Release）
  • rollback（只退一个版本）
  • status；不接受任意命令或镜像名；只动 backend / plugin-runner / web
  • 升级步骤复用 scripts/update.sh，updater 只是外壳（脚本尚未实测，动手时先验证再改）

为什么不用 Watchtower

  • 发现新镜像就重建：没有备份、不认我们的健康标准、失败不回退、不能从后台控制时机

11三期 · 回退与安全

镜像可以退，数据库只能人来决定

情况处理
新版本没执行迁移直接换回旧 tag 重建
执行了，都是 Expand（只加不删）面板列出这些迁移，确认后写入 allow_newer_schema，旧版本照常运行
执行了，含删除或改名给出备份恢复命令；不提供一键恢复，恢复会丢掉升级后的新数据

判断依据：schema_migrations.app_version 记录了每个迁移是哪个版本执行的。

风险措施
docker.sock ≈ root默认不启用；只监听 unix socket；三个固定动作
后台账号被盗仅 super_admin；目标必须是正式 Release；全程写 admin_audit_logs
镜像被篡改来源固定为自己的 GHCR；cosign 签名校验留作后续
备份泄露备份卷只挂给 postgres 和 updater
中断生成任务升级前显示进行中任务数并二次确认；重启后任务对账恢复
