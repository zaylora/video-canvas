# 自动更新设计（版本检查 · 数据库迁移 · 一键升级）

> 范围：参考 sub2api 的在线更新机制（调研见仓库根目录 `调研自动更新机制_6ace07a7_20261013_1827.md`），为 video-canvas 设计「版本化数据库迁移」「后台检查新版本」「一键升级」三件事。
> 配套：[自动更新设计-演示.html](./自动更新设计-演示.html)（讲解用幻灯片，含迁移流程模拟）。
> 日期：2026-10-14。状态：一期已实现（未提交，实现说明见 3.10）；二期、三期待实现。第 9 节的待确认问题已全部确认。

## 1. 设计摘要

**问题**：

1. **没有版本化迁移**：库结构靠启动时的 `AutoMigrate` 加四个手写的 `Migrate*` 函数维护，顺序只靠注释「必须在 AutoMigrate 之前/之后」约定。哪些变更做过、什么时候做的，库里没有任何记录；多实例同时启动也没有互斥。
2. **不知道有新版本**：后台看不到当前版本和最新版本，只能去 GitHub 看。
3. **升级全靠手工**：要登录服务器执行 `docker compose pull && up -d`，升级前也没有备份提醒。

**sub2api 的做法能不能照搬**：不能。它替换单个二进制，再由 systemd 拉起新进程。我们只有 Docker Compose 一种部署形态，后端镜像里除了 `/app/server` 还有 Node 和 Agent 运行时，前端是单独的 nginx 镜像，plugin-runner 是另一个容器。只换容器里的二进制，容器一重建就丢了，而且前端、Agent、plugin-runner 还停在旧版本。**能借鉴的是它的迁移器、版本检查和前端交互，执行升级要换成「换镜像、重建容器」。**

**推荐结论**：

| #   | 决定                                        | 一句话                                                                                              |
| --- | ------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| D1  | **不做二进制自替换**                        | 升级的单位是镜像，不是文件                                                                          |
| D2  | **生产用 SQL 迁移取代 AutoMigrate**         | `go:embed` 的 SQL 文件 + `schema_migrations` 记录表 + advisory lock + 每个文件一个事务              |
| D3  | **基线 = v0.3.2 的库结构**                  | 全新库执行基线 SQL；老库先跑一遍冻结的旧迁移链，再把基线记为已执行                                  |
| D4  | **测试仍可用 AutoMigrate，靠一致性测试兜底** | 新增一个测试，比对「跑完全部 SQL」与「AutoMigrate」两种方式建出的结构，模型和 SQL 不一致就失败       |
| D5  | **迁移只向前，按 Expand–Contract 写**       | 不写 down 脚本；删列、改名分两个版本做；数据库回退靠升级前的备份                                    |
| D6  | **检查更新走 GitHub Releases，可关闭**      | 只读、只提示、给出升级命令；内网部署可以关掉                                                        |
| D7  | **一键升级 = 可选的 updater 容器，默认关**  | 它挂载 docker.sock，负责备份、换 tag、拉镜像、重建、健康检查、失败时退回旧 tag；不自动回滚数据库    |

**分三期**，每期都能单独上线、单独产生价值：

| 期  | 内容                     | 依赖          | 预估改动                     |
| --- | ------------------------ | ------------- | ---------------------------- |
| 一  | 版本化数据库迁移         | 无            | 后端，中等                   |
| 二  | 后台版本标记与检查更新   | 无（建议在一期后） | 后端一个服务 + 前端一个组件，小 |
| 三  | 一键升级（可选）         | 一期、二期    | 新镜像 + compose + 前后端，大 |

### 2.2 设计约束

- 分层固定为 `router → middleware → handler → service → repository`，测试放 `backend/internal/tests/`，先写测试。
- 已上线的库是 `AutoMigrate` 建出来的，**不能要求用户手工处理**；从任何 0.3.x 版本升级都必须自动完成。
- 不把密钥、令牌写进仓库或日志。
- 生成任务是长任务：重启会中断正在跑的任务，项目已有任务对账恢复，但升级流程应提示进行中的任务数。

### 2.3 顺带发现的问题

- `docs/docker-production.md` 里的命令写的是 `docker-compose.prod.yml`，仓库里只有 `docker-compose.yml`。一期顺手统一。
- `update.sh` 的四个问题，三期一并修（见 5.1）：
  1. 不备份数据库，迁移失败后没有可恢复的备份；
  2. 总是从 `master` 分支同步 compose 文件，而不是目标版本的 tag，`master` 上未发布的改动会被带到生产；
  3. 健康判断只看容器是否 healthy，不确认跑起来的就是目标版本；
  4. 默认 `latest`，失败时脚本自己也提示「同名 tag 无法自动回滚」。

## 3. 一期：版本化数据库迁移

### 3.1 目录与文件

```text
backend/
├── migrations/                      # 迁移 SQL，和 plugins/embed.go 一样用 go:embed 打进二进制
│   ├── embed.go                     # //go:embed *.sql  var FS embed.FS
│   ├── 0001_baseline.sql            # v0.3.2 的完整结构
│   └── 0002_xxx.sql                 # 之后每次结构变更新增一个文件
└── internal/
    └── migration/
        ├── runner.go                # 迁移器：锁、记录表、校验、执行
        └── legacy.go                # 冻结的旧迁移链（从 repository/migrate.go 搬来）
```

**命名规则**：`NNNN_小写下划线描述.sql`，四位编号，按文件名排序即执行顺序。文件名以 `.notx.sql` 结尾的不包事务（见 3.4）。

### 3.2 记录表

```sql
CREATE TABLE IF NOT EXISTS schema_migrations (
    filename     TEXT PRIMARY KEY,
    checksum     TEXT NOT NULL,          -- 文件内容的 SHA-256
    app_version  TEXT NOT NULL,          -- 执行它的程序版本（pkg/version.Version）
    duration_ms  INTEGER NOT NULL,
    applied_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

`app_version` 是相对 sub2api 多加的一列：三期判断「回退到旧镜像是否安全」时要用（见 5.5）。

### 3.3 启动流程

`initialize.NewDB` 里 `if cfg.AutoMigrate { ... }` 整段换成 `migration.Run(ctx, db, log)`。配置项 `auto_migrate` 的名字保留，含义变成「启动时执行迁移」，避免已有部署的环境变量失效。

```text
migration.Run
 1. 从连接池取一条固定连接 conn（advisory lock 是会话级的，加锁和解锁必须在同一连接上）
 2. 循环 pg_try_advisory_lock(key)，拿不到就等 1 秒，最多等 10 分钟（ctx 超时）
    └─ 其他实例在迁移时，这里会等它做完，之后看到的全是「已执行」
 3. CREATE TABLE IF NOT EXISTS schema_migrations
 4. 基线处理（见 3.5）
 5. 按文件名顺序遍历内嵌 SQL：
      已记录且 checksum 一致 → 跳过
      已记录但 checksum 不同 → 报错并中止启动（已发布的迁移被改过）
      库里有记录、但二进制里没有这个文件 → 报错并中止（数据库比程序新，说明在用旧镜像跑新库）
      未记录 → 执行，并在同一事务里写入记录
 6. 解锁，归还连接
 7. 任一步失败：返回错误，NewDB 失败，进程退出，不启动 HTTP
```

第 5 步第三种情况很重要：回退镜像后，旧程序会在启动时明确报「数据库已被 vX.Y.Z 迁移过，当前程序是 vA.B.C」，不会带着不认识的结构继续跑。这条检查可以用配置 `database.allow_newer_schema: true` 显式跳过，前提是确认那些迁移是向后兼容的（Expand 阶段的加列、加表）。

### 3.4 事务与多语句

- 普通文件：`BEGIN` → 执行整个文件 → `INSERT schema_migrations` → `COMMIT`。PostgreSQL 的 DDL 是事务性的，文件中途失败会整个回滚，记录也不会写入。
- `.notx.sql`：不包事务，用于 `CREATE INDEX CONCURRENTLY` 这类不能放进事务的语句。全部执行成功后再写记录，**文件里的语句必须幂等**（`IF NOT EXISTS`），因为中途失败后已执行的部分不会回滚，下次启动会整个文件重来。
- 一个文件里放多条语句：pgx 在**没有参数**时走 simple protocol，支持一次发送多条语句。实现时第一个测试就要验证这一点（经 `database/sql` + GORM 的 pgx stdlib 路径）。如果不成立，退回「每个文件一条语句」的约定，不要自己按分号切分。
- 迁移事务里设置 `SET LOCAL lock_timeout = '30s'`，避免 `ALTER TABLE` 等锁等太久卡住启动；超时就失败，让运维看日志处理。

### 3.5 基线与老库升级

这是一期唯一的难点：线上库没有 `schema_migrations`，结构是 `AutoMigrate` 建的。

`0001_baseline.sql` 的生成方式：在空库上按**当前**启动顺序（4 个 `Migrate*` → `AutoMigrate` → `MigrateModelSingleConfig` → `idx_task_poll`）跑一遍，用 `pg_dump --schema-only --no-owner --no-privileges` 导出，再人工整理（去掉 `SET` 语句和 `schema_migrations` 本身）。

启动时的判断：

| 库的状态                                                  | 判定方式                                              | 处理                                                                                         |
| --------------------------------------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 全新空库                                                  | 没有 `schema_migrations`，也没有 `users` 表           | 正常执行 `0001_baseline.sql` 及之后的文件                                                    |
| 老库（≤ v0.3.2，AutoMigrate 建的）                        | 没有 `schema_migrations` 记录，但有 `users` 表        | 执行 `legacy.go` 里冻结的旧迁移链，把它补齐到 v0.3.2 的结构，然后**只记录**基线、不执行基线 SQL，再执行 0002 起的文件 |
| 已接入迁移器                                              | `schema_migrations` 里有 `0001_baseline.sql`          | 正常流程                                                                                     |

**冻结的旧迁移链**：把 `repository/migrate.go` 里的 `MigrateLegacyAIConfig`、`MigrateUserManagement`、`MigrateConversationDefault`、`MigrateChannelTrustedInternal`、`MigrateModelSingleConfig` 和 `idx_task_poll` 原样搬进 `migration/legacy.go`。

其中的 `AutoMigrate` 不能用 `model.All()`：以后模型会变，那样老库会被建成「未来的结构」，再跑 0002 起的文件就可能冲突。做法是在 `legacy.go` 里**复制一份 v0.3.2 时的模型结构体**（只留 GORM 标签，放在 `migration/legacy_models.go`），老库补齐时只对这份冻结的模型做 `AutoMigrate`。

旧迁移链**永久保留**（已确认）：任何老版本都能一步升到最新版，不要求用户按顺序升级。旧链和冻结模型从此不再修改，只在老库首次接入迁移器时执行一次，没有维护成本。

`EnsureBuiltinStorage`、`ImportLegacyS3` 依赖运行时配置，不属于结构迁移，留在 `bootstrapStorage` 不动。

### 3.6 测试怎么办

`isolatedDB` 在每个用例的独立 schema 里只 `AutoMigrate` 用到的几个模型，速度快、改动小，**保持不变**。为了保证「模型」和「SQL 迁移」不会各走各的，新增三组测试（都放 `backend/internal/tests/migration/`）：

| 测试                 | 断言                                                                                                                                         |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **结构一致性**       | 两个空 schema：A 跑全部 SQL 迁移，B 跑 `AutoMigrate(model.All()...)`。比对 `information_schema.columns`（表、列、类型、可空、默认值）和 `pg_indexes`（名称、定义）。不一致就失败，并列出差异。改了模型忘写迁移、或写了迁移忘改模型，都会在这里暴露 |
| **老库升级**         | 用冻结模型建一个「v0.3.2 老库」并写入样例数据 → 跑 `migration.Run` → 结构与 A 一致，数据还在，基线记为已执行而非重复执行                     |
| **迁移器行为**       | 重复执行无副作用；checksum 被改 → 报错；库里有程序不认识的记录 → 报错；两个 goroutine 并发 `Run` 只有一个真正执行；`.notx.sql` 正常执行；某个文件失败时它的变更和记录都没留下 |

另加一个不连库的单元测试：`migrations/` 下文件名符合规则、编号连续不重复。

结构一致性测试有些差异是合理的（比如 `idx_task_poll` 这种 GORM 标签表达不了的部分索引），用白名单显式列出，并注明原因。

### 3.7 CI 防护

在 [ci.yml](../../../.github/workflows/ci.yml) 加一步：拿当前分支和最近一个 `v*` tag 比对 `backend/migrations/`，**只允许新增文件**，修改或删除已发布的文件就失败。启动时的 checksum 检查是最后一道防线，这一步是让问题在合并前就暴露。

### 3.8 写迁移的规则（写进 backend/AGENTS.md）

1. 已发布的迁移文件永远不改；要修正就再加一个文件。
2. 只向前，不写 down 脚本。
3. 删列、改名、改类型这类破坏性变更按 **Expand–Contract** 分两个版本：
   - 第 N 版：加新列 / 新表，代码同时兼容新旧两种结构，必要时回填数据；
   - 第 N+1 版（或更晚）：确认已经没有代码读旧列，再删掉。
   这样第 N+1 版出问题时，退回第 N 版的镜像仍然能用当前的库。
4. 改 GORM 模型必须同时加迁移文件，结构一致性测试会检查。
5. 大表上加索引用 `.notx.sql` + `CREATE INDEX CONCURRENTLY IF NOT EXISTS`。

### 3.9 可观测性

- 每执行一个文件打一条 INFO 日志（文件名、耗时）；等锁超过 5 秒打 WARN（「另一个实例正在迁移」）。
- 新增 `GET /api/v1/admin/system/migrations`（admin 可读）：返回已执行列表和二进制里内嵌的文件列表。二期的版本面板会用到。
- 新增子命令 `/app/server migrate status`，和现有的 `plugin-runner` 子命令并列。运维可以 `docker compose run --rm backend migrate status` 查看，不需要启动服务。

### 3.10 实现说明（2026-10-14）

已按本节实现，和上文不一样或补充的地方：

- **基线的两个部分索引改回代码里的写法**：`idx_task_poll` 和 `uk_agent_runs_active` 的条件，pg_dump 导出的是 `= ANY ((ARRAY[...])::text[])`。再执行一次后，PostgreSQL 记录下来的定义和 AutoMigrate 建出的不同（语义相同，文本不同）。结构一致性测试抓到了这个问题，基线里这两处已改回 `status IN (...)`。
- **.notx.sql 只能有一条语句**：多条语句经简单协议发送时，PostgreSQL 会把它们放进一个隐式事务，`CONCURRENTLY` 会报错。
- **自动迁移的开关**沿用 `database.auto_migrate`；新增 `database.allow_newer_schema`（环境变量 `APP_DATABASE_ALLOW_NEWER_SCHEMA`）。
- **`migrate` 子命令**：`server [-c 配置] migrate status|up`。镜像的 ENTRYPOINT 已带 `-c`，所以容器里写 `docker compose run --rm --no-deps backend migrate status`。
- **`GET /admin/system/migrations` 挪到二期**，和版本接口一起做。
- **旧迁移函数的测试**从 `tests/repository` 移到 `tests/migration/legacy_*_test.go`，改为只依赖冻结模型和 SQL，不再经过仓储层。
- **lint**：`internal/migration/legacymodel/` 是原样快照，在 `.golangci.yml` 里整体排除。
- **已验证**：
  - 迁移器与旧迁移链的测试在 PostgreSQL 17（本机）和 16（与生产、CI 相同）上都通过；
  - 复制一份本机开发库（AutoMigrate 建的真实老库）跑升级，与全新库逐项比较，520 个结构项一致。

## 4. 二期：后台版本标记与检查更新

### 4.1 后端

新增 `service/update_check.go` 和 `handler/admin_system.go`，路由挂在 `/api/v1/admin/system`，admin 可读：

| 方法 | 路径                               | 说明                                                                 |
| ---- | ---------------------------------- | -------------------------------------------------------------------- |
| GET  | `/admin/system/version`            | `version.Get()` + 最新一条迁移的文件名                               |
| GET  | `/admin/system/updates?force=1`    | 检查新版本；`force` 跳过缓存，同一用户 1 分钟内最多一次               |
| GET  | `/admin/system/migrations`         | 见 3.9                                                               |

检查逻辑：

- 请求 `https://api.github.com/repos/{repo}/releases/latest`（只返回正式版，自动排除 prerelease 和 draft）。`repo` 来自配置 `update.repo`，默认 `zaylora/video-canvas`。
- 去掉 tag 的 `v` 前缀后按 semver 比较。当前版本是 `dev` 或解析失败时，返回 `has_update=false` 并标注「开发构建，不检查」。
- 结果在内存里缓存 **1 小时**（有 Redis 就放 Redis，多实例共享）。GitHub 失败时返回旧缓存并带 `warning`；没有缓存就返回当前版本和错误说明，**不报 500**。
- HTTP 客户端超时 10 秒，遵循 `HTTPS_PROXY` 环境变量。目标地址固定，不受用户输入影响，没有 SSRF 面。
- 匿名调用 GitHub API 的限额是每个 IP 每小时 60 次，有 1 小时缓存足够。
- 配置 `update.check_enabled`，默认 `true`；内网或离线部署设为 `false`，接口直接返回「已关闭」。

## 5. 三期：一键升级（可选组件）

### 5.1 为什么需要单独的容器

在 Docker 里，能真正升级的只有「拉新镜像、按新镜像重建容器」，这需要调用 Docker Engine。后端容器以非 root 运行、不该拿到 docker.sock，而且后端没法安全地「重建自己」：重建到一半，发出命令的进程就没了。所以交给一个独立的 **updater** 容器去做。

**升级逻辑复用 `scripts/update.sh`，不另写一套。** 仓库里的 `update.sh` 已经实现了「改 tag → pull → 重建 → 等健康 → 失败退回旧 tag」，命令行用户也在用。三期的做法是：

1. **先增强 `update.sh`**，让命令行升级和一键升级得到同样的保护：
   - 新增备份步骤（默认开，`--no-backup` 关闭）：`pull` 成功之后、`up -d` 之前执行 `docker compose exec -T postgres pg_dump -Fc`，存到部署目录的 `backups/pre-<目标版本>-<时间>.dump`，只保留最近 3 份；**备份失败就中止升级**，服务不受影响。放在 `pull` 之后，是为了镜像拉不下来时不白做一次备份。
   - compose 文件改为从目标版本的 tag（`v<版本>`）下载，只有目标是 `latest` 时才用 `master`。
   - 健康判断加一条：`/health` 返回的 `version` 等于目标版本。
   - 新增 `--status-file PATH`：每一步把阶段和结果写成 JSON，供 updater 读取。
   - `deploy.sh` 和 `update.sh` 的默认 tag 改为「GitHub 上最新的正式版本号」，不再写 `latest`。
   > **实测结果（2026-10-14）**：在本机 Docker Desktop 上用一个挂载了 docker.sock 的 `docker:27-cli` 容器（与 updater 的运行环境一致）跑了真实镜像 0.3.1 / 0.3.2，以及本地镜像仓库里的故障镜像。原脚本的问题与修复：
   >
   > | 问题 | 发现方式 | 修复 |
   > | --- | --- | --- |
   > | `deploy.sh` 从 `master/scripts/docker-compose.yml` 下载，404，README 的一键部署不可用 | 实测 | 改为从仓库根目录、目标版本的 tag 下载 |
   > | 新版本启动失败时 `up -d` 返回非 0，`set -e` 直接退出：不回滚，整站停止 | 实测 | `up -d` 失败也走回滚 |
   > | 拉取失败时只退回 tag，没退回已替换的 compose 文件 | 读代码 | 所有失败路径都退回 tag 与 compose 文件 |
   > | compose 文件总从 master 取 | 读代码 | 取目标版本 tag 的那份 |
   > | 只看容器健康，不确认版本；最多等 3 分钟 | 读代码 | 同时要求 `/health` 的 version 等于目标版本；默认等 600 秒 |
   > | 不备份；没有锁 | 读代码 | 拉取成功后 `pg_dump`，保留 3 份，失败中止；目录锁，冲突时不写状态文件 |
   > | `docker image prune` 清掉整台机器的悬空镜像 | 实测观察 | 改为 `--prune` 才清 |
   > | 默认 `latest`，失败无法回退 | 读代码 | `deploy.sh` / `update.sh` 默认取 GitHub 最新正式版本号 |
   > | 一期遗留：`APP_DATABASE_ALLOW_NEWER_SCHEMA` 写进 `.env` 不会传给 backend | 实测 | `docker-compose.yml` 加透传 |
   >
   > 修复后通过的场景：0.3.1↔0.3.2 升级与回退；拉取失败；启动失败自动回滚；镜像能启动但版本号不符时超时回滚；备份保留 3 份且 `pg_restore --list` 可读；同时运行两份；用当前分支构建的 0.4.0 升级真实的 0.3.2 部署（迁移器识别老库并补齐基线）；库被「未来版本」迁移后回滚得到 `failed_needs_attention`，按提示设置放行变量后旧版本可启动。另外确认 `up -d --remove-orphans` 不会重建或删除 `updater` profile 里正在运行的容器。
   >
   > 未覆盖：macOS（BSD 工具）上没有实跑，只按 POSIX / BSD 兼容写法编写并通过 shellcheck。
2. **updater 只是 `update.sh` 的一层外壳**：Go 程序收到 `upgrade` 请求后，执行 `update.sh --dir <部署目录> --tag <目标版本> --status-file ...`，再把状态文件转成接口返回。升级步骤只在 `update.sh` 里维护一份。

### 5.2 拓扑

```text
浏览器 ──HTTP──▶ web(nginx) ──▶ backend ──unix socket──▶ updater ──docker.sock──▶ Docker Engine
                                                           │
                                                           └─ 挂载部署目录（docker-compose.yml、.env、update.sh、backups/，读写）
```

- **镜像**：新增 `video-canvas-updater`（alpine + bash + curl + docker-cli + docker-cli-compose + 一个小的 Go 程序），CI 和另外两个镜像一起发布。`update.sh` 用部署目录里的那份，和命令行升级是同一个文件。
- **部署目录按宿主机的同一路径挂载**（`${DEPLOY_DIR}:${DEPLOY_DIR}`）：容器里执行 `docker compose` 时，路径和项目名都和在宿主机上执行时一致，不会被当成另一个项目。compose 文件里已经写死了 `name: video-canvas`，数据都在命名卷里，没有相对路径的绑定挂载。
- **启用方式**：compose 里放在 `profiles: ["updater"]` 下，默认不启动；运维执行 `docker compose --profile updater up -d` 才启用。backend 通过配置 `update.updater_socket` 判断是否可用，不可用时前端只显示二期的手动步骤。
- **通信**：和 plugin-runner 一样走共享卷里的 unix socket，不开网络端口。另外用 `APP_UPDATER_TOKEN` 做共享密钥，双重保护。
- **updater 自己不被重建**：它的升级仍然手动执行，它很少变化。`update.sh` 执行的是不带 profile 的 `up -d --remove-orphans`，实现时要实测确认：这条命令不会重建或删除处在 `updater` profile 里、正在运行的 updater 容器；如果会，就改成只对 `backend plugin-runner web` 三个服务执行。

### 5.3 升级流程

```text
super_admin 点「升级到 0.4.0」
  backend：
    1. 校验目标版本 = 二期检查到的 latest（不接受任意字符串）
    2. 拿全局升级锁（Redis SETNX，没有 Redis 就用 advisory lock），已有升级在跑 → 409
    3. 写审计日志 system.upgrade.start
    4. 查进行中的生成任务数，返回给前端二次确认（「有 3 个任务正在生成，升级会中断它们，完成后会自动对账恢复」）
    5. 确认后调用 updater POST /upgrade {target:"0.4.0"}，立即返回 job_id
  updater：执行 update.sh --tag 0.4.0 --status-file backups/upgrade-status.json，脚本按以下步骤走：
    1. 记下当前 IMAGE_TAG（回退用），改 .env 里的 IMAGE_TAG=0.4.0
    2. 下载 v0.4.0 的 docker-compose.yml（旧文件留 .bak）
    3. docker compose pull                                 ← 失败：改回 tag 和 compose 文件，结束，服务一直没停
    4. 备份：pg_dump -Fc → backups/pre-0.4.0-<时间>.dump，只保留最近 3 份
                                                          ← 失败：同上，结束；没有备份就不往下走
    5. docker compose up -d --remove-orphans              ← 新 backend 启动时自动执行 SQL 迁移
    6. 每 3 秒检查：全部容器 healthy，且 /health 的 version=0.4.0，最多 3 分钟
    7a. 成功：状态 = succeeded
    7b. 失败：改回旧 tag 和 compose 文件，再 up -d，状态 = failed_rolled_back，附上新 backend 最后 100 行日志
  updater 读状态文件，转成 GET /status 的返回
  前端：
    - 显示步骤进度；backend 重启期间请求会失败，改为轮询 /health
    - version 变成 0.4.0 → 读最终状态 → 提示成功并刷新页面
```

命令行用户执行 `./update.sh --tag 0.4.0` 走的是完全相同的步骤，同样有备份、版本确认和失败回退。

**`IMAGE_TAG=latest` 的部署**：第 1 步没有意义，第 7b 步也退不回去。前端检测到当前部署用的是 `latest`（updater 读 `.env` 告诉 backend）时，提示「请先把 IMAGE_TAG 固定为具体版本，才能使用一键升级和失败回退」。

### 5.4 失败时的数据库怎么办

7b 只退回了镜像，**不会自动恢复数据库**：

- 失败发生在迁移之前（镜像拉不下来、新进程起不来）：库没变，退回旧镜像就够了。
- 失败发生在迁移之中：单个文件有事务，失败的那个文件不会留下痕迹；但它之前已经成功的文件已经提交了。
- 失败发生在迁移之后（迁移成功，但服务健康检查不过）：库已经是新结构。

后两种情况，旧镜像启动时会触发 3.3 第 5 步的「数据库比程序新」检查而拒绝启动，状态会变成 `failed_needs_attention`。这时由管理员决定：

- 如果失败的新版本那几个迁移都是 Expand 型（只加不删），在面板里点「允许旧版本运行」（写入 `allow_newer_schema`）；
- 否则用第 1 步的备份恢复。面板给出恢复命令，**不提供一键恢复按钮**：恢复会丢掉升级之后写入的所有数据，必须人来决定。

### 5.5 手动回退到上一个版本

面板提供「回退到 0.3.2」（只能退一个版本，必须有 updater）。回退前用 `schema_migrations.app_version` 判断：0.4.0 有没有执行过迁移。

- 没有：直接换 tag 重建。
- 有：列出这些迁移文件，提示「这些变更不会撤销；如果其中有删除或改名，旧版本可能无法运行，请先确认，或改用备份恢复」，管理员二次确认后才执行。

### 5.6 安全

| 风险                         | 措施                                                                                           |
| ---------------------------- | ---------------------------------------------------------------------------------------------- |
| docker.sock 等于宿主机 root  | updater 默认不启用；只监听 unix socket；只暴露 upgrade / rollback / status 三个固定动作，不接受任意命令或镜像名 |
| 后台账号被盗后被恶意升级     | 只允许 super_admin；目标版本必须是 GitHub 上的正式 Release；全部操作写审计日志               |
| 拉到被篡改的镜像             | 镜像来自自己的 GHCR；后续可加 cosign 签名校验，本期不做                                        |
| 备份文件泄露                 | 备份卷只挂给 postgres 和 updater，不挂给 web                                                   |

### 5.7 不选 Watchtower 的原因

Watchtower 这类工具只会「发现新镜像就重建」：没有升级前备份，不知道我们的健康标准（version 字段），失败不回退，也没法从后台控制时机。我们需要的是一个受控、可观测的升级过程。

### 5.8 实现细节（2026-10-14 实测后确定）

- **部署目录挂载为 `.:/deploy`**，不要求同路径挂载：我们的 compose 文件里没有相对路径的挂载，项目名来自 `name:` 或 `.env`，在容器里执行 compose 操作的是同一个项目。`.` 由执行 `docker compose --profile updater up -d` 的那台机器解析，所以 **updater 必须由用户在宿主机的部署目录里启动**，不能由 updater 自己重建。
- **`up -d --remove-orphans` 不会动 updater**：实测 profile 里正在运行的容器，在不带 profile 的 `up -d --remove-orphans` 之后容器 ID 不变。
- **token 不是必填的 compose 变量**：写成 `${UPDATER_TOKEN:-}`。写成必填（`:?`）会让没配 token 的老部署执行 `docker compose up` 时整体失败。updater 拿不到 token 就拒绝启动；backend 没配 token 就当作 updater 不可用。
- **updater 接口**（unix socket + `Authorization: Bearer <token>`）：
  - `GET /status`：最近一次运行的状态文件（`update.sh --status-file` 写的 JSON）、`.env` 里的 `IMAGE_TAG`、是否正在运行、`backups/` 下的备份列表；
  - `POST /upgrade {"target":"0.4.0"}`：后台执行 `update.sh --dir /deploy --tag 0.4.0 --status-file /deploy/backups/upgrade-status.json`，立即返回；正在运行时 409。
  - 回退也是 `POST /upgrade`，target 换成上一个版本，由 backend 决定能不能退。
  - updater 只校验 target 是 `x.y.z`，不判断版本对错；版本对错由 backend 判断。
- **backend 接口**（super_admin 写，admin 读）：
  - `GET /admin/system/upgrade`：updater 是否可用（不可用的原因）、当前部署 tag、是否用 latest、进行中的生成任务数、updater 的状态和备份列表；
  - `POST /admin/system/upgrade {target}`：target 必须等于检查到的最新版本且比当前新；写审计 `system.upgrade`；
  - `POST /admin/system/rollback {target}`：target 必须等于最近一次成功升级记录里的 `previous`；写审计 `system.rollback`。
- **前端轮询**：backend 重启期间请求会失败，不能走带全局 toast 的请求封装。升级中每 2 秒静默请求一次 `GET /admin/system/upgrade`，连不上就显示「服务重启中」，直到拿到终态。nginx 不转发 `/health`，所以不用它。

### 5.9 界面（2026-10-14 与需求方确认）

原型：[版本与升级原型.html](./版本与升级原型.html)，控制条里「三期」两组按钮切换 updater 状态、身份和升级结局。

| 问题 | 决定 |
| --- | --- |
| 升级确认 | **确认弹窗**：列出会先备份、服务中断约 1 分钟、失败自动退回，以及进行中的生成任务数；点「开始升级」执行。不要求输入版本号 |

默认决定（按推荐项定）：

- 「升级到 vX」按钮放在版本卡右侧，只有 super_admin 能点；admin 看到禁用按钮和「仅超级管理员可升级」。
- updater 未启用：显示二期的手动步骤，底部说明如何启用一键升级，以及 `./update.sh --tag x` 的用法；`IMAGE_TAG=latest`：按钮禁用，说明原因和改法。
- updater 已启用：不再显示手动步骤；进度卡依次显示准备、拉取镜像、备份数据库、重建服务、等待新版本就绪，带进度条。backend 重启期间显示「服务重启中」；侧栏版本标记在升级中显示转圈（小圆点隐藏）。
- 结局：
  - 成功：2 秒后自动刷新页面；
  - 拉取失败：显示 warning「服务未改动」；
  - 已退回：显示 warning，附查看日志的方法；
  - 需要人工处理：显示 danger，原样展示脚本给出的操作建议。
  - 失败的结局可以关掉。
- 「升级记录与备份」卡：显示上次升级的结果和备份列表，只能查看，不提供下载和恢复。「回退到上一个版本」按钮放在这张卡上，确认弹窗里列出当前版本执行过的迁移。

新增前端文件（在 4.2 的基础上）：`pages/admin/settings/upgrade-panel.tsx`（进度卡、记录卡、确认弹窗）、`utils/admin/upgrade-status.ts`（把 updater 状态翻译成界面状态，纯函数，单测覆盖）。

## 6. 不做的事

- 不做无人值守的自动升级：发现新版本只提示，必须管理员点击。
- 不做数据库 down 迁移和一键恢复数据库。
- 不支持非 Docker 部署（裸机二进制、Windows）的在线升级。
- 不做多机或 K8s 编排下的升级：那种场景应该交给编排系统自己的滚动更新。迁移器的 advisory lock 已经保证多副本同时启动是安全的。

## 8. 风险

| 风险                                                  | 应对                                                                                                    |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 基线 SQL 和老库的真实结构有细微差异（老库经历过多次 AutoMigrate，可能残留列或索引） | 老库路径不执行基线 SQL，只补齐到冻结模型；结构一致性测试之外，再拿一份真实的生产库结构（只要 schema）做一次核对 |
| 一期改完后，开发者忘了写迁移、只改模型                 | 结构一致性测试会失败                                                                                    |
| 迁移在大表上锁表太久                                   | `lock_timeout`；规则要求大表索引用 `CONCURRENTLY`                                                       |
| updater 在 Windows / macOS 的 Docker Desktop 上行为不同 | 三期只承诺 Linux 主机                                                                                   |
