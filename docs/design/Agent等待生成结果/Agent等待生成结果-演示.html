Agent 等待生成结果

生成跑完，Agent 自己醒来接着干

现在 Agent 申请的生成被批准后，这一轮就结束了，图和视频出来它并不知道，要你手动发消息叫它。改成： 本轮照常结束、画布空出来；系统在后台盯着这批任务，全部结束后在同一个会话里自动开一轮，Agent 验收结果并提出下一步。 每次花积分仍然要你点批准，等待期间不占画布、不占会话、不花 token。

阅读说明。项目事实来自 2026-10-28 读取的代码（分支 release/v0.5.4），文件位置见 Markdown §2.1；方案是提案，尚未实现。原型和「出意外时」页的数据都是示意，在内存里，刷新复原。

一批生成从批准到 Agent 醒来

谁负责「知道任务结束」，谁负责「叫醒 Agent」。

你批准生成Go 创建任务，记下是哪次 Agent 运行发起的
登记后台监听一次 Pi 提交：写会话文档 app.watches + 建 Pi 后台任务 app.task-watch；本轮照常结束，画布释放
River 门铃任务进终态的同一个事务里入队一个通知 job，发给 Agent
全部结束 → 唤醒取结果摘要，同一会话自动开一轮
验收、推进看图 / 看视频，提出下一批申请等你批准
设计：任务状态的唯一事实在 Go 的数据库，所以「任务结束」由 Go 在结算事务里发出，不会漏发；门铃只说「某任务结束了」，结果醒来时再查，所以门铃重复、乱序都没关系。pi-durable 管三件事：监听状态存在会话文档里（和对话记录原子提交）；每批一个后台任务用持久睡眠做兜底和交付重试，重启自动续上；结果作为带 requestId 的输入投回会话，重放不会叫醒两次。Pi 任务不能被外部提前叫醒，所以秒级的快速路径靠 River 门铃。监听不用 LLM：等状态不需要模型。
门铃丢了、Agent 宕机、画布被占时（兜底）：每批的 Pi 后台任务在登记 2 分钟后醒来，之后每 60 秒一次，向 Go 查还没收到门铃的任务，所以最多晚两三分钟；Agent 重启后它按睡眠时间自动续上。Agent 不在线时 River 会退避重试门铃。你正在同一会话里聊天时，结果直接插进当前这一轮；画布被另一个会话占着，就等那次运行结束马上唤醒。

批准时有三种去向

默认一定会等；只有你明确说「不用管」时 Agent 才会放行。

后台等待（默认）
wait=true

提交就走
仅限你明确说不用管

不用等了
你中途取消

你要做 6 个镜头的图，再都做成视频时，会发生什么

全程你只需要点两次批准。

  1. Agent 建 6 个节点、写提示词，申请出图审批卡显示预估积分；页面在后台时会收到浏览器通知
  2. 你批准，本轮结束会话显示「后台等待生成 0/6」；你可以继续聊别的，或去开另一个会话
  3. 6 张图都结束，自动开新一轮消息流里出现「生成全部结束，Agent 继续」，Agent 逐张看图验收
  4. Agent 申请：重做 1 张不合格的 + 5 张合格的做图生视频新的审批卡，标签页标题变成「⏸ 待批准」
  5. 你批准，再次后台等待视频可能要十几分钟（示意）
  6. 全部结束，自动开新一轮，Agent 验收视频并汇报没有要做的就简短汇报，结束
边界：每一步花钱都要你批准，链条会停在审批卡上等你。
  • 审批不会过期失效；等审批时你在输入框发消息，就当作「拒绝这次申请 + 补充说明」交给 Agent，不会报「画布已有运行」。
  • 提醒只有标签页标题和浏览器通知，关了页面就收不到，回来时审批卡还在。
  • 醒来是在同一个会话里开新一轮，每一轮的预算和步数重新算。
  • 你正在同一会话里和 Agent 聊时，结果直接插进当前这一轮（学 Claude Code）；画布被另一个会话占着、或本会话在等审批时，等那次运行结束马上唤醒。

上线说明里要告诉用户：「不用等了」只取消 Agent 的跟进，不会取消已批准的生成，也不会退积分。

出意外时，唤醒会不会丢、会不会重复

左边选一个情况，右边逐步播放 Go、River、Agent 之间发生的事。时间和顺序是示意，用来说明每种情况最后都只唤醒一次。

谁记什么

任务归 Go，会话和运行归 Agent，所以两边各记一半。

记录放在哪为什么
任务属于哪次运行generation_tasks.agent_run_id（Go / PostgreSQL）结算事务里要据此决定发不发门铃；现在只能从幂等键反推，不可靠（用户请求也能带幂等键）
门铃River job agent.task_settled（同一事务入队）和积分结算同生共死，不会「任务结束了但没通知」
会话在等哪些任务会话级 Pi 文档 app.watches（Agent / pi-durable）运行和会话都在 Agent；文档和对话记录同库原子提交，登记监听与建监听任务一次提交完成
兜底轮询与交付重试Pi 后台任务 app.task-watch，每批一个持久睡眠、重启续上、崩溃循环自动挂起都由 pi-durable 管；不让会话变忙
唤醒去重Pi submit 的 requestId = wake:{会话}:{批}pi-durable 已保证会话内同一 requestId 只提交一次，重启有效

数据模型

Go 侧走 backend/internal/migration 现有迁移；Agent 侧走 agent/src/store/migrations.ts。

generation_tasks 新增（Go）
agent_run_idvarchar(32) not null default ''；部分索引 WHERE agent_run_id <> ''。只由 AgentGenerator.submit 写，用户请求无法设置（json:"-"）
River 新 job（Go）
队列 / kindagent_notify / agent.task_settled，并发 4，不占生成名额
args{ task_id, run_id }，按 args 唯一
重试MaxAttempts=25，River 默认退避 退避曲线未核实
入队条件finish() 事务内、agent_run_id ≠ ''、非试跑、Agent 已启用
Pi 文档 app.watches（会话级，defineDoc，version 1，fork: initial）
batches[审批 id]一批 = 一次审批批准的任务；全部结束才可交付
.runId / .createdAt发起它的运行、登记时间
.watcherTaskId这批的 Pi 后台任务 id，取消时用它 abortTask
.statewaiting → deliverable → delivered，或 canceled；Pi 提交串行原子
.deliveredRunId交付给哪次运行（新开的唤醒运行，或插话时的当前运行）
.tasks[任务 id]{ nodeId, status: pending|settled, taskStatus: succeeded|failed|expired|canceled|missing, settledAt }
清理已结束超过 7 天的批，在下次写文档时清掉
Pi 任务 app.task-watch（defineTask，background: true，属于会话）
wait（初始）sleepUntil(登记 + 2 分钟)，给门铃留宽限
check已交付或已取消 → 结束；否则向 Go 查仍 pending 的任务并写回文档；整批结束 → tryWake；没交付成 → sleepUntil(+60s)
abort无外部副作用，直接结束
安装引擎扩展 engine-watch 的 tasks；重启时先装扩展再 resume()

agent_runs 新增 trigger（user | wake，默认 user）和 wake_of（来源运行 id）。

接口

方法与路径方向说明
POST /internal/v1/watches/task-settledGo → Agent门铃。body { task_id, run_id, status }，头 X-Agent-Service-Token。按 run_id 找会话，在 Pi 文档里记账。200 已记账；404 没有对应监听（已取消或 wait=false），job 视为完成；5xx / 连不上由 River 重试
POST /internal/platform/v1/tasks/statusAgent → GoPi 监听任务兜底用。{ task_ids: ≤50 } → { items: [{ task_id, status, finished_at }] }，不存在或不属于该用户的返回 missing；400 参数错
POST /internal/platform/v1/tasks/digestAgent → Go唤醒用。返回 { text, items: [{ task_id, node_id, node_title, kind, status, error_message, outputs }] }；400 参数错
GET /agent/sessions/:id/watches前端 → Agent（经 Go 代理）监听条数据：总数、已结束数、状态 waiting | queued | delivered | canceled、每个任务
POST /agent/sessions/:id/watches/cancel前端 → Agent不用等了：文档里未交付的批置 canceled，abortTask 收掉监听任务；不取消生成
事件 watch.updatedAgent → 前端（现有事件推送）{ total, settled, state }
generate_media 参数 wait模型布尔，默认 true；用户明确说「不用管结果」才传 false

// Go：GenerationTaskService.finish()（提案）
WithTx(tx => {
  t = tx.UpdateIf(id, from, {status: target, ...})
  settleLedger(tx, t, target)
  if t.AgentRunID != "" && !t.IsTest && agentEnabled:
    tx.EnqueueAgentNotify({task_id: t.ID, run_id: t.AgentRunID})   // 同一事务；失败整笔回滚
})

// Agent：登记，在 decide 批准执行之后（提案）
conv.commit(tx => {
  doc = tx.doc(Watches, conv.id)
  task = tx.createTask(TaskWatch, {batchId: approvalId, sessionId}, {background: true})
  doc.batches[approvalId] = {runId, watcherTaskId: task.id, state: "waiting", tasks: {...pending}}
})

// Agent：门铃和监听任务共用的记账（提案）
settle(task_id, status):
  conv.commit(tx => doc.tasks[task_id]: pending → settled)   // 重复门铃：已 settled，无副作用
  if 整批无 pending: batch.state = "deliverable"; tryWake(session)

onTaskSettled(task_id, run_id, status):        // POST /internal/v1/watches/task-settled
  if 文档里没有该任务 或 该批已 canceled: return 404
  settle(task_id, status); return 200

// Agent：唤醒，按会话加锁（提案）
tryWake(session):
  batches = watches.deliverable(session)            // 整批 settled、未交付、未取消
  if batches.empty: return
  active = canvasActiveRun(session.canvas)
  if active && active.session == session && active.status == "running":
    digest = platform.tasksDigest(batches.taskIds)
    conv.submit({type: "input", whenBusy: "steer", content: wakeText(digest), requestId: ...})
    return markDelivered(batches, active.id)          // 插进当前这一轮
  if active: return                                  // 排队；任一运行终态时再调 tryWake
  digest = platform.tasksDigest(batches.taskIds)    // 失败：留给监听任务下次醒来
  run = startRun(session, {trigger: "wake", wakeOf: batches.runId})   // 撞 60001 → return
  conv.submit({type: "input", content: wakeText(digest),
               requestId: "wake:" + session + ":" + batches.minId,   // 重放不重复
               entry: {kind: "app.tasks_settled", data: {batchIds, taskIds}}})
  watches.markDelivered(batches, run.id)

// Agent：Pi 后台任务 app.task-watch（提案）
TaskWatch = defineTask({ name: "app.task-watch", version: 1, initial: () => ({phase: "wait"}),
  phases: {
    wait:  (task, rt, ctx) => rt.sleepUntil(batch.createdAt + 2min, {phase: "check"}, ctx),
    check: async (task, rt, ctx) => {
      if batch.state in ["delivered", "canceled"]: return complete
      for st in platform.tasksStatus(pendingIds): if terminal(st): settle(st.id, st.status)
      if batch.state == "delivered": return complete     // settle 里的 tryWake 已交付
      return rt.sleepUntil(now + 60s, {phase: "check"}, ctx)   // 重启后按时间续上
    },
  },
  abort: () => {},                                    // 无外部副作用
})

已确认的决定

  1. 目标是链式推进多步：生成完自动验收，自动提出下一批申请。
  2. 每次生成都审批：不做预算内自动批准。
  3. 后台监听、本轮结束：等待期间不占画布和会话，结束后在同一会话自动开新一轮；监听不用 LLM。（取代了先前「运行不结束、可插话」的决定，见 Markdown §9.3）
  4. 系统自动等，模型可放行：wait=false 仅限用户明确说不用管。
  5. 一批全部结束才唤醒一次。
  6. 提醒 = 标签页标题 + 浏览器通知，纯前端。
  7. 审批不收尾：等审批时发新消息 = 拒绝并补充说明。
  8. 只停 Agent，生成任务继续：对应「不用等了」和唤醒运行里的停止。
  9. 同会话正在回答时，结果插进当前这一轮（参考 Claude Code）；另一会话占着画布或本会话在等审批时仍排队。
  10. 监听用 pi-durable 原生：状态放会话级 Pi 文档，兜底轮询和交付重试由 Pi 后台任务做；River 门铃保留为快速路径。
  11. 已搁置：预算内自动批准、时间窗合并唤醒、站内通知、审批超时结束运行、子代理验收（列入后续）、自建监听表 + 引擎定时器。
  12. 主文档已回写：§1、§4.3、§6.4、§6.5、§8.2、§9.2、§11。
