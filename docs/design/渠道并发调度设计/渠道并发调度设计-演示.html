渠道并发调度设计

给每个渠道设“最多同时生成几个任务”，满了就在我们这边排队，
而不是撞上游的限制再失败；之后再让一个模型能在多个渠道之间自动挑空闲的。

A：渠道级同时生成上限（排队） · B：多渠道自动调度　|　← → 翻页，T 切换明暗

01 · 问题

上游满了，我们不知道，任务直接失败

今天发生了什么

  • 任务一建好，worker 有空位就立刻提交给上游
  • 上游账号同时生成数到顶了，返回“繁忙”
  • 可重试的错误最多重试 5 次，还不行就失败
  • 用户看到“平台繁忙，请稍后重试”，积分退回

库里的任务 32、34 就是这样失败的（YSWG，provider_error）。

为什么现有的限流挡不住

渠道页的“每秒请求数 / 最大并发”管的是请求：一个请求从发出到收到响应才占名额。

YSWG 这类异步接口，提交 1 秒就返回任务号，中间 60 秒的生成不占名额。所以“最大并发 3”，上游照样可以同时有几十个任务在生成。

缺的是一个管“任务”的上限：这个渠道此刻最多有几个任务在上游生成。

02 · 先分清两个东西

“请求”只占一瞬，“任务”占满整个生成过程

请求（现有限流管的）

提交 1 次 + 每 15 秒查 1 次，每次不到 1 秒。
“最大并发 3”= 同时最多 3 个请求在路上。

任务（这次要新增的）

从提交成功到上游出图，一直占着上游的一个生成位。
“最大同时生成 3”= 同时最多 3 个任务在上游。

同步接口（如文本）例外：一次请求等到正文返回，请求和任务几乎重叠，所以现有的“最大并发”对它碰巧有效。

03 · 现状与新增

一个任务要过的四道闸门

闸门管什么在哪一步拦拦下时用户看到配置
① 用户进行中上限每个用户同时进行的任务数提交接口，建任务之前“并发已满”，不建任务max_active_tasks_per_user 4
② worker 执行池整个服务同一时刻在处理的任务步骤领任务时：没空位就不领排队中worker.concurrency 8
③ 渠道同时生成上限（新）这个渠道此刻在上游生成的任务数领 pending 任务时：渠道满了就不领排队中渠道页，新字段
④ 渠道请求限流这个渠道发出的请求：每秒几个、同时几个真正发 HTTP 之前：等令牌和名额排队中 / 生成中（看哪个请求在等）渠道页 rps、最大并发

另有插件沙箱池（每个插件版本 8 个 JS 运行时），只占几毫秒，几乎不会成为瓶颈，见《协议插件设计 / 并发控制与沙箱池》。

③ 放在②之后、④之前：先有执行位，再看渠道还有没有生成位，最后才去发请求。

04 · 范围

这次要做到什么，不做什么

目标

  • 渠道能配“最大同时生成数”，0 或留空表示不限（和现在一致）
  • 满了的任务留在 pending，画布显示“排队中”，空出来自动提交，先到先提交
  • 多个后端实例一起跑也不会超限
  • 排队时间不吃掉生成超时；排太久有单独的“排队超时”
  • 渠道页能看到“生成中 3 / 5，排队 7”

不做（这一期）

  • 按“渠道 + 模型”分别设上限（见待确认）
  • 用户之间的公平调度（同一渠道内先到先得，单个用户最多 4 个任务已经限住了）
  • VIP 优先级、插队
  • 自动探测上游真实上限：数值由运营填
  • 多渠道调度：放到方案 B
05 · 方案 A：渠道同时生成上限

一个字段、一处领取规则、一个超时调整

配置

渠道新增 max_running

放进现有的 rate_limit_json：
{"rps":5, "max_concurrency":20, "max_running":10}
不用改表结构，旧渠道没有这个键就是不限。

调度

领 pending 时看余量

worker 每秒领任务时，pending 任务按渠道数一下“正在占位的任务数”，只领到上限为止。轮询、转存不受影响。

超时

排队与生成分开计时

生成超时改为从提交给上游起算；排队另设上限，超了按“排队超时”失败并退积分。

为什么放在“领任务”这一步，而不是“发请求”这一步：领了却发不出去，任务会占着 worker 执行位干等，还会拖慢别的渠道；不领它，它就安静地待在数据库里。

06 · 方案 A · 占位

哪些任务算“正在占这个渠道的生成位”

任务状态算占位？理由
pending，正在被提交（有有效租约、还没拿到上游任务号）算请求已经在路上或马上发出。不算的话，两个实例可能同时各提交一批，超限
pending，在等（没有租约）不算就是排队中的那些，还没碰上游
pending，提交失败后退避重试中不算上游没有接收这个任务，把位置让给别人
queued / running算已经在上游，占着上游的生成位
finalizing不算上游已经出结果，只是我们在下载、保存，不占上游
终态（成功 / 失败 / 取消 / 超时）不算结束了

按任务表的 provider 列（就是渠道 key）分组计数；运营试跑任务（is_test）也算占位，因为它也占上游。

07 · 方案 A · 调度

worker 领任务改成两路

第一路：在途任务（不变）

queued / running / finalizing 到点要查结果或转存，照常领。

必须不受上限影响：只有查到结果、任务结束，位置才会空出来。要是它们也排队，就死锁了。

第二路：pending（新规则）

每个渠道最多领 上限 − 占位 个，同一渠道内按创建时间先到先领；上限为 0 的渠道不限。

两路加起来仍然不超过 worker 的空位数（闸门②）。

-- 第二路的思路（示意，不是最终 SQL） WITH busy AS ( -- 每个渠道正在占位的任务数 SELECT provider, count(*) AS n FROM generation_tasks WHERE status IN ('queued','running') OR (status = 'pending' AND lease_until > now() AND provider_task_id = '') GROUP BY provider), ranked AS ( -- 到点的 pending，按渠道排名 SELECT t.id, row_number() OVER (PARTITION BY t.provider ORDER BY t.created_at) AS rn, c.max_running, coalesce(b.n, 0) AS n FROM generation_tasks t JOIN ai_channels c ON c.key = t.provider LEFT JOIN busy b ON b.provider = t.provider WHERE t.status = 'pending' AND t.next_poll_at <= now() AND (t.lease_until IS NULL OR t.lease_until < now())) SELECT id FROM ranked WHERE max_running = 0 OR rn <= max_running - n -- 再按 created_at 取前 limit 个，加租约

上限读渠道的当前配置（join 渠道表），不读任务快照：运营调大上限，排队的任务马上能用上。

08 · 方案 A · 并发安全

两个后端实例同时领，会不会一起超限

风险

实例 1 和实例 2 同一时刻都数到“渠道还剩 2 个位”，各领 2 个，结果提交了 4 个。

现有的 FOR UPDATE SKIP LOCKED 只保证不会领到同一个任务，保证不了“数完再领”这个整体不被打断。

做法：第二路领取串行

第二路在事务里先拿一把 PostgreSQL 事务级咨询锁（pg_advisory_xact_lock），数和领在同一把锁里完成，提交事务自动释放。

每个实例每秒只领一次，锁持有几毫秒，串行的代价可以忽略。第一路不加锁，轮询照旧并行。

为什么不用内存计数、Redis 计数

内存计数每个实例各算各的，必然超；Redis 计数要在任务状态变化的每个地方加减，进程崩溃时会漏减，计数会越来越偏。直接按任务表现算，任务表就是唯一事实来源，崩溃了也不会算错（租约过期自然不再算占位）。

10 · 方案 A · 超时

排队时间不能吃掉生成时间

现在

任务一创建就开始计时（模型配置的超时，默认 30 分钟）。排队 25 分钟的任务，提交给上游后只剩 5 分钟，大概率“生成超时”。

改成

  • 排队超时：在 pending 里最多等多久，默认等于模型超时；超了失败，文案“排队超时，积分已退回”
  • 生成超时：提交给上游成功那一刻重新起算（deadline_at = submitted_at + 模型超时）
时刻现在的 deadline改后的 deadline
10:00 创建，排队10:3010:30（排队超时）
10:20 被领走、提交成功10:30，只剩 10 分钟生成重新算成 10:50，完整 30 分钟

积分在创建时就已冻结，排队超时和其他失败一样全额退回。用户在排队中随时可以取消。

11 · 方案 A · 兜底

上限填大了，或者上游账号还被别处用着

我们这边的上限只能挡住我们自己发出的任务。上游仍可能返回“繁忙 / 并发已满”。

处理方式（沿用现有逻辑）

  • 插件把这类错误归为可重试（retryable）
  • 任务回到 pending，退避后重试；这期间不算占位，不会把渠道锁死
  • 重试 5 次仍失败才失败退款

给运营的提示

  • 日志里记“渠道 xx 提交时上游报繁忙”，渠道页显示最近一小时的次数
  • 次数多说明上限填大了，调小即可，立刻生效
  • 插件提示词里补一条：上游的“并发已满”要归为可重试
12 · 方案 A · 画布

用户看到的：排队中 → 生成中

排队中

任务是 pending，还没调用上游。
文案：“前面的任务处理完后会自动开始”。可以取消。

可选增强：显示“前面还有 3 个”（同一渠道里比它早创建的 pending 数），在对账查询时一起返回。

生成中

已提交给上游（queued / running）。已耗时从提交那一刻算，平台给进度就显示进度。可以取消。

即将完成

上游已出结果，正在保存（finalizing）。不能取消。

“排队中 = 没调用上游、生成中 = 已调用上游”这条定义已经在昨天改好了（任务视图新增 submitted_at）。方案 A 只是让“排队中”真的会出现，并且排得有道理。

同时生成（新）

限制发给上游的 HTTP 请求（提交、查询都算），防止被上游按频率限流。原来叫“最大并发”，容易和上面混淆，改名。

怎么填

上游规定填哪个
同时最多生成 N 个最大同时生成数 = N
每秒最多 N 次请求每秒请求数 = N
同步接口，同时最多处理 N 个请求两个都可以填 N
不知道先留空，看日志里有没有“上游繁忙”

“生成中 / 排队”按任务表实时统计，打开渠道页时查一次，不推送。

14 · 方案 B：多渠道自动调度（第二期）

一个模型绑多个渠道，谁有空用谁

配置

模型的 channels 允许多条（数据结构已经是数组，现在只是校验限死了 1 条）。每条有自己的上游模型 ID 和优先级：

"channels": [ { "channel": "yswg-a", "upstream_model": "yswg-turing-2", "priority": 1 }, { "channel": "yswg-b", "upstream_model": "yswg-turing-2", "priority": 2 } ]

调度

  • 建任务时快照冻结所有候选渠道，不选定
  • 领任务时按优先级挑第一个“启用且有余量”的渠道，写进任务的 provider，之后轮询都走这个渠道
  • 全都满了：留在 pending 排队，哪个先空用哪个
  • 提交时报可重试错误：下次重试可以换下一个渠道（故障切换）

B 必须建立在 A 之上：没有“这个渠道现在满不满”的判断，就没法“挑有空的”。所以先做 A。

17 · 落地

改动清单与验收

改动（方案 A）

  • 渠道：rate_limit_json 加 max_running，校验非负
  • 任务仓储：领取拆成两路，第二路加咨询锁与按渠道余量
  • worker：先领第一路，再用剩余空位领第二路
  • 任务服务：提交成功时重算 deadline_at；pending 超过排队超时按“排队超时”失败
  • 渠道页：新字段、改名、实时占位
  • 插件提示词：上游并发已满归为可重试

验收

  • 上限 2、同时提交 5 个：任意时刻上游最多 2 个，其余“排队中”，空位出来一秒内被领走
  • 两个后端实例同时跑，仍然不超过 2
  • 轮询、转存不受上限影响，不会死锁
  • 排队 25 分钟后提交的任务，有完整 30 分钟生成时间
  • 上限调大，排队任务下一秒开始提交
  • 上限为 0 的渠道，行为和现在完全一样
